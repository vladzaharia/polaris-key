**API (reference: Node; every SDK keeps the same members in its own idiom):**

- **D side.** `nearby.request({request, label?, signal?})` returns a `NearbyRequest`:
  - `approvers`: events with `{id, label, platform}`;
  - `choose(id)`: returns `{code: "123 456"}` and sends `VOUCH_REQ`;
  - `result`: `VouchStatus | null`, for display only;
  - `onRecord(0x0030–0x003F, fn)`: the Sync hook;
  - `close()`.
- **M side.** `nearby.onRequest(handler, {prompt})` returns `{stop, pause, resume}`. The handler gets `{label, platform, codes: [3], pick(code), decline(), finish(approveAnswer), sendRecord(type, body), close()}`:
  - `pick(code)` returns the verified `VouchRequest` `{request, deviceId, signKey, agreeKey, label, platform}`, or `mismatch`;
  - `finish()` maps the HTTP answer to `VOUCH_RESULT` (N6).
- **Gating.** `nearby` is gated by Identity discovery (`nearby` plus its endpoints), never by `services.connect` (R-13, Q6).
- **Unsupported runtimes.** These answer `nearby-unsupported`: web, desktop-bridge, Android until CC-15b, and Godot until CC-15b.

## 2. Rules every port keeps (N1–N12; the V5 text of CC-15.0b, and R-8's checklist)

1. **N1. `VOUCH_REQ` body.** `{v:1, request, deviceId, signKey, agreeKey, label?, platform, sig}` (Q1 adds `deviceId`).
   - `sig` is `pkey-proof/1` with purpose `vouch`.
   - Its fields are: slug; `deviceId` (D's `X-PKey-Device` on `start`); value `<b64url h>.<request>`; line 6 `-`. It is signed by D's device `signKey`.
2. **N2. M validates `VOUCH_REQ`.**
   - It is strict JSON (§1.2) of at most 4 KiB, and `v` is 1.
   - `request` matches `^nr_[A-Za-z0-9_-]{22}$`, and `deviceId` is 32 base64url characters.
   - Both keys pass §15.2 step 4.
   - `label` is cleaned as HELLO's is, and `platform` follows HELLO's rule.
   - `sig` verifies under `signKey` with **this session's** `h`.
   - Unknown members are ignored.
   - Any failure closes `peer_bad_frame`, and no route is called.
3. **N3. Who confirms.** On D, the code being shown is D's confirmation: the SDK calls `confirmSas()` at the `sas` event, then sends `VOUCH_REQ`. On M, `VOUCH_REQ` stays held (engine rule) until the person picks the matching code.
4. **N4. Number matching.**
   - M shows `sas` with two decoys from a CSPRNG. The three codes are distinct, each in [0, 10^6), in uniform random order.
   - Any of these closes `peer_bye` before `VOUCH_REQ` is delivered, with no route called: a pick other than `sas`, "Not now", the 120 s deadline (`peer_timeout`), or `stop()`. The handle came from an unverified session (Q4).
   - A server `deny` is sent only after the code matched, for example when the person cancels the licence choice.
5. **N5. Direction and order.**
   - `VOUCH_REQ` goes D→M, once, after the code.
   - `VOUCH_RESULT` goes M→D, at most once, after `VOUCH_REQ`.
   - `0x0030–0x003F` go M→D only after `VOUCH_RESULT` `approved` (R-9).
   - A wrong direction or a missing precondition closes `peer_not_allowed`. A repeat or a bad body closes `peer_bad_frame`.
6. **N6. `finish()` mapping.** Pinned as rows (§4).

   | `approve` answer                                                                                                                                         | `VOUCH_RESULT`              |
   | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
   | `200 approved`                                                                                                                                           | `approved`                  |
   | `204`                                                                                                                                                    | `denied`                    |
   | `403 not_nearby`                                                                                                                                         | `not_nearby`                |
   | `403 device_limit`                                                                                                                                       | `device_limit`              |
   | `404`, while discovery still names `nearbyApprove`                                                                                                       | `expired`                   |
   | `200 choose`                                                                                                                                             | nothing yet; M re-calls     |
   | anything else, including a 404 after discovery has lost `nearby` (N11), `400`, `403 account_required`, `409` after one key registration, `429` and `503` | no result; CLOSE `peer_bye` |

   On D, an unknown status displays as `denied`. D's poll is the authority. A session that ends without a result leaves D on its poll.

7. **N7. `vouch/1`.**
   - Both mode-v payloads list it.
   - If the intersection lacks it, M closes `peer_not_allowed` after HELLO and before the SAS (Q10).
8. **N8. Approver advert (M).**
   - The instance is `p1-` plus base32lower of 10 CSPRNG bytes (16 characters).
   - TXT is `v=1`, `m=v` and `h=productTag(slug, epoch)`.
   - It has its own listener. The instance and the port are both fresh at every listen and every 300 s.
   - Advertise only while all of these hold:
     - the device is signed in;
     - discovery names `nearby` and `nearbyApprove`;
     - the permission was already granted (`prompt:false`), or the host opened "Approve a nearby device" (`prompt:true`).
   - Stop on `pause()`, sign-out (after `cloudConnect.stop()`, before `connect.leave()`, G18), or discovery losing `nearby`.
   - Accept and dial use the **same predicate as mode a** (G6/G7, later CC-IPV6's `lanVerdict`), never a copy.
   - `HandshakeLimiter`: 5 a minute per advert, 4 waiting. A new instance gets a new limiter.
9. **N9. Approver choice (D).**
   - D browses for `m=v` with a matching `h` (current or previous epoch). It connects out, with no listener (R-4).
   - It dials at most 4 approvers at once, using one-time X25519 static keys.
   - Each session stops after HELLO. The engine holds `SAS_COMMIT` until the host calls `startSas()` (CC-15.2).
   - D lists approvers by their HELLO label and platform.
   - `choose(id)` starts the SAS on that session only. The others close `peer_bye` before any SAS record, so no other M ever prompts.
   - The host decides whether a single approver is chosen automatically. The reference kit chooses after 3 s.
10. **N10. Deadlines (D).**
    - The engine's 30 s and 120 s apply.
    - Browsing and waiting for `VOUCH_RESULT` both end at the request's `expiresIn` (300 s), then CLOSE `peer_bye`.
    - Mode v never uses the relay (G16 already refuses it).
11. **N11. Secrets.**
    - The request handle, `sig`, `h` and the nonces never appear in a log, repr or error (G19).
    - The one-time static keys are wiped after the handshake (G1).
12. **N12. No silent approval (L-3).** Nothing in the API approves without a `pick()` of the matching code. `finish()` refuses unless `pick()` returned a `VouchRequest` on this session.
