## 0. What the code does today

- **One privilege level.** `isPlatformAdmin`, `canAdminProduct` and `hasAnyAdminGrant` are one
  predicate on `PLATFORM_ADMIN_GROUP` (`W/admin/authz.ts:18-44`). The file says per-product admin
  "does not exist and is not planned" (`:6`).
- **A stateless session.** The session is an HMAC cookie that carries the IdP's `sub` and
  `groups` for 8 h (`W/admin/session.ts:44,51,55-71`). Its invariant is "a session either carries
  full platform authority or it was never issued" (`:1-6`). Nothing can revoke it short of
  rotating `ADMIN_SESSION_SECRET`.
- **The sign-in gate.** The callback gates on `hasAnyAdminGrant` and answers with an HTML 403
  (`W/admin/auth.ts:331-338`). The IdP is `adminOidcConfig(env)`: the `ADMIN_OIDC_*` trio, else
  the platform trio (`W/platformOidc.ts:45-47`). The flow is found by `state` alone
  (`auth.ts:316-318`), with no browser binding: AT-2's "login CSRF" branch. The portal's SSO is
  bound to the browser by `__Host-pkey_sso` (`THREAT-MODEL.md:5192-5201`).
- **Where the checks run.** Product routes are gated once, with a budgeted `access.denied` audit
  row (`W/admin/api.ts:110-144`). Platform routes re-check inside handlers: `github.ts:171`,
  `platformStoreConnections.ts:178`, `summary.ts:32`, `platform.ts:205`, `products.ts:169` and
  `me.ts:36`. Four product routes also re-check "platform admin only": `trustPolicy.ts:62`,
  `outletCredentials.ts:80` and `ciPublishing.ts:122,153`.
- **The docs gate.** The docs site admits anyone who has a session (`W/docs.ts:7-11,160`).
- **The settings registry.** Every entry declares a `capability`, and nothing reads it
  (`core/settings/types.ts:239-240`, `define.ts:21`, `rules.ts:179,415`). Rule 1 refuses a
  `securityWidening` entry at platform scope (`rules.ts:376-379`). `core.adminGroup` is stored and
  grants nothing (`core/settings/core.ts:64-85`). The manifest parser defaults it to `"admin"`
  (`shared-manifest/src/index.ts:4511`), so nearly every linked product stores `'admin'`.
- **Accounts already exist.** One `account_links` row per sign-in method, passkeys included
  (`services/identity/passkeys/repo.ts:170-200`). `account_sessions` are revocable and record
  `amr_json` (`migrations/0068_a_accounts.sql:120-130`, `portal/accountSessions.ts:109-140`).
  - **Groups.** `recordLinkGroups` stores the IdP's `groups` on a link (`portal/repo.ts:294-301`),
    called from `portal/repo.ts:285`, `portal/auth.ts:537` and `platformMigration.ts:331`, but not
    by every `signIn()`. `touchLink` bumps `last_used_at` on every `signIn()`
    (`accounts/repo.ts:294-318`).
  - **Step-up.** It allows 5 minutes (`accounts/links.ts:33,49`). I-16's passkey add checks it
    against `PasskeyCaller.authenticatedAt` (`passkeys/routes.ts:334-340,402-407,504,563`).
- **The account-id boundary.** The global account id must never reach a console body
  (`test/accountIdBoundary.test.ts:1-10`).
- **The pepper.** `KEY_HASH_PEPPER` is optional (`env.ts:348`). Unset, `hashKey` falls back to
  an unkeyed SHA-256 (`crypto.ts:128-129`).
- **The issuer allowlist.** `issuerHostAllowed` is fail-open by design: "Unset means not
  enforced" (`services/identity/oidc.ts:281-298`). It guards customer OIDC, not operators.
- **The constants scan.** The SDK-constants scan skips `W/admin/` (`tools/gen-sdk-constants.ts:528-539`).
  Console errors therefore stay out of `errors.json`, provided only the console layer emits them.

## 1. Summary

- **The owner's four roles, summed.** Superadmin, Platform admin, Product admin (bound to one
  product or to All products, and optionally narrowed to areas) and Console access. There are no
  deny rules and no custom roles.
- **One deny-by-default `can(principal, scope, area, level)`.** It lives in `W/core/rbac/`. Every
  admin route declares an **area**, a stable id from an append-only list that is independent of
  the sidebar. A drift gate fails when a route changes area without a migration that rewrites the
  bindings.
- **Operators are accounts.** The console session is bound to an `account_sessions` row and is
  revocable within 30 s.
  - **Strong methods.** Console entry and step-up need a passkey, or SSO through an operator
    connection, whose issuer allowlist fails closed.
  - **Email codes.** An email code alone never opens the console.
  - **New methods.** A method becomes strong only after a 5-minute step-up through an existing
    strong method (one exception, SM-6, for low-privilege invites).
- **The root rule.** `PLATFORM_ADMIN_GROUP` at the console IdP maps to Superadmin. It is computed
  from `env`, never stored, and cannot be removed. Today's operators need no setup.
  - **Break-glass.** A deliberate `ADMIN_OIDC_*` sign-in that involves no account. It stays at
    least 30 days and goes after 14 days unused, once two Superadmins are on passkeys.
  - **SSO rules.** One platform setting, `console.access`, in the `ClaimMatcher` format that
    `license.access` shares. Rules grant only Product admin and Console access.
- **The data.** One table (`console_role_bindings`), two nullable columns on `account_links`
  (`strong_at`, `asserted_at`) and one index. There is no P0-49 job, because no stored value
  changes meaning. `products.admin_group` retires in three steps, so no serving Worker reads a
  dropped column.

## 2. The authorization contract

### 2.1 Areas, roles and the matrix

Areas live in `W/core/rbac/areas.ts` as `AREAS`. The list is append-only: an id is never renamed
or reused.

| Id         | UI name        | Scope      | Covers (today's `W/admin/api.ts` routes, and planned ones)                                                                                                                                                         |
| ---------- | -------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `console`  | Console        | membership | `/me`, `/logout`; `/summary` and `GET /products`, both filtered to products the principal can view; `GET /access/admins`                                                                                           |
| `platform` | Platform       | platform   | `/platform/*` (settings, deployment, operations, activity, feeds, store connections, override migration); `POST /products`, `/products/link-repo`, `/products/kek`, `/github/*`; every route of the system product |
| `members`  | Members        | both       | Platform → Members and invites, and `console.access` (ST-31, ST-32); Product → Settings → Members (ST-31)                                                                                                          |
| `docs`     | Docs           | platform   | `/docs/*` (`W/docs.ts`)                                                                                                                                                                                            |
| `core`     | Core           | product    | The product record, `services`, `activity`, `refusals`, `devices`, `users`, `assets`, `blob-gc`, presentation and Integration (ST-41)                                                                              |
| `license`  | Licensing      | product    | `license/*`, `bundles`                                                                                                                                                                                             |
| `config`   | Managed config | product    | `config/*`, account overrides                                                                                                                                                                                      |
| `ship`     | Ship builds    | product    | `release/*`, `distribution/*` (feeds included), `update/*`                                                                                                                                                         |
| `signin`   | Sign-in        | product    | `identity/*`                                                                                                                                                                                                       |
| `sync`     | Cloud Sync     | product    | `sync/*` (U-05)                                                                                                                                                                                                    |

| `settings` | Settings       | product    | `claims/*`, `settings/backfill`, product delete; access-policy settings (§3). For `settings/:key` and `claims/:key`, the key's `rbacArea` decides                                                                  |

Roles are summed. In the matrix, "✓" means both view and edit:

| Role           | Bound at                                           | `console` | `platform` | `members` (platform)             | `docs`         | Product areas                                                                   |
| -------------- | -------------------------------------------------- | --------- | ---------- | -------------------------------- | -------------- | ------------------------------------------------------------------------------- |
| Superadmin     | platform                                           | ✓         | ✓          | ✓, every grant, `console.access` | ✓              | ✓ every area of every product, the system product included                      |
| Platform admin | platform                                           | ✓         | ✓          | ✓ within the grant rules (§2.3)  | ✓              | none (products it creates come through G6)                                      |
| Product admin  | `product:<slug>` or `products:*`, optional `areas` | ✓         | none       | none                             | none, ST-35: ✓ | the bound areas, else all ten. `products:*` never covers a `system = 1` product |
| Console access | platform                                           | ✓         | none       | none                             | none, ST-35: ✓ | none                                                                            |

**Why.**

- The roles are exactly the owner's four. The owner's literal Platform admin is "console plus
  Platform settings", so it gets no product content.
- A storefront manager is `product_admin @ product:tonebox` with areas `["ship", "commerce"]`. It
  can publish builds, but it cannot change signing keys or the trusted publisher (§3).
- The system product stays a platform resource, as today (`api.ts:166-170`). It is unreachable
  through `products:*`, so an All-products binding cannot reach our own SDK releases or signing
  keys.

### 2.2 `can()` and the principal (ST-29)

```ts
// W/core/rbac/can.ts. Pure: no I/O and no HTTP. Re-exported by W/admin/authz.ts.
export type Level = "view" | "edit";
export type Role =
  | "superadmin"
  | "platform_admin"
  | "product_admin"
  | "console_access";
export type Scope =
  | { kind: "platform" }
  | { kind: "product"; slug: string; system: boolean };
export interface Grant {
  role: Role;
  scope: "platform" | "products:*" | `product:${string}`;
  areas: readonly AreaId[] | null; // null = every area; product_admin only
  source: "root" | "rule" | "grant" | "invite" | "creator" | "breakglass";
}
export interface Principal {
  memberId: string;
  grants: readonly Grant[];
}
export function can(
  p: Principal | null,
  scope: Scope,
  area: AreaId,
  level: Level,
): boolean;
```

`can()` denies unless a rule below allows. The rules are:

1. A `null` principal is denied.
2. Area `console` is allowed when the principal has at least one grant (membership).
3. Superadmin is allowed everything.
4. A product scope whose `system` is true is evaluated as `{kind: "platform"}` with area
   `platform`.
5. Platform scope: Platform admin is allowed on `platform`, `members` and `docs`.
6. Product scope: a `product_admin` grant whose scope is `product:<slug>` or `products:*` allows
   a product area when its `areas` is `null` or contains the area.

`level` is unused by the four built-in roles, which all grant both view and edit. It exists so
that Product editor and Product viewer, if a product ever asks for them, add matrix rows rather
than call sites.

**Where the principal is resolved.** `can()`, the bindings store and
`resolvePrincipal(env, db, subject, now)` all live in `W/core/rbac/`.

- **Callers.** The console layer, ST-34's token path and F-33's registry host (its "console
  member" listing) share the resolver.
- **The boundary.** Root and rule grants need Identity's `account_sessions`, `accounts.status` and
  `account_links`, and Core may not import a service (rule 6; P0-17 makes `test/boundaries.test.ts`
  transitive). Identity therefore provides them through a read-only `consoleSubject` hook declared
  in `core/hooks.ts`. This is the P2b-01 pattern: the types are in Core, there is exactly one
  provider, the hook returns plain records, and `null` means deny. It is a platform hook with no
  per-product enablement check, because the account tables exist on every deployment.
  `test/hooks.test.ts` pins its single provider.
- **If P0-17 moves the account substrate.** If P0-17 moves it into `core/accounts/`, the resolver
  reads it directly and the hook is not added.
- **Cost.** Hooks never hand out statements (`hooks.ts` rule 2), so a cache miss costs two
  concurrent D1 reads: the hook and the bindings read.
- **Errors.** Core returns booleans and data only. Every 403 and 401 is emitted by the console
  layer, so the constants scan stays unchanged (§0).

### 2.3 Grant rules (ST-31; enforced in the grant handlers, not in `can()`)

- **G1, no escalation.** A grant of role R at scope S with areas A needs the granter to pass
  `can()` for `members` edit at S and to hold R at S with areas ⊇ A. A Superadmin holds
  everything.
- **G2, Superadmin-only writes.** Only a Superadmin may:
  - grant or revoke Superadmin and Platform admin;
  - edit `console.access`;
  - set an I-30 connection's audience to include operators (§2.5, SM-2).
- **G3.** Console access can be granted by anyone with `members` edit at platform scope or on a
  product, because inviting someone to a product brings console access with it.
- **G4, step-up.** Every widening write needs a console step-up (§2.6). The widening writes are a
  new binding, wider areas, an invite, a rule, an operator audience, and making a method strong
  (SM-3(a), (d), SM-7).
  - The confirm is L1, or L2 for Superadmin, Platform admin, `products:*`, rules and operator
    audiences.
  - Narrowing and revoking need no step-up.
- **G5, audit and notice.** Every grant and revoke writes `rbac.grant`, `rbac.revoke` or
  `rbac.rule` to `platform_audit`, and to the product's `audit` for product scope.
  - The grantee and every Superadmin are emailed through `core/notify` (P0-21). When email is off,
    a copyable link is shown instead.
  - ST-27 adds an `access.changed` alert kind.
- **G6, the creator.** Creating or linking a product gives the creator Product admin on it
  (`source: "creator"`), unless a grant already covers it.
- **G7, no last-Superadmin guard.** The root rule always remains (§2.4).
- **G8, product deletion.** Deleting a product makes two more writes in the same batch, so a
  later product with the same slug inherits nothing:
  - it deletes the product's `product:<slug>` bindings;
  - it removes every `console.access` rule whose grant names `product:<slug>`, as a settings
    history entry with source `product.delete`. That edit only narrows, so it needs neither a
    Superadmin nor step-up (G2, G4).

### 2.4 The root rule and SSO rules

**The root rule** is computed and never stored.

- **When it applies.** A principal holds `superadmin` with `source: "root"` when the account has
  an `account_links` row that meets all five conditions:
  - its `issuer_key` is `portalIdentityIssuerKey(adminOidcConfig(env).issuer)`;
  - its `tenant_scope` is `''`;
  - its `strong_at` is set;
  - its `groups_json` contains `PLATFORM_ADMIN_GROUP`;
  - its `asserted_at` is no older than `ADMIN_SESSION_TTL_SECONDS` (8 h).
- **`asserted_at`, not `last_used_at`.** The new column records when the IdP last asserted the
  link's groups.
  - **The writer.** It is written only in the same `UPDATE` as `groups_json` (and `claims_json`).
    Today that is `recordLinkGroups`; after I-30 it is the `/callback` writer.
  - **Why not `last_used_at`.** `touchLink` bumps `last_used_at` on every `signIn()`, and some
    callers never rewrite `groups_json` (§0). A future path through the console-idp issuer that
    skipped `recordLinkGroups` would therefore extend a stale group without limit.
  - **The test.** ST-30 signs in through that issuer by every path and asserts that
    `asserted_at` moves only with `groups_json`.
- **Why 8 h.** Removing someone from the group therefore takes effect at their next IdP sign-in,
  or 8 h after their last one. That is today's bound (`session.ts:51`).
- **Where it shows.** ST-31 shows the root rule read-only on Members. Nothing can edit or shadow
  it.
- **Recovery.** Lockout recovery is "be in the group and sign in through the IdP" (RUNBOOK,
  ST-35).

**SSO rules** (ST-32) are the platform setting `console.access`.

- **Evaluation.** Rules are evaluated per request, the same way as the root rule. The input is the
  account's strong OIDC links through operator connections (SM-2, checked at evaluation): their
  stored `groups_json` and `claims_json`, under the same 8 h `asserted_at` freshness. A deleted
  rule, or a connection that stops qualifying, therefore stops granting within 30 s.
- **The shape.** The `when` object is the `ClaimMatcher` that LX-36's `license.access` reuses
  verbatim:

```jsonc
{
  "rules": [
    {
      "id": "r_9f2c4a", // server-assigned, stable
      "label": "Tonebox release managers", // optional, at most 80 characters
      "when": {
        // ClaimMatcher: "connection" plus exactly one of "group", "domain" or "claim".
        // "domain": "example.com" needs a DNS-verified, enforced domain of that connection.
        // "claim": { "name": "department", "equals": "games" }
        "connection": "console-idp", // "console-idp", or an operator connection's I-30 id
        "group": "tonebox-release",
      },
      "grant": {
        "role": "product_admin", // product_admin or console_access only
        "scope": "product:tonebox",
        "areas": ["ship", "commerce"],
      },
    },
  ],
}
```

- **Limits.**
  - At most 50 rules.
  - A rule grants only `product_admin` or `console_access`. Superadmin comes only from the root
    rule or a binding, and so does Platform admin, so `console.access` stays strictly below the
    root.
- **Which connections a rule may name.** Exactly the operator connections of SM-2. They are
  checked at write time, where a non-qualifying connection is refused, and again at every
  evaluation.
- **Domain rules.** A `domain` matcher needs the domain to be verified and enforced on that
  connection. I-30 re-checks DNS daily and fails closed. An address confirmed only by email code
  never matches.
- **Writes.** Only a Superadmin writes rules (G2), always with step-up, an L2 confirm, a match
  preview and notices. A stolen session cannot introduce an IdP, for two reasons:
  - the allowlist is deploy-time and fails closed;
  - making a connection an operator connection is itself a Superadmin write with step-up.

### 2.5 The strong-method rule (ST-30 defines and enforces it; ST-31 adds SM-6 and SM-7)

A method is strong when two things hold:

- its `account_links.strong_at` is set;
- for an OIDC link, its connection still qualifies under SM-2. This is read at every use and never
  frozen into `strong_at`.

A console session passed SM-1 when it was minted, so it may use the console. It does **not**
confer strength: anything that makes a method strong needs a **console step-up**, meaning the
cookie's `authAt` is an SM-1 sign-in no older than 5 minutes. A portal session is never treated
as strong, so no strength column is added to `account_sessions`.

- **SM-1.** Console entry, console step-up and minting an admin token (ST-34) all need a strong
  sign-in no older than the step-up window. The sign-in is either:
  - a passkey assertion with user verification, or
  - an OIDC sign-in through an **operator connection**.

  In both cases the method must be strong. An email code or a magic link is never strong.

- **SM-2, operator connections** are identified by issuer, and only platform-scope connections
  qualify (a product connection is always `customers`, I-27 §2.3).
  - **`console-idp`.** The issuer of `adminOidcConfig(env)` always qualifies, whichever client
    signs in through it. It is deploy-time, as S-13 §8.2 requires of "the admin IdP".
  - **An I-30 connection** qualifies when both of these hold:
    - its `audience` is `operators` or `both`;
    - `operatorIssuerAllowed(env, issuer)` returns true.
  - **Who sets the audience.** Setting `audience` to include operators is a Superadmin-only write
    (G2) with step-up, an L2 confirm, a `rbac.operator_connection` audit row and a notice to every
    Superadmin. Changing the issuer or client of such a connection is the same write. I-30's
    `source: env` seed is deploy-time and is exempt.
  - **`operatorIssuerAllowed`.** This new helper in `W/core/rbac/operatorIssuer.ts` **fails
    closed**: with `OIDC_ISSUER_ALLOWLIST` unset or empty, no I-30 connection qualifies, and only
    `console-idp` does. It deliberately does not reuse `issuerHostAllowed`, which is fail-open
    (§0). Tests cover the unset, empty and non-listed cases.
- **SM-3, how a method becomes strong.** `strong_at` is set when one of these holds:
  - **(a)** the method is added in a console session **after a console step-up**. The console's
    `/manage/api/me/passkeys/*` delegates to I-16's ceremony with two values from the console
    session:
    - `PasskeyCaller.authenticatedAt` is the cookie's `authAt`, **never `now`**;
    - `sessionIdHash` is the console's `account_sessions` row.

    So I-16's own check (`passkeys/routes.ts:504,563`) refuses a stale console session with
    `step_up_required`. The action is audited (`rbac.method_strong`) and emailed to the account
    and to every Superadmin.

  - **(b)** it is an operator-connection link created by signing in through that connection,
    either as a new account or as a join where that IdP asserted the account's verified email.
  - **(c)** a sign-in through `console-idp` whose ID token asserts `PLATFORM_ADMIN_GROUP` uses
    it. The link is marked before SM-1 is checked, so today's operators get in at once.
  - **(d)** the person confirms it in the console after a step-up through an existing strong
    method. This is the "Use for the console" action
    (`POST /manage/api/me/methods/:id/strong`), audited and emailed like (a).

- **SM-4.** A method added in the portal (under an email code, say) is never strong until
  SM-3(d) runs.
- **SM-5.** Removing a method needs no strong session. Losing every strong method blocks console
  entry and does not end membership.
- **SM-6, the invite bootstrap (ST-31, Q2).** This is the one exception to SM-4, recorded in §10.
  - **Who.** It applies only to invites for Console access and for `product:<slug>` Product
    admin.
  - **What.** An account with no strong method and an unexpired invite of that kind on its
    verified primary email may enrol its first passkey as strong in the invite step.
  - **Notice.** The inviter and every Superadmin are notified when the invite is accepted.
- **SM-7, inviter confirmation (ST-31).** An invite for Superadmin, Platform admin or `products:*`
  never uses SM-6. It converts through one of two paths:
  - an operator-connection sign-in (SM-3(b)), or
  - inviter confirmation. The invitee enrols a passkey in the invite step, and it is not yet
    strong. The inviter or any Superadmin then confirms it on Members
    (`POST /manage/api/bindings/:id/confirm-method`), seeing its creation time and authenticator
    name. The confirmation needs step-up and an L2 confirm, and it is audited and emailed.

### 2.6 Session binding and break-glass (ST-30)

- **The cookie.**
  - The name, attributes and 8 h TTL are unchanged (`session.ts:44,259-268`).
  - The signing tag moves from `pkey.admin.v1|` to `pkey.admin.v2|` (`session.ts:155`), so every
    v1 cookie fails closed: one re-sign-in, as with R1-08.
  - The body is `{sub: memberId, aid, sid, name, email, csrf, exp, authAt}`, with no `groups`.
    `authAt` is the time of the last SM-1 sign-in, and only a sign-in or step-up moves it.
  - The portal cookie already carries `accountId` and `sid` (`portal/session.ts:15-29`), so this
    adds no new kind of exposure.
- **`memberId`.**
  - **The value.** It is `"mbr_"` followed by the first 22 characters of
    `base64url(HMAC-SHA-256(KEY_HASH_PEPPER, "console-member|" + accountId))`.
  - **Its uses.** It is the audit actor (`actor_sub`), the limiter key (`api.ts:404`), and the id
    that `/me` and Members show.
  - **With the pepper unset.** It follows `hashKey`'s fallback, an unkeyed SHA-256, like every
    other peppered hash. The account id still never appears, but anyone who knows an account id
    can link it. Production sets the pepper (platform inventory, keyring).
  - **Rotation.** The pepper has no rotation story. Rotating it already breaks every licence-key,
    device-token and CI-token hash, and it would also re-key every `mbr_` actor id and every
    `granted_by` value. Giving it one is a §9 trigger.
  - **Old audit rows** keep the IdP `sub` together with `actor_name` and `actor_email`, which
    already attribute them, so history is not rewritten (§10).
- **Members by id.** `/manage/api/members/:memberId` never decodes the id.
  - **The lookup.** The handler runs the Members list query, computes each candidate's
    `memberId`, and takes the match. The candidates are accounts with a binding, plus accounts
    whose operator-connection links currently earn a root or rule grant. An unknown id is a 404.
  - **The cache.** The list is cached per isolate for 30 s, as the principal is.
- **Sign-in.**
  - **The card.** The console card (P0-38) runs I-05 `signIn` for `console-idp` with the portal's
    issuer key, so one person keeps one account. It can also sign in with a passkey.
  - **The flow is bound to the browser** that started it, as the portal's `__Host-pkey_sso` is: a
    `__Host-pkey_console_sso` cookie whose peppered hash the flow holds. The break-glass branch
    uses it too. Without it, a planted session would put an operator inside the attacker's
    account.
  - **The session.** It opens an `account_sessions` row that expires in 8 h, stores the IdP's
    groups on the link (with `asserted_at`), and writes `console.signin` to `platform_audit`
    (actor `mbr_`). That row is the source of Members' "last console sign-in".
  - **The gate.** It mints the cookie only when SM-1 holds and the principal has a grant, or an
    invite it can convert. Otherwise it shows "{email} doesn't have console access" with **Open
    your library**, instead of today's HTML 403.
- **Per request.**
  - The cookie is verified first.
  - `resolvePrincipal` (§2.2) then reads two things:
    - Identity's session row (live, not revoked, `account_id = aid`), `accounts.status = 'active'`
      and the strong OIDC links;
    - Core's bindings.
  - The principal is cached per isolate for 30 s, keyed by `sid`. Revoking the session ("Sign out
    everywhere"), disabling the account, deleting or merging it (§5.1, cascade), or revoking a
    binding therefore takes effect within 30 s.
- **Step-up** is an SM-1 sign-in no older than 5 minutes. With the console IdP this keeps today's
  `prompt=login` and `max_age=0` (`auth.ts:283-288`).
- **Break-glass.**
  - **The path.** A link on the console sign-in page, `/manage/login?breakGlass=1`, runs today's
    flow against `adminOidcConfig(env)`. It mints `{sub: <IdP sub>, bg: true, …}` only when the
    verified ID token's `groups` contains `PLATFORM_ADMIN_GROUP`. No account is involved, so the
    principal is root Superadmin with no D1 read.
  - **Notice.** Every use writes `rbac.breakglass` to `platform_audit` and emails every
    Superadmin.
  - **Why it exists.** A defect in the account path (a join offer, the card, passkeys) must never
    lock operators out.
  - **Removal.** The branch is deleted when all three of these are true, as recorded in P0-24's
    ledger:
    1. at least 30 days have passed since ST-30's production deploy;
    2. there have been 14 consecutive days with no `rbac.breakglass` row;
    3. at least two accounts hold a Superadmin binding and a strong passkey.

    The `ADMIN_OIDC_*` trio stays as `console-idp` (Q1).

- **Membership ends** on account deletion and merge, because the absorbed account's row is deleted
  and the binding cascades (`merge.ts:288`, `deletion.ts:255`). A disabled account ends it through
  the per-request status check.

### 2.7 The route table and the area drift gate (ST-29)

```ts
// W/admin/routes.ts (W/console/routes.ts after P0-17)
interface AdminRoute {
  method: "GET" | "POST" | "PUT" | "PATCH" | "DELETE";
  path: string; // "/products/:slug/ci-tokens/:id", "/products/:slug/license/**"
  area: AreaId | "byKey"; // byKey: settings/:key and claims/:key use the key's rbacArea
  level?: Level; // default: GET is view, otherwise edit
  stepUp?: true;
  handler: AdminHandler; // (ctx) => Promise<Response>

```

- **Scope.** `/products/:slug/**` is product scope. Every other route is scoped by its area.
- **Dispatcher order.**
  1. Session, then principal.
  2. The limiter.
  3. CSRF on mutations.
  4. Match: 404, or 405 with `Allow`.
  5. One product load (404).
  6. `can()`: a 403 in P0-16's nested shape,
     `{error: {code: "forbidden", reason: "no_access", scope, area}}`, with the budgeted audit row
     of `api.ts:120-142`.
  7. Step-up: a 401 in the same shape with reason `step_up_required`.
  8. The handler.
- **Service routes.** A service's `adminHandle` is declared by prefix with a fixed area: license
  → `license`, config → `config`, release, distribution and update → `ship`, identity →
  `signin`, sync → `sync`. P0-25 later splits the prefixes without changing areas.
- **The session read.** Only this module calls `sessionFromRequest()`. `docs.ts` uses the same
  resolver, gated by `can(p, platform, "docs", "view")`.
- **The drift gate.**
  - `test/rbacAreas.test.ts` pins `AREAS` to `test/fixtures/rbac-areas.json`, which is
    append-only.
  - `test/rbacRouteAreas.test.ts` compares every route's `(method, path) → area` with
    `test/fixtures/rbac-route-areas.json`.
  - A new or removed route updates that file in the same change.
  - A changed area fails unless `AREA_MOVES` in `areas.ts` lists the move: route, from, to and the
    migration **suffix** (`_rbac_move_<n>.sql`, because the lead renumbers `00XX` at merge). The
    gate finds the file by that suffix. Two kinds of move are allowed:
    - **Into a new area** (one added to `AREAS` in the same change, as a split). The migration
      rewrites `console_role_bindings.areas_json` and `console.access` grants so that holders of
      `from` also hold `to`. Because `to` covers only routes split out of `from`, this widens no
      one.
    - **Into an existing area.** No binding is rewritten, so holders of `from` lose the route: a
      narrowing. The entry carries `narrows: true` and needs the security reviewer's sign-off in
      the PR. Rewriting bindings into an existing area is refused, because it would widen holders
      to every route of `to`.
  - The sidebar (`nav.ts`, ST-45) is never an input.

## 7. Rollout and rollback

1. **ST-29** deploys with no behaviour change: the only principal is root, as today.
2. **ST-30.** The migrations run first, then the Worker.
   - **First sign-in.** Every console cookie, and every copied `PKEY_ADMIN_COOKIE`, is refused
     once. Operators sign in through the card with "Continue with Pocket ID". That reuses their
     portal account when the link exists, or creates one, and writes `asserted_at`. A join offer
     goes through PX-21's flow, and break-glass covers any failure.
   - **The deploy window.** An isolate of the old Worker that is still serving ignores the new
     columns and rejects v2 cookies, which costs at most one more sign-in.
   - **Rollback.** Redeploy the previous Worker. Operators sign in through today's callback, and
     the new columns stay unread. The down scripts are needed only to remove them.
3. **ST-31.** The table lands first.
   - Until a Superadmin grants something, the only members are root ones. Invites need email
     delivery, or the copyable link.
   - **Rollback.** An old Worker ignores the table: non-root members lose access and root is
     unaffected.
4. **ST-32.** The setting `console.access` starts empty, and the conversion offers appear.
   - **Rollback.** The rules go unread, so rule-derived members lose access. The release-N Worker
     still names `admin_group`, which exists until ST-25b.
5. **Windows in days** (P0-24 ledger rows):
   - break-glass, as in §2.6;
   - `PKEY_ADMIN_COOKIE`: 30 days with no cookie-authenticated CLI call;
   - `adminGroup` offers: at least 30 days after ST-32, and every offer closed (ST-25);
   - the `admin_group` column: at least 14 days after ST-25, with the rollback target at ST-25 or
     later (ST-25b).
6. **Clients.** No SDK and no device route are affected. The console SPA ships in the same
   Worker assets, so UI and API change together.
7. **If the owner vetoes D2:**
   - ST-29 still lands, because it is code quality and puts the docs gate on `can()`;
   - ST-30 and ST-34 drop;
   - ST-31 and ST-32 bind console-IdP subjects (`issuer_key`, `subject`) instead of accounts;
   - SM-1 to SM-7 and break-glass fall away.

## 8. Risks and decisions

**Risks.**

- **Lockout.** The root rule cannot be removed, break-glass covers the window, and the last
  resort is a deploy rollback.
- **A stale group.** A group change takes up to 8 h to take effect, the same as today.
- **Per-request cost.** Two concurrent D1 reads, cached for 30 s. Admin traffic is small and is
  already limited to 600 requests a minute (`api.ts:398-412`).
- **An area move that silently changes access.** The §2.7 gate catches it, and it refuses
  widening moves.
- **Operators whose Pocket ID email already has a customer account.** PX-21's join flow handles
  them; break-glass covers them meanwhile.

**Decisions under delegated authority (2026-10-05).** Each is open to the owner's veto, in which
case the Alternative applies.

**Deliberate deviations from the backlog**, for the security review:

- **SM-6 against D2's step-up rule.** D2 and ST-28's scope say a method added in a session that
  was not strong counts only after step-up through an existing strong method. An invitee has none,
  so SM-6 lets mailbox control at invite time stand in for it. It applies to Console access and
  `product:<slug>` only; the platform roles and `products:*` use SM-7.
- **The audit actor.** ST-30's scope says the audit actor becomes the account id "with a sub
  mapping". The plan uses `mbr_`, because the account id would reach Activity bodies, against
  `accountIdBoundary.test.ts`. There is no mapping table: pre-ST-30 rows keep the IdP `sub`, name
  and email, and Activity filters them by name or email.
- **Four product routes are loosened.** `trust-policy` (`trustPolicy.ts:62`),
  `outlet-credentials` (`outletCredentials.ts:80`) and `ci-publisher` (`ciPublishing.ts:122,153`)
  answer "platform admin only" today. They become product area `keys`, so a Product admin holding
  `keys` on that product can write them. Today the distinction is moot, because one predicate
  covers both; the security review signs it (checklist item 18).
- **Rules grant less than the scope allows.** The backlog lets rules grant any role. The plan
  limits them to `product_admin` and `console_access`, so that `console.access` stays below the
  root.
- **The manifest field stays.** ST-25's note includes "manifest `product.adminGroup`". The field
  stays accepted with the warning, because refusing it breaks `products/djdl/product.json`.
  Refusal is ST-19 §7 step 3's decision.
- **No pruning by ST-32.** ST-32's "minimal `claims_json` retention" is I-30's claim-map rule.
  ST-32 adds no pruning of its own.
