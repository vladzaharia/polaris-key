## 1. Summary

- **A delegation is a CI-signed `kind: delegation` release record** naming a content key
  (`delegate.publicKey`), a pack-id scope (`deliverable`, matched on whole segments), the data-only
  `types` it may sign, and a signing window (`issuedAt` to `expiresAt`, at most 366 days). Only a
  **pinned release key** verifies it, so the Worker cannot forge or widen one.
- **A delegated pack record names its delegation in its JWS header**: `kid` =
  `pkd1-<sha256 of the delegation's compact JWS>`. The device fetches the delegation by that hash
  from the record route, verifies it, then verifies the record with the delegated key. The
  signature is still checked before the payload is parsed, and the chain never depends on a
  Worker-signed member. A pre-P4-19 SDK refuses the record at step 13 (`jws`): it is safe and
  needs no version change.
- **A content key signs only pack records of `files.tree`, `data.json` or `l10n.table`, for
  compatible or standalone packs.** It never signs app records, revocations, delegations,
  script-capable types, pins, holds, embedded baselines or replacements. The data-only rule
  (an extension allow-list plus a content sniff) runs on the device before activation, in the CLI
  lint before signing, and as the extension rule at ingest.
- **Revocation and rotation use P4-13's record unchanged.** A `kind: revocation` naming the
  delegation's hash revokes every pack signed under it. The feed entry gains
  `kind: "delegation"`, and ingest yanks those releases. One content key maps to one delegation;
  rotating means a new key and a new delegation, then revoking the old one.
- **Corpus, append-only.** There is a new `delegationCases` section in `cases.json`, after
  `revocationCases`, and a new `dataOnlyCases` section at the end of `content/cases.json`. Every
  existing section, P4-13's and P4-10's included, stays byte-identical. Python and Swift move to
  P4-25, and Godot to P4-26. The critical path stays at 9 weeks (§8.3).

## 2. Contract

### 2.1 Versions, and what clients already in the field do

The slots already exist: V4 §2.5 reserves `delegation` ("verified, never acted on"), and step 13
selects the key by header `kid`. P4-19 adds the following and nothing else:

- one kid convention;
- one record body, read by a usability function beside the claims (P4-13's pattern);
- one optional member in a feed `revocations` entry;
- one optional member in `PackInstall`.

Its effect on each kind of client:

- **v3 SDKs** are untouched.
- **v4 SDKs that predate P4-19** (P3-04 to P3-08, P4-06/07, P4-13):
  - A delegated pack record's `kid` is not a pinned release key, so step 13 refuses it (`jws`). The
    device never installs it and keeps what it runs.
  - A required pack whose only release is delegated stays missing, as on a failed fetch.
  - A `kind: delegation` record verifies as a reserved kind, as `record-valid-kind-unknown-verify-only`
    already pins, and is never fetched.
  - A feed `revocations` entry with `kind: "delegation"` parses as before, because P4-13's parser
    ignores unknown members (V4 §2.4.1). Its target is never in H, so it is never fetched.

  **No field client misbehaves**: each one refuses or ignores, and none half-accepts.

- **SDK downgrade** (state written by P4-19, read by an older SDK): a stored delegated install
  fails its reload verification and is dropped, so the pack is fetched again or reported missing.
  `revocations.json` is unchanged in shape.

`PROTOCOL_VERSION` stays 4. No selector key is added, because a v4 client refuses any selector key
it does not know.

### 2.2 The delegation record (new V4 §2.5.4, [C] via `delegationCases`)

```jsonc
{
  "schemaVersion": 1,
  "aud": "diceroll",
  "deliverable": "diceroll.events", // the scope root: a pack id (§8), not "app"
  "kind": "delegation",
  "version": "3", // the CLI writes the decimal seq; display only
  "seq": 3, // per (product, deliverable), ≥ 1
  "issuedAt": 1760000000, // the window opens
  "expiresAt": 1775552000, // the window closes; ≤ issuedAt + MAX_DELEGATION_TTL_SECONDS
  "delegate": { "publicKey": "<base64url, 32 raw Ed25519 bytes>" },
  "types": ["files.tree", "data.json"], // 1–MAX_DELEGATION_TYPES (8), unique
  "notes": "Events team, 2026", // optional, display
}
```

`delegationOf(doc, nonWire) → DelegationBody | null` is usable when all of these hold:

- `kind === "delegation"`, and `deliverable` is a pack id (`isPackId`).
- `delegate` is an object whose `publicKey` is strict base64url (V4 §1) decoding to exactly 32 bytes.
- `types` is an array of 1–8 unique `PACK_TYPE_PATTERN` strings, and its **effective types**
  (`types ∩ DELEGABLE_PACK_TYPES`) are non-empty. Unknown or non-delegable entries are
  ignored, so a later SDK that grows the list does not invalidate today's delegations.
- `expiresAt` is an integer by §3.1's token rule at `/expiresAt` (minimum 1), with
  `issuedAt < expiresAt ≤ issuedAt + 31,622,400`.

`builds` and `content` are ignored, as on any non-app kind, and unknown members are ignored. The
common claims of §2.5 are unchanged.

**The delegated kid.** `DELEGATED_KID_PATTERN` is `^pkd1-[0-9a-f]{64}$`, where the hex is the
delegation's record hash (§2.5's hashing rule). It is 69 bytes, longer than
`RELEASE_KEY_KID_PATTERN`'s 64-byte bound, so a declared release key can never collide with it. An
SDK refuses host options that pin a release kid matching it (`invalid-options`).

### 2.3 Verifying a delegated pack record (V4 §3.5 amended; bounds and order)

`verifyReleaseRecord(jws, opts)` gains an optional `delegation` (the delegation's compact JWS),
which the caller fetches first. A function `delegationHashOf(jws)` reads the header kid only and
returns the hex, or null. **Without `opts.delegation`, behaviour is byte-for-byte today's.** The
order is:

12. **Hash** the record against the pin (unchanged).
13. **Pinned release kid:** today's path. A supplied `delegation` is ignored, and the result's
    `delegation` is null.

    **Otherwise**, when `opts.delegation` is supplied and the kid matches the pattern:
    1. `verifyDelegation(opts.delegation, {releaseKeys, productTrust, expectedAud, expectedHash: <kid hex>})`
       runs steps 12–14 on the delegation (the ASCII bound, the hash, a key from the **pinned
       release keys only** with the product-key refusal, and `verifyJws`), then its claims, then
       `kind === "delegation"`, then `delegationOf`.
    2. The delegated key's raw bytes equal no pinned release key and no key of the effective
       product trust set.
    3. `verifyJws(record, {[kid]: delegate.publicKey})` with `typ: pkey-release+jws`.

    Any failure in (1) or (2) is step `delegation`; a failure in (3) is `jws`. Otherwise
    (unpinned kid, no delegation supplied, or a malformed `pkd1-` kid) the step is `jws`, as today.

14. **Claims** (unchanged).
15. **Cross-check** against the pin (unchanged).
16. **Scope** (delegated records only, step `scope`). All of these must hold:
    - `kind === "pack"`;
    - `deliverable === D` or `deliverable` starts with `D + "."`, where D is the delegation's
      `deliverable`;
    - `type` is in the effective types;
    - `delegation.issuedAt ≤ record.issuedAt ≤ delegation.expiresAt`.

**Why this order.**

- The record's bytes are bound by its hash first.
- The delegation is fully verified before any signature work with a key it supplies.
- The record's payload is parsed only after its own signature verifies, so V4 §1's
  signature-before-parse rule holds.
- Scope comes last because it reads the record's claims.

**Bounds per record:**

- two SHA-256s;
- at most two Ed25519 verifications;
- one delegation, and one level only, because a delegation verifies against pinned release keys
  and never through another delegation;
- the delegation is subject to `MAX_RECORD_JWS_BYTES`.

**Bounds per check:** at most `MAX_DELEGATIONS_PER_CHECK` = 16 distinct delegations are fetched;
a target beyond that waits for the next check. Verified delegations are cached in the process by
hash.

The result gains `delegation: {sha256, deliverable, types, issuedAt, expiresAt} | null`.
`ReleaseRecordStep` gains `delegation` and `scope`.

**`recordRevoked(recordSha256, delegationSha256 | null, revoked) → "record" | "delegation" | null`**
is the one rule for applying revocations to a delegated release. It is pure, ported to every SDK,
and pinned by `delegationCases`.

### 2.4 Where the delegated path is allowed

| Surface                                                                                                  | Delegated path                     | Why                                                                 |
| -------------------------------------------------------------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------- |
| A feed target of a compatible or standalone pack (`packs.install`, `ensure()`)                           | **yes**                            | the content team's channel                                          |
| Reloading a stored install (`verifyStoredRecord`), with `PackInstall.delegation`                         | **yes**                            | an installed release stays valid after its window (decision 6)      |
| An app record; a stamp or record pin; a hold; a revocation; a replacement; a marker or embedded baseline | **never** (no `delegation` passed) | release-key surfaces: the release key vouches for exact bytes there |

The engine knows which surface it is on: it allows the delegated path only for a release that is
neither the stamp's pin or hold for that pack nor a stored revocation's replacement. Ingest refuses
the same combinations (§6.2), so an honest Worker never produces them.

**What a content key can never sign, by mechanism:**

| Record                                                                          | Refused at                                                                                          |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| an app record                                                                   | `jws` on every app path (no delegation is passed); `scope` if a runner passes one                   |
| a revocation                                                                    | `jws`: `verifyRevocation` never passes a delegation (P4-13 decision 3, reaffirmed)                  |
| a delegation                                                                    | `delegation`: a delegation verifies against pinned release keys only; as a record, `scope` (`kind`) |
| `godot.pck`, `godot.zip`, `audio.bank`, `ml.model`, `custom.*`, an unknown type | `scope`: not in `DELEGABLE_PACK_TYPES`, so never effective even when listed                         |
| a pack outside its scope or window                                              | `scope`                                                                                             |

### 2.5 Data-only enforcement (new V4 §2.8, [C] via `dataOnlyCases`)

`DELEGABLE_PACK_TYPES = ["files.tree", "data.json", "l10n.table"]`.

- `godot.pck` and `godot.zip` are excluded because they mount scripts (CONTENT §12).
- `audio.bank` is excluded because it may be a Godot audio pack.
- `ml.model` is excluded because of custom-op runtimes.
- `custom.*` is excluded because a game handler may execute it.

A delegated release passes **`dataOnlyRefusal(path, head) → "extension" | "content" | null`** for
every file of every variant it installs. It applies to delegated installs only; release-signed
packs keep their own rules.

1. **Paths are already normalised.** `checkPaths` (A7 §3.3) refuses empty, `.` and `..` segments
   before any byte is written. So Godot's `simplify_path()` is the identity on every admitted
   path, and the Godot port asserts that equality as well (P4-08's finding).
2. **Extension allow-list** (`DATA_ONLY_EXTENSIONS`): the final segment's text after its last
   `.`, ASCII-lowercased, must be one of `json`, `csv`, `tsv`, `po`, `txt`, `png`, `jpg`, `jpeg`,
   `webp`, `ogg`, `wav`, `mp3`, `ttf` or `otf`. A file with no extension is refused. This is an
   **allow-list**, because Godot chooses its resource loader by extension: `.tres`, `.material`,
   `.theme`, `.translation`, `.res`, `.gd` and every future loader extension are refused because
   they are not on it.
3. **Content sniff, never by extension.** Take the first `DATA_ONLY_HEAD_BYTES` (64) decoded
   bytes, and skip a UTF-8 BOM and then ASCII whitespace inside them. The file is refused when
   what remains starts with any of:
   - Godot formats: `RSRC`, `RSCC`, `GDPC`, `GDSC`, `[gd_`;
   - archives and native code: `PK\x03\x04`, `\x7fELF`, `MZ`, the five Mach-O magics, `\0asm`;
   - scripts: `#!`, `extends` + space or tab, `class_name` + space or tab, `@tool`.

   The check fails closed: a coincidental match refuses a file and never admits one.

**Where it runs:**

- **On the device:** the extension rule over the files index **before any object is fetched**,
  so a refused pack costs no download, and the sniff on each file's first decoded bytes as the
  applier writes it (full, file and delta strategies alike). A refusal aborts the plan, discards
  staging and raises the new client code `pack-not-data-only` (detail: the path and the rule).
- **In the CLI lint**, before signing, over the real files, with the same client-core function
  (as `lintTreePaths` reuses `checkPaths`).
- **At ingest**, the extension rule over the parsed index paths (§6.2).

The data handlers themselves (P4-16) must parse untrusted data and never evaluate it. The rule
cannot police what host code does with a JSON file, and the threat model says so.

### 2.6 Revocation and rotation

- **Revoking a delegation** uses P4-13's §2.3 record unchanged:
  - `deliverable`, `version` and `seq` are the delegation's;
  - `revokes` is the delegation's hash;
  - `replacement` is refused at ingest, and a device ignores it.

  `verifyRevocation` and `revocationOf` are unchanged: the scope root passes `isPackId`. The feed
  entry carries `kind: "delegation"` (§2.7). The device stores it in `revocations.json` by target,
  as P4-13 does, and `recordRevoked` then refuses every release whose delegation hash is a target
  (`pack-revoked`, detail `delegation`).

- **Permanent.** Like any revocation, it can never be undone; a later one may change only
  `reason` (newest `issuedAt` wins, `newerRevocation`).
- **One key, one delegation.** Ingest refuses a delegated key that any stored delegation of the
  product already names, revoked or not. Revoking the delegation therefore revokes the key.
  **Rotation:** generate a key, mint a delegation, re-publish what must survive, then revoke the old
  delegation. **Renewal** of an expiring window is the same flow; already-installed releases need
  no re-publish (decision 6).
- **No `relearn` for delegation targets.** Delegated releases are never embedded, and P4-13's
  `relearn` governs embedded mounts only, so a dropped delegation entry adds nothing to it. A torn
  file can lose a delegation revocation until the next feed re-teaches it. This is the same
  residual P4-13 states for downloaded installs.

### 2.7 Client order and persistence (V4 §3.4 steps 10–14, amended)

- **Feed entries.** `FeedRevocation.kind?: "delegation"`. `feedContent` keeps a present
  `"delegation"`. It drops the **entry** when `kind` is any other `VOCAB_TOKEN_PATTERN` string (a
  forward value), and makes `revocations` unusable when `kind` is not a string. An absent `kind` is
  carried as absent, so P4-13's `feedContentCases` expectations are unchanged.
- **Step 11, relevance.** In addition to P4-13's H, an entry with `kind: "delegation"` is relevant
  in two cases:
  - its target is the delegation hash of an active install;
  - its `pack` covers, by the whole-segment rule, a pack in H's pack set (the stamp's expects,
    pins and holds, active installs, feed targets).

  It is fetched within P4-13's 64-per-check cap, verified with `verifyRevocation` and stored.

- **Decision input.** `decideUpdate` and `update-matrix.json` are unchanged. The caller adds to
  `content.revocations` one entry `{target: <recordSha256>, pack, replacement: null, replacementUsable: false}`
  for each release whose delegation `recordRevoked` names. That covers every active install, and
  every feed-target record already fetched and verified in this process. A feed target not yet
  fetched is refused at install, and is then known for the rest of the process (as C31 is for a
  record target).
- **`PackInstall.delegation?: string`** holds the delegation's compact JWS, verbatim.
  - `asInstall` accepts it when it is absent or a string.
  - Reload checks that its hash equals the record's kid hex, and runs the delegated path.
  - `PACK_STATE_VERSION` stays 1, because the member is optional.

### 4.2 `delegationCases` (`cases.json`)

**Shape.** Each case is `{id, description, mode, jws, delegation, releaseKeys, productTrust,
expectedAud, expectedHash, pin, revoked?, entry?, expect}`, where:

- `mode` is one of `record`, `release-only`, `revocation` or `feed`;
- `release-only` verifies with no delegation passed;
- `expect` is `{verify: "ok", kind, delegation: {...} | null, revoked?}` or
  `{verify: "fail", step}`.

The base fixture is the scope root `djdl.events`, a `files.tree` record `djdl.events.halloween`,
and types `[files.tree, data.json]`.

## 6. Worker

### 6.1 Migration, tables, hooks

The migration (numbered at rebase) creates two tables, with no `ALTER`, so a replay is a no-op.
`TABLE_OWNERS.release` gains both, and `data-model.mdx` is regenerated.

- `release_delegations(product, record_sha256, deliverable_id, seq, version, kid, jws, public_key,
types_json, issued_at, expires_at, ingested_at, revocation_sha256 NULL, revocation_jws NULL,
revocation_kid NULL, revocation_reason NULL, revocation_issued_at NULL)`:
  - `PRIMARY KEY (product, record_sha256)`, `UNIQUE (product, deliverable_id, seq)` and
    `UNIQUE (product, public_key)`;
  - the revocation lives on the row because `release_revocations.target_release_id` is a
    `NOT NULL` foreign key to a release.
- `release_delegated_records(product, record_sha256, delegation_sha256)`, with
  `PRIMARY KEY (product, record_sha256)`.

**Hooks** (`core/hooks.ts`, no new service edge):

- `ReleaseCatalog.revocations()` entries gain `kind?: "delegation"`;
- `CatalogPackRelease` gains `delegation: string | null`.

### 6.2 Ingest

Every refusal is `release_record_rejected`, with the reason in brackets.

**A `kind: delegation` submit** (no ticket, no descriptor) runs these checks in order:

1. The shared checks against the product's release keys.
2. `delegationOf` is usable, and **every** listed type is in `DELEGABLE_PACK_TYPES`
   [`delegation-body`].
3. The delegated key is no declared release key, no current or retired product signing key, and
   no key of any stored delegation [`delegation-key`].
4. `seq` follows the product's last delegation for that `deliverable` [`seq`]. A byte-identical
   resubmit changes nothing.
5. `issuedAt ≤ now + 300` and `expiresAt > now` [`delegation-window`].

**A delegated pack record** comes through P4-02's ticketed flow. `verifyRecordJws` gains the
delegated branch, tried only when the kid matches the pattern. Its checks:

- (a) the delegation is stored [`delegation-unknown`] and not revoked [`delegation-revoked`];
- (b) the delegated key is not a product signing key now [`product-key`] and is no declared release
  key [`delegation-key`];
- (c) the signature [`signature`] and the claims [`claims`];
- (d) step 16's scope [`delegation-scope`];
- (e) the window, `now < expiresAt`, and `now − 86,400 ≤ record.issuedAt ≤ now + 300`
  [`delegation-window`]. An honest Worker so refuses a backdated record.

Then come every P4-02 and P4-12 pack check, unchanged: `pack-unknown`, `pack-type`,
`pack-entitlement` (against the **operator-owned gate**), `pack-index`, `pack-object`,
`pack-requires`, and the rest. After them:

- the deliverable's binding is `compatible` or `standalone` [`delegation-binding`];
- every parsed index path passes the extension rule [`delegation-data-only`].

The `release_delegated_records` row is written in the same batch.

**App releases and revocations:**

- **App publishes** refuse a pin or hold that names a delegated record [`pin-delegated`,
  `hold-delegated`]. `embeds` ⊆ pins, so `pin-delegated` covers embeds too.
- **Revocations** (P4-13 §6.2): check 3 accepts a stored delegation as a target, with matching
  `deliverable`, `version` and `seq` [`revocation-target`]. A replacement on a delegation target,
  or a delegated replacement, is refused [`revocation-replacement`]. A revocation signed by a
  `pkd1-` kid fails `kid`, because only release keys revoke.
- **One D1 batch** writes the following, then re-resolves:
  - the revocation onto the delegation row (superseding by `newerRevocation`; never cleared);
  - a `release_yanks` row (`reason: delegation-revoked`, `by: ci:<kid>`, `INSERT OR IGNORE`) for
    every release in `release_delegated_records` under it;
  - the clear of the product's sets.

### 6.3 Record route, composition, discovery, console

- **The record route** also serves `release_delegations.jws` and `revocation_jws` by hash.
  Access rule (1) governs them, as for pack and revocation records.
- **Composition.** Delegation revocations join `revocations` with `kind: "delegation"` and
  `pack` = the scope root. They rank as **referenced**: they are kept at P4-13's size step 3 and
  truncated after unreferenced ones, because any device holding a release under the delegation needs
  them.
- **Discovery.** The Release fragment gains `delegations: true`, which the CLI requires.
- **Rule 10.** No new route. The submit body's schema and refusal reasons, the record route's
  description and the discovery fragment change in `polaris-key.v3.yaml`.
  `routeCoverage.test.ts` is unchanged and re-run. The transcripts are re-recorded
  (`pnpm gen:transcripts`).
- **Console, read-only (decision 11).**
  - The admin read model (`packs/adminView.ts`) gains `signer: {kind: "release", kid} | {kind: "delegated", delegation, scope, seq}`
    on each pack release.
  - A new narrative-only admin route, `GET …/release/delegations`, lists each delegation with:
    - its scope, types, `seq`, window and status (`active`, `closed` or `revoked`);
    - the signing release kid, the delegated key's fingerprint, its release count and its
      revocation.
  - The console shows it as a "Content keys" table in the product's Release section. There are no
    write controls: minting and revoking are CI acts.
  - It is not in the wire spec, like every console route (`admin.ts`). `boundaries.test.ts` passes.

### 6.4 CLI and Action (no real keys stored)

- **`pkey release keys generate --content --out <file>`** writes an Ed25519 PKCS#8 PEM (mode 0600,
  never over an existing file) and prints the public key. A content key has no declared kid; its
  kid is derived from the delegation.
- **`pkey release delegate --prefix <packId> --types <t,…> --public-key <b64url> [--expires-in <days>] [--notes <text>] [--dry-run]`**:
  - It signs with `PKEY_RELEASE_KEY` (`recordSigner`); the default window is 180 days, the maximum 366.
  - It refuses a public key equal to any declared release key.
  - It takes `seq` from the stored delegations, self-checks with `releaseRecordClaims` and
    `delegationOf`, and submits `{record}`.
  - It prints the delegation hash, the content kid `pkd1-…` and the window.
- **`pkey release publish`** for a pack, with `PKEY_CONTENT_KEY` (or `--content-key-file`) and
  `--delegation <sha256>`:
  - It fetches the delegation from the record route and checks it with `verifyDelegation` against
    the manifest's declared `releaseKeys`.
  - It checks that the content key's public half is the delegated key, that the pack and type are
    in scope, and that the binding is compatible or standalone.
  - It runs `dataOnlyRefusal` over every file, plus P4-03's tree lints.
  - It sets `issuedAt` to now inside the window, and warns within 14 days of the window's end.
  - It signs with the derived kid, self-verifies through client-core's delegated
    `verifyReleaseRecord`, and submits through the same uploads preflight and ticket.
  - It refuses when both a release key and a content key are given.
- **`pkey release revoke --delegation <sha256> --reason <text>`** (release key; no
  `--replacement`).
- **The Action** gains the inputs `content-key` and `delegation`, exclusive of `release-key`. The
  bundle is rebuilt (`bundle:action -- --check`).
- **Tests** generate keys into temporary directories at run time. The only committed private keys
  are the corpus's published test keys.

## 7. Rollout

1. **P4-19's PR merges** in the corpus lane, after P4-10. Every existing runner stays green.
2. **The Worker deploys:** the migration, ingest, the record route, composition, discovery and the
   console read model.
3. **The CLI and Action release** (`delegate`, the content-key publish, `revoke --delegation`).
   Against an old Worker they refuse, because discovery has no flag.
4. **The SDKs release:** Node and React (P4-19), then Python and Swift (P4-25), then Godot
   (P4-26).

**Adoption rule** (RUNBOOK and docs): a product delegates only once every live app build it cares
about embeds a P4-19 SDK. Older builds simply never install delegated releases (§2.1).

**Old Workers, on rollback:**

- The tables stay, and a pre-P4-19 Worker refuses delegated submits (`kid`).
- Stored delegated releases are still served, but their delegations are not. Devices then cannot
  install them and retry: availability only, never trust.
- The yanks keep releases under a revoked delegation out of an old Worker's sets.
- Devices that learned a revocation keep refusing the target.

**Feature flags.** None. Nothing changes for a product until it mints a delegation.

### 8.2 Risks and follow-ups

**The threat model** (`docs/security/THREAT-MODEL.md`):

- **§2 gains A14, "Delegated content keys".** They live in CI (a GitHub Environment secret per
  content team). Their loss lets an attacker publish data-only packs in one scope until the
  window closes or a revocation lands.
- **§3 gains "Content-key delegation (P4-19)"**: the trust boundary (§2.3–§2.6) and the residuals
  in §8.2.
- **AT-3 gains a branch, `Hold a delegated content key (P4-19)`:**
  - CAN publish data-only pack releases (types ∩ `DELEGABLE_PACK_TYPES`) of compatible or
    standalone packs under its scope, signed inside its window, through the trusted publisher.
    Handlers must refuse malformed or offensive data safely.
  - CAN keep its releases installed after the window closes; only a CI revocation of the
    delegation stops them.
  - CANNOT sign an app record, a revocation, a delegation, a `godot.pck`, `godot.zip`,
    `audio.bank`, `ml.model`, `custom.*` or unknown-type pack, or a pack outside its scope
    (`jws`, `delegation` or `scope` in every SDK).
  - CANNOT ship a Godot resource, a script, an archive or a native binary: the device's extension
    allow-list and content sniff, the same check in the CLI lint, and the extension rule at ingest.
  - CANNOT reach a pin, hold, embedded baseline or replacement.
  - CANNOT re-delegate.
  - CANNOT sign outside its window through an honest Worker. Together with the product key it can
    backdate inside the window, and only revocation bounds it.
- **AT-3's product-key branch gains:**
  - CANNOT forge a delegation or widen its scope.
  - CAN withhold a delegation record (packs under it then cannot install) or its revocation (as
    for any revocation).
- **A release-key line:** a stolen release key can mint delegations, which is no worse than the
  key itself.
- **§9's review triggers gain:**
  - `DELEGABLE_PACK_TYPES` or `DATA_ONLY_EXTENSIONS` grows;
  - a delegation gains a scope dimension;
  - the delegated path is allowed on a surface beyond §2.4's two.
