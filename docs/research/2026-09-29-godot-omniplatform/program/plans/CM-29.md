## 0. Binding decisions

### 0.1 Owner, 2026-10-07 (not reopened)

1. **Commerce is a service**: a `tools/services.json` row, slug `commerce`, `requires: ["license"]`,
   `defaultEnabled: false`.
2. **The requirement rule** (§0.2), packaged in ST-38.
3. **0.9 removes instead of deprecating.** No route alias or window for 0.8 clients. Exceptions only
   for two-release DB contracts and for paths that already-installed native binaries call.
4. **Store notifications are never lost.** Either re-register moved hook URLs in the same release or
   keep the paths; choose from each store's retry window.
5. **Wire changes ride W-LX.** The corpus change goes through LX-18; the SDK wave (LX-19/LX-20)
   carries the new constants and the route move. `PROTOCOL_VERSION` stays 4.

### 0.2 The requirement rule (ST-38 implements it for every `requires` edge)

- A service can be enabled only when every requirement is enabled.
- Disabling a requirement disables its dependents, transitively, in the same audited batch, and the
  console confirmation names them.
- Re-enabling a requirement does not re-enable its dependents.
- A manifest that declares a dependent on while its requirement is off is a validator error.

Today the console already cascades a turn-off in one PATCH (`dependentsOf`, `chainFlip`,
`packages/admin/src/console/pages/core/Services.tsx:193-212`, confirmation `:591-600`) but pulls
requirements **on** when a dependent is switched on; the admin API refuses an incoherent set
(`core/servicesAdmin.ts:194-196`). ST-38 makes the cascade the server's (one `writeSetting` of
`core.services`, one audit row, `?dryRun=1` at `:207-229` returns the cascaded dependents for the
confirmation) and replaces the pull with "available only while its requirements are on". For
Commerce: the switch is available only while Licensing is on; turning Licensing off names Commerce.

### 0.3 Decisions this plan makes (with evidence)

- **D1. The store hook URLs stay where they are, permanently.** `POST /<p>/distribution/hooks/app-store`
  and `…/play-rtdn` remain the registered, advertised URLs; the router hands them to Commerce.
  - Google Play: the RTDN endpoint is a Pub/Sub push subscription in the developer's GCP project.
    Polaris Key has no Pub/Sub client (`git grep pubsub.googleapis` finds nothing), so re-registration
    is a human step per product and cannot be guaranteed "in the same release". Pub/Sub retries a
    non-2xx with backoff only until the subscription's retention ends (default 7 days) [vendor docs].
  - App Store: Apple retries a V2 notification five times, 1, 12, 24, 48 and 72 h apart (about 6.5
    days), in production only; sandbox gets one attempt [vendor docs]. The URL can be PATCHed only
    where the product has ASC API access, and the ASC write gate admits only today's URL
    (`core/storefront/rules/appStore.ts:175`, `connectors/asc/provision.ts:432-436`).
  - A missed human step loses refunds after those windows. Keeping two router rewrites costs nothing.
  - Production today (read-only, 2026-10-07): 0 `dist_connector_events` rows for either hook, 0
    `platform_credentials`, 0 `outlet_credentials`, 0 `dist_connector_settings`. Nothing is
    registered yet, so keeping the paths has no legacy cost either.
- **D2. The device routes get no native-binary exception.** Every successful `binding` call inserts a
  `dist_purchase_bindings` row (`commerce/state.ts:253-280`), and claims need commerce settings.
  Production has 0 bindings, 0 purchases, 0 store products and 0 commerce settings on all four
  products (djdl, polaris-key, storyrime, storytime). No installed binary has ever used these
  routes, so they move in the LX-20 release with no window. Moving now also avoids a later cost:
  an old client that cannot claim leaves a Play purchase unacknowledged, and Google refunds it
  after 3 days.
- **D3. Code layout follows CQW-14.** `services/commerce/` with per-store storefront facets in
  `services/commerce/stores/<store>/{purchases,catalog,notifications}.ts`; shared store
  infrastructure in `core/stores/<store>/{client,credentials,events}.ts` (P0-27); channel facets stay
  in `services/distribution/stores/<store>/`.

### 3.3 Readiness

- `services/commerce/readiness.ts` computes, per in-scope store:
  - **channel set up**: `hooks.delivery()?.outlets()` (`core/hooks.ts:999`) has a live outlet of that
    store's kind. It is null while Distribution is off. A-20 and A-28 later read the store-app
    binding instead;
  - **credential resolves**: `appStoreCredential`, `playCredential`, `steamCredential`;
  - **Ready** = Commerce on ∧ channel ∧ credential.
- The channel is a readiness fact, not a service requirement. Manual and external sources (Core
  subscriptions, LX-41) need no channel. Polaris Key checkout (CM-01 onward) needs a merchant, not a
  channel.
- Commerce on with no storefront Ready lands on the **Commerce setup**: ST-38's one not-set-up
  component, listing each in-scope store with its missing fact and next step (for example "Set up
  the App Store channel in Ship builds", or "Assign the app"). It reuses `setupOf`
  (`commerce/admin.ts:55-80`) until CM-21's state machine and CM-23's Sales tab replace it.
- **Gating.**
  - Claims keep today's per-store gate in CM-29. CM-21 switches them to "answer once Ready"
    (CM-20 D14), and that Ready includes the channel.
  - Hooks are never gated on readiness. They answer whenever Commerce is on and the store's
    verification resolves (`appleContext`, `playContext`), so a refund always lands while Commerce
    is on.

### 3.5 Enabling it for existing products (P0-49 job `commerce.enable`)

- **Select** products with a `dist_connector_settings` row `commerce`, or any `dist_purchases` row.
- **Dry run reports**, per product:
  - License on or off. With License off it never enables (coherence) and is listed;
  - `services_source`;
  - stores configured and purchase count;
  - a flag on manifest-sourced products. A resync rewrites `services_json` wholesale
    (`repo.ts:1776-1781`), so the repo must declare `modules.commerce` or the next push turns
    Commerce off. That is an owner step per adopter. The `modules` schema has no
    `additionalProperties: false`, so a repo can declare it ahead of the release.
- **Apply.** `json_set(services_json, '$.commerce', {"enabled":true})`, keeping `services_source`,
  audited as `product.services.update` by the job's system actor.
- **Down path.** Remove the key from the products the job wrote.
- **When.** The lead runs the read-only selection on production before the deploy (0 rows on
  2026-10-07), then dry-runs and applies right after the deploy. Any gap is covered by Apple's
  first retry at 1 h, Pub/Sub retention, StoreKit's unfinished transactions and the acknowledgement
  retry (`commerce/index.ts:496-533`).

## 8. Risks and open questions

**Q1. Brand accent.** Should Commerce share License's chartreuse (a declared share), or should the
ΔE00 floor drop to 17.0 for a ninth, red-orange accent? **Recommend the share.** It needs no
threshold weakened (§3.6). The owner signs off.

**Q2. "The corpus change goes through LX-18."** CM-29's seven re-recorded discovery transcripts
cannot be separated from the Worker change that causes them. **Recommend** that CM-29 hold the
corpus lane as the first W-LX member, immediately before LX-18, with LX-18's §14 text covering it.
The alternative is to fold CM-29 into LX-18's PR, which roughly doubles LX-18.

**Q3. The interim device spelling.** Between CM-29 and the LX-20 release, `/<p>/distribution/commerce/*`
keeps answering through the router, so that SDK replays and released apps stay green until the wave
moves them. It is removed in the release that moves the SDKs. **Recommend accepting it.** It is not
a window after a replacement, and it makes a Worker rollback from the wave safe.

**Q4. Refunds while Commerce is off.** Turning Commerce (or License) off stops the hooks. Apple's
retries run out after about 6.5 days. **Recommend** keeping the registry rule (a disabled service
runs no code) and saying so in the confirmation, rather than an always-on hook exception. CM-22's
re-verify covers re-enables after a long gap.

**Risk.** Manifest-sourced products must declare `modules.commerce` or a push turns Commerce off. The
job's report lists them. Production has none.
