The plan runs past two pages because the payload tables (§2.3, §2.4), the verification order
(§2.5) and the row lists (§4) are the specification P3-02 builds. Splitting would move them,
not shorten them, and every part gates the same P3-02. If the approver prefers, §2.9 and §4.7
(the outlet matrix) can become a planning package of their own; only P3-11 and the capability
table depend on them.

Names follow what P2-03 and P2b-01 landed: `seq`, `deliverable_id`, `build_id`,
`release_channel_policy.{min_supported, critical, pointer_release_id}`, and the Core hooks
`releaseCatalog`, `delivery` and `outletCapabilities` (`packages/worker/src/core/hooks.ts`).

## 1. Summary

- **Two signed documents.** `pkey-feed+jws` is signed by the Worker's product key. It is
  device-less and covers one channel; its TTL is 900 s and its `seq` grows per (product,
  channel). `pkey-release+jws` is signed by a CI-held release key. It is P2-04's descriptor
  moved into a signed payload, fetched by its SHA-256 and verified only against the release keys
  the app pins. `PROTOCOL_VERSION` becomes 4 in a new `WIRE-CONTRACT-V4.md`. The four v3
  documents keep their shapes and bytes.
- **One stricter verifier for all six `typ`s.** Ed25519 gets fixed rules: `S < L`, canonical
  `A` and `R`, no small-order `A` or `R`, and the cofactorless equation. JSON gets an I-JSON
  profile: well-formed UTF-8, no BOM, no lone surrogates, no U+0000 in a member name, plus
  today's rules. The probe found 14 vectors on which today's four backends already disagree,
  and 4 more that all of them accept but should refuse. 26 new `jwsCases` pin the strict
  verdicts, and P3-02 adds the missing checks in `shared-jws`, Python, Swift and GDScript (§2.2).
- **Corpus.** It stays in `conformance/corpus/v2/` with `corpusVersion` 2:
  - `cases.json` gains 26 `jwsCases`, 32 `feedCases` and 28 `releaseRecordCases`;
  - a new `update-matrix.json` (`updateMatrixVersion` 1) holds 52 decision rows, 9 capability
    cases and 6 bucket vectors;
  - a new `outlet-matrix.json` (`outletMatrixVersion` 1) holds the capability defaults, 24
    signals and 46 detection rows;
  - `stage-matrix.json` goes to version 2 for boot confirmation;
  - `CORPUS_TARGETS` mirrors every file to Swift and Godot.
- **The decision** is a pure, synchronous `decideUpdate` over the verified feed and record, the
  installed build, the outlet and the host's update methods. It returns `none`, `code-ready`,
  `binary`, `store`, `platform` or `blocked`, with `packs`, `prestage`, `content-floor` and
  `revoked-content` reserved. Capabilities default per outlet in one table, which the feed can
  narrow but never widen.
- **Routes and order.** P3-03 serves `GET /{product}/update/{channel}/feed.jws?platform=` and
  `GET /{product}/release/records/{sha256}`. The SDKs follow in this order: P3-02 → P3-05 →
  P3-04, P3-06, P3-07, P3-08 → P3-11. Clients and workers already deployed are unaffected (§7).

### 2.2 One stricter verifier for every `typ`

**§1.1 Ed25519 (normative, [C]).** A verifier applies these checks to the 64-byte signature
`R ‖ S` and to the trusted key `A` before its backend's verify call:

1. `S`, read as a 256-bit little-endian integer, is less than
   `L = 2^252 + 27742317777372353535851937790883648493`.
2. `A` and `R` are canonical encodings. The 255-bit `y` (bit 255 cleared) is below
   `p = 2^255 − 19`, and the encoding is neither of the two "x = 0 with the sign bit set"
   strings, `01 00…00 80` and `ec ff…ff ff`.
3. Neither `A` nor `R` is one of the eight small-order encodings (`SMALL_ORDER_ENCODINGS`,
   lowercase hex, checked with noble on 2026-10-01):
   `0100…00` (order 1); `ecff…ff7f` (order 2); `0000…00` and `0000…0080` (order 4);
   `26e8958fc2b227b045c3f489f2ef98f0d5dfac05d3c63339b13802886d53fc05`, its `…fc85` twin,
   `c7176a703d4dd84fba3c0b760d10670f2a2053fa2c39ccc64ec7fd7792ac037a` and its `…03fa` twin
   (order 8).
4. The equation is cofactorless, `[S]B = R + [k]A`. Every backend measured does this. No
   prime-subgroup check is made, so a mixed-order key with a cofactorless-valid signature
   verifies.

Checks 1–3 are byte comparisons. A lenient backend therefore never accepts what a strict one
refuses.

**§1.2 Strict JSON (normative, [C]).** These rules apply to the decoded header (before the
signature check) and to the decoded payload (after it), for all six `typ`s:

1. The bytes are well-formed UTF-8 (RFC 3629): no ill-formed sequences, no overlongs, no
   surrogate code points, nothing above U+10FFFF.
2. There is no byte order mark at the start.
3. The text is exactly one JSON object (RFC 8259), as today.
4. No string contains an unescaped U+0000–U+001F, as RFC 8259 already requires.
5. No escape is a lone surrogate. Every `\uD800`–`\uDBFF` escape is immediately followed by a
   `\uDC00`–`\uDFFF` escape, and every `\uDC00`–`\uDFFF` escape immediately follows one
   (RFC 7493 §2.1).
6. No object has two members with the same name, as today (RFC 7493 §2.3).
7. No member name contains U+0000. Values keep V3 §10's representation limit and its
   `docNulReplaced` annotation.

**The signer.** `signJws` in `packages/shared-jws` throws if its serialized header or payload
would break rule 5 or rule 7. `JSON.stringify` cannot break the others. So the Worker never signs
a document a v4 SDK refuses. No real data trips it:

- D1 stores text as UTF-8, and a lone surrogate becomes U+FFFD on the way in;
- catalog key patterns rule out U+0000 in a name.

backends in line. That confirms README §9.1 #19. The rule for any later disagreement is
the brief's: the strict verdict, an explicit pre-check in the lenient backend, and never a
loosened expectation.

**The fixes, by verifier (P3-02, one commit each):**

- **`packages/shared-jws/src/index.ts`**, which Node, React and `client-core` use:
  - `ed25519Prechecks(key, sig)` runs before `crypto.subtle.verify`;
  - `parseStrictJson` decodes with `new TextDecoder("utf-8", { fatal: true, ignoreBOM: true })`
    and refuses a leading U+FEFF;
  - `hasDuplicateKeys` becomes `scanStrictJson`, which also refuses lone-surrogate escapes and
    U+0000 in a decoded member name;
  - export `SMALL_ORDER_ENCODINGS` for tests.
- **Python** (`sdks/python/src/polaris_key/core/jws.py`): the same Ed25519 pre-checks; a raw-text
  scan for lone-surrogate escapes; refuse `"\x00" in key` in `_reject_duplicate_keys`.
- **Swift** (`sdks/swift/Sources/PolarisKeyCore/JWSVerifier.swift`):
  - the small-order check on `A` and `R` (CryptoKit already refuses non-canonical encodings);
  - a byte-level `StrictJSON.validate` on the header bytes and on the payload bytes in step 13,
    covering rules 1, 2, 4, 5 and 7 and JSON syntax. Today step 13 runs only the duplicate scan,
    and `JSONDecoder` skips members it does not decode.
- **Godot** (`sdks/godot/addons/polaris_key/core/{crypto/ed25519.gd,json_strict.gd}`):
  - the `x = 0` sign-bit rule for `A`, and the small-order table for `A` and `R`;
  - `PKeyJson.parse_bytes` refuses ill-formed UTF-8 (the re-encoded text must equal the bytes)
    and a leading BOM (no longer stripped);
  - refuse a member name whose escape is `\u0000`, before `nul_as_fffd` runs.

### 2.3 The channel feed, `pkey-feed+jws`

Signed by the product key (`signDoc(…, "pkey-feed+jws")`). It carries no device id, so every
caller of a channel gets identical bytes. Payload cap 65 536 bytes.

| Field                    | JSON type      | Req. | Verifier check (refusal reason)                                                                                                                         |
| ------------------------ | -------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schemaVersion`          | integer        | yes  | `=== 1` (`claims`)                                                                                                                                      |
| `iss`                    | string         | yes  | `=== "key.plrs.im"` (`claims`)                                                                                                                          |
| `aud`                    | string         | yes  | `===` the product (`claims`)                                                                                                                            |
| `channel`                | string         | yes  | matches `CHANNEL_NAME_PATTERN`; equals the requested channel, or `CHANNEL_ALIASES[requested]` when the request used an alias (`channel`)                |
| `selector`               | object         | yes  | keys ⊆ {`platform`}; `platform`, when present, equals the client's platform (`selector`). P4 may add keys; a v4 client refuses any key it does not know |
| `seq`                    | integer        | yes  | 1 ≤ `seq` ≤ 2^53 − 1 (`claims`); against the floor (`rollback`, §2.5 step 8)                                                                            |

- **One feed per (product, channel)**, requested as
  `GET /{product}/update/{channel}/feed.jws?platform={platform}`. The Worker answers with the
  channel-wide document (`selector: {}`) while its UTF-8 JSON fits in 65 536 bytes. Otherwise it
  splits the channel into per-platform documents (`selector: {platform}`) and answers with the
  one for the requested platform. A per-platform document that still does not fit is refused
  with a 5xx (P3-03). The SDK always sends `platform`, so a split is invisible to it.
- **`seq` per (aud, channel), shared by every selector of the channel.** The Worker composes the
  whole channel at once. It bumps `seq` when the composed content's SHA-256 changes, and every
  selector document carries the same `seq`. A client keeps one floor per (aud, channel), so
  switching selectors (today platform; in P4 `contentApi`) can never evade it.
- **TTL.** `expiresAt = issuedAt + FEED_TTL_SECONDS` (900, the top of README §3.9's 5–15 min).
  The Worker may reuse a signed document while its content is unchanged and it is less than
  450 s old. A content change (pointer, floor, halt, rollout) signs a new one at once.
- **Stale means freeze.** A feed is stale when `now ≥ expiresAt + CLOCK_SKEW_SECONDS`, with
  `now` the effective clock. The decision then answers `none {reason: "stale"}`: keep running
  and never update automatically (notes/E5 §1.4).
- **No clock floor.** Neither the feed nor the record raises the clock floor, so V3 §4.2 and its
  `clockFloorCases` stay exactly as they are. The feed's freshness is checked against the
  effective clock, so winding the system clock back cannot revive an expired feed.

### 2.5 Client verification order

Each step names the corpus family that pins it. `now` is the effective clock,
`max(system, highWaterMark)` (V3 §4.2).

1. Read `update.endpoints.feed` and `release.endpoints.record` from discovery. If either is
   absent (an older Worker, or Update off), refuse with `service-unavailable` before dialling.
   The host falls back to `update.check()` (P3-03's transcripts).
2. `GET …/update/{channel}/feed.jws?platform={platform}`. If the body equals the committed JWS
   for this channel, nothing changed: go to step 10 (each SDK's wiring tests, P3-04 to P3-08).
3. `verifyJws` with the **effective** trust set (pins ∪ manifest keys, as for documents) and `typ`
   `pkey-feed+jws`. This includes §2.2's rules (`jwsCases`; `feedCases` reason `jws`).
4. The claims in §2.3 (`feedCases` reason `claims`).
5. Channel binding (`feedCases` reason `channel`).
6. Selector (`feedCases` reason `selector`).
7. Network path only: freshness at `now` (`feedCases` reason `freshness`).
8. The `seq` floor for (aud, channel), derived from the committed feed. Accept
   `seq > floor.seq`, or `seq == floor.seq` with `issuedAt > floor.issuedAt`. Refuse anything
   else (`feedCases` reason `rollback`). This is README §3.3's "refuse a lower `seq`". Rolling
   back means rolling forward: CI publishes a higher version.
9. Commit the feed: Core's read-modify-write of `feeds[channel]` (§2.6; each SDK's restart
   tests).
10. Take the target for this platform. If there is none, decide without a record (step 18).
11. Use `releaseRecords[sha256]` from the cache, or `GET …/release/records/{sha256}`. Refuse a
    body longer than 88 844 characters (the compact JWS bound: 1 370 + 1 + 87 386 + 1 + 86).
12. **Hash before signature.** The lowercase hex SHA-256 of the exact body bytes must equal
    `release.sha256`, before any Ed25519 work (`releaseRecordCases` step `hash`).
13. `verifyJws` with the **pinned release keys only**, never merged with, and never added to
    from, the product trust set; `typ` `pkey-release+jws` (`releaseRecordCases` step `jws`,
    including the key-separation cases).
14. The record claims in §2.4 (`releaseRecordCases` step `claims`).
15. Cross-check against the pin: `kind` and `deliverable` are `"app"`, and `version` and `seq`
    equal the pin's (`releaseRecordCases` step `cross-check`).
16. Commit the record to `releaseRecords[sha256]` (each SDK's restart tests).
17. If the outlet's entry has a `rollout`: `bucket = rolloutBucket(rollout.salt, installId)`
    (`update-matrix.json` `bucketVectors`).
18. `decideUpdate` (`update-matrix.json` rows), then `bootDecision` (each row's `expect.boot`).
19. When acting, verify the bytes against the record: payload `size` and `sha256`, before
    staging and again before a swap (P3-10 unit tests; host behaviour, not a corpus family).

**Reload path** (cache load). Each `feeds[channel]` goes through steps 3–6 with no freshness
and no floor (`feedCases` `feed-valid-reload-path-expired`); the survivor gives that channel's
floor. Each `releaseRecords[h]` goes through steps 12–14 with `h` as the pin, and is dropped
unless a surviving feed's target for this platform pins it. Anything that fails is absent.

### 2.6 Cache, floors and keys

`CacheRecordV3` (`packages/client-core/src/store.ts:34`) gains two optional slices.
`CACHE_VERSION` stays 3, because the change is additive: v3 loaders ignore unknown members, and
a v4 loader treats a record without them as "no floor yet".

```ts
feeds?: Record<string /* canonical channel */, string /* pkey-feed+jws, verbatim */>;
releaseRecords?: Record<string /* lowercase hex sha256 */, string /* pkey-release+jws */>;
```

- **Signed artifacts only** (V3 §4.1). Floors are derived on load, never stored.
- **What is written.** The SDK writes the slice for the channel it fetched and leaves other
  channels' entries alone, so switching back cannot be rolled back. It may drop entries for
  channels it no longer follows. A record is kept only while a committed feed pins it.
- **Release keys.** `pinnedReleaseKeys` (`pinned_release_keys` in Python and GDScript) maps
  `kid` to a raw 32-byte Ed25519 key in base64url, the `TrustSet` encoding. It is configured by
  the host, compiled into the app, and never persisted, merged or extended from the network. An
  empty map makes `decide()` refuse with `not-configured`. Two or more keys are valid at once
  during a rotation. Discovery may advertise `release.releaseKeyFingerprints` (lowercase hex
  SHA-256 of each raw key) for tooling such as `pkey release keys check`. No SDK reads it.

### 2.8 The update decision

**Inputs** (`UpdateDecisionInput`). The brief's "previous channel" is `staged.channel`, and its
"capabilities" are computed inside, from `outlet`, `subkind` and the feed.

| Input                         | Type                                              | Source                                                                                                      |
| ----------------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `now`                         | integer                                           | the effective clock                                                                                         |
| `feed`                        | `ChannelFeedDoc`                                  | verified, on the network or the reload path                                                                 |
| `record`                      | `ReleaseRecordDoc` \| null                        | the verified, cross-checked record that the target for `installed.platform` pins; null if absent or refused |
| `installed.version`           | string                                            | the running version (the stamp's `version`; after a sidecar code update, the code pack's version)           |
| `installed.binaryVersion`     | string (optional)                                 | the executable's version; defaults to `version`                                                             |
| `installed.buildNumber`       | string \| null                                    | the stamp's `build`; informational in v4                                                                    |
| `installed.platform`, `.arch` | enums `platform`, `arch`                          | the device (arch is the device's: `arm64`, `x86_64`, `armv7`, `wasm32`)                                     |
| `installed.format`            | string \| null                                    | the installed build's format (optional stamp field, §8)                                                     |
| `installed.engine`            | string \| null                                    | `godot-<major>.<minor>` from the stamp; null outside Godot                                                  |
| `outlet`, `subkind`           | `OutletId` \| `"unknown"`, string \| null         | the host's value, or `detectOutlet` (P3-11)                                                                 |
| `channel`                     | string                                            | the canonical channel followed                                                                              |
| `staged`                      | `{version, channel}` \| null                      | an update the host staged and verified                                                                      |
| `skipVersion`                 | string \| null                                    | the version the boot guard rolled back                                                                      |
| `bucket`                      | integer \| null                                   | `rolloutBucket` for the salt of this outlet's rollout                                                       |
| `methods`                     | subset of `["native", "sidecar-pck", "download"]` | what this host can do; default `["download"]`                                                               |

**Bucket.** `bucket = u32_be(SHA-256(UTF-8(salt) ‖ UTF-8(installId))[0..4]) mod 10000`:

- `salt` is the feed's 32-character hex string, hashed as text;
- `installId` is the SDK's device id, the value it sends as `X-PKey-Device`;
- there is no separator;
- the first four digest bytes are read big-endian as an unsigned integer;
- the device is eligible iff `bucket < bp`.

**Algorithm.** The first rule that applies decides. `cmp` is `compareSemver`, the one comparison
(`client-core/src/semver.ts`).

1. **Stale.** If `now ≥ feed.expiresAt + 300`, the answer is `none {reason: "stale"}` and the
   staged update is kept.
2. **Unknown version.** If `installed.version` or `binaryVersion` does not parse as SemVer, the
   answer is `none {reason: "unknown-version"}`.
3. **Setup.**
   - `caps = effectiveCapabilities(outlet, {subkind, server: entry?.capabilities})` (§2.9);
   - `target` is the feed's target for the platform, and `entry` is `target?.outlets[outlet]`
     (`unknown` never has an entry);
   - `belowFloor` means `feed.app.floor` exists and `cmp(binaryVersion, floor.minVersion) < 0`.
     The floor is judged against the binary (A4 P5, P6).
4. **The offer.**
   - When `caps.binaryUpdates` is `self`, the offer is `target.release`, but only when
     `entry.live.seq === target.release.seq` and `record` is not null.
   - Otherwise the offer is `entry.live`.
   - If there is no offer, the answer is `blocked {reason: "app-floor"}` when `belowFloor`,
     else `none {reason: "not-available"}`.
5. **Behind.** If `cmp(offer.version, installed.version) < 0`, the answer is
   `none {reason: "behind", behind: true}`. The floor is suppressed (A4 P1). There is no
   downgrade.
6. **Up to date.** Let `newerRun` be `cmp(offer.version, installed.version) > 0` and
   `newerBin` be `cmp(offer.version, binaryVersion) > 0`. If `!newerRun` and not (`belowFloor` and `newerBin`), the
   answer is `blocked {reason: "app-floor"}` when `belowFloor`, else
   `none {reason: "up-to-date"}`.
7. **Halted.** If `entry.halted`, the answer is `blocked {reason: "app-floor"}` when
   `belowFloor`, else `none {reason: "halted"}`.
8. **Rollout.** Applies when `entry.rollout` is present, the device is not below the floor and
   `target.critical` is false. If `bucket < rollout.bp` does not hold, the answer is
   `none {reason: "out-of-bucket"}`. A critical release and a below-floor device bypass the
   rollout.
9. **Platform.** If `caps.binaryUpdates === "none"`, the answer is
   `platform {release: offer, mandatory: belowFloor}`.
10. **Store.** If `caps.binaryUpdates === "store"`, the answer is
    `store {release: offer, listingUrl: entry.listingUrl ?? null, mandatory: belowFloor}`.
11. **Self-updating outlets.** The answer is the first of these that applies:
    - a. **`code-ready`.** All of: not `belowFloor`, `newerRun`, `caps.codeUpdates`,
      `staged.channel === channel`, `staged.version === offer.version`, and
      `offer.version !== skipVersion`.
    - b. **`binary {method: "sidecar-pck"}`.** All of: not `belowFloor`, `newerRun`,
      `caps.codeUpdates`, `"sidecar-pck"` in `methods`, `offer.version !== skipVersion`, and a
      code-pack build exists. A code-pack build has `format: "pck"`, a platform that is null or
      equal to the device's, a compatible arch, `requires.engine === installed.engine` (both
      non-null), and `cmp(binaryVersion, requires.minBinary ?? "0.0.0") ≥ 0`.
    - c. **`binary {method: "native"}`, then `{method: "download"}`.** Requires `newerBin`, the
      method in `methods`, and an eligible binary build:
      - its platform equals the device's and its format is not `pck`;
      - its arch is the device's, `universal` or `any`, preferred in that order;
      - its format equals `installed.format` when that is known;
      - ties go to the build id in ascending order.
    - d. **Otherwise**, in this order:
      - `blocked {reason: "app-floor"}` when `belowFloor`;
      - `none {reason: "skipped"}` when `offer.version === skipVersion`;
      - `none {reason: "no-build"}` when no eligible build exists;
      - `none {reason: "no-method"}` otherwise.

On every answer except `stale`, `discardStaged` is `staged !== null && action !== "code-ready"`.
That covers A4 P11 (a channel switch drops staged code) and E5 §5.2 (a halt discards what was
staged).

**Outputs** (`UpdateDecision`). `release` is `{version, seq}`, plus `sha256` on `code-ready` and
`binary`. Every member also carries `discardStaged`.

| `action`     | Members                                                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `none`       | `reason` ∈ `up-to-date`, `behind`, `not-available`, `halted`, `out-of-bucket`, `stale`, `skipped`, `no-method`, `no-build`, `unknown-version`; `behind` |
| `code-ready` | `release`, `critical`                                                                                                                                   |
| `binary`     | `method` ∈ `native`, `download`, `sidecar-pck`; `release`; `build` (a build id); `mandatory`; `critical`; `prestage: []` (reserved; filled by P4-13)    |
| `store`      | `release`, `listingUrl`, `mandatory`, `critical`                                                                                                        |
| `platform`   | `release`, `mandatory`, `critical`                                                                                                                      |
| `blocked`    | `reason`: `app-floor` (`content-floor` and `revoked-content` are reserved for P4-13)                                                                    |
| `packs`      | reserved for P4. Never produced in v4                                                                                                                   |

**`bootDecision`** maps a decision onto the stage machine's `decide.done` (P1-09):

- `none`, and `platform` that is not mandatory, give `none`. Platform outlets stay silent.
- `code-ready`, and `binary` or `store` that is not mandatory, give `optional`.
- A mandatory `binary`, `store` or `platform`, and every `blocked`, give `required`.

**Invariants and the rows that pin them** (§4.6):

- no downgrade, and `behind` suppresses the floor (rows 2–3);
- the floor is judged against the binary (row 7);
- engine and `minBinary` gating, and the binary supersedes code (rows 9–11);
- the skipped version is never re-offered automatically (rows 15–16);
- a channel switch drops staged code (row 13);
- store builds never self-update code (row 31);
- a halted or out-of-bucket outlet gets `none` (rows 19, 21, 23);
- a stale feed never updates or blocks (rows 39–40);
- capabilities only narrow (rows 42–45);
- format and arch gating (rows 47–49).

| `unknown`                  | `none`          | false         | false         | false           | `none`      | false               | any                                 |

- **What the fields mean.**
  - `binaryUpdates` says who installs a new build:
    - `self`: the SDK downloads it or hands it to a native updater;
    - `store`: the SDK opens a store, or a store app, that installs it;
    - `none`: the platform installs it without the app (Steam, Flathub, App Installer, and a
      reload on web).
  - `codeUpdates` gates `sidecar-pck` and `code-ready`; `dataUpdates` and `downloadedScripts`
    gate P4's packs.
  - `channelSwitch` gates the dev-menu picker; `commerce` is for P6.
- **Narrowing** (`effectiveCapabilities`). The defaults for `outlet` are narrowed first by the
  subkind (`SUBKIND_NARROWING`), then by the feed entry's `capabilities`:
  - booleans are `default && narrowing`;
  - `binaryUpdates` takes the narrower value in the order `none` < `store` < `self`;
  - `commerce` becomes `none` only when a narrowing says `none`; any other value is ignored;
  - nothing widens.
- **Subkinds** (S-06 notes b and c):
  - `homebrew`, `npm`, `pnpm`, `npx`, `scoop`, `chocolatey` and `flatpak` narrow `direct` to
    `binaryUpdates: none` and `codeUpdates: false`, because the package manager or Flatpak updates
    the install;
  - `appimage` narrows nothing, because AppImageUpdate is a native method.

**Detection.** This plan adopts notes/S-06's eight precedence rules and its signal table, with
these decisions on S-06's open points:

- `AppDistributor.web` maps to `direct`;
- the five rows backed only by documentation (`ios.appDistributor`, and the
  `windows.packageIdentity`, `windows.signatureKind`, `windows.appInstallerUri` and
  `windows.externalLocation` rows) stay `attested`. Lowering them would make every stamp-less
  App Store install `unknown`;
- Android `play` stays `declared` until P5-06 records the Play Store's certificate digest in
  `platformData`;
- a `subkind` is part of the result, with the narrowing above;
- web runtimes (the React browser adapter, Godot web exports) synthesise `stamp.outlet = "web"`.

The algorithm, made deterministic for `detectOutlet({stamp, signals})`:

1. Drop every launcher signal whose identity condition fails (§4.7), and every diagnostic signal
   (`steam.appIdFile`, `itch.appEnv`).
2. **Attested signals that name an outlet decide.** Two that name different outlets give
   `unknown`. For the macOS receipt: a receipt alone means `app-store`; a receipt with
   `ProductionSandbox` means `testflight`; a store signing leaf must name the same outlet as the
   receipt. `linux.flatpakInfo` keeps a `direct` + `flatpak` stamp, and otherwise names
   `flathub`.
3. Otherwise start from the stamp, with confidence `stamp`. With no stamp the result is
   `unknown`: declared and heuristic evidence never selects an outlet on its own (S-06 rule 7).
4. **Vetoes.** A veto that names the current outlet gives `unknown`.
5. **Restricting signals,** declared before heuristic and then in vocabulary order. The first
   whose outlet's `binaryUpdates` is no wider than the current one moves the result there, with
   its subkind. A signal naming the current outlet only raises the confidence to its own.

The result is `{outlet, confidence ∈ attested | declared | heuristic | stamp | null, source:
signal name | "stamp" | null, subkind}`. Async platform calls have a 2 s deadline, and a timeout
is no evidence. Detection runs at every launch and is never cached. Raw signal values never
leave the device.

### 2.10 Boot confirmation (`stage-matrix.json` version 2) and telemetry names

P1-09 left the confirmation criterion to this plan (its decision 5 and risk 1). **A launch is
confirmed** the first time one of these holds. A confirmed launch resets `failedBoots` to 0,
under P1-09's counting rule (§2.3 there).

- The machine's outcome is `waiting`, `blocked` or `offline`. The app is running and waiting
  for the player, so quitting at the activation screen can never roll back a good update.
- The outcome has been `ready` for `BOOT_OK_SECONDS` (10, Diceroll's value) with the process
  alive.
- The game calls `confirmBoot()` while the outcome is `ready`.

`running` and `error` never confirm, so a launch that ends in `error` (for example, a pack that
does not mount) counts as failed.

The pure part is `bootConfirmation(outcome) → "now" | "after-ok-seconds" | "never"`. The timer
and `confirmBoot()` are host-side (P3-10). The stage machine itself is unchanged: no new event,
no new emit, and every existing row, probe and guard case stays byte-identical. The vocabulary
gains `confirmations`, so the version goes to 2 (§4.8).

**Telemetry names** (README §3.6 and P6-03). These travel on the unsigned `devices/report`, so
they are not a wire change. They are fixed as the `updateEvent` enum in
`conformance/parity/enums.json`: `update_offered`, `update_downloaded`, `update_applied`,

    - the stored bytes exactly, `application/jose`, `ETag: "<sha256>"`;

    - an unknown hash is 404.

non-plan-mode. It keeps `version`, `tag` and `url`, adds `build`, `sha256`, `size`,
`downloadUrl`, `minOS` and `critical`, selectable with `?platform=&arch=&outlet=`, and documents
them in OpenAPI only. SDKs keep reading the v3 fields in `check()`; the signed feed is their path
for everything else. Its routes keep the `/update/{channel}/<file>` family the feed now joins.

**P2b-04.** `GET /{product}/distribution/blobs/sha256/{hash}` must serve every artifact a record
names, by its SHA-256, wherever the bytes are: R2 directly, or GitHub through
`releaseCatalog.openSource`. Clients then need only the record's hash (§2.4).

## 7. Rollout

1. **P3-02 merges.** The contract, the corpus and `PROTOCOL_VERSION` 4 land, with the verifier
   fixes in every SDK.
   - **Deploying the Worker** changes only discovery's `protocolVersion`.
   - **Deployed v3 clients.** No SDK enforces `protocolVersion`: Node and Swift read it from
     discovery, and nothing compares it. The licence, config, trust and bundle documents are byte-identical,
     so deployed clients are unaffected.
   - **New SDK releases** carry the stricter verifier. Everything the Worker signs already
     passes it (the transcripts and the corpus prove this), and the signer guard (§2.2) makes
     sure it stays that way.
2. **P3-03 deploys** the routes, the tables and the record ingest.
   - **Older Workers** have no `endpoints.feed`. A v4 SDK refuses with `service-unavailable`,
     and the host keeps using `check()`.
   - **A rollback** to a pre-P3-03 Worker has the same effect. The new tables just sit unused.
   - **What the feed carries.** A product with no `releaseKeys`, or a release published before
     v4, has no record, so the feed carries no target for it. Installs get signed updates from
     the first CI-signed release onwards.
   - **Untouched surfaces.** `/update/version`, the appcasts and `/release/dl` keep their
     behaviour.
3. **The SDK wave:** P3-05, then P3-04, P3-06, P3-07 and P3-08, then P3-11.
   - Cache records stay version 3. A downgraded SDK ignores the new slices; a v4 SDK reading an
     old record has no floor yet, so it accepts the first fresh feed.
4. **Then P3-09, P3-10, and Diceroll's D-03.**

There are no feature flags. The feed answers only where Update, and so Distribution, is enabled.
In the corpus lane, P3-02 and P1b-04 must not be in flight together: whichever lands later
rebases, re-runs `pnpm gen:corpus` and commits the result.
