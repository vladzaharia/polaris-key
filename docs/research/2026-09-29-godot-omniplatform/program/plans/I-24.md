## 0. Owner decisions encoded (binding, 2026-10-04)

- **S-16 D9, read as S-19 decision 2 reads it.** D9 is a rule about what the document contains. The
  user claim lands here, and only here. The signed-in account may still feed the document's inputs.
- **S-19 decision 1 (model OC).** A licence is an access contract: tier, seats, term and offline window.
  Grants are reasons for entitlements. Each device has exactly one anchor licence, and named-user
  seats sit on that anchor (S-19 §7.3.1 "Team and named-user seats").
- **S-19 decision 4 (`entitlementHolder: device`).** The holder is the account signed in on the
  device (`devices.subject`). A seat user sees the company licence's slice plus their own
  licences and grants, and never the owner's personal ones (S-19 §7.8).
- **S-19 decision 5 (legacy byte-identical).** `entitlementModel: legacy` reproduces today's
  documents byte for byte. §2.4 keeps this true for every licence that has no named-user seats.
- **S-19 decision 3 (anchor `rank-first`).** S-19 §7.5 steps 1–3, which I-09 carries inline until
  LX-10, gain one candidate source (§2.3).
- **S-16 and I-04.** The holder is the pairwise subject (`ps_…`) and never the account id (I-04
  §6.2). Seat holders reuse `devices.subject` and there is no `holder_account_id` column (S-17
  §6). App sign-in works only through Identity, so named-user seats need the Identity toggle on
  (owner, 2026-10-04).
- **S-18 D2 (model C).** A console edit of a tier's seat policy claims the field, and **Revert**
  returns it to the manifest value. **S-18 D20, resolved by S-19:** the account is not a settings scope.

## 1. Summary

- **Signed shape:** `pkey-license+jws` gets an optional `profile.user = {"subject":"ps_…"}`. It
  is present only on a device that holds a named-user seat. Every v4 verifier already ignores
  profile members (V4 §3.2). A new client-core usability function, `licenseUserOf(doc)`, reads
  the member.
- **Policy entitlements:** the Worker injects the enforced keys `license.maxUsers` (N) and
  `license.devicesPerUser` (M) into the reserved `license.*` prefix (S-19 §7.4), only on
  named-user licences. The reader is `licenseNamedUsersOf(doc)`.
- **HTTP:**
  - `device_limit` gains `scope: "user"` when the per-user cap refuses.
  - Key entry on a new device of a named-user licence answers `account_required` with `signInUrl`.
  - New codes `seat_limit`, `seat_invite_invalid` and `named_users_require_identity` cover the
    console and portal.
- **Data:** tier and licence columns for N and M, plus one seat-holder table and one invite
  table, both keyed by pairwise subject. Every licence without named-user seats keeps
  byte-identical documents.
- **Order:** this plan → contract → `errors.json` → corpus → client-core → Worker → transcripts →
  Node, React, Python, Swift, Godot and Kotlin, plus the React, SwiftUI, Godot and Compose kits.

## 2. Contract

### 2.1 Signed document (WIRE-CONTRACT-V4, I-24a)

- **§2.1** adds this member:

  ```jsonc
  "profile": { "name": "…", "firstName": "…", "email": "…", "activatedAt": 0,
               "user": { "subject": "ps_…" } }
  ```

  It is written into the existing licence document. The top-level `name`, `firstName` and
  `email` stay the licence holder's (the buyer, for example "Acme Corp"), so old SDKs greet as they do
  today. `user` is the **seat holder**, the pairwise subject signed in on this device. It carries no
  name, no email and no account id (§8 Q3).

- **§3.2** adds a sentence. `profile.user` is read only by `licenseUserOf`. The function returns
  `{subject}` when `profile` is an object, `user` is an object and `subject` is a string that wholly
  matches `PAIRWISE_SUBJECT_PATTERN` `^ps_[A-Za-z0-9_-]{22}$` (§3.3 rule 1). Otherwise it
  returns `null`. The member never refuses a document. Unknown members of `user` are ignored.
- **§2.1 and §8:** the reserved policy keys `license.maxUsers` (integer 1–10 000) and
  `license.devicesPerUser` (integer 1–100) are `enforced` entries. `licenseNamedUsersOf(doc)`
  returns `{maxUsers, devicesPerUser}` only when both keys hold a plain integer token in range
  (the §2.4.1 content-member rule). Otherwise it returns `null`. §8 gains rows for the two keys
  and for the pattern.
- **§9** adds an "I-24 changes no counter" sentence. **§10** adds a ledger entry: _the seat holder
  is read beside the claims_.
- **Bundles (§7):** an admin bundle for a named-user licence must name a `subject` that is a
  current seat holder. Its inner licence document then carries `profile.user`, and the bundle
  counts against that holder's M.

### 2.2 Packages

- **`shared-protocol`** (`src/license.ts`): `DocProfile.user?: SeatHolder`, where
  `SeatHolder = {subject: string}`, and `NamedUsers = {maxUsers: number; devicesPerUser: number}`.
  - `PAIRWISE_SUBJECT_PATTERN` moves from `worker/src/core/accountSubjects.ts:34` into `src/core.ts`.
    I-09's `identity` subpath re-exports it, and the Worker imports it.
  - `PolarisErrorCode` gains the three codes below.
  - The `exports` layout is unchanged.
- **`client-core`**: `licenseUserOf(doc)` and `licenseNamedUsersOf(doc)` in `src/license.ts`, exported
  from the package root. **`verify.ts` does not change**, and neither do the gate, the stages or
  `CACHE_VERSION`.
- **`shared-jws`** does not change.

### 2.3 HTTP (I-09's §12, extended by I-24a)

- **Sign-in activation** (device code, redirect token, attach, and the I-13 exchange later)
  changes in two places:
  - **Step 1 candidates** gain the licences on which the subject is a seat holder, have a
    free per-user slot (fewer than M authorized, non-dormant devices with this `(license_id,
subject)`), and are below `deviceLimit`.
  - **Step 2 ordering** stays `rank-first`, and a tie goes to a licence the account owns.
  - If the subject's only candidates are full seats, the answer is
    `403 {"error":"device_limit","limit":M,"deviceCount":n,"scope":"user"}`, the flat body
    `authorizationError` already emits (`activation.ts:51`).
  - `scope` is `"user"` only for this refusal. The ordinary seat refusal stays byte-identical, with
    no `scope`.
- **Key entry** (`license/activate`, `identity/session/license`) of a named-user licence on a device
  that is not enrolled answers `403 {"error":"account_required","signInUrl":…}`. This check runs
  before the `license_owned` and `key_entry_limit` checks. Re-entry on an enrolled device works as
  today.
- **Sign-out** (I-04 §8 Q3, extended): a sign-in-bound device is released when its licence is the
  account's own _or_ it holds a named-user seat for the subject that signed out. Without this, a
  device would sit on a named licence with no holder.
- **Discovery:** no change. Named-user status travels in the document.

### 2.4 Byte identity, and clients and workers already deployed

- **Byte identity.** `profile.user` and the two policy keys are emitted **only** when the
  effective `max_users` (licence ?? tier) is non-null **and** `devices.subject` is set. For every
  other licence the document builder's output is unchanged. A Worker property test proves it
  over the transcript fixtures. No live licence has seats until an operator sets them.
  - Whichever of I-24a and LX-09 lands second makes LX-09's `legacy` resolver reproduce these
    additions as part of "today", and still read no contributor beyond the anchor.
  - In `legacy` mode a seat user sees the company slice only. Their own grants arrive in `combined` (S-19
    §7.3.2).
- **Old SDKs** verify the new documents (the members are unchecked or ignored, and every decoder
  is total: `models.py:272`, `Models.swift:89`, `Models.kt:114`, `license.gd:126`). They meet
  `account_required` only on a new install of a named-user licence. Node maps it to `device-limit`,
  which is the wrong copy, but no state is lost. The §7 platform switch keeps named-user licences
  from being created until I-24b and I-10a/b are released.
- **New SDKs on an old Worker** see no `user` and report `seatHolder() == null`.
- **Old Worker on rolled-back code** ignores the new columns. A named-user licence then acts as an ordinary
  licence: `deviceLimit` still holds, and only the per-user cap opens.

## 8. Open questions for the owner

1. **Q1 How a person becomes a named user.**
   - **Recommend:** an explicit holder list on the licence. The owner adds people in the portal
     with single-use invite links, and the developer adds them through the admin API by subject.
     This needs one table beyond the device binding, and the brief's "no `holder_account_id`"
     still holds.
   - Alternatives: "join by key while signed in" (no table, but a leaked key fills the seats) or
     "the first N signed-in users".
2. **Q2 Does the owner use a seat?** **Recommend:** yes, once they run a device on the licence.
   They hold an implicit `owner` row and need no invite.
3. **Q3 What `profile.user` carries.** **Recommend:** `subject` only. A consented name or email
   (I-04 Q2 grants) can be added later as another optional member.
4. **Q4 Which devices get the user claim.**
   - **Recommend:** only devices that hold a named-user seat. This keeps S-19's legacy byte
     identity for every other licence.
   - Alternative: every signed-in device. This changes live documents and would need the holder
     report first.
5. **Q5 Per-user refusal code.**
   - **Recommend:** reuse `device_limit` with `scope:"user"`. Old SDKs then already show the
     right copy.
   - Alternative: a new code, `user_device_limit`.
6. **Q6 Whose config account layer a seat device gets.**
   - **Recommend:** the seat user's own layer. This matches S-19 D4 and I-04's "signed-in account
     wins" rule.
   - This amends S-17 §5 ("Seats (I-24) … every device of the licence gets the owner's layer").
     Licence overrides still apply to every device.
7. **Q7 Key-bound devices when a licence becomes named-user.**
   - **Recommend:** they keep working as "unassigned" devices. They count against `deviceLimit`
     and against no user, and they go away when they become dormant or an operator releases them.
     New key entry is refused.
   - Alternative: deauthorize them at once.
8. **Q8 Split I-24 into I-24a and I-24b.** **Recommend:** yes. One package cannot carry the Worker,
   the console, the portal, six SDKs and four kits in 1–2 weeks.
