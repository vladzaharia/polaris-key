## 1. Summary

- One vocabulary everywhere: `stable`, `beta`, `pr-<n>` (a `pr` grant covers every PR), a
  product's manual channels, and `dev`, the licence gate's pseudo-channel for `0.0.0-dev*` builds.
  `staging` (→ `beta`) and `latest` (→ `stable`) are accepted aliases that no SDK emits after this
  change. Every name matches `^[a-z0-9][a-z0-9-]{0,63}$`.
- The build gate (`checkBuildGate`, run by `/license/document` and identity's `/session`) and the
  `entitled` release check share one normaliser and one entitlement predicate, in a new
  `packages/worker/src/core/channels.ts`. Release resolves a `staging` selector as `beta` unless
  the product declares a manual channel named `staging`.
- `channelForVersion` maps `0.0.0-beta*` and `0.0.0-staging*` to `beta` in the Worker,
  `client-core`, Python and Swift, so SDK beta builds send `X-PKey-Channel: beta`.
- `gate-matrix.json` goes from 21 to 38 rows: 18 are appended, and one carried row is retired
  because it pins the dev-build bypass that R3-01 removed. The Node, Python and Swift ports are
  rewritten to mirror the server, and a new Worker test makes the real `checkBuildGate` the oracle
  for every row.
- No signed document, claim, `typ`, cache record or encoding changes. Old clients get the same
  decisions, except for the widenings in §2.4 and two narrow tightenings: `0.0.0-beta*` builds,
  and a literal `manual` grant under `entitled`.

## 2. Contract

### 2.1 `docs/security/WIRE-CONTRACT-V3.md`

Add a normative **§5.1 Channel vocabulary** after §5's bullet list. It is marked **[C]** because
gate-matrix v2 pins it.

| Name      | What it is                                                               | Valid as                         |
| --------- | ------------------------------------------------------------------------ | -------------------------------- |
| `stable`  | the shipping channel; every grant holds it                               | header, selector, grant          |
| `beta`    | the pre-release channel                                                  | header, selector, grant          |
| `pr-<n>`  | one pull request; `<n>` is 1–7 digits, kept as written                   | header, selector, grant          |
| `pr`      | the PR family: as a grant it covers every `pr-<n>`                       | header, grant                    |
| `dev`     | the gate pseudo-channel of `0.0.0-dev*` builds (R3-01); Release has none | header, grant                    |
| manual    | a name from the product's `release.manualChannels`                       | header, selector, grant          |
| `staging` | the legacy alias of `beta`                                               | header, grant; selector (rule 6) |
| `latest`  | an alias of `stable`                                                     | header, selector                 |

1. **Alphabet.** Every name matches `^[a-z0-9][a-z0-9-]{0,63}$`. This is the intersection of the
   manifest's `CHANNEL_RE` (`shared-manifest/src/index.ts:347`) and the feed routes'
   `^[a-z0-9-]+$` (`update/routes.ts:20`, `router.ts:181`). The routes keep their own pattern,
   which every valid name passes.
2. **Build-implied channel**, `impliedChannel(version)`:

   | Version          | Channel                                             |
   | ---------------- | --------------------------------------------------- |
   | `0.0.0-dev*`     | `dev`                                               |
   | `0.0.0-beta*`    | `beta`                                              |
   | `0.0.0-staging*` | `beta`                                              |
   | `0.0.0-pr-?<d>*` | `pr-<d>`, or `pr` when `<d>` has more than 7 digits |
   | anything else    | `stable`                                            |

   Only the `0.0.0-<word>` sentinels carry a channel: `2.0.0-beta.1` stays `stable`, as
   `gate.test.ts:101` pins today.

3. **Header**, `normalizeChannelHeader(header, version)`:

   | `X-PKey-Channel`               | Becomes                                             |
   | ------------------------------ | --------------------------------------------------- |
   | `stable`, `latest`             | `stable`                                            |
   | `beta`, `staging`              | `beta`                                              |
   | `dev`                          | `dev`                                               |
   | the literal `pr`               | the build's `pr-<n>` if it has one, else `pr`       |
   | `pr-<d>`, `pr<d>`              | `pr-<d>`, or `pr` when `<d>` has more than 7 digits |
   | any other name in the alphabet | itself                                              |
   | anything else                  | refused with `channel-not-entitled`                 |

   An unknown well-formed name is never a free pass: it must be granted by name (R3-01, R3-13).

4. **Predicate**, `channelEntitled(granted, channel)`, where `granted` is the `channels`
   entitlement (absent means `["stable"]`, as `entitledChannels` already says):
   - `stable` is always granted;
   - otherwise `granted` must contain the name exactly;
   - two exceptions widen a grant: `staging` also covers `beta`, and `pr` also covers `pr-<n>`.

   Nothing else widens one. `dev` and manual names are granted only by their exact name, and a
   `beta` grant never covers a manual channel named `staging`. Grants are matched as stored and
   are never rewritten.

5. **Gate order is unchanged.** The server checks, in order:
   1. the dev bypass: `allowDevBuilds ?? granted includes "dev"`;
   2. the version window;
   3. a malformed header, which is refused;
   4. every channel in {build-implied, header} other than `stable`, each against rule 4.
6. **Release selectors keep their grammar:** `latest`, `stable`, `beta`, `pr-<1–7 digits>`, a
   manual name, or a pinned `X.Y.Z`. `staging` resolves as `beta`, and it is looked up **after**
   the manual names, so a declared manual `staging` channel wins.

Other edits in the contract:

- §5, the "Build gate placement" bullet, points to §5.1.
- §9: the counters are unchanged, and gate-matrix v2 retired one carried row (the pre-R3-01 dev
  bypass). The sentence "nothing it pinned was dropped" is corrected to say so.
- §10 gains the class "channel vocabulary and aliases (§5.1)", covered by gate-matrix.

### 2.4 `PROTOCOL_VERSION`, stated against `AGENTS.md` rule 2

Rule 2 bumps `PROTOCOL_VERSION` for a wire change. This change reaches the wire only through two
things:

- the values the unsigned `X-PKey-Channel` header may carry;
- the value SDKs send by default for `0.0.0-staging*` and `0.0.0-beta*` builds.

No signed document, `typ`, claim, envelope, cache record or encoding changes, and the device row
stores no channel (`core/devices.ts:671-687`). So **`PROTOCOL_VERSION` stays 3**, and every other
counter stays too.

A throwaway differential compared today's `checkBuildGate` with an implementation of §2.1 over
8 versions × 16 headers × 9 grant sets × 2 compat floors (`0.0.0` and `0.0.0-0`). 132 of the
2,304 decisions change, every one between `ok` and `channel-not-entitled`: 114 wider, 18 tighter.
A second run compared today's `channelAllowed` with the new selector and predicate (9 selectors ×
7 grant sets): 3 of 63 change, two wider and one tighter.

- **Wider:**
  - `beta`, `latest`, manual names and per-PR grants such as `pr-42` now work at the gate;
  - a legacy `staging` grant covers `beta`, and so, under `entitled`, the beta feed;
  - a `beta` grant covers `staging` headers, `0.0.0-staging*` builds and the `staging` feed.
- **Tighter, in two cases:**
  - a `0.0.0-beta*` build now implies `beta`; before, it was `stable`. All 18 tighter gate
    decisions are this case. A product reaches it only with a compat floor below `0.0.0`
    (`compat_min` is `NOT NULL DEFAULT '0.0.0'`, `migrations/0001_init.sql:17`, and the manifest
    requires semver), because every other product refuses `0.0.0-*` builds as `version-too-old`
    first; djdl's floor is `0.0.0`. No SDK emits a `0.0.0-beta*` version on its own. A browser
    sends only `X-PKey-Version`, so on identity's `/session` the version alone decides;
  - under `entitled`, a literal `manual` grant no longer covers every manual channel. No picker
    offers that grant, and no document describes it.

## 7. Rollout

**Order:**

1. One implementation PR, committed in wave order: contract, catalog, corpus, SDKs, then console
   and docs.
2. **Deploy the Worker to production before any SDK is published.** This is a human step: a `v*`
   tag runs `deploy.yml`. No staging environment is live (`docs/DEPLOYMENT.md:3-6`).
   - An old Worker refuses `beta`, so a new SDK's `0.0.0-staging*` or `0.0.0-beta*` build would
     get `channel_not_allowed` from it. Only products with a compat floor below `0.0.0` are
     exposed; every other product already refuses those builds as `version-too-old` (§2.4).
   - As a stopgap, a host can pass `channel: "staging"`.
3. Publish the SDKs, again as human steps: the Changesets "Version Packages" PR for npm (GitHub
   Packages), a `python-v*` tag for PyPI, and a `swift-v*` tag for SwiftPM.
4. djdl's owner adds `beta` to the `channels` enum in the `.pkey/schema` of `vladzaharia/djdl`.
   This blocks nothing: the licence and tier pickers can already grant `beta`.

**Effects on clients and Workers already deployed:**

- **Nothing is published yet** (every package is `0.0.0`, `contribute/releasing.md:13`). "Old
  clients" means apps built from this repository, such as djdl's, and they keep working (§2.4).
- **Documents, ETags and cache v3 records** are untouched. A client whose cache holds a
  `blocked: channel-not-entitled` hint from the old Worker (for example a `beta` header) clears it
  on its next document fetch that the new Worker answers 200.
- **Grants** need no migration. `staging` grants stay valid, and the console labels them.
- **`public` products:** `/<p>/update/staging/…` stops returning 404. Only 200s are edge-cached
  (`release/gateway.ts:249`), so no stale entry exists.
- **`entitled` products:** licences that hold `staging` gain the beta feed. This is intended:
  djdl labels that grant "Pre-release builds". A literal `manual` grant loses the manual feeds
  (§2.4).
- **No feature flag.** Rolling back is a redeploy of the previous Worker tag, and it is safe only
  until the new SDKs ship. After that, a rollback refuses their beta builds again.

**Follow-ups:**

- make both manifest warnings errors, and tighten the schema patterns;
- validate channel names in the admin licence and tier API, which accepts any string today;
- drop `staging` from `{{channels}}`;
- if a product needs it, let an aliased request fall back to the other spelling's asset suffix
  (D8), and let the no-channel asset preference skip the product's manual channel tokens too;
- remove the aliases, which is a wire removal: plan mode, wire v4 at the earliest.

## 8. Risks and decisions (resolved as recommended unless the lead overrides)

- **D1 `PROTOCOL_VERSION`:** no bump (§2.4).
- **D2 The SDK header for `0.0.0-staging*`:** send `beta`. The Worker ships first and accepts
  both.
- **D3 Swift `enum Channel`:** add `.beta` and deprecate `.staging`.
  - Exhaustive `switch`es in adopters' code need a `.beta` case. Nothing is published, so the
    cost is at its lowest now.
  - A `String`-backed struct would break more call sites for no gain, because
    `CoreOptions.channel` is already a `String`.
- **D4 Channel names in manifests:** two warnings now, errors later (§3).
- **D5 `gateMatrixVersion`:** stays 2. The row shape is unchanged, the runners iterate rows
  generically, and a bump would churn every runner's version assertion.
- **D6 Retire the carried dev row, and absorb P1b-05 Part C into P0-04.** Part C is the rewritten
  ports, rows 16–18 and the Worker oracle. This overrides the brief's "Out" list, for three
  reasons:
  - P1b-05 may not change corpus rows, and P0-04's new rows fail today's ports anyway;
  - P1-03 depends on P0-04 but not on P1b-05, and must port the server gate, so the stale row
    would stop it;
  - it means one corpus regeneration instead of two.
- **D7 PR identity at the gate is `pr-<n>`.** The literal `pr` header is narrowed to the build's
  number, so per-PR grants behave as they do in Release. `channelForVersion` keeps returning `pr`,
  and SDKs keep sending it.
- **D8 The `staging` alias keeps the requested spelling** for the asset suffix, the enclosure, the
  title and the cache key, so existing `-staging-` assets still match a `staging` request, and a
  `beta` request matches `-beta-` assets. The entitled check uses the canonical `beta`, and
  P0-02's floors already key by kind (§6). A cross-spelling asset fallback is a follow-up (§7).
- **D9 Grants are never rewritten.** There is no D1 migration.
- **D10 The console reads manual channels from the existing Release admin API.** No route is
  added.
- **D11 Declined: P1b-07's `entitledChannels` corpus case.** It pins an accessor, not a gate
  decision; a later corpus plan can add it.
- **D12 `dev` is not an alias.** Report §11 decision 5 said to map `staging` and `dev` as
  aliases; the brief already amended `dev` to a gate pseudo-channel. Mapping `dev` onto `beta` or
  `stable` would let a `beta` grant, or no grant at all, switch on the bypass that R3-01 made
  opt-in. So `dev` stays a grant of its own, and Release has no `dev` channel (§3 warns on a
  manual one).
- **Residual risks:**
  - the two tightenings (§2.4);
  - in a product with a manual `staging` channel, the gate still reads a `staging` header as
    `beta`. That can only relax a check the client declared about itself, and the build-implied
    check still applies;
  - licence and tier channel columns accept any string, so a non-canonical grant is dead. The
    console no longer offers one, and the follow-up validates it.
