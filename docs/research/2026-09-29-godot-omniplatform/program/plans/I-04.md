## 1. Summary

- **Phase 1 adds four device-facing routes.** `POST /<p>/identity/email/start` and
  `POST /<p>/identity/email/verify` (the in-app email code), and `GET` and `DELETE
/<p>/identity/user` (who am I, and in-app deletion). `verify` answers the **device-code flow
  state** that SDKs already parse (`ready` / `confirm`), so P1-07's confirm-and-attach works
  for email as it does for device code.
- **Discovery grows, additively.** The Identity fragment gains `methods[]` and the four new
  endpoint URLs. SDKs detect the features from it, and old SDKs ignore both.
- **Nine new wire error codes**, each registered in `conformance/parity/errors.json` by the work
  package whose Worker source first emits it (the constants gate refuses an un-emitted code, §2.5).
- **A product-scoped principal.** The tables `identity_users`, `identity_links` and
  `identity_sessions` are added, with `licenses.user_id` and `devices.user_id`. `licenses.sub` is
  backfilled into links and kept, so the migration is reversible (§6.1). `.pkey/product` gains an
  `identity` block (§3).
- **Order:** contract (this plan) → `errors.json` → Worker routes → transcripts → the six SDKs
  (Node, React, Python, Swift, Godot, Kotlin). Nothing in `conformance/corpus/` changes.

`docs/security/WIRE-CONTRACT-V4.md`, which holds:

- 12.1 the discovery fragment;
- 12.2 the email-code flow;
- 12.3 the account routes;
- 12.4 the error table;
- 12.5 the compatibility rules;
- 12.6 the reservations for phases 2 and 3.

I-08 also adds a §8 registry row for `flowId` and the link kinds, and a §9 sentence saying that

**`shared-protocol`.** I-08 adds a new subpath `@polaris-key/protocol/identity`
(`packages/shared-protocol/src/identity.ts`, a `package.json` `exports` entry, and the pinned
layout in `test/exports.test.ts`). It holds the first identity types: `IdentityMethodKind`,
`IdentityMethod`, `IdentityDiscovery`, `EmailStartRequest`, `EmailStartResponse`,
`EmailVerifyRequest`, `AuthFlowState` (the full union, also used for the device-code poll),
`IdentityUserView`, plus `EMAIL_CODE_LENGTH = 6` and `FLOW_ID_PATTERN = ^[A-Za-z0-9_-]{22,64}$`.
**`shared-jws` and `client-core` do not change.** Identity flows live in each SDK's identity
client, not in the verify core.

### 2.2 Discovery fragment (V4 §12.1)

```jsonc
"identity": {
  "enabled": true, "configured": true,
  "endpoints": { /* today's keys, minus authPoll (I-01) */,
    "emailStart": ".../identity/email/start", "emailVerify": ".../identity/email/verify",
    "user": ".../identity/user" },
  "methods": [ { "id": "email", "kind": "email", "inApp": true },
               { "id": "default", "kind": "platform" } ]
}
```

- `methods` lists only the product's **enabled** methods, in manifest order. Each entry has
  `id`, `kind` and nothing secret. `inApp` appears on `kind: email` only.
- `configured` becomes "at least one method is usable".
- `emailStart` and `emailVerify` are present only when an email method is enabled. `user` is
  always present.
- An SDK offers in-app email only when **both** `methods` holds `kind: email` with
  `inApp: true` **and** `endpoints.emailStart` is present. In every other case it falls back to
  the hosted page.
- An unknown `kind` is ignored, so I-12 and I-20 can add kinds without an SDK release.

### 2.3 Email-code flow (V4 §12.2)

Both routes are JSON and `cache-control: no-store`. They require `Authorization: Bearer pkeyt_…`
(a live device token) and send the `X-PKey-*` metadata headers. They answer CORS for the
product's `web.origins`, as `auth/device/start` does. Errors use the **nested `WireError`**
shape (§8 Q2).

**`POST /<p>/identity/email/start`**

- Request: `{ "email": string ≤ 254, "method"?: string, "deviceName"?: string }`.
  - `method` defaults to the product's single email method.
  - `deviceName` is trimmed to 120 characters and shown in the email.
- `200`: `{ "flowId", "expiresIn": 600, "codeLength": 6, "resendAfter": 60 }`.
- **The answer is identical** for a known email, an unknown one, a suppressed one, a locked-out
  recipient and a recipient over its per-recipient limit. In the last three cases nothing is
  sent.
- A new `start` for the same device, recipient and method kills the previous flow.
- `flowId` is opaque. It is bound to (product, method id, device id of the bearer) in I-02's
  single-use store.

**`POST /<p>/identity/email/verify`**

- Request: `{ "flowId", "code"?: "NNNNNN", "confirmIdentity"?: true, "attachLicense"?: boolean }`.
- The first call carries `code`.
  - With `confirmIdentity: true`, the code is consumed and the flow moves to `verified`. The
    answer is `{status:"confirm", identity, attachable}` and nothing is minted.
  - The next call carries `flowId` and `attachLicense` with no code. It completes exactly as the
    device-code poll does (P1-07 semantics, unchanged).
  - Without `confirmIdentity`, the first call completes the flow at once.
- `200` is `AuthFlowState`: `{status:"ready", token, schemaVersion, identity:{name?, email},
attached?}` or `confirm`.
  - The bearer must belong to the device that started the flow. `token` is that device's new
    token, bound to the user's licence. On an Identity-only product it is bound to the user with
    no licence.
  - With License on, no licence for the user and no auto-issue policy, the answer is `403
not_entitled`.
- **Safety defaults** (I-02's constants, not reopened): a code is 6 digits and lives 10 minutes.
  It dies after 5 wrong attempts. 10 wrong attempts across codes in an hour lock the recipient
  out of new codes for 15 minutes, and the lockout answers like success. Send limits are 5 an
  hour and 20 a day per recipient (hashed), 3 starts an hour per device, per-IP and per-network
  limits, and a per-product daily cap.

### 2.4 Account routes (V4 §12.3)

- **`GET /<p>/identity/user`** (bearer) answers `200 { "user": IdentityUserView | null }`, where
  `IdentityUserView = { id, displayName|null, email|null, createdAt, links: [{ id, method,
kind, email|null, createdAt }] }`. It is `null` when the device has no user. It never carries
  subjects, hashes or other products' data.
- **`DELETE /<p>/identity/user`** (bearer) starts I-06's soft delete (14 days, then hard delete
  with personal columns scrubbed). It also deauthorizes every device of the user and answers
  `202 { "deleteAfter": <epoch> }`.
  - It needs a sign-in **on this device** within the last 10 minutes; otherwise it answers `403
reauth_required` and the SDK runs sign-in again. This meets App Store 5.1.1(v).
- **`signOut()` needs no new route.** It is the existing self `DELETE /<p>/devices/<id>` plus
  clearing the local token.

### 2.5 Error codes (V4 §12.4; `errors.json`, `kind: wire`, `service: identity`)

| Code                  | HTTP | Where                                                                               | Registered by |
| --------------------- | ---- | ----------------------------------------------------------------------------------- | ------------- |
| `code_invalid`        | 400  | `email/verify`: wrong code, flow still alive                                        | I-08          |
| `flow_expired`        | 410  | `email/verify`: unknown, expired, used or dead flow, or another device's            | I-08          |
| `email_unavailable`   | 503  | `email/start`: sender throttled, quota or product cap spent (offer others)          | I-08          |
| `reauth_required`     | 403  | `DELETE /identity/user` without a recent sign-in on this device                     | I-08          |
| `user_disabled`       | 403  | any sign-in completing for a disabled user                                          | I-06          |
| `link_conflict`       | 409  | linking an identity already attached to another user (Block)                        | I-06          |
| `last_link`           | 409  | unlinking a user's only link (never orphan)                                         | I-06          |
| `license_owned`       | 409  | presenting the key of a licence that has an owner. It never moves by key            | I-06          |
| `license_email_bound` | 403  | claiming an email-carrying licence without that verified email (`claimByKey` false) | I-06          |

- **Reused codes:** `unauthorized`, `bad_request`, `rate_limited` (per-device and per-network
  limits only; per-recipient limits answer success), `attestation_required`, `not_entitled` and
  `not_found`.
- `auth_method_disabled` keeps its code, and its description widens to "this product's sign-in
  method, or its in-app start, is off".
- The device-code routes keep their LEGACY FLAT bodies, unchanged.
- **Client codes** (kebab-case) are named in I-11's plan.

### 2.6 What this pre-decides for later plans (V4 §12.6)

- **I-10 exchange:** `POST /<p>/identity/token`, JSON camelCase like device code (`{method,
subjectToken, subjectTokenType?}`), not OAuth form encoding. It answers `AuthFlowState`,
  including `confirm` and attach. `methods[]` entries gain an `exchange: true` flag.
- **I-13 native redirect:** `POST /<p>/identity/auth/token` (PKCE code redemption) answers
  `AuthFlowState`. The `/auth/poll` route is deleted there.
- **I-16 issuer:** the issuer is `https://key.plrs.im/<p>/identity`, with discovery at
  `/<p>/identity/.well-known/openid-configuration`. **The OP endpoints live under
  `/<p>/identity/oauth/*`**, so the exchange keeps `/identity/token` without a clash. The issuer
  uses RS256 on its own keyring and no device SDK consumes it.
- **I-22 link and unlink:** `POST /<p>/identity/user/links` (the body is an email flow or an
  exchange credential) and `DELETE /<p>/identity/user/links/<id>`, using the codes above.

**Clients already in the field.** v4 SDKs ignore unknown discovery members, so `methods` and the
new endpoints are invisible to them. Device code, activation and the documents are unchanged. A
new SDK talking to an old Worker finds no `methods` and reports in-app email unavailable
(`sign-in-unavailable`). It never guesses a URL.

### 3.1 Rules

| Code                                | Rule                                                                                               | Schema   | WP   |
| ----------------------------------- | -------------------------------------------------------------------------------------------------- | -------- | ---- |

| `invalid_identity_method_id`        | `id` matches `^[a-z][a-z0-9-]{0,31}$`                                                              | rejects  | I-08 |

| `invalid_identity_in_app`           | `inApp` is boolean, and only on `kind: email`                                                      | rejects  | I-08 |

**Legacy `oidc` block.** With no `identity.methods`, the `oidc` block reads as the single method
`{id: "default", kind: oidc.provider === "custom" ? "oidc" : "platform"}`. Every existing
product therefore keeps working with no manifest edit. I-05 persists methods in an
`identity_methods` table and keeps reading `oidc_config` as the fallback.

**Defaults:** `inApp: true`, `emailAutoLink: false`, `conflict: block`, `claimByKey: false`,
`promptAddEmail: true`. The reserved branding names (Polaris, Polaris Key, plrs, portal, console,
admin) are a check in the console's `branding_json` writer (I-08). They are not a manifest rule.

**Shipped copies.** `actions/publish/dist` inlines `@polaris-key/manifest`, so each manifest
change rebundles it (`bundle:action -- --check`). I-08 updates the `authoring-pkey-manifests`
skill.

**Safety defaults, encoded verbatim:**

- A licence carrying an email attaches only to a user with that verified email, never by key,
  unless the product sets `claimByKey: true`.
- A licence with an owner never moves by presenting its key (`license_owned`).
- Polaris runs no recovery desk. Beyond a user's remaining links, recovery is the developer's,
  through the audited console relink tool (step-up, reason, notice, 72-hour undo).
- Custom auth domains are deferred, and passkeys enrol on `key.plrs.im` only.

## 8. Risks and open questions (each needs the owner's decision)

S-16 is corrected here where the code disagrees: §2.1 (no V4 HTTP section), §2.3 (two
"activation responses" exist), §2.4 (account routes were missing), §6.1 (`devices.user_id`, the
backfill), §2.5 (codes land with their emitter), §2.6 (the token-path clash) and §6.2 (the
Turnstile CSP, and that the trust policy already exists).

1. **Q1: the shape of `verify`.** Use the device-code `AuthFlowState` (`ready` / `confirm`), or
   `ActivationResult` (`token, schemaVersion, device, license`)? **Recommend `AuthFlowState`**:
   it is one parser and it carries attach. The SDKs read the licence from the document anyway.
2. **Q2: the error body of the new routes.** **Recommend the nested `WireError`.** Every SDK
   already parses both shapes. Device code stays flat.
3. **Q3: in-app email needs a device token.** A `requires-license` product without auto-issue
   has none before sign-in, so it gets the hosted-page fallback (device code) only. Accept this
   for phase 1, or allow an attested, token-less start? **Recommend accepting it.**
4. **Q4: `DELETE /identity/user` in phase 1** (a sign-in within 10 minutes, a 14-day soft
   delete)? **Recommend yes, in I-08.** App Store 5.1.1(v) needs it once in-app sign-in ships.
5. **Q5: email normalisation.** Trim, NFC and lowercase the whole address, with no provider dot
   or plus folding. **Recommend yes.**
6. **Q6: the backfill.** Lazy plus a cron batch, keeping `sub` until after I-09. **Recommend
   yes.** Risk: a product that changed issuers has old subjects labelled with the current issuer.
   The batch logs them for operator review.
7. **Q7: the kill switch** stays off in production until the I-21 check passes. **Recommend
   yes.**
8. **Q8: who writes the D-14 replacement.** The brief says I-08. **Recommend I-06**, because it
   lands the model first.

- §2.3's limits rest on I-02's Durable Object. I-08 must not start before I-02 is merged.
- The Turnstile CSP is a new script origin on `key.plrs.im`. It is scoped to the hosted-page
  routes only.
