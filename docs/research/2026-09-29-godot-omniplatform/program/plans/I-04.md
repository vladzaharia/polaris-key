## 1. Summary

- **Key entry gains two refusals on Identity products**: `key_entry_limit` (403, `portalUrl`) and
  `license_owned` (403, `signInUrl`) on `POST /<p>/license/activate` and
  `POST /<p>/identity/session/license`, plus an optional `keyEntries: {used, limit}` member. Never on
  an enrolled device, never on a product with Identity off.
- **Four device routes and one browser route, Identity on only**: `POST /<p>/identity/attach`,
  `GET /<p>/identity/subject`, `POST /<p>/identity/signout`, `POST /<p>/identity/redirect/token`,
  and the browser entry `GET /<p>/identity/authorize` (S256 PKCE web redirect). The device-code
  poll's `ready` gains `subject`.
- **Discovery's identity fragment grows additively**: `account`, `keyEntryLimit` and six endpoint
  URLs. Old SDKs ignore them.
- **Ten new wire codes** (one reserved) in `conformance/parity/errors.json`, five parity rows,
  eight new transcripts and three re-recorded.
- **The data model** that I-05 migrates: `accounts`, `account_links`, pairwise subjects with
  aliases, `licenses.account_id`, `devices.subject`, and the Core accessors and hooks S-17 and F-21
  build on. Order: this plan → `errors.json` → Worker → transcripts → Node, React, Python, Swift,
  Godot, Kotlin and the four UI kits.

### 2.2 Key entry (§12.2; I-09)

A **key entry** is `POST /<p>/license/activate` (surface `app`), `POST
/<p>/identity/session/license` (surface `browser`) or a portal Activate License submission (surface
`portal`, I-11). **Enrolled** means a `devices` row with this `(product, device_id)`, this
`license_id` and `status = 'authorized'`. Order on the two device routes, Identity on:

1. existing rate limit, key and licence lookup (unchanged);
2. if the device is enrolled: proceed as today, never refuse, never count;
3. if `licenses.account_id IS NOT NULL` → `403 {"error":"license_owned","signInUrl":…}`, nothing
   counted (D24);
4. if the count of `license_key_entries` rows for the licence ≥ the limit →
   `403 {"error":"key_entry_limit","portalUrl":…,"keyEntries":{"used":n,"limit":n}}`;
5. `authorizeDevice` as today (`device_limit`, `fingerprint_required`, `hardware_mismatch`); on
   success insert one `license_key_entries` row and answer the activation response plus
   `"keyEntries": {"used", "limit"}`.

Refused and failed attempts never count; refresh, offline grace, documents, `license/enroll`,
store binding and sign-in-based activation never count. A licence with only a legacy `sub` and no
`account_id` is not owned (§8 Q6). Concurrent new devices at `limit − 1` may overshoot by the
number of racing requests; the limit is an on-ramp nudge, D24 is the security boundary (§8 Q5).

`portalUrl` = `<origin>/portal/activate?product=<slug>`; `signInUrl` =
`<origin>/portal/signin?product=<slug>` (§8 Q4). Both are built by the Worker from its own origin,
never carry the key, and are not auth failures: an SDK never wipes state or retries on either.

### 2.3 Attach, subject and sign-out (§12.3; I-09)

All take `Authorization: Bearer pkeyt_…` and `X-PKey-Device`, are `no-store`, and answer CORS for
the product's `web.origins` without credentials.

- **`POST /<p>/identity/attach`** `{ "confirm": boolean }` attaches the device's floating licence
  to the account signed in on the device (`devices.subject`), P1-07 style.
  - `confirm: false` → `200 { "status":"confirm", "license": {id, tierId, name|null} }`; no write.
  - `confirm: true` → `200` activation response (`token` rotated, `schemaVersion`, `device`,
    `license`) plus `"subject"` and `"attached": "claimed"`; already attached to this account →
    the same with no `attached`.
  - Errors: `401 unauthorized`; `403 account_required` (no sign-in on the device); `403
license_owned` (attached to another account; no `signInUrl`); `403 license_email_bound`
    (email-bound, no verified match, `claimByKey` false); `404 not_found` (no licence on the
    device, or Identity off).
- **`GET /<p>/identity/subject`** → `200 { "subject": "ps_…" | null }`.
- **`POST /<p>/identity/signout`** → `200 { "released": boolean }`. Runs Core's clearing hook for
  this device. `released: true` means the device was also deauthorized, which happens only when its
  licence belongs to the signed-out account and the device was bound by sign-in
  (`devices.bound_by = 'signin'`; §8 Q3). SDKs run Cloud Sync's flush-before-sign-out first
  (S-17 §5.4 rule 5).

### 2.4 Device-code passthrough (§12.4; I-08)

The routes are unchanged; the user-code page becomes the login card with the passthrough header,
browser-bound callback (R1-07) and explicit Continue. Poll members:

- `confirm` keeps `attachable` (it already exists, `oidc.ts:1866`; S-16 called it new).
- `ready` gains **`subject`**. `identity.name` and `identity.email` appear in `confirm` and
  `ready` only for claims the person consented to share with this product on "Continue to <App>"
  (D19; §8 Q2); otherwise `identity` is omitted.

### 2.5 Web redirect (§12.5; I-08)

- **`GET /<p>/identity/authorize`** `?redirect_uri&state&code_challenge&code_challenge_method=S256`.
  `redirect_uri`'s origin must equal a `web.origins` entry exactly and its path must be in
  `identity.redirectPaths` exactly; otherwise the card renders `400 redirect_uri_mismatch` and never
  redirects. Another method, a missing `state` (16–512 chars) or a malformed challenge → card `400
bad_request`. Success: card → Continue → `302 redirect_uri?code=…&state=…`. The code is single use
  (I-02's store), lives 60 s, is bound to `(product, redirect_uri, code_challenge)`.
- **`POST /<p>/identity/redirect/token`** (JSON) `{ code, code_verifier, redirect_uri }` with
  `X-PKey-Device` and metadata headers → `200` activation response plus `subject` (`license` is
  `null` on a licence-less device). Errors (nested): `400 invalid_grant` (unknown, used or expired
  code, verifier or `redirect_uri` mismatch), `403 not_entitled`, `429 rate_limited`. CORS for
  `web.origins` only, no credentials. No token or code ever travels in a fragment. This is S-17's
  web principal. **The path is S-16's `redirect/token`, not S-17's `web/token`** (correction); I-15
  reuses it for native redirect URIs.

### 2.6 Discovery (§12.6; I-08 and I-09)

Identity on: the fragment gains `"account": true`, `"keyEntryLimit": n`, and endpoints `attach`,
`subject`, `signout`, `authorize`, `redirectToken`, `accountPortal` (the portal product page, for
`openAccount()`). An SDK uses a feature only if its endpoint is present; it never builds a URL.

### 2.7 Clients and workers already deployed

- **Old SDKs** ignore the new members. They meet the refusals only on a _new_ install of an
  Identity product, never on an enrolled device. Node maps any 403 other than
  `fingerprint_required` to `device-limit` (`sdk-node/src/license/endpoints.ts:76-91`), so an old
  app shows "device limit reached": wrong copy, no state loss. I-10a and I-10b record each SDK's old
  behaviour; the platform setting in §7 keeps refusals off until they ship.
- **New SDKs on an old Worker** find no `account` member and report the features unavailable.
- **Existing installs** keep tokens, refresh, grace and documents unchanged (owner).

- `resolveSyncPrincipal(db, device)` = `resolveSubject(device.subject)`; never the licence owner.
  `overrideAccount` (U-03) adds the licence-owner line for Config only.
- **The binding.** `devices.subject` holds the pairwise subject, never the account id. Core's
  activation path sets it (with `bound_by = 'signin'`) when Identity's sign-in calls it; key entry
  never sets it; it is never signed. The KV token record mirrors it.
- **The clearing hook** `clearDeviceSubjects(db, env, scope, reason)`: sign-out, sign out
  everywhere, account disable, account deletion, per-product removal, relink. **Plain licence detach
  does not clear it** (S-17 §5.8 item 2; corrects S-16 §5.1's table).
- **The revocation hook** `onLicenseOwnershipEnded(db, env, {product, licenseId, accountId,
reason: "detached" | "relinked" | "account_deleted"})`: F-21 revokes licence-bound registry tokens
  minted by that account; I-11 owns it; whichever lands second extends it.
- **The registry** `registerSubjectStore(name, {merge, delete, export})`: merge re-keys
  `(product, from, to)`; per-product removal and account deletion call every `delete` before the
  subject row goes. A guard test fails if a subject-keyed table has no registration.

The global account id never leaves the Worker's Identity and Core code (S-16 §5.1 reworded): it is
in no developer-facing API, export, event, token or SDK response.

## 8. Risks and open questions (owner decisions)

1. **Q1 Several accounts linked to one licence** (`portal_license_links` allows it; one
   `account_id` cannot). **Recommend** the owner by source `oidc` > `email` > `admin` >
   `license-key`, then earliest; the others lose the link, get an email and appear in an operator
   report; the revocation hook runs for them.
2. **Q2 Name and email in the device-code poll.** **Recommend** only consented claims (D19, §5.4
   item 12); the UI kits show "Signed in with your Polaris Key account" otherwise.
3. **Q3 Sign-out releases a sign-in-bound device** (`devices.bound_by`). **Recommend yes**, Steam
   style; key- and enrol-bound devices only lose the binding.
4. **Q4 `signInUrl` target.** A bare login-card URL cannot sign a TV in. **Recommend**
   `/portal/signin?product=<slug>`, which explains "choose Sign in on your device" and offers the
   device-code entry; SDKs prefer starting device code themselves.
5. **Q5 Race overshoot** on the limit. **Recommend accepting it** (bounded by the 30/min/IP limit).
6. **Q6 Legacy `sub`-only licences** (custom IdP products) count as floating until I-17 or layer 2.
   **Recommend yes.**
7. **Q7 Default `keyEntryLimit`** 10, range 1–100, no unlimited value with Identity on.
   **Recommend yes.**
8. **Q8 `subject.merged` and `subject.deleted` delivery.** No developer webhook channel exists in
   the Worker. **Recommend** a pull feed now (`subject_events`, the Users page and an admin API
   cursor) and push webhooks later.

**Risks.** I-08 needs I-02 and the R1-07 callback binding before device-code passthrough ships.
The migration touches every portal account and OIDC licence (I-05 rehearsal). The plan is longer
than two pages because one contract serves eight packages; it is not split because I-08 and I-09
execute disjoint sections.
