# U-22.5 plan: the records binding of `cloudSync.saves` (machine change, all ports)

**This is a plan. It contains documents only, no code.** Written 2026-10-31 by the U-22.5 / U-22.11
builder, which stopped at a client-core boundary. It awaits the lead's approval.

## 1. Why this exists

`SavesClient` (client-core `sync/saves.ts`, U-22.3) is finished and tested against a fake. It takes a
`SaveRecords` port, and the plan says "the cloud-sync machine binds it (U-22.5)". The machine cannot be
bound as it stands. U-22.5 and U-22.11 list no client-core file, so this is a change nobody approved.

What the machine (`client-core/src/cloud-sync.ts`, Python `cloud_sync/machine.py`, and the Swift, Kotlin and
Godot ports) lacks:

| #   | Need of `SaveRecords`                                                                     | Machine today                                                                                                                                                                                                                                                                  |
| --- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R1  | `get`/`list` return the record's `file` pointer (U-10 A1: `{version,size,sha256,format}`) | A pull row is stored as `{value, version}`; `file` is dropped. A file-only row (no `value`, no `ct`, V5 §13.4) is stored with `value: null`, and in E2E mode a row with no `ct` at or above `encryptionSince` is judged plaintext and marked `bad`, so it reads as unreadable. |
| R2  | `set(id, value, baseVersion)` at the version `finalize` answered (D-3)                    | `put` enqueues with `baseVersion = p.records[rk]?.version ?? "*"`. After `finalize` the server's version is one ahead of the machine's row, so the set loses its own CAS. No pull runs in between.                                                                             |
| R3  | the outcome of that one `set`: version, conflict with the server copy, rejection          | `result()` takes the server copy on a conflict (`copyRow`) and emits nothing the caller can read. `put` returns `{ok:true}` at once. A `rejected` is a `SyncEvent` by `mutationId`, which `put` does not return.                                                               |
| R4  | `list()` of a collection                                                                  | no listing API (`record(collection, id)` only).                                                                                                                                                                                                                                |
| R5  | `delete(id, baseVersion)`                                                                 | `put` only; a tombstone push exists on the wire, not as a machine call.                                                                                                                                                                                                        |
| R6  | `wireId(id)` (blinded in E2E)                                                             | the host codec blinds ids when it seals a push, but `SaveRecords` needs the wire id for the file routes before any push.                                                                                                                                                       |

Working around R2/R3 in the SDK (pull after `finalize`, then compare values) is racy: a conflict looks like
success whenever the values match. Working around them by pushing outside the machine needs the machine's
`clientId` and mutation ids. Neither is acceptable.

## 2. Proposal (the smallest correct change)

Additive, behind new calls; no existing call changes behaviour.

1. **Rows keep `file`.** `Versioned.file?: {version,size,sha256,format}` is set from a change's `file`.
   A change with a `file` and neither `value` nor `ct` is a good row with `value: null` (not `bad`).
   `journal()` and the persisted journal carry `file` only when present, so every existing
   `sync-scenarios.json` case stays byte-identical.
2. **`records(collection)`**: `[{id, value, version, file}]`, the effective rows (R4).
3. **`putAt(collection, id, value, baseVersion)`** (R2): enqueues one `set` at that exact version, never
   coalesced with a queued edit and never rebased. Returns `{ok:true, mutationId}`.
   **`removeAt(collection, id, baseVersion)`** is the delete (R5).
4. **`onOutcome(fn)`** (R3): `fn({mutationId, status:"ok", version})`, `({mutationId, status:"conflict",
server:{value,version,file}})` or `({mutationId, status:"rejected", code})`, called once per
   `putAt`/`removeAt` when its result arrives (or on sign-out, as `{status:"dropped"}`). The conflict is
   still applied to the row as today; the callback is the only addition.
5. **`wireId(collection, id)`** on the host codec port (R6): `blind("record", collection, id)` in E2E,
   the id in server mode.

`sync.records` stays `planned` (D-2); `collection()` stays reserved.

## 3. Corpus and ports

This is a machine contract, so it is plan-mode and an all-languages event.

- **Corpus.** Append-only rows to `sync-scenarios.json` (a new family `fileRecordCases`, regenerated with
  `pnpm gen corpus`, Godot mirror included): a pull row with `file` (server and E2E), a file-only row, a
  `putAt` at a given version that is ok, one that conflicts, one rejected, `removeAt`, and a sign-out with
  one pending. The reference machine is client-core's; every port replays the file.
- **Ports.** Node and Python in U-22.5 and U-22.11. Swift, Kotlin and Godot in their `.x5` slices (the
  `SaveRecords` binding there is the same code); until then their runners skip the new family by name.
- **Gates.** `pnpm gen corpus --check`, `sync-scenarios` replay in each runner, `pnpm gen parity --check`.

## 4. What U-22.5 and U-22.11 then do (already scoped by the slice plan)

- **Node** (`sdk-node/src/cloudSync/`): a `MachineRecords` adapter (the `SaveRecords` over §2), an engine
  assembly (`NodeFileTransport`, `FileJournal`, `FileChunkCache`, `TransferEngine` with
  `maxRetryAfterSeconds: 3600`, and `SYNC_CHUNK_MAX_STORED_BYTES` imported from protocol), a `SavesApi`
  (`list`, `read`, `write`, `delete`, `revisions`, `resolve`; `transfers()`; `pause`/`resume`/`cancel`) that
  emits `transferProgress`/`transferDone`/`transferFailed` on `client.events`, the journal and cache purged
  with the person (`FileJournal.clear`, the cache directory) in the same `finally` as the ring, and the
  `api.json` Node spellings.
- **Python** (`cloud_sync/`): `saves.py` (a port of `saves.ts`), the same assembly with the engine's
  `max_retry_after_seconds=3600`, synchronous `client.cloud_sync.saves` and `transfers()`, the purge, and
  the `api.json` Python spellings.
- **Flips.** `sync.saves` in both manifests. Then `cloudsync-files-single` (the one transcript tagged
  `sync.saves`) starts to run in both replayers.

## 5. Estimate

Machine change and corpus: about 90 minutes in client-core, 60 in Python, and a corpus slice of 45. Node API
60, Python saves port 90. Order: corpus and client-core, then Node and Python in parallel.

## 6. Done already (commits on `wp/U-22.5`)

- Node and Python file transports with chunk calls; both replayers serve and assert raw bytes
  (`bodyBase64`) and run `cloudSyncFile` and `cloudSyncChunk`; `sync.files` and `sync.files.delta` flipped
  in both manifests.
- Not done: `sync.saves`, the saves API, `transfers()`, the transfer events and the api spellings. They
  wait on this plan.
