The build attempt on `wp/ST-19-manifest-cleanup` stopped before it changed any code. This plan
rebuilds the duplicate list from the validator, the schemas, `pkey init`, the settings registry,
and the three real manifests: `djdl`, `storyrime` and the monorepo's root `.pkey/`.

## 1. Summary

- A new table, `DEPRECATED_SPELLINGS` (`packages/shared-manifest/src/spellings.ts`), lists every
  duplicate spelling the validator accepts. Each row gives the canonical path and which spelling
  wins today. The validator reads the table to emit two new **warning** codes:
  `deprecated_spelling` (an old spelling is used) and `conflicting_spelling` (both spellings are
  present; the message names the value that is used).
- The JSON schemas mark every old spelling `"deprecated": true`, with a description that names the
  replacement. They still accept it, so every new mutation entry is `schema: "accepts"`.
- The settings registry's `manifest.path` values move to the canonical spellings. A parity test
  makes them stay there. ST-06's coverage test learns the `product:`, `licensing:` and `release:`
  wrappers. The duplicate spellings leave `PENDING`, and one generated `NOT_A_SETTING` row now
  covers them.
- `pkey init`, the monorepo's `.pkey/schema.yaml`, the docs and the `authoring-pkey-manifests`
  skill all switch to the canonical spellings. `pkey validate` warns on `djdl`. It prints nothing
  for the monorepo's `.pkey/`.
- Refusing the old spellings is a later decision (the brief's "Out"). §7 describes how that will
  work.

### 3.2 Validator rules (`V/` and the new `spellings.ts`)

- `spellings.ts` exports `DEPRECATED_SPELLINGS: readonly DeprecatedSpelling[]` with these fields:
  - `doc`: `"product" | "schema" | "release" | "distribution"`;
  - `pointer`: the old spelling's JSON pointer. A `*` segment stands for an array index;
  - `canonical`: in registry form, for example `product:licensing.tiers`;
  - `wins`: `"canonical" | "deprecated"`;
  - `code`: `deprecated_spelling`, or for row 18 the existing `listing_url_field_deprecated`;
  - `conflictCode`: `conflicting_spelling`, or for rows 16 and 18 the existing error codes.

  `index.ts` re-exports the table.

- One pass, `checkSpellings(documents, warnings)`, runs at the start of `validateDocuments`. It
  emits one warning per old spelling present, at that spelling's pointer, with a message such as
  `defaultDeviceLimit is a deprecated spelling; write licensing.defaultDeviceLimit.`. When both
  spellings are present, it emits `conflicting_spelling` at the old pointer, naming the spelling
  whose value is used, for example `…both are set; the root value (5) is used.`. Rows 16 and 18
  keep their existing checks and are skipped by the pass.
- `ok` is unchanged, because warnings never fail validation. The parsers (`parseManifest`,
  `parseIngestDocuments`) are not touched.

### 3.3 Mutation table (`test/schema-parity.test.ts`)

- The source sweep (`["index.ts", "distribution.ts"]`) adds `spellings.ts`.
- `deprecated_spelling` gets one hand-written entry for each of rows 1–15 and 17. Each entry is
  `schema: "accepts"` and its `file` is the row's document. `conflicting_spelling` gets one entry
  for each document it can occur in: product, schema and release.
- A table-driven test checks every row of `DEPRECATED_SPELLINGS`. For each row it asserts:
  - the row's code is emitted at the row's pointer;
  - the conflict code is emitted when the row's canonical spelling is also present;
  - the parsed value equals the `wins` side;
  - the row has a mutation entry.
- `base()` moves to the canonical spellings: `licensing.defaultDeviceLimit` and
  `licensing.defaultMaxOfflineDays` instead of the wrapper. A new assertion checks that `base()`
  emits no `deprecated_spelling`.
- The `products/djdl/*` fixture stays as it is, because it mirrors the real repo. Its test now
  asserts the exact warning set as well as `errors: []`: rows 1–6 and 11.

### 3.4 JSON schemas (`schemas/v1/*.schema.json`)

- Each old-spelling property gets `"deprecated": true` (a JSON Schema 2020-12 annotation) and a
  description that starts with "Deprecated: write …". Old spellings that live inside the release
  body or a tier are marked where they are defined (`releaseBody`, tier items).
- No property is removed, and no `oneOf` changes. The product schema's `anyOf` still allows the
  flat form. Editors show old spellings struck through.
- `schema.schema.json`'s `catalog` description changes from "Alias of entries" to
  "Deprecated: write entries".

## 7. Rollout

1. **ST-19 (this plan): accept both spellings and warn.** Old Workers, CLIs and Actions accept
   every spelling, and so do new ones. Only the new CLI and editors show the warnings. Deploy
   order does not matter, and no manifest has to change on the day of the deploy.
2. **Migrate.** After ST-19 merges, djdl and storyrime move to the canonical spellings (§5). With
   Q6, ST-17's dry run shows warnings for every linked product, which is the evidence that no
   product still uses an old spelling.
3. **Refuse (a later package, not registered).** This follows the `reservedNames` precedent
   (LX-05):
   - add `ValidationOptions.deprecatedSpellings: "warn" | "error"`;
   - back it with a platform setting that defaults to `warn`;
   - the owner flips it once step 2 shows no warnings;
   - in error mode, a resync that is refused leaves the product at its last good apply. Devices
     are unaffected.
   - Deleting the alias reads from the parsers comes after error mode has been stable for one
     release. A `pkey.dev/v2` `apiVersion` is not needed.

## 8. Risks and decisions for the human

- **Q1. Split out the non-spelling `PENDING` entries? Recommended: yes, as a new ST-19b.**
  - ST-06 gave ST-19 32 entries. About 21 of them are real settings with no registry entry yet:
    `release.github`, `binaryName`, `channelWorkflow`, `betaBranch`, `summaryMarker`,
    `manualChannels`, `deliverables`, `publishing.trustedPublisher` (with `ci_publishers`),
    `channelPolicy`, `keys`, `compatMax`, `core.registration`, `core.secrets`,
    `identity.provisioning` and `distribution.transports`.
  - Registering them with readers, docs, capability and ownership does not fit 0.5–0.7 weeks
    next to this plan, and they need no plan mode.
  - ST-19b would be a `pkey-implementer` package of 0.4–0.6 weeks, depending on ST-19. ST-25
    would gain ST-19b as a dependency.
  - Alternative: keep everything in ST-19 and resize it to 1.0–1.3 weeks.
- **Q2. Canonical layout? Recommended: wrapped.** That means `product:` for identity and compat,
  `licensing:` for licence defaults, tiers and profiles, and `release:` in `.pkey/release`. This
  is what `pkey init` writes, what the docs and the monorepo show, and what S-18 calls canonical.
  - Cost: djdl gets 9 warnings and storyrime gets 3.
  - Alternative: canonical flat, which matches djdl and today's registry paths. That would make
    every scaffolded product and the docs "deprecated" instead.
  - **Q2b. Tier profile reference: recommended `profileId`.** That means changing the scaffold.
- **Q3. Keep today's precedence when both spellings are present? Recommended: yes.** In rows 3–6
  and 15 the old spelling wins today. Flipping that would change parsed values for a manifest
  that sets both, so ST-19 only warns (`conflicting_spelling`, naming the value used). Step 3 of
  §7 removes the ambiguity.
- **Q4. Warn on legacy `modules:` names (row 12)? Recommended: yes, with the same code.** The
  docs promised that old manifests "keep validating unchanged", and they still do. `pkey init
--modules licensing` keeps working and already writes slugs. No real product uses the legacy
  names today.
- **Q5. Two files for one document (`product.json` and `product.yaml`)? Recommended: a CLI-only
  warning in `loadManifest`.** The Worker reads the first match and would need extra GitHub reads
  to notice. Because this is not a validator code, rule 9 does not apply to it.
- **Q6. Surface warnings at link and resync? Recommended: not in ST-19.** Add it to ST-17's
  brief: the dry-run plan gains `warnings[]`, and the console's Resync confirm shows them. ST-18's
  brief also changes: "Promote to repo" must write the registry's canonical paths.
- **Risk: an editor treats `deprecated: true` as an error.** VS Code and the yaml language
  server show strikethrough only, and Ajv ignores the keyword.
