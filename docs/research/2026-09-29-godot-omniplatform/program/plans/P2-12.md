## 1. Summary

- The legacy appcast, `/update/version` and `/release/dl` (with `?checksum=sha256`) resolve through
  `resolve.ts` from the release store for every linked product. They render from store rows in
  GitHub's shape, as GitHub last listed them, so a product without records gets the same bytes as
  today.
- GitHub is read only at ingest. The release webhook keeps the store current. A 15-minute
  freshness pass covers what GitHub sends no event for, such as assets added or replaced after
  publication, and covers missed or failed deliveries.
- Before the switch, a P0-49 job compares the old and new output for every product in
  production. The switch ships only when no unexplained difference remains and djdl's beta
  builds resolve without the workflow. P2-12b deletes the old path.
- `release.channelWorkflow` and `release.betaBranch` are removed at the switch. From then on a
  manifest that sets them fails validation with an error naming the replacement. Once P2-12b
  lands, the installation token stops asking for `actions` and `pull_requests`.
- No wire, corpus, transcript, SDK or migration change.

## 2. Contract

There is no change to WIRE-CONTRACT-V4. §5.1 rule 6 already says that resolution, floors and the
`entitled` check go by the canonical channel. It also says the requested spelling is kept for the
asset suffix, the enclosure, the feed title and the edge-cache key. The legacy renderer keeps all
of these, because `classifyChannel` (`channels.ts:58-84`) stays the selector grammar. Rule 4's
predicate (`core/channels.ts:102-112`) is not touched. **"dev includes beta" stays a write-time
rule in the editors** (LX-33, P2-08), and grants are matched as stored.

**Clients already in the field:**

- **Sparkle installs** keep every `SUFeedURL` form: the four alias routes (`router.ts:31`,
  `:207-213`, `:243-245`), `?arch=`, and the unparameterised feed's default of arm64. The alias
  routes fall under rule 6's exception for paths that installed native binaries call, and P2-12
  does not change them
  (`services/update/feed.ts:50`). They get identical bytes, apart from the classes approved in
  §6.5.
- **SDK `update.check()`** calls `/update/version` without `?platform=` (for example
  `sdk-node/src/update/client.ts:729-733`). It gets the same `{version, tag, url}` body and the
  same cache header. `tag` is always a GitHub tag and `url` is always GitHub's `html_url`, because
  the legacy view offers no tagless or GitHub-less row (D5). No SDK reads anything new.

removes them (D7). There is no deprecation step and no warning first.

### 6.2 Changes to `resolve.ts`

- `DeliverableState` gains `listed`, `absent` and `floors`, read only for `app`:
  - `listed`: the rows whose `metadata_json.tag` is set;
  - `absent`: `SELECT subject_id FROM release_health WHERE product = ? AND subject_kind = 'release' AND status = 'degraded' AND json_extract(details_json, '$.absentUpstream') = 1`;
  - `floors`: `SELECT channel, version, release_id FROM release_channel_floors WHERE product = ?`.
- `ResolveInput` gains `hidden?` and `floor?`. `channelMembers` drops hidden rows **before**
  `byId` (`:339`), so a hidden promote pointer is not added back at `:383`. `resolveCandidates`
  applies the floor to the members before the pointer joins them.
- `resolveInState(state, { view })`:
  - `"legacy"`: `hidden` is every row not in `listed`, plus `absent`; `floor` is the canonical
    channel's effective floor (D5).
  - `"store"`: `hidden` is the undescribed rows in `absent` (`guard.ts:18-21`), with no floor.
- **Narrow read for the legacy view.** `loadDeliverableState(..., { narrow: true })` selects no
  `notes` and reads `metadata_json` only through `json_extract` of `$.tag`, `$.prerelease` and
  `$.descriptor.status`. `storeRelease()` then reads the picked row and its artifacts by key.
- **When the rules apply.** PR 1 passes `view: "legacy"` only from the new compute steps and the
  job, and the store view still hides nothing, so no route changes. PR 2 turns on the store view's
  hiding. From then on, storefront feeds, the download page and `builds/` stop offering an
  undescribed release that was deleted upstream; today they offer it, and its GitHub bytes 404.
  The dry run lists these releases per product.
- New `resolveStoreSelector(db, cfg, raw)` in `storeRelease.ts` replaces `resolveSelector`
  (`gateway.ts:412`):
  - `classifyChannel` parses the selector;
  - `policyChannelOf` (moved from `gateway.ts:380-390` to `channels.ts`) gives the canonical name;
  - `resolveInState` picks the release, and `storeRelease()` returns `{release, sel}`.

- **Grants.** P2-12 never widens a grant. The `entitled` check keeps `classifyChannel` and

- **Promote and pin.** `release_channel_policy` is read once (`resolve.ts:527-531`). The second

### 6.5 Data migration (P0-49 job `update-resolver`, from `services/update/resolverCompare.ts`)

**Dry run.** The dry run covers every product with a resolved release config.

- **Probes:**
  - the appcast with no `arch`, with `arm64` and with `x86_64`;
  - `/version` on every selector, plus the current stable pinned both bare and as `v`;
  - `/dl` for `cli` and `dmg` × `arm64` and `x86_64` × plain and `checksum`.
- **Selectors:** omitted, `latest`, `stable`, `beta`, `staging`, each manual channel, each floored
  channel, and, for workflow products, each `pr-<n>` named by the last 10 runs.
- **How each probe runs:** both compute steps run on one synthetic request. The probe bypasses
  the edge cache, the access check and the rate limit. The old step keeps `ghCache`'s 90-s
  resolution cache, so it costs what serving costs. Products run one at a time. The job pauses,
  and resumes later through P0-49, when GitHub answers 403 or 429 or `x-ratelimit-remaining`
  drops below 500. The Sparkle memo is shared, so each DMG streams at most once per run.
- **What is compared:** status, `content-type`, `cache-control` and the body's SHA-256. For `/dl`
  the comparison is the chosen release id and the asset's name and size, not the bytes.

**Report rows.** Each row is `{product, surface, probe, old, new, class}`.

- `identical`;
- expected:
  - `beta-includes-stable`;
  - `workflow-channel`;
  - `beyond-page-cap` (the legacy read stopped at three pages);
  - `duplicate-version` (the legacy path preferred `v<version>`; the store takes the later
    publication);
  - `descriptor-channel` (the descriptor's `channel` wins over GitHub's flag);
  - `descriptor-files` (a described release's descriptor names a file that GitHub does not list);
- blocking: `stale-store`, `unexpected`;
- retry: `upstream-error`.

**Apply actions.** Each action is dry-run first, audited through P0-18's writer and recorded in
P0-24's ledger.

- **`backfill-store`.** It runs P0-26's release-store sync for a linked product that has no `app`
  rows or whose listed rows lack `listedAssets`. It is the on-demand remedy for `stale-store` rows,
  since the freshness pass normally gets there first. There is deliberately no down step, because
  the rows are exactly what any sync writes.
- **`materialise-workflow-beta`.** For a product with `channel_workflow`, the job reads the tags
  that `channelTagsFor(beta)` gives now. It sets `release_metadata.channel = 'beta'` on undescribed
  `app` rows whose `channel` is NULL and whose id is in that set. The sync never overwrites the
  column (`store.ts:66`). The apply is idempotent and can be re-run.
  - The first dry run copies each product's `channel_workflow` and `beta_branch` into the job
    record, and later runs read them from there, so no run depends on the column's current value.
  - The apply already moves those rows into `beta` on the store surfaces (the download page,
    `builds/` and storefront feeds). That is their intended meaning.
  - Down: from the list in the job record, reset only the rows whose `channel` is still `'beta'`
    and that are still undescribed.

**Switch rule.** PR 2 merges when the latest report meets all three conditions:

1. it has zero blocking rows;
2. the lead has acknowledged every expected row in P0-24's ledger, by class and count;
3. for every product the job record lists with a `channel_workflow`, no `workflow-channel` row's
   old answer is a build published after the latest `materialise-workflow-beta` run.

Condition 3 holds only once djdl's workflow publishes beta as GitHub prereleases or with
descriptor `channel: beta` (Q2's owner step). Until then, every new short-SHA build would belong
to no channel, and beta and `pr-<n>` testers would silently stop getting builds.

The order in production:

1. djdl's workflow changes;
2. the lead re-runs the materialise apply;
3. the lead runs the dry run until the switch rule holds, and PR 2 deploys;
4. djdl's repository drops `channelWorkflow` and `betaBranch` in a change prepared beforehand and
   merged right after the deploy.

Step 4 comes last because a resync writes `channel_workflow` as NULL when the field is absent
(`resync.ts:665`). Done earlier, it would cut djdl's `pr-<n>` channels off the legacy path before
the switch. Until step 4 lands, a djdl manifest push fails with the error that names the
replacement, and it changes nothing.

`tracks.md` rule 5 says that N+1 switches "once the report shows zero diffs". This rule accepts
six expected classes instead, because they are the deliberate convergence on one meaning per
track (D6) and cannot reach zero by construction. The deviation is recorded in P0-24's ledger
entry (§7).

### 6.7 Freshness

A new `releaseFreshness(ctx)` in `freshness.ts` is called from Release's `scheduled` hook
(`index.ts:46`, beside `sweepNativeSessions`). That hook runs on `CONNECTOR_POLL_CRON`, every 15
minutes (`scheduled.ts:505`, `core/registry.ts:536-560`). For the hook's product, when it is
linked (`isResolved`):

- **When a product is due:**
  - its newest `app` `published_at` is within 86,400 s of `now`; or
  - its newest `release_health.checked_at` is more than 3,600 s old, over subject `release` or
    `channel`, both of which every sync writes (`store.ts:1061`, `:1183`); or
  - it has no such row. Counting `channel` rows keeps a repo with no releases from being due on
    every tick.
- **What it runs:** one `syncReleaseStoreReport` (P0-26's pipeline). It never throws. A failed sync
  does not move `checked_at`, so the product stays due.
- **The cap:** at most 25 syncs per tick, counted across the products the hook visits in that
  tick. A product over the cap reports `freshness: "deferred"` and stays due.
- **The report:** `{ freshness: "synced" | "fresh" | "deferred", statements }` in the cron report.

**Review note: there is no daily pass.** Every surface that P2-12 moves needs Release enabled,
because Update needs Distribution and Distribution needs Release (`services/update/index.ts:14-15`).
The hook runs for every product with Release enabled (`core/registry.ts:550`), so its 1-h rule
already covers what a 03:17 pass would add.

### 6.9 Security, THREAT-MODEL and PRIVACY

The reviewer checks the following THREAT-MODEL rows. A new subsection, **"One update resolver
(P2-12)"**, says:

1. **Trust is unchanged.** For a product without records, whoever can write its GitHub releases
   decides what it serves, as today. A release-level `.sig` is honoured only by the legacy
   renderer, and only after it verifies against `sparkle_ed25519_pub`. The extended renderer's
   rule that only a descriptor's sidecar counts is untouched.
2. **Freshness and deletion.**
   - A delivered release webhook updates the store at once.
   - Without one, the freshness pass catches up within 15 minutes while the product's newest
     release is under 24 h old, and within 75 minutes otherwise. Both bounds add up to 300 s at
     the edge. Today's live read takes up to 90 s plus that 300 s. The cases without a webhook are
     an asset uploaded, replaced or deleted after publication, a missed delivery, and a failed
     sync.
   - A store that is behind serves the newest release it knows, never one it does not know.
   - Deletion withdraws a release once a complete sync sees it gone (D5). A repo with more than
     1,000 releases never gets a complete read, so deletion never withdraws a release there.
   - **A yank is the supported way to withdraw a build.** It applies at once on every surface.
3. **Cost.**
   - A cache miss costs the narrow D1 state read (§6.2), plus the picked row and its artifacts.
     Today it costs KV and up to three GitHub list calls.
   - A non-public product's Sparkle checks are never edge-cached, so each one is such a miss.
     Only the per-IP `release` bucket (30/min) and D1 bound them.
   - An appcast flood no longer spends the installation quota.
   - The freshness pass spends up to 10 list calls per sync, with at most 25 syncs per tick.
   - Each sync bumps the release generation. A product's edge entries therefore turn over at most
     every 15 minutes during its first day after a release, and hourly after that.
4. **Least privilege.** From P2-12b the installation token drops `actions: read` and
   `pull_requests: read`.
5. **The job.** The lead runs it. It writes only store rows that a sync would write, and
   `channel` on undescribed rows whose `channel` is NULL.

Two existing passages are amended:

- 221-229, about pins and floors: they now point at `resolve.ts` and D5;
- the cost bullet at 1738-1745, about the extra read a legacy appcast costs.

**PRIVACY:** no change. No personal data is added. The reports hold release metadata only.

## 9. Rollout and rollback

Each release is a v0.9.x.

- **Release N.** No route changes its resolver. The freshness pass, `listedAssets` and the
  comparison go live. The step-2 materialise apply puts djdl's current workflow builds into
  `beta` on the store surfaces.
- **Release N+1.** The switch, and the two settings become a validator error. **Rollback** is
  `wrangler rollback` to N. There is no migration in
  between, and N reads everything N+1 wrote. During the deploy, old and new Workers both answer
  from the same rows. Orphaned `ghCache` resolution entries expire after 90 s.
- **The plan for legacy `SUFeedURL`s.**
  - The four URL forms stay router aliases under rule 6's native-binary exception, and P2-12 does
    not change them.
  - The enclosure stays `/release/dl/<segment>/<name>`.
  - The unparameterised feed stays arm64.
  - A product without records keeps the one-item legacy bytes for as long as it has no records.
    This is a renderer, not a flag.
  - When such a product starts publishing records, it moves to the extended appcast at the same
    URL, as it does today. Sparkle reads both.
  - Installed copies need no update.
