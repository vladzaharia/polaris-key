## 1. Summary

- **A product becomes an OpenID provider** at `https://key.plrs.im/<p>/identity`, on layer 1's issuer,
  `authorize` and `token`, adding discovery, JWKS, `userinfo`, revocation and RP-initiated logout.
- **Registered clients** (`cl_…`: websites, SPAs, native apps) are declared by the product's developer
  in the console or manifest; no dynamic registration. The own client (`client_id` = slug) is unchanged.
- **Tokens:** an RS256 `id_token` and an RFC 9068 `at+jwt`, 600 s each; opaque rotating refresh tokens
  with family revocation. `sub` is the product's pairwise subject.
- **A per-product RS256 keyring** under `PLATFORM_KEK`, apart from the Ed25519 document keys. Issuer
  tokens are not Polaris signed documents: `PROTOCOL_VERSION` stays **5** and I-21 changes no corpus
  file (SP-68 adds RS256 vectors to `backend-matrix.json`). **Consent per client**, built on D22.

## 2. The person's flow, per platform

**Sign in with <Product>** opens `<issuer>/authorize` in the system browser. The V5 §12.9 bind hop lands on
the Locker card: "<Client> wants you to sign in with your <Product> account", both icons, "by <developer>"
and "Returns you to <host>". The person signs in if needed; ConsentStep (§3.4) needs **Continue** on the
first sign-in to each client (D22); a `302` returns `code`, `state` and `iss`. A return shows "Continue as
<name>" (one tap, I-08 D3); `prompt=none` with a live grant is silent (D4); sign-out uses `end-session`
(§3.5). Relying parties use generic OIDC libraries.

| Platform               | Client type and redirect                                                                                                            | How                                                                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Web (server)           | `web`: confidential (`client_secret_basic`), https                                                                                  | openid-client, Authlib, Discourse's OIDC plugin. A refresh token with `offline_access`                                 |
| Web SPA                | `spa`: public, PKCE `S256`, https. CORS on `token`, `userinfo` and `revoke` for the origins of its redirects                        | oidc-client-ts, with one refresher per tab group (R1)                                                                  |
| iOS, iPadOS, macOS     | `native`: public, PKCE, a universal link or a private-use scheme (`com.example.app:/cb`)                                            | AppAuth-iOS on `ASWebAuthenticationSession`; it shares the Locker session, so a returning person needs one tap. See R4 |
| Android                | `native`: App Links or a private-use scheme                                                                                         | AppAuth-Android on Auth Tab, else Custom Tabs. Never a WebView (S-16 §5.4 item 14)                                     |
| Desktop                | `native`: loopback `http://127.0.0.1/cb` or `[::1]`, registered without a port. Any port matches (RFC 8252 §7.3); never `localhost` | The system browser and a listener (V5 §12.12 rule 6)                                                                   |

## 3. Protocol

### 3.1 Endpoints and discovery

All under `<issuer>` on the API host, served only while Identity is on (V5 §12.8) and
`identity.issuer.enabled` is true; otherwise the registry's `404` (navigations: the `identity_disabled` `303`).

| Route                                                                                        | Method    | Notes                                                                                                                             |
| -------------------------------------------------------------------------------------------- | --------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `/.well-known/openid-configuration`                                                          | GET       | New. `max-age=300`, CORS `*`                                                                                                      |
| `/jwks`                                                                                      | GET       | New. `max-age=300`, CORS `*`. Keys in states `next`, `active` and `retired`, each with `kid`, `use: "sig"` and `alg: "RS256"`     |
| `/authorize`                                                                                 | GET, POST | Extended (§3.2). A `POST` form navigation (OIDC Core §3.1.2.1) is new                                                             |
| `/token`                                                                                     | POST      | Extended (§3.3): `authorization_code` for clients, `refresh_token`, and the device exchange (D6)                                  |
| `/userinfo`                                                                                  | GET, POST | New. A bearer `at+jwt` in the header, or an `access_token` form member. Failure: `WWW-Authenticate: Bearer error="invalid_token"` |
| `/revoke`                                                                                    | POST      | New (RFC 7009). A refresh token revokes its family. An access token gets `200` but is not revoked; it expires within 600 s        |
| `/end-session`                                                                               | GET, POST | New (RP-Initiated Logout 1.0): `id_token_hint`, `client_id`, `post_logout_redirect_uri` (exact match) and `state`                 |
| Customer host `/signout`, `GET /api/signout/requests/<h>`, `POST …/confirm`, `POST …/cancel` | GET, POST | New. Reached through a single-use `eo_` handle (120 s) over the bind hop                                                          |

`openid-configuration` carries `issuer`, an `*_endpoint` or `jwks_uri` member per route above,
`service_documentation`, `scopes_supported` and `claims_supported` (§3.4), `response_types_supported`
`[code]`, `response_modes_supported` `[query]`, `grant_types_supported` `[authorization_code,
refresh_token, token-exchange]`, `subject_types_supported` `[pairwise]`, `id_token_signing_alg_values_supported`
`[RS256]`; token and revocation auth methods `[client_secret_basic, client_secret_post, none]`;
`code_challenge_methods_supported` `[S256]`; `prompt_values_supported` `[none, login, consent]`;
`authorization_response_iss_parameter_supported: true`; and `false` for the `claims`, `request` and
`request_uri` parameters and for front- and back-channel logout. Polaris discovery's identity
fragment gains only `"accessToken": true` (D6), while the exchange is served.

### 3.2 `authorize` for a registered client (changes from V5 §12.4)

| Parameter                                         | Rule                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client_id`, `redirect_uri`                       | Checked first. The client must be active. The URI must match a registered one exactly: a query only as registered, no fragment, no userinfo, no wildcard, no `localhost`; the loopback port is free. A failure renders the branded `invalid_client` or `redirect_uri_mismatch` page and never redirects. A success appends `code`, `state` and `iss` |
| `response_type`                                   | `code`. Anything else redirects `unsupported_response_type`                                                                                                                                                                                                                                                                                          |
| `scope`                                           | Must include `openid`. It is intersected with the client's allowed scopes; unknown values are ignored                                                                                                                                                                                                                                                |
| `code_challenge`, `nonce`                         | A public client must send PKCE `S256`. A confidential client sends PKCE or a `nonce` (RFC 9700 §2.1.1; OIDF Basic sends no challenge). `plain` is `invalid_request`. `nonce` is at most 255 characters                                                                                                                                               |
| `state`                                           | Optional, at most 512 characters, echoed back                                                                                                                                                                                                                                                                                                        |
| `prompt`, `max_age`                               | `login`, or a session older than `max_age`, forces a fresh sign-in. `auth_time` is always issued. `consent` always shows ConsentStep. `none` is D4: without a session, `login_required`; without a covering grant, `consent_required`; combined with another value, `invalid_request`                                                                |
| `id_token_hint`, `login_hint`                     | The hint is verified against this issuer's keys, and an expired one is accepted. A different `sub` answers `login_required`. `login_hint` works as in layer 1. `display` and `ui_locales` are ignored                                                                                                                                                |
| `request`, `request_uri`, `claims`, Polaris hints | `request_not_supported`; `request_uri_not_supported` (PAR stays the own client's, V5 §12.12). `claims`, `name_hint`, `purpose`, `license_choice` and `key_return` are ignored: a client binds no device                                                                                                                                              |

The `rq_` handle's `ClientRecord` gains `registered: {clientId, name, developerName, iconUrl, returnHost,
nameVerified}` (extends PX-W13; `appName` stays the product's). Continue writes the client grant
(§3.5). The code is single use for 60 s, bound to client, redirect, challenge, `nonce`, granted scope
and claims, account, subject and `auth_time`.

### 3.3 `token` for a registered client, and the device exchange

| Case                 | Rule                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Request              | A form body (JSON is `invalid_request`), no `X-PKey-Device`, and a `no-store` answer. Confidential clients use exactly one of `client_secret_basic` or `client_secret_post`; a failure is `401 invalid_client`. Public clients send `client_id` and the verifier                                                                                                                                              |
| `authorization_code` | Atomic, as in V5 §12.5 rule 2. A reused code also revokes the family it issued (RFC 6749 §4.1.2), through a 10-minute tombstone                                                                                                                                                                                                                                                                               |
| `200`                | Exactly `access_token`, `token_type: "Bearer"`, `expires_in: 600`, `scope` and `id_token`, plus `refresh_token` only with `offline_access` (`IssuerTokenResponse`). No layer-1 member                                                                                                                                                                                                                         |
| `refresh_token`      | May narrow `scope`. It rotates and issues a new access token and `id_token`, with the same `sub`, `aud` and `auth_time` and no `nonce`. A rotated token presented again revokes the family (`invalid_grant`, audit `identity.refresh.reuse`). Each use re-checks the client, the grant, both toggles, the account and the subject                                                                             |
| Device exchange (D6) | Own client only. Token exchange with `client_id=<slug>`, `subject_token=` the caller's own `pkeyt_`, `subject_token_type=urn:polaris-key:token-type:device` and `requested_token_type=urn:ietf:params:oauth:token-type:access_token`. `X-PKey-Device` must match and the device must be signed in. Answer: `{access_token, issued_token_type, token_type, expires_in: 600, scope: ""}`; never a refresh token |
| Errors               | Flat (RFC 6749 §5.2): `invalid_request`, `invalid_client`, `invalid_grant`, `unauthorized_client`, `unsupported_grant_type` and `invalid_scope`. `client_credentials` is `unsupported_grant_type` until U-16                                                                                                                                                                                                  |

### 3.4 Tokens, scopes, claims and who signs what

| Token         | Format                                                             | Lifetime                          | Members                                                                                                                                                                             |
| ------------- | ------------------------------------------------------------------ | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id_token`    | JWS RS256, `typ: "JWT"`, `kid` = the RFC 7638 thumbprint           | 600 s                             | `iss`, `sub` (`ps_…`), `aud` = `client_id`, `azp`, `exp`, `iat`, `auth_time`, `nonce`, `at_hash`; when consented, `name`, `picture`, `email`, `email_verified`, `pkey:entitlements` |
| Access token  | JWS RS256, `typ: "at+jwt"` (RFC 9068)                              | 600 s                             | `iss`, `sub`, `aud` = `<issuer>`, `client_id`, `exp`, `iat`, `jti`, `scope`, `auth_time`, and `pkey:entitlements` when granted. Read by `userinfo`, SP-68 and U-16                  |
| Refresh token | `pkeyo_` + 43 base64url, stored as an HMAC under `KEY_HASH_PEPPER` | 30 d idle, 90 d absolute, rotated | Kept server side: family, client, account, scope, claims, `auth_time` and `replaced_by`                                                                                             |
| Client secret | `pkeycs_` + 43 base64url, peppered, shown once                     | At most 2 live                    | Checked at `token` and `revoke`                                                                                                                                                     |

| Scope               | ConsentStep line ("<Client> gets …")               | Delivers                  |
| ------------------- | -------------------------------------------------- | ------------------------- |
| `openid`            | None: the header names the account and the product | `sub`, `auth_time`        |
| `profile`           | Your screen name; your picture (two toggles, I-34) | `name`, `picture`         |
| `email`             | Your email address (a toggle, D19)                 | `email`, `email_verified` |
| `pkey:entitlements` | Which <Product> features you have                  | `pkey:entitlements`       |
| `offline_access`    | Stay signed in to <Client> while you're away       | A refresh token           |
| `pkey:licenses`     | Reserved, not served (D5)                          | —                         |
| `pkey:sync`         | Reserved for U-16's `client_credentials`           | —                         |

**Claims.** `picture` is PX-W16's `avatarUrl(…)` made absolute, or absent. `email_verified` is true
only for the account's Polaris-verified primary email (IS-10). `pkey:entitlements` is
`resolveSubjectEntitlements(p, sub)` filtered to `userGrant` keys (LX-01 §7), never licence state.
`userinfo` reads live and refuses once the grant is gone. `claims.required` lines cannot be switched
off (declining is Cancel); the licence line and `cloudSync` never show for a client; the copy says a
shared claim is the same for every app (S-16 §5.4 item 12).

**Who signs what.** The **product issuer key** (RSA-2048, per product, D2) signs only that product's
tokens; it is sealed under a new `keyvault.ts` kind, `issuer-signing-key` (AAD
`pkey:v2:<product>:issuer-signing-key:<kid>`). The **Ed25519 product and release keys** sign only
`pkey-*+jws`; `shared-jws` and client-core stay EdDSA-only, and the Worker's `jose` path pins RS256.
Continue is authorised by session, CSRF and binder, never signed. Clients use shared secrets
(`private_key_jwt` waits for I-25). **Rotation:** every 90 days; a `next` key is published 7 days
before it signs, a `retired` one stays 30 days; an emergency rotation (Superadmin, step-up, audited)
drops a `kid` at once.

### 3.5 Consent, revocation and end-session

`identity_client_grants (account_id, product, client_id, claims_json, scopes_json, scope_hash,
granted_at, modified_at, last_used_at)`, keyed `(account_id, client_id)`. `scope_hash` is V5
§12.7.3's function with `pkey:*` and `offline_access` under `services`; a declined optional item is
not asked again (I-34). A client grant neither needs nor writes `account_product_grants`. D22 holds:
every interactive sign-in shows Continue; only `prompt=none` with a covering grant is silent.

| Path                                     | Effect (an access token already issued expires within 600 s)                                |
| ---------------------------------------- | ------------------------------------------------------------------------------------------- |
| Locker → Connected apps → **Disconnect** | Deletes the grant and revokes its refresh families; `userinfo` refuses at once              |
| Console: disable or delete a client      | Revokes every family; delete also removes the grants                                        |
| Identity or the issuer turned off        | Revokes the product's families. Grants and keys stay, so turning it back on re-asks nobody  |
| Account deletion, per-product removal    | Deletes the grants and families (`deletion.ts`)                                             |
| Merge (D21)                              | Revokes the absorbed account's families; its grants move to the survivor where it has none  |
| Product deletion, refresh reuse          | Product deletion removes everything (`productDeletion.ts`); a reuse revokes that one family |

Locker says "<Client> is signed out within 10 minutes", which matches the real lifetime.
**End-session** redirects only to a `post_logout_redirect_uri` registered on the client that
`id_token_hint` or `client_id` names. It stores an `eo_` handle and `303`s to
`<customer>/signout?request=eo_…&bind=…`, where Locker asks "Sign out of Polaris Locker too?" (**Sign
out** ends that host's session; **Stay signed in** does not), then returns with `state`. Refresh
tokens survive it (`offline_access`); Disconnect ends them. No front- or back-channel logout (R3).

## 5. Catalog, manifests and settings (rule 9)

In I-09's nested `identity:` block (I-35 adds `methods`, `connections` and `claims` beside them):

```yaml
identity:
  issuer: { enabled: true }
  clients:
    - key: forum # ^[a-z][a-z0-9-]{1,31}$, unique per product; the server mints the cl_ id once
      name: "DJDL Community" # checkDisplayName + reserved terms
      developerName: "Example Partner Ltd" # optional; absent = the product's developer
      type: web # web (confidential) | spa | native
      redirectUris: ["https://forum.example.com/auth/oidc/callback"]
      postLogoutRedirectUris: ["https://forum.example.com/"]
      scopes: [openid, profile, email, pkey:entitlements, offline_access]
      claims: { required: [name] }
```

| Validator code                  | Rule                                                                                                                                                                           | Schema  |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------- |
| `invalid_client_key`            | The key pattern above                                                                                                                                                          | rejects |
| `duplicate_client_key`          | The key is unique within the product                                                                                                                                           | accepts |
| `too_many_clients`              | At most 20 clients                                                                                                                                                             | rejects |
| `invalid_client_redirect`       | At most 10. Each is https with no fragment or userinfo, or loopback `127.0.0.1` or `[::1]` with no port, or a reverse-DNS scheme other than `im.plrs.*` and `locker.polaris.*` | rejects |
| `client_scope_unknown`          | Each scope is in `ISSUER_SCOPES`, and `openid` is present                                                                                                                      | rejects |
| `client_claim_not_requested`    | `claims.required` ⊆ what the scopes deliver                                                                                                                                    | accepts |
| `reserved_display_name`         | Reused (PX-W13) for `name` and `developerName`                                                                                                                                 | accepts |
| `issuer_clients_without_issuer` | `clients` needs `issuer.enabled: true`                                                                                                                                         | accepts |

Each code gets a `test/schema-parity.test.ts` row and a `schemas/v1/product.schema.json` change, then
`bundle:action -- --check`. Ingest upserts by `(product, key)`; a client dropped from the manifest is
disabled, never deleted. Secrets never live in a manifest (the console's **Generate secret**). The setting
`identity.issuer.enabled` (product, boolean, default `false`) joins ST-03's registry (`pnpm gen settings`).

## 7. SDKs, in order

1. **Relying parties:** no Polaris SDK; the docs cover openid-client, Authlib, AppAuth and the Godot recipe.
2. **I-21b** (new, 0.4–0.6 engineer-weeks, after I-21.13), `identity.accessToken()`: **client-core**
   first (`AccessTokenExchangeResponse`, `accessTokenRequest()`, the cache rule: memory only, reused
   until `expires_in − 60`, cleared on sign-out), then **Node, React, Python, Swift, Kotlin, Godot**,
   each replaying `identity-access-token.json` and flipping `identity.accessToken` to `implemented`.
   Without `accessToken` in discovery the call fails `service-unavailable`.
3. **SP-68** (after I-21b): `requireSignIn()` in the four server cores accepts `Bearer <at+jwt>` (JWKS
   via `openid-configuration`) and passes `issuerTokenCases`; typed N/As as `server.signin` (web,
   desktop-bridge, iOS, Android, Godot). **U-16** (parked) adds `client_credentials` with `pkey:sync`.

## 10. Privacy, quotas and neighbouring work

**Privacy.** A client gets the product's pairwise `sub` and `auth_time`; with consent only, the screen
name, picture URL, primary email with `email_verified`, and `userGrant` entitlement ids. Never the
account id, sign-in methods, other products, the birth date (I-27 §2.4), licence keys or licence state.
Stored: grants (until Disconnect or deletion) and refresh hashes (purged 30 days after they end); I-11's
full and per-product exports include the grants, deletion removes them; developers see per-client
counts and sign-in history. `docs/PRIVACY.md` gains "Sign in with <Product>: what an app you sign in to
gets"; the DPA sentence ("the developer controls what its clients receive") goes to legal review.

**Quotas** (fail closed, as I-02): 20 clients per product (`MAX_ISSUER_CLIENTS`); per client 10
redirect URIs, 10 post-logout URIs, 2 secrets; 10 refresh families per account and client (oldest
revoked). `authorize` 60/min per network (layer 1); `token` 30/min per network (public), 600/min per
confidential `client_id`, 20 failed authentications/min per network; exchange 10/min per device;
`userinfo` 120/min per subject and client; `revoke` 60/min per client; `end-session` 30/min per network.

**Neighbours.** **I-32** is the opposite direction (the product signs people in _through_ its own IdP;
here _into_ other apps): a product-connection identity's `email_verified`, groups and claims never pass
through (IS-10). **LX-36:** the issuer never calls `accessFor()`, mints or upgrades (D7); automatic
licences issued earlier show in `pkey:entitlements`. **I-34:** consent mechanics reused; I-21.15 adds
client rows to its page.

**Rollout and compatibility.** Migrations, then the Worker with the issuer dark (setting default
false), then the staging OIDF runs, then a product turns it on. Deployed SDKs and DJDL's installed
builds see no change: they never send `openid`, the layer-1 `token` answer is byte-identical (the
transcript gate), and they ignore `accessToken`. An I-21b SDK on an old Worker fails
`service-unavailable`; an old Worker mid-deploy never reads the new tables. Rollback: issuer off
answers `404` and refuses refresh, issued tokens die within 600 s; a code revert leaves tables unused.

## 13. Decisions (★ is the recommendation; the lead takes it unless the owner vetoes)

- **D1 Build.** ★ In-house on `jose` (`^6.2.12`, already in the Worker) on I-08's endpoints: one server
  (I-27), no hosting, the Worker's own login and consent. Alt: headless Ory Hydra (Go + Postgres off Workers).
- **D2 Keys.** ★ An RS256 keyring per product (RSA-2048, RFC 7638 `kid`): an RP skipping `iss` still rejects
  other products' tokens; deletion is clean. Alt: one platform keyring (signatures verify across products).
- **D3 Tokens.** ★ §3.4: 600 s `id_token`/`at+jwt`; refresh 30 d idle, 90 d absolute, rotated, reuse kills
  the family, no grace. Alt: opaque access tokens with introspection (breaks SP-68's offline check).
- **D4 Silent sign-in.** ★ `prompt=none` needs a live Locker session **and** this client's covering grant;
  interactive always shows Continue (D22 holds; OIDF Basic passes). Alt: always `consent_required` (risk [U]).
- **D5 Scopes.** ★ Serve `openid profile email offline_access pkey:entitlements`; reserve `pkey:licenses`
  (no licence state) and `pkey:sync` (U-16); build the resolver if LX-09 has not. Alt: `pkey:licenses` in `userinfo`.
- **D6 Own app to own backend (SP-68).** ★ Device-token exchange for a 600 s `at+jwt` (Worker: I-21; six SDKs:
  I-21b); own-client `openid` stays `invalid_scope`. Alt: `id_token` in the layer-1 answer (every SDK changes).
- **D7 Access policy.** ★ The issuer only reads: no `accessFor()`, no mint, no upgrade; relying parties gate
  on `pkey:entitlements`. Alt: a per-client "only people with access to <Product>" switch, later.
- **D8 Registration.** ★ The product's developer only, ≤ 20, no dynamic registration; a partner client shows
  "by <Partner>" and gets the product's `sub` (disclosed). Alt: platform review, or a per-client pairwise `sub`.
- **D9 Third-party TV, console and mobile Godot clients.** ★ Not in I-21 (no RFC 8628 grant for clients,
  I-27); own apps use layer 1. Alt: the device grant on `token`.
- **D10 Prefixes.** ★ `pkeyo_` (refresh) and `pkeycs_` (client secret); `pkeyrt_` is the relay ticket and
  `pkeyr_` the registry token. Alt: unprefixed, invisible to secret scanning.
- **D11 OIDF.** ★ Run Basic OP, Config OP and RP-Initiated Logout OP on staging, results linked; pay for a
  listing only when a customer asks. Alt: certify at launch (a fee and an owner account).

## 15. Risks and what is left out

- **R1** Two SPA tabs refreshing at once revoke their family; the docs say keep one refresher (a short
  grace window is the fallback). **R2** `resolveSubjectEntitlements` may land here before LX-09; the
  licensing owner reviews it. **R3** No front- or back-channel logout: a relying party learns of a
  Disconnect at its next refresh, or within 600 s. **R4** App Review 4.8: an iOS app whose main login
  is Sign in with <Product> may also need Sign in with Apple [U].
- **Left out:** custom auth domains (owner-deferred), dynamic registration, `private_key_jwt` (I-25),
  DPoP, `form_post`, request objects, a per-client pairwise `sub`.
