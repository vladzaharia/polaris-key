## 1. Summary

- **No wire change.** Signed documents, headers, routes, the seven component names,
  `FINGERPRINT_COMPONENTS`, the hash formulas and the matcher are untouched. What changes is where
  native SDKs read three components, and how a token store reports itself.
- **Fingerprint sources** (Node and Python; Swift only shares the `ramBucket` rule):
  - Windows reads `boardSerial` and `machineModel` from one PowerShell `Get-CimInstance` call:
    the same WMI properties `wmic` read, so Windows 10 sees no drift. No `wmic` remains.
  - Linux reads `machineUuid` from `/etc/machine-id`, else `/var/lib/dbus/machine-id`.
    `product_uuid` and `board_serial` are never read, so root and non-root agree. The device id
    uses the same rule.
  - `ramBucket` follows one integer rule everywhere; Node stops emitting `"0.5"` below 1 GiB.
- **Corpus.** `fingerprint.json` gains `windowsCimCommand` and three case arrays: `windowsCim`
  (16), `linuxAnchor` (9) and `ramBuckets` (13), mirrored like the rest. Node and Python run all
  three; Swift runs `ramBuckets`; the Worker keeps checking the unchanged formulas.
- **Store status.** `client-core`'s `Store` gains an optional `status()`. Node, Python and Swift
  implement it and expose `storeStatus()` / `store_status()`, and both CLIs print it.
  - Node moves to `@napi-rs/keyring` ^2.1.0 and pins Linux to the Secret Service.
  - Swift uses the data-protection keychain where entitled and reports `legacy-keychain` where
    not.
  - This closes security finding R4-11.
- **Directories.** Node, Python and Swift gain `dataDir`, `cacheDir` and `stateDir` with platform
  defaults, plus a backup-exclusion helper for packs (P4-06, P4-07). The config directory does
  not move.

> differently by different SDKs today; only stability within one SDK is promised for them.
>
> 1. **Windows CIM** (`windowsCim`, `windowsCimCommand`). One PowerShell call prints
>    `{"boardSerial": …, "machineModel": …}` for the last instance of each class, with non-ASCII
>    escaped. The parser strips one leading U+FEFF, requires a JSON object, and keeps a value
>    only if it is a string that is non-empty after trimming ASCII whitespace (U+0009–U+000D,

>    is read. The same value is the device id's raw input on Linux.
> 3. **RAM bucket** (`ramBuckets`). `g = floor(bytes / 2^30)`. Omitted when `g = 0`, otherwise the
>    largest power of two not above `g`, in decimal. Divide before any logarithm.

## 4. Corpus

### 4.1 `fingerprint.json`

Four keys are appended after `vectors`. The existing keys and values are byte-identical.

```jsonc
{
  "fingerprintVersion": 1, "componentOrder": [ … ], "componentHashLength": 22, "hwidLength": 32,
  "deviceIds": [ … ], "vectors": [ … ],          // unchanged
  "windowsCimCommand": {
    "program": "powershell.exe",                // resolved as %SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe
    "args": ["-NoLogo", "-NoProfile", "-NonInteractive", "-Command", "<SCRIPT>"],
    "timeoutMs": 10000
  },
  "windowsCim":  [ { "id", "description", "stdout": "…", "expected": { "boardSerial"?, "machineModel"? } } ],
  "linuxAnchor": [ { "id", "description", "files": { "<path>": "<content>" }, "expected": { "source", "value" } | null } ],
  "ramBuckets":  [ { "id", "description", "bytes": 17179869184, "bucket": "16" | null } ]
}
```

`<SCRIPT>` is one line with no double quotes, so Windows argument quoting cannot mangle it. It
emits pure ASCII, so neither the console code page nor a missing console (`windowsHide`) can
corrupt a value:

```powershell
$ErrorActionPreference='Stop';$b=$null;$m=$null;try{$b=@(Get-CimInstance -ClassName Win32_BaseBoard -Property SerialNumber)[-1].SerialNumber}catch{};try{$m=@(Get-CimInstance -ClassName Win32_ComputerSystem -Property Model)[-1].Model}catch{};$j=ConvertTo-Json -Compress -InputObject @{boardSerial=$b;machineModel=$m};$o='';foreach($c in $j.ToCharArray()){$n=[int]$c;if($n -gt 126){$o+='\u'+$n.ToString('x4')}else{$o+=$c}};$o
```

- `[-1]` takes the last instance, which is the row the old `wmic … /format:csv` parser took
  (`fingerprint.ts:148-158`).
- Each query has its own `try`, so a failing class costs only its own component.
- It uses only two cmdlets, a hashtable literal, and methods on `string` and `int`, all of which
  Constrained Language Mode permits. H1 checks a locked-down host if one is available.

**`ramBuckets` (13 cases),** bytes to bucket: `0`, `536870912` and `1073741823` give `null`;
`1073741824` gives `"1"`; `2147483647` gives `"1"`; `2147483648` gives `"2"`; `16496934912` (a
16 GB Linux `MemTotal`) gives `"8"`; `17179869184` gives `"16"`; `34200436736` (a 32 GB Windows
total) gives `"16"`; `68719476736` gives `"64"`; `1099511627776` gives `"1024"`; `6597069766656`
gives `"4096"`; `1125899906842623` gives `"524288"`.

- The last pins exactness. From 1 PiB up, a float `log2(bytes / 2^30)` rounds a total just below a
  power of two up to the next bucket (`"1048576"` here), which is why rule 3 divides first. Below
  1 PiB the old float formulas and the integer rule agree (every boundary, plus 2 million random
  totals up to 128 TiB, measured for this plan), so Python and Swift change nothing on a real
  machine.
- Every input is below 2^53. A reader that cannot determine RAM omits the component without
  calling the helper.

### 5.3 `ramBucket` (Node; the helper everywhere)

- Node `ramBucket(bytes)` (replacing `:62-66`) and Python `ram_bucket(total_bytes)` (replacing the
  body of `:119-131`) implement rule 3 with integers.
  - Node floor-divides by 2^30, then doubles a power of two up to it.
  - Python uses `1 << ((b >> 30).bit_length() - 1)`.
- Swift adds `public static func ramBucket(bytes: UInt64) -> String?` using `leadingZeroBitCount`.
  `Fingerprint.swift:118-124` calls it.
- The comments in all three, and the docs (§6), lose the false "15.9 vs 16.0 GiB" claim. 15.9 GiB
  buckets to `"8"`; what the bucket buys is stability while the reported total stays between two
  powers of two.

### 5.4 Directories (Node, Python, Swift)

**Semantics.** All four options are **bases**, and the SDK appends `<product>`. That is how
`configDir` works today. Each resolver is pure: no directory is created, so nothing new appears
on disk until P4 uses one.

| Base   | Linux and other POSIX                                         | macOS (Node, Python, Swift)                     | Windows (Node, Python)             | iOS (Swift)                               |
| ------ | ------------------------------------------------------------- | ----------------------------------------------- | ---------------------------------- | ----------------------------------------- |
| config | `$XDG_CONFIG_HOME` or `~/.config` (**unchanged**)             | Node, Python: same as Linux; Swift: `~/.config` | same as Linux (`~\.config`)        | Application Support (unchanged)           |
| data   | `$XDG_DATA_HOME/polaris-key` or `~/.local/share/polaris-key`  | `<Application Support>/polaris-key/data`        | `%LOCALAPPDATA%\polaris-key\data`  | `<Application Support>/polaris-key/data`  |
| cache  | `$XDG_CACHE_HOME/polaris-key` or `~/.cache/polaris-key`       | `<Caches>/polaris-key`                          | `%LOCALAPPDATA%\polaris-key\cache` | `<Caches>/polaris-key`                    |
| state  | `$XDG_STATE_HOME/polaris-key` or `~/.local/state/polaris-key` | `<Application Support>/polaris-key/state`       | `%LOCALAPPDATA%\polaris-key\state` | `<Application Support>/polaris-key/state` |

- **Roots.** On macOS, Node and Python use `~/Library/Application Support` and `~/Library/Caches`
  under `HOME`, which is the container home inside a sandbox. Swift uses
  `FileManager.urls(for: .applicationSupportDirectory | .cachesDirectory, in: .userDomainMask)`.
- **XDG.** The new XDG variables count only when set, non-empty and absolute (the XDG spec). macOS
  and Windows ignore them. `%LOCALAPPDATA%` falls back to `~\AppData\Local`.
- **The config fix.** The single config change is Node's `??` becoming `||` (`context.ts:97`): an
  empty `XDG_CONFIG_HOME` now means `~/.config`, as it already does in Python. Before, it meant
  `./<product>` under the working directory.
- **API.**
  - Node `core/dirs.ts`: `resolveDirs(productSlug, overrides?, host?)` returns
    `ProductDirs { config, data, cache, state }`. `excludeFromBackup(dir)` returns
    `"excluded" | "not-applicable" | "failed"`.
  - Python `core/dirs.py`: `resolve_dirs(...)` returns a `ProductDirs` dataclass;
    `exclude_from_backup(path)` returns the same strings.
  - Swift `PolarisKeyCore/Directories.swift`: `ProductDirs.resolve(...)` and
    `ProductDirs.excludeFromBackup(_:)`. `KeychainStore.defaultConfigDir()` (`Store.swift:215-223`)
    moves into it, unchanged.
  - The options are Node `CoreOptions.dataDir|cacheDir|stateDir`, Python
    `data_dir|cache_dir|state_dir`, and Swift `CoreOptions` URLs appended to the init with `nil`
    defaults. Each core context exposes the result as `dirs`.
  - Swift's `createLocal` (`PolarisKeyClient.swift:422-427`) must copy the three new options.
    Node and Python already spread theirs.
- **Backup exclusion.** The caller creates the directory first, at 0700.
  - Apple: Swift sets `isExcludedFromBackup`; Node and Python run `/usr/bin/tmutil addexclusion`.
  - Every POSIX host also gets a `CACHEDIR.TAG` (signature line
    `Signature: 8a477f597d28d172789f06886806bc55`), which tar, borg and restic skip under
    `--exclude-caches`.
  - Windows returns `not-applicable`: it has no per-directory exclusion convention, and
    `%LOCALAPPDATA%` neither roams nor sits in OneDrive's known folders.
  - The helper never throws.

### 5.5 Store status (Node, Python)

**Node** (`core/store.ts:139-225`, `@napi-rs/keyring` `^1.1.6` becoming `^2.1.0`; the lockfile is
regenerated):

- **What 2.x changes.** 2.0.0 rejects on store errors where 1.x returned `null` or `false`. 2.1.0
  adds `EntryOptions.linux.store`. `AsyncEntry(service, account, options?)` is otherwise
  unchanged.
- **The Linux pin.** On Linux, entries are created with `{ linux: { store: "secret-service" } }`.
  Today a headless host silently gets the kernel keyring (keyutils), which is in memory, does not
  survive a reboot, and after which `setToken` has deleted the file copy. With the pin that host
  gets a 0600 file and a `keyring-unavailable` status. The verified source is
  `keyring-node/src/linux_credential_builder.rs` at `v1.3.0`, the version locked today.
- **Writes.** `setToken` writes, reads back, and clears the file only when the read-back equals the
  token. Otherwise it writes the file. Reads and deletes keep their fallbacks.
- **`status()`.** It does not throw, and it decides in this order:
  1. the module cannot load, or the entry cannot be constructed, gives `file` with
     `keyring-unavailable`. Inside a single-executable build, `isSea()` from `node:sea` only
     _explains_ the failure in `detail`; the import is still attempted;
  2. a probe `getPassword()` that rejects gives `file` with `keyring-error`;
  3. the keyring holds the token gives `keyring`;
  4. only the 0600 file holds it gives `file` with `keyring-error` ("written after a keyring
     failure; it moves on the next token write");
  5. neither holds it gives `keyring`.
- **Other stores.** `FileStore` reports `{ backend: "file" }` (the host chose it) and
  `InMemoryStore` reports `{ backend: "memory" }`.
- **Surfaces.** `PolarisKeyClient.storeStatus()` returns `Promise<StoreStatus | null>`, `null` when
  the store has no `status`.
  - The CLI command `status(client, store?)` (`cli/commands.ts:126`) gains an optional second
    argument. The commander and yargs adapters pass `await client.storeStatus()`.
  - It prints `Token store: keyring`, or `Token store: file (degraded: keyring-unavailable: <detail>)`.
  - Existing callers of `status(client)` are unaffected.

**Python** (`devices/store.py:170-232`, `keyring>=24` unchanged):

- the same order and the same read-back;
- `status()` also counts the `fail` and `null` backends as `keyring-unavailable`. Today the
  `null` backend silently swallows `set_password`, after which the file copy is deleted and the
  token is lost;
- `PolarisKeyClient.store_status()` returns `Optional[StoreStatus]`, and `cli/core.py:326`
  `status()` prints the same line. The types are `StoreStatus` and `StoreDegraded` dataclasses
  with `to_dict()`, plus the two tuples, all in `core/store.py`.

### 5.6 macOS keychain (Swift)

`KeychainStore` (`Store.swift:244-298`) goes through an internal `KeychainAPI` seam (copy, add,
update, delete), so tests inject a fake.

- **`setToken`.** Write with `kSecUseDataProtectionKeychain: true` and
  `kSecAttrAccessibleAfterFirstUnlock`. On success, delete any legacy item (best effort). On macOS
  only, `errSecMissingEntitlement` (−34018) writes the legacy file-based keychain instead, as today.
  Any other status throws `StoreError.keychain`, as today.
- **`getToken`.** Read the data-protection keychain first. On macOS, when it reports not found or
  missing entitlement, read the legacy keychain.
  - A legacy hit while the data-protection keychain is available is migrated: written there, then
    the legacy item deleted.
  - A failed migration still returns the token.
- **`clearToken`.** Delete from both. Not found, and missing entitlement on the data-protection
  side, count as success. Anything else throws.
- **`status()`.** An attribute-only probe of the data-protection keychain:
  - −34018 gives `keychain` with `legacy-keychain`;
  - another failure gives `keychain` with `keyring-error`;
  - otherwise `keychain`.

  `InMemoryStore` reports `memory`.

- **iOS.** iOS always uses the data-protection keychain and never takes the legacy branch, which is
  `#if os(macOS)`.
- **Surfaces.** `CoreContext.storeStatus()` and `PolarisKeyClient.storeStatus()` sit beside
  `storeFailure()` (`:363`).

## 7. Rollout

**Order.** One PR. No Worker deploy is needed. The docs ship with the next Worker deploy, because
the Worker serves them. Publishing is a set of human steps: the Changesets PR for npm, and
`python-v*` and `swift-v*` tags. Nothing has been published yet: every JS package is `0.0.0`, and
no `python-v*` or `swift-v*` tag exists.

**What a device sees when an upgraded SDK next activates, enrols or registers.** Matching runs
only on those calls, never on sync, and every bind re-baselines the stored fingerprint.

| Device                                        | Change                                                    | `normal`          | `lenient` | `strict`                 |
| --------------------------------------------- | --------------------------------------------------------- | ----------------- | --------- | ------------------------ |
| Linux, non-root                               | none                                                      | —                 | —         | —                        |
| Linux, root (services, root containers)       | `machineUuid` differs, `boardSerial` gone: 2, anchor lost | tolerated (2 ≤ 2) | tolerated | mismatch once, see below |
| Windows 10                                    | none: the same WMI properties                             | —                 | —         | —                        |
| Windows 11 without `wmic`                     | two components newly present                              | exact             | exact     | exact                    |
| Windows with PowerShell blocked or timing out | two components gone, anchor held                          | tolerated (≤ 3)   | tolerated | mismatch once            |
| Windows, non-ASCII serial or model            | that value is now exact rather than mis-decoded           | tolerated         | tolerated | mismatch once            |
| Node, under 1 GiB RAM                         | `ramBucket` gone, anchor held                             | tolerated         | tolerated | mismatch once            |
| Linux root and Node under 1 GiB               | 3 changed, anchor lost                                    | mismatch once     | tolerated | mismatch once            |

- **"Mismatch once".** The Worker retires the binding and answers `hardware_mismatch`
  (`core/devices.ts:251-281`). Both CLIs already say "run the command again to re-bind", and the
  retry binds through the normal seat check.
- **Keyless enrolment** dedupes on the anchor alone (`computeEnrollHwid`).
  - A root-run Linux machine that enrolled under its `product_uuid` key gets a new key. If it ever
    re-enrols without a stored token, it mints a second free licence once.
  - Today one machine already holds two keys, one per privilege; afterwards it holds one.
  - The same applies to an operator-disabled licence under the old key, which running non-root
    already bypasses today.
- **Device ids** do not change for any installed device: the persisted `device` file wins.
- **Tokens.**
  - A headless-Linux Node host's token in the kernel keyring is abandoned, so the host re-activates
    once. It would have done so at its next reboot anyway.
  - Every other keyring entry is read where it was.
  - Entitled Swift apps on macOS migrate the legacy item on first read. Unentitled ones are
    unchanged and report `legacy-keychain`.
- **The config directory** is unchanged, except for Node with an empty `XDG_CONFIG_HOME` (§5.4).
- **No feature flag.** A flag would be a second code path for the corpus to pin. Rolling back means
  pinning the previous SDK version. A device that re-baselined drifts back by the same amount, once.

## 8. Decisions and risks (resolved as recommended unless the lead overrides)

- **D1 Versions.** `PROTOCOL_VERSION` 3 and `fingerprintVersion` 1 stay, and there is no new corpus
  file (§2.4).
- **D2 Windows.** One PowerShell CIM call, pinned in the corpus, with a 10 s timeout.
  - It takes the last instance, keeps placeholders, trims ASCII whitespace, escapes non-ASCII and
    hides the console. There is no `wmic` fallback, by the acceptance criteria.
  - The 10 s timeout is generous on purpose. A timeout that fires on a cold start and not on a
    warm one would make a Windows 11 fingerprint flap between five and seven components, and a
    missing component counts as drift.
  - `GetSystemFirmwareTable("RSMB")` is rejected: it needs native code in Node, and its strings are
    not guaranteed to equal WMI's, which would drift Windows 10.
- **D3 Linux anchor.** Rule 2, with `uninitialized` treated as absent. A literal `uninitialized`
  would give every such host the same anchor, and so one shared free licence across customers. The
  Node device id adopts the rule.
- **D4 `ramBucket`.** The integer rule. Node omits values below 1 GiB.
- **D5 The config directory does not move.** This resolves the brief's open question.
  - A move needs a migration in all three SDKs at once. Any SDK that missed it would stop finding
    the `device` file. Where that id came from the random fallback it would mint a new id, and so
    use a seat.
  - Packs, the only consumer that needs proper roots, get the new bases.
- **D6 Layout** `polaris-key/<type>/<product>`. A vendor segment cannot collide with the host app's
  own folder, which is usually named after the product, and APFS is case-insensitive. Bases match
  `configDir`'s semantics.
- **D7 The status vocabulary** adds `keystore`, `custom` and `not-persistent` to the brief's
  shape, for P5-06, host stores and P1-02's web storage. Reasons are stable identifiers; `detail`
  is free text.
- **D8 Node keyring.** `^2.1.0` with the Linux pin and read-back. There is no self-healing move from
  file to keyring on reads: the next token write moves it.
- **D9 Python keyring.** `fail` and `null` count as unavailable, and writes use read-back.
- **D10 macOS keychain.** Data-protection first, with the legacy fallback, migration on read and
  deletion from both, rather than only documenting the trade-off (notes/E9 §12 item 5). An
  unsigned CLI keeps working and says why it is weaker.
- **D11 Registry.** Only `ramBuckets` becomes a family proof (§3).
- **D12 One package, not two.** The five fixes share `fingerprint.ts`/`.py`, the stores, the
  contexts, three manifests and three READMEs. A storage-only split could leave the corpus lane,
  but it would double the manifest and README churn. The lead may still split along §5.4–5.6 if
  the corpus lane is congested.
- **Residual risks:**
  - real-device behaviour is proven only with recorded output and fakes (§9 hand-offs);
  - `machine-id` is copied by image cloning and regenerated on each boot on read-only systems, as
    the device id already is;
  - Python and Node still read `cpuModel` (Windows) and `primaryMac` (multi-NIC) differently;
  - Swift's keychain account (`token`) differs from Node's and Python's (`device-token`), so tools
    that share a device id hold separate tokens.
- **Follow-ups (unowned):**
  - a `requireKeyring` fail-closed option (R4-11's optional half);
  - cross-SDK `cpuModel` and `primaryMac` rules;
  - absolute paths for `reg` and `cmd`;
  - the desktop bridge relaying the host's store status;
  - a `pkey doctor` command;
  - re-minting persisted device ids that were hashed from `uninitialized`.
