## 2. Contract

Verified against code first (the code is the fact). Corrections to the brief, recorded here and in the brief at implementation:

**`docs/security/WIRE-CONTRACT-V4.md`**

- **§13 Product backends.**
  - 13.1 Headers [C]: `X-PKey-License` (compact `pkey-license+jws`, at most 16 384 bytes) and the existing `X-PKey-Device`
    (optional; if sent it equals `deviceId`; not proof of possession). `Authorization` is never read, and the token and the config
    document are never sent.
  - 13.2 Verdict order [C], README §5.1 steps 1 to 6 exactly:
    1. no header: `license_required` (401);
    2. over 16 384 bytes or not three base64url segments: `license_invalid`;
    3. the strict verifier with `typ` `pkey-license+jws`, `kid` from pins plus manifest keys, `iss` `key.plrs.im`, `aud` a
       configured slug, device match, `issuedAt ≤ now+300`: else `license_invalid`;
    4. freshness: `now ≤ expiresAt+300`, or with `maxAgeSeconds` `now−issuedAt ≤ maxAgeSeconds+300` and never past
       `graceUntil`: else `license_stale`;
    5. `licenseState` usable: else `license_stale`;
    6. the route requirement: `not_entitled` (403, existing wire code) or `sign_in_required` (403, `profile.user.subject`
       matches `^ps_[A-Za-z0-9_-]{22}$`).
  - 13.3 Problem body and challenge [C]: `application/problem+json`, `Cache-Control: no-store`,
    `WWW-Authenticate: PKey-License realm="<realm>", error="<code>"` on 401 only, `type` `https://key.plrs.im/docs/reference/errors/#<code>`,
    `title`/`detail` from `copy.<locale>.json` chosen by `Accept-Language` among the eight (English fallback). The body never
    names the failing step.
  - 13.4 Trust [informative]: pins, signed manifest fetch every 900 s, at most once per 60 s on an unknown `kid`, pinned keys
    always verify. Not corpus-pinned, since it is I/O.
  - 13.5 Client rule [C]: refresh first if `effectiveNow > expiresAt − 1800`; on `license_stale`/`license_invalid` force-sync and retry
    once; `not_entitled` and `sign_in_required` are never retried; a failed sync returns the backend's response.
  - 13.6 Declared limits: the one-hour replay window and the ~65-minute revocation bound (maxAge+300 s plus the Worker's
    refusal to re-issue). Stated plainly, no mitigation.
- **§8 rows:** `X-PKey-License`, scheme `PKey-License`, `sdkId` values `node-server`, `python-server`, `swift-server`, `kotlin-server`.
- **§9:** "SP-53 changes no counter; adds `backendMatrixVersion = 1`." **§10:** one ledger entry (new credential header; replay window).

**`packages/shared-protocol/src/core.ts`** (next to `HEADER_*`, line ~318): `HEADER_LICENSE = "X-PKey-License"`,
`BACKEND_AUTH_SCHEME = "PKey-License"`, `BACKEND_LICENSE_MAX_BYTES = 16384`, `BACKEND_TRUST_REFRESH_SECONDS = 900`,
`POLARIS_REQUEST_HEADERS = [HEADER_LICENSE, HEADER_DEVICE]` (as a readonly tuple). Constants only; no document type changes.
`shared-jws` is untouched: step 3 calls the existing strict verifier. **Compatibility:** deployed v4 clients never send the
header and ignore the constants; a backend that adopts a drop-in before its apps update sees `license_required` (README §9.4).

## 4. Corpus

- **Generator.** `tools/corpus/backend.ts` (`buildBackendMatrixV1()`), driven from `tools/sign-corpus.ts` through the same single
  target list as the other matrices (`V2_BACKEND_MATRIX_OUT`, source dir plus Godot mirror). The independent reference is
  `tools/corpus/reference/backend.ts`; it must not import `client-core`. The generator self-checks that the reference and the
  client-core implementation agree on every row.
- **Sections.**
  - `verdict`: `{headers, now, options, trust}` → `{status, code, context}`. The document is signed in-generator with corpus
    keys. Rows: one per step, edges at 16 384/16 385 bytes, `+300` skew on `issuedAt` and `expiresAt`, `maxAgeSeconds` plus
    `graceUntil` cap, wrong `typ`/`iss`/`aud`/`kid`, device mismatch, each `licenseState`, entitlement present/absent,
    `profile.user.subject` absent/malformed/valid, multi-product `aud`.
  - `problem`: `{code, locale}` → `{status, challenge, type, title, detail}` for 5 codes × the eight locales plus
    unknown-locale fallback.
  - `client`: `{issuedAt, expiresAt, now, response}` → `send | refresh-then-send | refresh-and-retry | surface`.
- **Version.** `backendMatrixVersion: 1`, append-only within it. Subject-bearing rows build `profile.user` inline in the
  generator, so SP-53 does not depend on SP-54's Worker change.
- **Mirrors and lists.** `sdks/godot/tests/corpus/v2/backend-matrix.json` (generated). AGENTS.md rule 1 gains the filename
  (and `packages/docs/.../contribute/corpus.md` per its drift page). Swift and Kotlin read `conformance/` in place. `pnpm gen corpus
--check` is the drift gate.
- **Runners.** `conformance/runners/node/corpusV2.test.ts` and `browser/corpusV2.browser.test.ts` replay all three sections
  through `client-core` (`backendVerdict`, `clientBackendAction`; `problem` through a small `backendProblem()` helper in the
  same file). Other languages replay in their own packages (§5).

## 6. Worker

No change: no route (rule 10), migration, table or OpenAPI entry. The new codes are produced by SDK server cores, which is why
`kind: "backend"` exists. The Worker's `LEGACY_SDK_NAMES`/sightings take the new `sdkId` values as free strings (ST-40 only
records them). The generated `reference/error-codes` page (gen-reference) lists backend codes; its drift gate is
`pnpm gen reference --check` (plus `pnpm gen constants --check`, `pnpm parity:check`, `pnpm gen corpus --check`).

Docs rows (no code): `docs/PRIVACY.md` "Product backends": the holder's name and email travel with the document to the
developer's own backend, never to Polaris Key; `docs/security/THREAT-MODEL.md`: replay within `maxAge+300 s` (default
~65 min), header spoofing (device header is a consistency check; document is bound only by signature and `aud`), junk-`kid` fetch
amplification capped at one per 60 s, no secrets in logs, and backend trust (pins verify without Polaris Key availability).

## 7. Rollout and sequencing

1. **After UK-03.** UK-03 appends `ui-matrix.json` rows and bumps its version; SP-53 branches from the integration branch that
   contains it, so `ui-matrix.json` is not regenerated twice. If the four new copy keys change `ui-matrix.json` (UK-45 precedent),
   SP-53 regenerates it in the same commit and says so.
2. **One batched regeneration with SP-54.** SP-54 (blocked on I-05) changes `cases.json` `licenseDocCases` and the identity
   transcripts; SP-53 adds `backend-matrix.json` and registry files. They touch disjoint generated files. Recommended order: both plans
   approved together; SP-53 merges first; SP-54 rebases and runs the single `pnpm gen corpus` over the union; the lead merges
   both in one integration batch with one gate. If I-05 is late, SP-53 does not wait.
3. **Reader overlap.** SP-53's `backend.ts` reads `profile.user.subject` with a private total decoder; SP-54 exports
   `licenseUserOf` and swaps it in (one-line change, no corpus effect).
4. **Deploy.** Nothing deploys for SP-53 (no Worker change). Old clients and Workers are unaffected. SDK server releases follow SP-55 to SP-57.

## 8. Risks and decisions for the human

1. **Counters.** Recommend no change: new file under `corpusVersion 2` with its own `backendMatrixVersion 1`, as every other
   matrix did. Alternative (bump `PROTOCOL_VERSION` to 5) is unjustified since no signed shape changes.
2. **`X-PKey-Device`.** Recommend keeping it optional (README). It is a consistency check only.
3. **`copyVersion`.** Recommend it stays 1 (additive keys). Confirm if any SDK treats the key set as versioned.
4. **Realm value.** Recommend the configured product slug (README example `realm="acme"`), so no new config field.
5. **Batching.** Recommend decision 7.2 above: SP-53 first, SP-54 absorbs the single regeneration. Alternative: hold SP-53 until
   I-05 lands, which delays SP-55 to SP-58 for no gain.
6. **Brief edits.** Approving this plan amends the SP-53 brief (file path corrections in §2) and the SP-54 brief (adopt
   SP-53's reader plan in §7.3); SP-55 to SP-58 briefs are unchanged.
