## 1. Summary

- **Signed shape:** `profile.user = {"subject": "ps_…"}` is written into the `pkey-license+jws` document whenever the **requesting device's** `devices.subject` is set (an account sign-in bound it). It is absent for key-entry, open-enrol and bundle documents.
- **Reader:** client-core `licenseUserOf(doc)` returns `{subject}` or `null`. Server cores (SP-55, SP-56, SP-57, SP-62) use it for `requireSignIn()`.
- **Why now:** `requireSignIn()` needs a signed fact for "a person signed in here". Today the only candidate is `profile.email`, which is the **licence holder's** email and is set on key-activated devices too. The UK-45 Python finding is this bug: `ui/terminal/flows.py:189` computes `signed_in = signed_in or bool(profile and profile.email)`.
- **Byte identity:** every document for a device without a subject is unchanged. Only the transcripts that contain a signed-in device change.
- **No version bump.** Old v4 verifiers and decoders ignore the member. Native SDKs get a reader later (§5, SP-54b).

## 2. Contract

**`docs/security/WIRE-CONTRACT-V4.md`**

- **§2.1** (licence document): the `profile` example gains `"user": { "subject": "ps_…" }`. Prose: `user` is the pairwise subject (`account_product_subjects`, one per account and product) signed in **on this device**. It carries no name, email or account id. The top-level `name`, `firstName` and `email` stay the licence holder's.
- **§3.2**: one sentence. `profile.user` is read only by `licenseUserOf`. It returns `{subject}` when `profile` is an object, `user` is an object and `subject` wholly matches `^ps_[A-Za-z0-9_-]{22}$` (§3.3 rule 1: whole-string, no trailing `\n`, ASCII classes only). Otherwise `null`. The member never refuses a document. Unknown members of `user` are ignored.
- **§9**: "SP-54 changes no counter". **§10** ledger: _the signed-in subject is read beside the claims_.

**`packages/shared-protocol`**

- `src/license.ts`: `DocProfile.user?: { subject: string }` and `export type SignedInUser = { subject: string }`.
- `src/core.ts`: `PAIRWISE_SUBJECT_PATTERN` moves here from `worker/src/core/accountSubjects.ts:39` (the Worker re-imports it). I-09's `identity` re-export and I-24a follow it.
- `PROTOCOL_VERSION` (`core.ts:9`) is unchanged. `shared-jws` does not change.

**`packages/client-core`**: new `src/license.ts` with `licenseUserOf(doc: unknown): SignedInUser | null`, exported from `src/index.ts`. `verify.ts` (`profile` is absent or an object, `:98`), the gate and `CACHE_VERSION` are unchanged. `licenseNamedUsersOf` stays I-24a's and is added to the same file.

**Decoders**: no change to Python (`core/models.py` `DocProfile.from_any`), Swift, Kotlin or Godot in this package. They already decode `profile` totally.

## 7. Rollout

1. **Sequencing.** SP-54 has no technical dependency on UK-03 (`ui-core`, no wire; SP-54 depends on I-05, `done`). Schedule it **after UK-03** so UK-03's branch is not rebased over a regenerated corpus. It lands **before I-24a** and before SP-55/56/57/62, which read the member.
2. **One regeneration.** SP-53 adds only `conformance/corpus/v2/backend-matrix.json` (its own generator `tools/corpus/backend.ts`) and the Godot copy. SP-54 changes `cases.json` and transcripts. The two outputs are disjoint, so there is no conflict. Plan for the lead's batch: merge SP-54 then SP-53, run `pnpm gen corpus && node tools/gen-transcripts.mjs` **once** on the integrated tree, commit the result once, then run `pnpm gen --check` once. Each builder still runs the scoped drift gate on its own branch; neither re-commits the other's generated files. SP-53's `sign_in_required` rows must call SP-54's `licenseUserOf`/pattern constant, so SP-54 goes first within the batch.
3. **Deploy order.** Worker first (members appear), then the server SDK releases that require them. A backend using `requireSignIn()` against an older Worker answers `sign_in_required` for every device.
4. **Documents in the field.** An already-issued document has no `user` until the device refreshes (about an hour online). A device that signed in just before the deploy is refused by `requireSignIn()` until then. A client that signs in must refresh the licence document afterwards (flagged to SP-58; I-10 does this already for the kit).
5. **Old clients and Workers.** Old SDKs ignore the member (V4 §3.2; every decoder is total: `models.py:272`, `Models.swift`, `Models.kt:113`, `services/license.gd`). New SDKs against an old Worker see `licenseUserOf == null`. A Worker rolled back drops the member; nothing else depends on it.

## 8. Risks and open questions for the human

1. **Emission condition.** Emit when `devices.subject` is set **and** matches the pattern; a malformed stored value emits nothing and does not fail the route (an unrepresentable value must not become a 500). _Recommend yes._ Alternative: refuse with `document_not_representable`. Not recommended: the subject is Worker-generated.
2. **Contents.** `subject` only; no name or email (I-24 Q3). The email privacy risk already exists on the licence holder's profile, so adding a person's email would widen it. _Recommend `subject` only._ A consented name can be a later optional member.
3. **Native readers (the UK-45 finding).** The brief keeps native SDKs out. Without a reader, Python/Swift/Kotlin/Godot kits keep guessing sign-in from `profile.email`. _Recommend adding **SP-54b** (0.5 to 0.8 weeks, `pkey-sdk-porter`)_ with the four readers and `licenseUserCases` replay, depending on SP-54 and blocking UK-48. Alternative: fold into I-24b when revived, which leaves the bug for months.
4. **Parity row.** A feature id (`license.signedinuser`) would make the typed gap explicit. _Recommend SP-54b adds it_ (planned in the four native `parity.json`, implemented in Node/React by the type); SP-54 adds none so it does not touch generated constants.
5. **Version.** Keep `PROTOCOL_VERSION` 4 and `corpusVersion` 2. _Recommend yes._ A bump would force every SDK and the pinned 4.x clients to move for an ignored member.
6. **`licenseUserCases` ownership.** SP-54 creates the section with `user` only; I-24a extends it with `namedUsers`. _Recommend yes._
7. **Brief corrections** (same branch as the implementation): no Swift mirror; `identity-attach.json` is I-09's; only `devicecode-happy.json` changes; SP-64's text "no client SDK changes" gains "except SP-54b".
