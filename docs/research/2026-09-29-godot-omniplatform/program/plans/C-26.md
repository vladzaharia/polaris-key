## 0. Facts

- **The Worker side is done.** The U-09 records engine (`.2`–`.10`, plus R) rides A3. Collections are declared in the catalog (`matchCollection`, `shared-catalog/src/cloudSync.ts`). The policies are `lastWrite`, `max`, `min`, `revision`, `merge` (fields) and `union` (elements).
  - The Worker codes are already registered: `collection_unknown`, `op_invalid_for_policy`, `value_invalid` and `entitlement_required` (`errors.json`).
  - A3 records seven transcripts with feature `sync.records`: `cloudsync-records-{cas,e2e,forget,max,merge,orset,quota}`.
- **The machine already speaks records, with no public handle.**
  - client-core `cloud-sync.ts` has `put(collection, id, value)` (:780), `add` and `remove` (:852, :857), and `record(collection, id)` (:1065).
  - **G1 is still open.** The machine sends `merge` edits as `setMember` and `removeMember`, where V5 §13.3 says `setField` and `removeField`. That is `U-09.11 ★`, which is not yet built.
- **Host codecs.** client-core `sync/hostCodec.ts` seals every record shape: value, field (`id U+0000 field`) and element (`id U+0000 canonicalJson(e)`). The Python, Swift, Kotlin and Godot codecs seal scalar values only and refuse field and element shapes (U-22 D-2).
  - `sync-vectors.json` `envelopeCases` has no record field or element row. Its 28 rows are `$settings` and `saves`.
- **API and parity.**
  - `api.json` `cloudSync.collection(name)` is `reserved: "U-23"` under feature `sync.saves`.
  - `features.json` `sync.records` names U-10 for the transcript proof.
  - Every SDK lists `sync.records` as `planned`, wp U-22 or U-23. Those packages ship saves only, so LF:2018 re-points them here.
- **The id.** No `C-` phase exists in `workpackages.json`. "C-26" also reads like CC-26 (the device-key stores). The highest U id in use is U-45.

## 1. Decisions (taken)

- **D-1 Register this package as U-46,** titled "collection(): records beyond saves in every SDK". "C-26" stays an alias in the plans only. _Why:_ it avoids a lifelong mix-up with CC-26 and stays in the sync phase.
- **D-2 The API.** Node spelling; the other SDKs use their idioms, and Python also has an `AsyncClient` mirror. `cloudSync.collection(name)` returns a `SyncCollection` with:
  - `get(id)`: an `EffectiveValue` or `null`;
  - `ids()`;
  - `put(id, value, {ifVersion?})`: `lastWrite`, `max`, `min`, or `revision` with `ifVersion` as compare-and-set;
  - `update(id, {set?, remove?})`: `merge`;
  - `add(id, element)` and `remove(id, element)`: `union`;
  - `delete(id)`;
  - `on(listener)`: the changes in this collection.

  The handle reads the served catalog. An undeclared name raises `collection_unknown` locally, and an op that the policy does not allow raises `op_invalid_for_policy`. Both codes are already registered, so no new code is needed.

- **D-3 `saves` stays its own API** (U-22/U-23). It keeps its own revision and file logic, and the handle is not rebased under it now.
- **D-4 Unknown fields survive (folds Daybook A-S3).** `update` sends only the fields it names, and `get` returns the stored JSON untouched. A-S2 (a three-way merge helper) and A-S8 (pass semantics) stay Daybook's own rows.
- **D-5 Two waves.**
  - Wave 1: client-core, Node, React and Python, after U-09.11 and A3.
  - Wave 2: Swift, Kotlin and Godot, which also lift the D-2 codec refusal.

  _Why:_ the Worker is live, and wave 1 reuses client-core in full.
