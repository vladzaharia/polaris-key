## 0. Owner decisions encoded (binding, 2026-10-04)

Quoted from the brief; every section below implements them and none reopens them.

- **Cloud Sync is its own service** named "Cloud Sync" (slug `sync`), with its own toggle; it
  depends on Config and on the product's Identity service, because Cloud Sync needs sign-in:
  descriptor `requires: [config, identity]`, enforced by the console Services toggle.
- **The principal is the account × product**, seen by the product only as its pairwise subject.
  Core resolves it as `resolveSyncPrincipal(device) = devices.subject`, set only by sign-in through
  the product; there is no licence-owner fallback for Cloud Sync. Config's account override layer
  keeps its owner fallback (`subjectFor(license.account_id, product)`), so owned licences on
  key-entry devices still get account overrides.
- **The licence-level config override layer is removed everywhere**, replaced by user-level managed
  config attached to the account per product (the account override). No "products without Identity
  keep licence overrides" exception. **Floating licences have no such layer** and are prompted to
  sign up. **Overrides on licences with no owner are dropped at migration**, with an
  operator-visible report; no grace period.
- **No Cloud Sync without signing in, ever** (literal sign-in). Floating licences, key-activated
  devices and products without Identity get local persistence only; settings upload at the first
  sign-in; U-26 stays retired. The SDK and UI kits offer sign-in on `account_required`.
- **Defaults confirmed:** the MVP (about 67 agent-days) first, then the anonymous-to-signed-in merge
  and saves, before collections; per-product ceilings of 50 GiB, 100k users holding data and 2,000
  pushes per second; 1 MiB with saves off for signed-in users with no licence for the product; the
  platform pays Cloudflare until per-product billing; web apps use a device token issued to an
  origin on the product's `web.origins` allowlist through I-08.
- **S-17 decisions 20–24, decided:** 20, entitlement overrides stay on the licence and only
  `config` and `secrets` move; 21, a 30-day notice counted from I-07 and I-11 live, and a 90-day
  report; 22, Cloud Sync needs sign-in (no licence-owner line, so no leaked-key residual and no
  new-device alert); 23, web Cloud Sync uses I-08's web redirect, which needs Identity; 24, the
  developer-backend credential follows Identity (I-21 client credentials with `pkey:sync`, else
  I-25).
- **Principal change.** Sign-out, a relink that clears the binding or a merge alias changes the
  device's principal; the SDK treats it exactly like sign-out (discard the cloud cache and keep
  local values as the unbound partition).
- **S-16 D17–D23 accepted**; D21: on merge the survivor's pairwise subject wins per product, the
  other becomes an alias that `resolveSyncPrincipal` resolves, and the developer receives
  `subject.merged`. **Carried defaults 5–16** of S-17 §7.3 are encoded as stated (locked keys
  refused locally and kept dormant on the server; precedence in the existing `local` slot; LWW,
  CAS and `prompt` defaults; `ui.scopes` stays a hint; data follows the account, not the licence;
  receipts and end-to-end encryption later; residency optional; no cross-product scope).
- The binding column is I-05's (`devices.subject`, I-04 §6.1), so U-02 adds no migration; the
  code-exchange route is `POST /<p>/identity/redirect/token` (I-04 §2.5). `config-matrix.json`
  and the signed corpus are untouched; the precedence order is unchanged. The SDK namespace is
  `cloudSync` (`cloud_sync` in Python and GDScript), never `sync`.

## 1. Summary

- **A new opt-in service, Cloud Sync (`sync`)**, row 7 of `tools/services.json`, default off,
  `requires: ["config", "identity"]`. One SQLite Durable Object per `(product, pairwise subject)`;
  routes under `/<p>/sync`; reads the catalog through a Core accessor (rule 6).
- **Settings are catalog `config` keys with a `user` block**, persisted locally by the Config SDK
  on every product and synced by Cloud Sync for signed-in devices. They fill the existing `local`
  slot, so `ConfigSource`, the resolution order and `config-matrix.json` do not change.
- **Unsigned device wire, feature-detected**: pull `GET /<p>/sync`, push `POST /<p>/sync/ops`
  (op table, push rules 1–8), save routes (U-10), `403 account_required` with a sign-in offer,
  the `sync` discovery fragment, CORS for `web.origins` with bearer only.
- **The account override replaces the licence config override** on every product: a Config layer
  keyed `(product, subject)`, merged by Core where `licenses.overrides_json` config and secrets sit
  today, with the licence-owner line; entitlement overrides stay on the licence (decision 20).
- **Evidence**: 13 `cloudsync-*` transcripts in the MVP (§4.2), `sync-scenarios.json` replayed by
  all six SDKs, nine parity ids, fourteen error codes. Order: this plan → U-02/U-04/U-18 →
  `errors.json` → U-05 Worker → transcripts → Node, React, Python, Swift, Godot, Kotlin.

### 2.1 Principal and authentication (§13.1)

- Every route takes `Authorization: Bearer pkeyt_…` and `X-PKey-Device`, resolved by
  `validateDeviceToken` and then `resolveSyncPrincipal(db, device)` (I-04 §6.2). No route accepts
  a subject or account id; the DO name is `idFromName("<product>:<subject>")`, derived server-side.
- **No principal → `403`** nested body
  `{"error":{"code":"account_required","message":"Sign in to use Cloud Sync.","signInUrl":"<origin>/portal/signin?product=<slug>"}}`.
  `account_required` is I-09's code (I-04 §4); `signInUrl` is an additive member. SDKs start
  device-code sign-in (or the web redirect in React) themselves and use `signInUrl` as fallback.
- **Normative:** a Cloud Sync response never changes licence state. A `401` on `/sync*` pauses
  Cloud Sync (`status().state = "blocked"`) until the next licence or config document fetch, which
  stays the only path that records `lastSyncUnauthorized` (`client-core/src/store.ts`,
  `gate.ts`). `403 account_required` leaves licence state, cached documents and
  `lastSyncUnauthorized` untouched.
- **Browser devices** hold the token from `POST /<p>/identity/redirect/token` (I-08) in IndexedDB.
  Every `/sync*` path joins the CORS inclusion list in `core/cors.ts` and `routeCoverage`;
  `Access-Control-Allow-Credentials` is never sent; the `pkey_<slug>_session` cookie is not
  accepted. `CORS_ALLOW_METHODS` gains `PUT` (U-10, for the upload); `CORS_EXPOSE_HEADERS` is
  unchanged.
- Gating: Cloud Sync off, or Config or Identity off → `404 not_found` (registry contract). Reads
  of one's own data are always allowed. Writes additionally obey `cloudSync.writes.requireLicense`
  (a usable licence on the device, scoped as `coreDeviceAllowed`) and `writes.minTrust`, both
  answered per mutation as `rejected/access_denied` with `reason: license_required | trust`.

### 2.3 Push (§13.3)

Body: `{"clientId":"c_…","cursor":N,"atomic":false,"mutations":[{"mutationId":41,"target":{"setting":"audio.music.volume","scope":"user"},"op":"set","value":0.6,"editedHlc":"0190f3a2c1b4:0003"}]}`.
`target` is `{setting, scope}` (`scope` ∈ `user`, `platform`, `device`; the server derives the
platform family from the device row and the device id from the credential, never from the body)
or `{record: [collection, id]}`. More than 100 mutations → `400 bad_request`; more than 256 KiB →
`413 body_too_large`.

| Target policy                   | Ops (a mismatch is `rejected/op_invalid_for_policy`)                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Setting `lastWrite`             | `set`, `clear`, each with `editedHlc`                                                                                          |
| Setting `max` / `min`           | `set` (server keeps the max or min), `clear` (reset at its clock; older `set`s ignored)                                        |
| Setting `merge`                 | `setMember {member, value}`, `removeMember {member}`, `clear`, each with `editedHlc`                                           |
| Record `revision` / `lastWrite` | `set`, `delete` with `baseVersion` (number CAS, `"*"` create-only, absent unconditional) or `editedHlc`; `inc {by}` on numbers |
| Record `merge`                  | `setField`, `removeField`, `delete`, each with `editedHlc`                                                                     |
| Record `union`                  | `add {element}`, `remove {element, observedSeq}`, `delete`                                                                     |

Response `200`: `{"subject","serverNow","results":[…],"lastMutationId",…pull members}`. Each result
is `{mutationId, status}` with `status` one of:

- `ok` + `version` (+ `renamedTo` or `dropped: true` when a catalog migration applied);
- `conflict` + `server {value, version, editedHlc, members?}`: CAS mismatch, or an LWW write older
  than the stored clock (§8 Q6); the SDK resolves by policy and enqueues zero or one new mutation;
- `rejected` + `code` ∈ `value_invalid`, `setting_unknown`, `collection_unknown`, `access_denied`
  (`reason`), `quota_exceeded` (`scope: user | product`, `remainingBytes`), `op_invalid_for_policy`,
  `store_requires_flag`;
- `duplicate` (at or below `clients.last_mutation_id`); `aborted` (rest of a failed atomic batch).

**Push and journal rules 1–8** are normative as S-17 §5.4 states them, with two precisions:
(1) `last_mutation_id` advances past every processed mutation; only a request-level failure leaves
it — transport error, 5xx, and `400`, `401`, `403`, `409 client_mismatch`, `413`, `429`; (4) `clientId`
matches `^c_[A-Za-z0-9_-]{22}$` (128 random bits), per (install, partition), stored with the next
`mutationId` (integer, 1 … 2^53−1, strictly increasing) in one atomic journal write. Rules 2
(conflicts resolved as new mutations), 3 (one outstanding CAS per target), 5 (sign-out: flush up
to 5 s, `{unsynced: n}`, pending kept per partition for 30 days, `discardUnsynced`), 6 (renamed and
dropped keys answer `ok`), 7 (`cursor_expired` keeps the journal) and 8 (HLC physical part
`localNow + serverOffset`) are unchanged.

**HLC.** `^[0-9a-f]{12}:[0-9a-f]{4}$` (48-bit ms, 16-bit counter), `clientId` the final tie-break.
The server clamps `editedHlc > serverNow + 300 000 ms` to `serverNow`. Pre-contact operations are
re-stamped by the first response's offset when it exceeds 5 minutes (S-17 §5.5).

**Locked keys.** The SDK refuses `setConfig` on a key `enforced` or `hidden` in its current
document (`setting-locked`, journals nothing). The server keeps values for keys enforced for some
devices and refuses only keys with no `user` block (`setting_unknown`).

### 2.4 Pull (§13.4)

`{"subject","serverNow","cursor","more","lastMutationId","catalogVersion","aliases":{"gfx.q":"graphics.quality"},"limits":{…},"usage":{bytes,records,saves},"changes":[…],"tombstones":[…]}`;
a change is `{setting, scope, value, version, editedHlc, updatedBy, members?}` or
`{record:[c,id], value, version, …}` or `{record:[c,id], removed: element}`. Pages of ≤ 500
changes (`more`). A cursor older than the 90-day tombstone horizon → `410 cursor_expired`. U-08
adds `empty: true` for a principal with no data. **Principal change:** when `subject` differs from
the SDK's partition key, or a call answers `account_required`, the SDK treats it exactly like
sign-out (discards the cloud snapshot, keeps that partition's pending operations under rule 5, and
falls back to the unbound partition's own values); after a merge alias the old partition's pending
operations expire with it (U-18 pins this).

### 2.5 Discovery (§13.5)

Every response gains `services.sync`. Off: `{"enabled":false}`. On:
`{"enabled":true,"settings":true,"collections":false,"saves":false,"limits":{"maxMutationsPerPush":100,"maxPushBytes":262144,"maxValueBytes":8192,"settingsBytes":65536,"totalBytes":268435456},"endpoints":{"pull":"…/sync","push":"…/sync/ops","saves":null}}`.
`collections` and `saves` turn true only when the product declares them and U-09 or U-10 has
shipped; `limits` are the product's licensed defaults (the principal's effective limits arrive in
the pull). An SDK uses an endpoint only if present, never builds a URL.

### 2.9 Rule 2, and clients and workers already deployed

**No bump.** Rule 2 governs the signed encoding (`typ`, claims, envelope). Cloud Sync data is never
signed; the config document keeps its shape, signing and ETag rules; the resolution order and
`config-matrix.json` are unchanged; every new member and route is optional and detected from
discovery. That is the class of change §9 already records for v4 and I-04 for identity routes.
`gen:corpus -- --check` changes only by the added unsigned matrix (§4.1).

- **Old SDKs** ignore `services.sync`, the catalog's `user` and `cloudSync` members and the
  account override (content only). Tolerance was checked for U-01: every SDK accepts any catalog
  object with a numeric `schemaVersion` and an `entries` array and never inspects entries
  (`sdk-node/src/config/client.ts` `isCatalog`, `sdk-react/src/browser/catalog.ts`,
  `python/…/config/client.py:158`, `swift/…/PolarisKeyConfig/Fetch.swift` `isCatalog`,
  `kotlin/…/config/ConfigEndpoints.kt` `isCatalog`, `godot/…/services/config.gd` `_is_catalog`).
  U-04 adds a per-SDK unit test that a catalog with `user` and `cloudSync` members still parses,
  and re-records `discovery-capabilities.json` with `sync` present (an added slug, as Identity
  was).
- **Owned licences on old SDKs** keep receiving the same config values after migration through the
  owner line (§6.3). **Floating licences** lose config and secret overrides at the run (owner).
- **New SDKs on an old Worker** find no `services.sync` and no `user` blocks: `setConfig` answers
  `setting-unknown` unless the compiled mirror declares the key, which persists locally only.
- **React desktop**: bridge contract `BRIDGE_VERSION` 3 → 4 carries `setConfig`, `clearConfig`,
  `settingState`, `onChange` and `cloudSync.*` (U-20); an old host answers v3, and the renderer
  degrades to read-only settings.

### 6.3 The account override layer and the migration (U-03)

`resolveMergedPayload` (`core/payload.ts`) becomes: catalog defaults → tier profile → licence
profiles → store grants → licence **entitlement** overrides → **account overrides** (`config`,
`secrets`) → device overrides. The account layer is read for `overrideSubject(device) =
resolveSubject(device.subject) ?? subjectFor(license.account_id, product) ?? none` **outside** the
`if (license)` block, so a licence-less signed-in device gets it; a floating licence gets none.
The buckets are disjoint, so the entitlement and account layers do not interact. The catalog prune
still runs before signing. Migration steps 1–5, the eight tests and the merge hook are S-17 §5.12
and §5.5 as stated; step 4 makes `PUT /licenses/{id}/overrides` refuse `config` and `secrets`
with `400 bad_request` naming the account override route and keep `entitlements`. The notice
starts 30 days before the run, counted from I-07 and I-11 both live; the report stays 90 days.
Admin routes (rule 10): `GET` and `PUT` of one subject's account override under I-12's Users
routes in `/manage/api/products/{product}/…` (the exact path follows I-12).

## 8. Open questions (recommendations)

1. **Q1 Where the scenario corpus is generated.** S-17 has a separate `gen:sync-scenarios` driven
   by the `client-core` reference. The stray-file guard fails any `corpus/v2/*.json` that
   `gen:corpus` does not write, and the stage-matrix rule forbids a golden file sharing code with
   its implementation. **Recommend** `gen:corpus` with literal data (§4.1).
2. **Q2 `byTier` with several licences.** **Recommend** the largest limit among the account's
   usable licences for the product, per limit.
3. **Q3 `platform` families.** **Recommend** fixed `desktop`, `mobile`, `console`, `web`, mapped
   from the device's registered platform by a Core function.
4. **Q4 Save bucket.** `BLOBS` carries bucket-lock rules on its content prefixes and a collector
   built on `blob_refs` (`core/blobGc.ts`); a `u/` prefix there would need both carved out, and
   personal data must be deletable at once (Art. 17). **Recommend** a dedicated bucket (binding
   `SYNC_SAVES`, no lock, no lifecycle on live data); **human input**: create it before U-10 (and
   an EU twin if U-24 offers residency).
5. **Q5 Where the SDK learns `user` policies.** Local persistence works without Cloud Sync, so they
   cannot come only from `/sync`. **Recommend** `/config/schema` cached beside the journal, the
   compiled mirror before first fetch, and a refetch when the pull's `catalogVersion` changes.
6. **Q6 A stale LWW write.** **Recommend** `conflict` with the server copy (the SDK enqueues
   nothing, `onChange origin: remote`) rather than a sixth status.
7. **Q7 Glossary.** "Principal" already names the **device principal** (WIRE-CONTRACT-V4 §6,
   concepts). **Recommend** the noun **Cloud Sync principal**.
8. **Q8 Incident switch.** **Recommend** `sync.writesPaused` as in §7.
9. **Q9 "Licensed".** **Recommend**: the account holds a usable licence for the product (a Core
   accessor), whatever licence the device runs.

**Risks.** The first device-writable data service (U-19 gates it); six offline state machines
(scenario corpus); the run drops floating-licence overrides (the notice and report). The plan
exceeds two pages because one contract serves fifteen packages; it is not split because each
section is executed by disjoint packages.

**Corrections to the research.** `payload_too_large` → `body_too_large`; transcripts are
`cloudsync-*`; the scenario corpus is written by `gen:corpus`, not a separate generator;
`CORS_ALLOW_METHODS` needs `PUT`; the product push limit cannot live on one `RateLimitDO`; the
`features.json` and `errors.json` `service` enums need `sync`; `account_required` is I-09's code.

**Brief changes** (lead, after approval): U-04 (glossary, A3, enum additions, tolerance tests,
discovery re-record); U-05 (`protocol/sync`, `gen:constants` subpath, sharded limiter,
`sync.writesPaused`, transcript names); U-18 (generator in `sign-corpus.ts`, no `client-core`
import, `client-core/cloud-sync` checked by the Node runner); U-10 (bucket, `PUT` in CORS); U-03
(`override_migration_report`, layer outside `if (license)`); U-06, U-20, U-07, U-21 (client codes,
Q5 policy source).
