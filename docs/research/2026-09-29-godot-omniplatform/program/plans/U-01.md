## 0. Owner decisions encoded (binding, 2026-10-04)

Quoted from the brief and the notes' owner headers; every section implements them, none reopens
them.

- **Cloud Sync is its own service** named "Cloud Sync" (slug `sync`), with its own toggle; it
  depends on Config and on the product's Identity service, because Cloud Sync needs sign-in:
  descriptor `requires: [config, identity]`, enforced by the console Services toggle.
- **The principal is the account × product**, seen by the product only as its pairwise subject:
  `resolveSyncPrincipal(device) = devices.subject`, set only by sign-in through the product; no
  licence-owner fallback for Cloud Sync. Config's account override layer keeps its owner fallback
  (`subjectFor(license.account_id, product)`), so owned licences on key-entry devices still get
  account overrides.
- **The licence-level config override layer is removed everywhere**, replaced by the account
  override (user-level managed config per account × product). No exception for products without
  Identity. **Floating (unowned) licences have no such layer** and are prompted to sign up.
  **Overrides on licences with no owner are dropped at migration** with an operator-visible
  report; no grace period.
- **No Cloud Sync without signing in, ever.** Floating licences, key-activated devices and
  products without Identity get local persistence only; settings upload at the first sign-in; U-26
  stays retired. SDKs and UI kits offer sign-in on `account_required`.
- **Defaults confirmed:** MVP (about 67 agent-days) first, then the anonymous-to-signed-in merge
  and saves, then collections; per-product ceilings 50 GiB, 100k users holding data, 2,000
  pushes/s; 1 MiB with saves off for signed-in users with no licence for the product; the platform
  pays Cloudflare until per-product billing; web apps use a device token issued through I-08 to an
  origin on the product's `core.web.origins` allowlist.
- **S-17 decisions 20–24, decided:** 20 entitlement overrides stay on the licence, only `config`
  and `secrets` move; 21 a 30-day notice counted from I-07 and I-11 both live, and a 90-day
  report; 22 Cloud Sync needs sign-in (no leaked-key residual, no new-device alert); 23 web Cloud
  Sync uses I-08's web redirect; 24 the developer-backend credential follows Identity (I-21 client
  credentials with `pkey:sync`, else I-25).
- **Principal change** (sign-out, a relink that clears the binding, a merge alias) is handled
  exactly like sign-out. **S-16 D17–D23 accepted**; D21: the survivor's pairwise subject wins per
  product, the other becomes an alias `resolveSyncPrincipal` resolves, the developer gets
  `subject.merged`. Carried defaults 5–16 of S-17 §7.3 are encoded as stated.
- **S-19 (model OC):** a licence is an access contract; grants are entitlement reasons; a device's
  entitlements are combined over its contributors by `resolveDeviceEntitlements` (LX-09); the
  **holder is the account signed in on that device** (`entitlementHolder: device`), so the S-19
  holder and the Cloud Sync principal are the same account on a signed-in device; existing products
  stay in **`legacy` mode, byte-identical**, until the operator switches. Decision 19: quotas gain
  **`byEntitlement`** (`combine: max`) and keep **`byTier`** on the highest-rank contributing
  licence. `requiresFlag` reads the resolver; `writes.requireLicense` reads the anchor's
  usability. Config is not combined. Decision 18's "download ticket" rename touches nothing here.
- **S-18:** ceilings and quotas are `product_settings` rows in the settings registry (§5.4), not a
  `sync_product_settings` table; developer limits are `claimable`; the account is not a settings
  scope (account overrides are customer config, not settings).
- Fixed names: the binding column is I-05's `devices.subject` (U-02 adds no migration); the
  code-exchange route is `POST /<p>/identity/redirect/token`; the SDK namespace is `cloudSync`
  (`cloud_sync` in Python and GDScript), never `sync`.

## 1. Summary

- **A new opt-in service, Cloud Sync (`sync`)**, the seventh row of `tools/services.json`, default
  off, `requires: ["config","identity"]`. One SQLite Durable Object per `(product, pairwise
subject)`; routes under `/<p>/sync`; catalog and settings read through Core accessors (rule 6).
- **Settings are catalog `config` keys with a `user` block**, persisted locally by every Config SDK
  and synced for signed-in devices. They fill the existing `local` slot, so `ConfigSource`, the
  resolution order and `config-matrix.json` do not change.
- **Unsigned device wire, feature-detected:** pull `GET /<p>/sync`, push `POST /<p>/sync/ops` (op
  table, push rules 1–8), save routes, `403 account_required` with a sign-in offer, the
  `services.sync` discovery fragment, CORS for `core.web.origins` with bearer only.
- **The account override replaces the licence config override** on every product, keyed
  `(product, subject)`, with the licence-owner line for Config only; entitlement overrides stay on
  the licence.
- **Evidence:** 18 new `cloudsync-*` transcripts (13 in the MVP) and one re-recorded (§4.2), `sync-scenarios.json` replayed by all six
  SDKs, nine parity ids, fourteen wire and client codes. Order: this plan → U-02/U-04/U-18 →
  `errors.json` → U-05 Worker → transcripts → Node, React, Python, Swift, Godot, Kotlin.

### 2.1 Principal, authentication and gating (§13.1)

- Every route takes `Authorization: Bearer pkeyt_…` and `X-PKey-Device`, resolved by
  `validateDeviceToken`, then `resolveSyncPrincipal(db, device)` (I-04 §6.2). No route accepts a
  subject or account id; the DO name is `idFromName("<product>:<subject>")`, derived server-side.
- **No principal → `403`**, nested body
  `{"error":{"code":"account_required","message":"Sign in to use Cloud Sync.","signInUrl":"<origin>/signin?product=<slug>"}}`
  (I-09's code; `signInUrl` additive). SDKs start device-code sign-in (the web redirect in React)
  themselves and use `signInUrl` as fallback.
- **Normative:** a Cloud Sync response never changes licence state. A `401` on `/sync*` pauses Cloud
  Sync (`status().state = "blocked"`) until the next licence or config document fetch, which stays
  the only path that records `lastSyncUnauthorized` (`client-core/src/store.ts`, `gate.ts`).
  `account_required` leaves licence state, cached documents and `lastSyncUnauthorized` untouched.
- **Browser devices** hold the token from `POST /<p>/identity/redirect/token` in IndexedDB. Every
  `/sync*` path joins the CORS inclusion list (`core/cors.ts`, `routeCoverage`);
  `Access-Control-Allow-Credentials` is never sent; the `pkey_<slug>_session` cookie is not
  accepted. `CORS_ALLOW_METHODS` gains `PUT` (U-10); `CORS_EXPOSE_HEADERS` unchanged.
- **Gating.** Cloud Sync, Config or Identity off → `404 not_found`. Reads of one's own data are
  always allowed. Per mutation, U-02's Core accessor
  `syncAccess(db, product, device, now) → {subject, anchorUsable, licensed, entitlements, topTier}`
  answers three checks (S-19 §8 U-01 row):
  - `cloudSync.writes.requireLicense` → `anchorUsable` (the device's anchor licence is usable,
    scoped as `coreDeviceAllowed`); else `rejected/access_denied`, `reason: license_required`;
  - `writes.minTrust` → `reason: trust`;
  - a store's `requiresFlag` → `entitlements[flag]` truthy; else `store_requires_flag`.
  - `entitlements`, `licensed` (≥ 1 usable contributing licence) and `topTier` (highest
    `tiers.rank` among contributing licences, ties to the anchor) come from
    `resolveDeviceEntitlements` once LX-09 lands. Until then `syncAccess` reads the anchor's merged
    entitlement bucket and tier, which is by definition `legacy` mode. In `legacy` mode a
    licence-less signed-in device gets an empty set and `licensed = false`; in `combined` mode it
    gets the holder's account-held and store-held grants (S-19 §7.3.1).

### 2.3 Push (§13.3)

Body:
`{"clientId":"c_…","cursor":N,"atomic":false,"mutations":[{"mutationId":41,"target":{"setting":"audio.music.volume","scope":"user"},"op":"set","value":0.6,"editedHlc":"0190f3a2c1b4:0003"}]}`.
`target` is `{setting, scope}` (`scope` ∈ `user`, `platform`, `device`; the server derives the
platform family from the device row and the device id from the credential) or
`{record: [collection, id]}`. More than 100 mutations → `400 bad_request`; more than 256 KiB →
`413 body_too_large`.

| Target policy                   | Ops (a mismatch is `rejected/op_invalid_for_policy`)                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Setting `lastWrite`             | `set`, `clear`, each with `editedHlc`                                                                                          |
| Setting `max` / `min`           | `set` (server keeps the max or min), `clear` (reset at its clock; older `set`s ignored)                                        |
| Setting `merge`                 | `setMember {member, value}`, `removeMember {member}`, `clear`, each with `editedHlc`                                           |
| Record `revision` / `lastWrite` | `set`, `delete` with `baseVersion` (number CAS, `"*"` create-only, absent unconditional) or `editedHlc`; `inc {by}` on numbers |
| Record `merge`                  | `setField`, `removeField`, `delete`, each with `editedHlc`                                                                     |
| Record `union`                  | `add {element}`, `remove {element, observedSeq}`, `delete`                                                                     |

Response `200`: `{"subject","serverNow","results":[…],"lastMutationId",…pull members}`; each result
is `{mutationId, status}` with `status`:

- `ok` + `version` (+ `renamedTo`, or `dropped: true`, when a catalog migration applied);
- `conflict` + `server {value, version, editedHlc, members?}` (CAS mismatch, or an LWW write older
  than the stored clock, Q6); the SDK resolves by policy and enqueues zero or one new mutation;
- `rejected` + `code` ∈ `value_invalid`, `setting_unknown`, `collection_unknown`, `access_denied`
  (`reason`), `quota_exceeded` (`scope: user | product`, `remainingBytes`),
  `op_invalid_for_policy`, `store_requires_flag`;
- `duplicate` (at or below `clients.last_mutation_id`); `aborted` (rest of a failed atomic batch).

**Push and journal rules 1–8** are normative as S-17 §5.4 states them, with two precisions: (1)
`last_mutation_id` advances past every processed mutation, and only a request-level failure leaves
it (transport error, 5xx, `400`, `401`, `403`, `409 client_mismatch`, `413`, `429`); (4) `clientId`
matches `^c_[A-Za-z0-9_-]{22}$`, one per (install, partition), stored with the next `mutationId`
(integer 1 … 2^53−1, strictly increasing) in one atomic journal write. **HLC**
`^[0-9a-f]{12}:[0-9a-f]{4}$`, `clientId` the final tie-break; the server clamps
`editedHlc > serverNow + 300 000 ms` to `serverNow`. **Locked keys:** the SDK refuses a set on a key
`enforced` or `hidden` in its current document (`setting-locked`, nothing journalled); the server
refuses only keys with no `user` block (`setting_unknown`).

### 2.4 Pull (§13.4)

`{"subject","serverNow","cursor","more","lastMutationId","catalogVersion","aliases":{…},"limits":{…},"usage":{bytes,records,saves},"changes":[…],"tombstones":[…]}`;
a change is `{setting, scope, value, version, editedHlc, updatedBy, members?}`,
`{record:[c,id], value, version, …}` or `{record:[c,id], removed}`. Pages of ≤ 500 changes. A cursor
older than the 90-day tombstone horizon → `410 cursor_expired`. `limits` are the principal's
**effective** limits (§6.5). U-08 adds `empty: true`. **Principal change:** a `subject` different
from the SDK's partition key, or `account_required`, is handled exactly like sign-out (discard the
cloud snapshot, keep that partition's pending operations under rule 5, fall back to the unbound
partition's own values); after a merge alias the old partition's pending operations expire with it.

### 6.3 The account override layer and the migration (U-03)

`resolveMergedPayload` (`core/payload.ts`) becomes: catalog defaults → tier profile → licence
profiles → store grants → licence **entitlement** overrides → **account overrides** (`config`,
`secrets`) → device overrides. The account layer is read for
`overrideSubject(device) = resolveSubject(device.subject) ?? licenseOwnerSubject(license) ?? none`
**outside** the `if (license)` block, so a licence-less signed-in device gets it and a floating
licence gets none. Buckets are disjoint; the catalog prune still runs before signing. Provisioned
secrets (`proxy.subscriptionUrl`) move with the other secrets (S-19 §8 U-03 row).

**S-19 seam.** Config is not combined: in both `legacy` and `combined` modes LX-09's resolver keeps
the config and secrets buckets as `A`'s tier and profiles → account overrides → device overrides.
The account layer is part of "today" for LX-09's `legacy` byte-identity gate: whichever of U-03 and
LX-09 merges second rebases, and LX-09's live-document snapshot is taken after U-03's run.
Re-anchoring changes the tier profile, never the account layer.

Migration steps 1–5, the eight tests and the merge hook are S-17 §5.12 and §5.5 as stated; step 4
makes `PUT /licenses/{id}/overrides` refuse `config` and `secrets` with `400 bad_request` naming
the account override route and keep `entitlements`. The notice starts 30 days before the run,
counted from I-07 and I-11 both live; the report stays 90 days. Admin routes (rule 10): `GET` and
`PUT` of one subject's account override under I-12's Users routes in
`/manage/api/products/{product}/…`.

### 6.5 Limits and ceilings (U-05)

Licensed defaults and platform ceilings are S-17 §5.7's table (settings ≤ 256 keys, 8 KiB per

## 8. Open questions for the owner

1. **Q1 Where the scenario corpus is generated.** S-17 proposes a separate `gen:sync-scenarios`
   driven by `client-core`, but the stray-file guard fails any `corpus/v2/*.json` that `gen corpus`
   does not write. **Recommend** `gen corpus` with literal data (§4.1).
2. **Q2 Licence-less signed-in devices in `legacy` mode.** S-19 §7.3.1 says `requiresFlag` reads the
   holder's grants, but `legacy` reads no contributor beyond the anchor. **Recommend** one code
   path: Cloud Sync takes whatever `resolveDeviceEntitlements` returns, so in `legacy` a
   licence-less device has no entitlements and is unlicensed, and in `combined` it gets the
   account's grants.
3. **Q3 `byEntitlement` shape.** **Recommend** a map from limit to a developer-declared numeric flag
   (`{"totalBytes":"sync.storageBytes","saveSlots":"sync.slots"}`, the names S-19 uses as the
   scaffold default), not reserved system keys; the flag must combine by `max` (rule 8b).
4. **Q4 Save bucket.** `BLOBS` carries bucket-lock rules and a `blob_refs` collector; personal data
   must be deletable at once. **Recommend** a dedicated bucket (binding `SYNC_SAVES`, no lock).
   **Human input:** create it before U-10 (and an EU twin if U-24 offers residency).
5. **Q5 Where limits live.** **Recommend** the split in §3: data shape in the catalog
   (`.pkey/schema`), limits and access policy as claimable settings in `.pkey/product`, so a
   console claim never fights a catalog publish. SDKs learn `user` policies from `/config/schema`
   cached beside the journal, the compiled mirror before the first fetch, and a refetch when the
   pull's `catalogVersion` changes.
6. **Q6 A stale LWW write.** **Recommend** `conflict` with the server copy (the SDK enqueues nothing,
   `onChange origin: remote`) rather than a sixth status.
7. **Q7 Glossary.** "Principal" already names the device principal (WIRE-CONTRACT-V4 §6).
   **Recommend** the noun **Cloud Sync principal**.
8. **Q8 Platform families for `scope: platform`.** **Recommend** fixed `desktop`, `mobile`,
   `console`, `web`, mapped from the device's registered platform by a Core function.
9. **Q9 Does U-05 wait for LX-09?** **Recommend no**: `syncAccess` reads the anchor's merged set
   (equal to `legacy`) until LX-09 replaces its body.
