## 1. Finding and boundary

**Finding.** R1-07 is the RFC 8628 remote-phishing residual rooted in R8-03. A
starter controls an enrolled device, its `deviceCode`, and any client-supplied
`deviceName`. They send a victim the `verificationUriComplete` URL. The victim
opens `/identity/auth/device?user_code=…`, receives a CSRF token and the
`__Host-pk_lcb` browser binder, authenticates at the IdP, and can reach the
license chooser. The starter then polls with its `deviceCode`, sees the victim
identity, and may claim or migrate the victim's license through
`attachLicense: true`.

**What is already protected.** `confirmDeviceFlow` rejects cross-site and bad or
replayed CSRF submissions, deletes the user-code index, uses no device code in
the URL, and stores a hash of `__Host-pk_lcb`; `handleAuthCallback` requires
that cookie. That rejects the older curl-confirm-and-forward-authorize attack.
`__Host-pk_req` similarly binds a PX-W13 `rq_…` presentation request to the
browser that created it.

**Why that does not close this variant.** In the complete-URI attack the victim
is the confirming browser, so they correctly possess both browser cookies.
Neither cookie is known to the device poller, and neither says who owns the
physical device. A user code, a device label, a request handle, a CSRF token,
a browser callback, or a challenge relayed between attacker and victim can all
be created or relayed by the starter. They are not an unforwardable proof of
user intent for that device.

**Required invariant.** No device-code flow may cause callback completion,
chooser/consent disclosure, account-bound token minting, `ready`, identity
exposure to `/device/poll`, claim, migrate, or `attachLicense` unless the system
has a proof that is both (a) scoped to that exact single-use flow and (b) not
obtainable by a starter who forwards `verificationUriComplete` to a victim.
On failure it must write nothing, mint nothing, and reveal no account, license,
or flow existence.

## 2. Decision required before code

There is no unforwardable proof in the current RFC 8628 inputs. A device-code
holder can relay any challenge it receives to a victim; a browser cookie binds
a browser, not the person or physical device. I-37 therefore **must not** claim
that a fresh CSRF token, `__Host-pk_lcb`, `__Host-pk_req`, a user-code re-entry,
or a new poll nonce closes R1-07.

The owner chooses one of these security policies before implementation:

| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |

## 3. Approved-option implementation contract

This section is executable after the owner chooses **D1.A**. If the owner
chooses D1.B, replace this section with the approved channel design before an
implementer starts.

### 3.1 Worker and service changes

1. In `packages/worker/src/services/identity/oidc.ts`, give every flow created
   by `handleAuthDeviceStart` an explicit `viaDeviceCode` / capability marker
   that survives the user-code lookup, confirmation, callback and poll. Do not
   derive the decision from a request parameter or label.
2. At `confirmDeviceFlow`, preserve the current same-origin check, single-use
   CSRF spend, user-code-index delete, no-referrer/no-store 303 and
   `__Host-pk_lcb` binder. Those are independent protections and remain
   required. The browser may authenticate, but its callback must not make a
   device-code flow eligible for account-bound activation.
3. In `handleAuthCallback`, before any chooser redirect, account/license
   lookup that affects the flow, identity storage visible to device poll, mint,
   claim or migrate, branch on the stored device-code marker. Atomically
   invalidate/drop that continuation and return the selected generic refusal.
   A rejected callback must not fall through to auto-issue or an old
   device-code activation path.
4. In `handleAuthDevicePoll`, reject every device-code status that would
   otherwise expose the authenticated identity or advance to `ready` after an
   account callback. It returns the existing documented generic terminal/error
   status selected by the approved contract, not a new accidental bearer
   response. It must never offer `attachable` or execute `attachLicense` for
   the rejected flow.
5. Apply the identical policy to `handleAuthDeviceVerify`; the legacy device
   code is never logged or copied into an error, redirect, request handle, or
   audit detail. Let existing records expire at `FLOW_TTL_SECONDS` (600) rather
   than attempting an unsafe migration.
6. Keep `createSignInRequest` and `__Host-pk_req` for trusted presentation only.
   The portal must not accept a request handle, `deviceName`, `userCode`, or
   browser cookie as authorization to bypass the stored capability marker.

### 3.2 Protocol and client impact

- Preserve the response schema of `POST /<p>/identity/auth/device/start` unless
  D2 removes `verificationUriComplete`; any removal is a deliberate discovery
  and contract change, documented before code and feature-detected by clients.
- The device poll remains keyed by `deviceCode`; it must not acquire an
  account, license, request handle, browser cookie, or callback `state` member.
- Do not send a device code in a URL, form field, browser storage, request
  record, transcript, or console/audit payload. Existing `deviceName` remains
  display data only.
- D1.A means device-code sign-in no longer provides an account-bound completion.
  The plan must point users to the separately approved same-device sign-in
  route; I-08/PX-14 own that UX and must not disguise the refusal as success.

### 3.3 Documentation changes

Update these together with the implementation:

- `docs/security/THREAT-MODEL.md`: replace the contradictory “closed” wording
  and the `I-08 / PX-W13` residual ownership with the selected I-37 policy;
  state exactly which device-code capabilities remain and which attack paths
  tests prove closed. Preserve a residual for phishing through a victim using
  an attacker-controlled physical browser, which no cookie can observe.
- `docs/security/WIRE-CONTRACT-V4.md`: document any D2 discovery/start response

- `packages/docs/src/content/docs/features/sign-in/device-flow.md`: remove the

- `plans/I-04.md` §2.4/G and `wp/I-08-app-passthrough.md`: correct the
  statement that browser-bound callback alone closes device-code R1-07.
- `wp/I-37-device-code-explicit-confirm.md`: record the final option and exact
  acceptance evidence. Do not mark R1-07/R8-03 closed merely because UI copy
  or a browser cookie changed.

## 4. Test plan and acceptance evidence

Add or amend tests before changing threat-model status:

1. **Complete-URI attack:** an attacker-controlled enrolled device starts a
   flow, forwards `verificationUriComplete`, and a victim confirms/authenticates
   in their own browser. Assert generic refusal; no chooser/consent response,
   no identity on the poll, no token, no claim/migrate/attach, and no changed
   license/device rows.
2. **Typed code and QR equivalence:** run the same attack through a typed user
   code and a scanned complete URI. Both must obey the stored device-code
   marker; page presentation differences may not create a bypass.
3. **Existing binder regression:** preserve the curl-confirm-and-forward-
   authorize test. Missing, duplicate, malformed, foreign, expired and replayed
   `__Host-pk_lcb` / `__Host-pk_req` values still refuse without minting.
4. **Legacy route:** a pre-deploy `/device/verify?device_code=` record follows
   the same policy for its remaining 600-second lifetime and cannot create a
   fallback route.
5. **State and concurrency:** callback/poll races, double callback, code expiry,
   and callback after a terminal refusal perform no partial identity, license,
   device, token, or attachment write.
6. **Allowed path:** exercise the owner-approved replacement same-device route
   end to end, including a poll that remains `pending` until its secure terminal
   condition. This proves the security fix did not turn a browser page into a
   deceptive success state.
7. **Portal evidence:** the request API still gives `404 not_found` without the
   matching binder, ignores display query parameters, and the card/refusal
   screen uses no secret or attacker-controlled label as a trust assertion.

The named Worker attack suites, portal e2e, Workerd tests, UI snapshots and
`pnpm gen --check` are all required by the brief. Add exact test names to the
brief during implementation.

## 5. Rollout and rollback

1. **Prepare.** Land the threat-model and contract/documentation correction in
   the implementation PR. Do not claim resolution before attack tests prove the
   selected policy.
2. **Deploy.** Deploy the Worker atomically. Existing unconfirmed flows retain
   the old record shape but are governed by the stored/default device-code
   marker. They expire naturally within 600 seconds. No database migration,
   backfill, or SDK release is needed for D1.A.
3. **Observe.** Count only coarse, non-secret refusal outcomes; do not emit user
   codes, device codes, callback state, request handles, account IDs, or device
   labels in telemetry. Review generic-refusal volume and legitimate recovery
   reports before expanding a replacement route.
4. **Rollback.** A rollback to pre-I-37 restores the vulnerable behaviour, so it
   is an emergency availability action only and must be paired with disabling
   device-code account completion at the edge/feature policy if that protection
   remains available. There is no safe compatibility fallback. Because D1.A adds
   no schema, an ordinary roll-forward restores the fail-closed code. Do not
   re-enable `verificationUriComplete` or legacy verify as a rollback shortcut.
