## 0. What changes from the approved plan

- **The policy.** D1.A said a device-code flow never produces an account-bound outcome. This plan replaces it with an explicit approval after sign-in, enforced by a fail-closed server-side marker (B9, SIGN-IN.md §4.2). Browserless TV and console apps keep account sign-in, so the regression the lead accepted at I-08 D1 is withdrawn.
- **What this does not do.** Old §1–§2 still hold: no page can prove that the person who signed in holds the device. **R1-07/R8-03 is therefore reduced, not closed.** §9 states exactly what is closed and what stays open.
- **The wire change goes.** The old D2 (deprecate `verificationUriComplete`) is withdrawn (D2 below), which removes the only all-SDK change. D3 (retire `/device/verify`) and D4 (generic refusal copy) stand.

## 1. Summary

- **The marker.** `approvedAt` on the device-code flow record in I-02's single-use store. Only an explicit decision sets it (**Sign in on {device}**, or a licence choice on the chooser), and only in the browser that confirmed the code and signed in. Until it is set, `/device/poll` answers `pending` and nothing account-bound happens: no identity, no `confirm`, no activation, no attach, no token.
- **The confirm step.** New `GET|POST /<p>/identity/auth/device/approve`, a script-free Worker page. It shows the app, the account, the device label, the code, and where and when the request started. It has two actions: **Sign in on {device}** and **Deny** (**Not you?** also denies). I-38a gives it the hosted look, and PX-14 later renders the same decision in the card.
- **Deny** reuses the poll's generic `error`. No new status is added.
- **P1-07 attach is retired on device code.** The person approving is never told that the starter's licence and devices would join their account.
- **Legacy and entry pages.** `/device/verify` is retired. The entry page no longer names the product before the code resolves (B9.3) and carries the "Only use a code from your own product" line.

## 6. Worker

### 6.1 The marker

The marker lives on `FlowRecord` (`productOidc/config.ts`): the `oidc-flow` artefact, addressed by the peppered `state`, with a 600 s life (`FLOW_TTL_SECONDS`). It is not on `DeviceFlowRecord`, which is keyed by the device code that no browser path may touch. It is not in any response, and not on the SDK side.

- **`approvedAt?: number`** is the marker. Two writers set it, each through one compare-and-set that spends a single-use page token: `decideDeviceFlow(…, "approve")` in the new `productOidc/deviceApproval.ts`, and `completeChoice` for a device-code flow (the licence choice is the explicit step, per B9). No request field, cookie, header, label, user code, request handle or `state` maps to it.
- **`approveToken?: string`** is the peppered hash of the current DeviceConfirm page's token.
- **Fields stored at `/device/start` for display only:** `startedAt`, `userCode`, and `startPlace: {country, label}`. The place comes from Cloudflare's `request.cf` through `requestLocation`, which moves from `portal/deviceLogin.ts` to `services/identity/place.ts` (same service).
- **Deny** sets the existing `error` field to `"denied"`.

**Fail-closed rule.** A flow is a device-code flow when `viaDeviceCode === true || deviceId !== undefined` (`isDeviceCodeFlow`). The second arm catches a record written before the `viaDeviceCode` marker existed (old amendment 3). Such a flow counts as approved only when `typeof approvedAt === "number"`. Anything else is unapproved: absent, malformed, or written by an older Worker.

### 6.2 Where it is enforced

| Site                                                          | After                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pollAuthFlow` (`poll.ts`)                                    | An unapproved device-code flow answers `{"status":"pending"}`. This check comes before the N9 account check, identity disclosure, `confirm`, `activateFromIdentity`, the attach and `authorizeAndMint`. A flow with `error` set answers `error`, which is already the first check                                     |
| `handleAuthCallback` (`callback.ts`)                          | Branches on `isDeviceCodeFlow`, not on `viaDeviceCode`. It opens the chooser if its trigger holds. Otherwise it stores `identity`, writes the `oidc-choice` index and 303s to `…/auth/device/approve`. It never reaches `activateFromIdentity` or `completeBrowserFlow`                                               |
| `completeChoice` / `handleAuthChoose` `cancel` (`chooser.ts`) | For a device-code flow, the update that records the choice also sets `approvedAt`. `cancel` is Deny                                                                                                                                                                                                                   |
| `completeBrowserFlow`                                         | Refuses a device-code flow (defence in depth)                                                                                                                                                                                                                                                                         |
| P1-07 attach (`attachableLicense`)                            | Never offered on device code (D6): `confirm` says `attachable: false`. `attachLicense: true` is treated as `false`, so the sign-in completes, nothing merges, and a host that ignores `attachable` cannot loop on `confirm`. The poll passes no `enrolledLicenseId`, and the dead attach path in `poll.ts` is removed |

### 6.3 Server contract of the confirm step

- **Reaching the page.** The callback `303`s there (`no-store`, `no-referrer`). The URL carries no `state`, code or handle, so a reload or a forwarded copy reaches the flow only through the binder. The page is on the callback host, which is the API host, beside the chooser (D8). On the customer host, LK-04's bind hop already puts `__Host-pk_lcb` there.
- **Finding the flow.** Only `__Host-pk_lcb` leads to it: the binder's peppered hash → the existing `oidc-choice` index (`choiceKey`) → `state`. The flow must be a device-code flow with `confirmedAt`, `consumedAt` and `identity` set, a matching `binder`, and neither `approvedAt` nor `error`. Anything else gets `startAgainPage()` ("Start again on your device", 403, D4): the stale index is dropped and nothing else is written.
- **`GET`** mints a 32-byte token, stores its hash in `approveToken` (CAS on `approvedAt: null`) and renders §6.4. A new render replaces the previous token.
- **`POST`** takes the form fields `token` and `decision`. It requires Fetch Metadata same-origin (`sameOriginPost`), then makes one CAS: `expect {approveToken: hash(token), approvedAt: null, error: null}`.
  - **`decision=approve`:** set `approvedAt` and unset `approveToken`; delete the index and clear the binder (`binderClearCookie`); render the done page (`signin.device.done` / `doneLede`). The next poll mints exactly as today.
  - **`decision=deny`** (Deny, and **Not you?**): set `error: "denied"` and unset `identity`, `claimAccount` and `approveToken`; delete the index and clear the binder; render the denied page. The poll answers `error` until the record expires (D3).
  - **A missing or unknown decision, or a spent, stale or foreign token:** `303` back to `GET`, nothing written. Of two racing POSTs, exactly one CAS wins.
- **Expiry:** the flow's own 600 s from `/device/start`. The token and the index share it, and nothing extends it.
- **Rate limit:** new bucket `authDeviceApprove`, 60 a minute per client network, GET and POST together. It fails closed (the `core/rateLimit.ts` map).
- **Headers:** `brandedHtmlSecurityHeaders` (`frame-ancestors 'none'`, `form-action 'self'`), `no-store`, `no-referrer`, no script.
- **Audit:** `identity.signin.device_approved` and `identity.signin.device_denied`, written with `appendAudit`. The summary names the label and nothing else: no place, code or `state`. Both are added to `packages/admin/src/console/sections/core/model/activityVerbs.ts`.
- **One write path.** `decideDeviceFlow(env, product, stateKey, tokenHash, decision, now)` is the only writer of the decision. PX-14's card route calls it.

4. **`/device/start`** stores `startedAt`, `userCode` and `startPlace` through `beginAuthFlow`'s extras. Its response is unchanged.

## 7. Rollout

1. **Order.** LK-04, then I-37 in the current auth wave. It is a Worker deploy only, with no flag and no SDK release, and it no longer has to share a tag with I-08 and I-15. I-38a and I-37b follow in the next wave, and PX-14 after that.
2. **Flows in flight at deploy.**
   - Flows that have not reached the callback get DeviceConfirm.
   - Flows already past it hold an `identity` and no `approvedAt`. They answer `pending` until they expire (at most 600 s) and then `timeout`, and the person gets a new code.
   - Nothing is grandfathered: that would be the bypass. No migration or backfill.
3. **Deployed clients.** See §5. They need one more browser press. Deny ends in their generic failure. The TV hand-off copy says "Choose Continue to {product}…" until I-37b ships.
4. **Rollback.** An older Worker ignores `approvedAt`, so flows waiting at DeviceConfirm would complete at their next poll, because their `identity` is stored. Roll back only in an availability emergency. Denied flows keep `error` and stay refused. Rolling forward restores the gate, and there is nothing to undo.
5. **Observe.** Count approved, denied, and expired-unapproved flows per product. Log no codes, labels, places or account ids.

## 9. Threat model and docs

**`docs/security/THREAT-MODEL.md`.**

- **"The device-code user-code page (P1-06)."** Add a fifth control: the approval marker (§6.1).
- **"Remote phishing".** The heading becomes "residual R1-07 reduced by explicit approval; open".
  - **Closed, each proven by tests:** completion without an explicit approval; approval from any browser except the one that confirmed the code and signed in; approval from a request handle, a label, a user code, `state` or either cookie alone; replay, cross-flow and expired approvals; the starter's P1-07 claim and migrate (attach retired); the `/verify` path.
  - **Open (R1-07, reduced):** someone persuaded to press **Sign in on {device}** after seeing the place. The starter's one device is then authorized on their licence: seat-checked, listed in their devices and revocable. The device also receives their name and verified email (`ready.identity`). A VPN in the victim's country hides the place. No package owns this residual; I-40 becomes optional.
- **"What the opt-in attach adds under R1-07."** Mark it retired on device code and keep it as history.
- **The I-26 chooser's residual paragraph and the I-08 bullet "R1-07 for device code".** Point both at this policy.

**Other documents.**

- **`docs/PRIVACY.md`:** the start place is held with the sign-in for at most 600 s and shown to the person signing in. It is never stored, logged or audited after that.
- **`features/sign-in/device-flow.md`:** the approval step, Deny, the attach retired, `/verify` retired.
- **`features/sign-in/troubleshooting.md`:** "pending until approved".
- **`docs/design/SIGN-IN.md`:** §3.13 gets the rows for the DeviceConfirm, done and denied pages. §4.2 step 4 notes that the step is on the API host until PX-14.

## 10. Tests

New `test/deviceApproval.test.ts`, and amendments to `attack/R8-oidc.test.ts`, `identityBinders.test.ts`, `oidcLicenseChoice.test.ts`, `platformDeviceEntry.test.ts` and LK-04's `customerDevicePage.test.ts`:

1. **The gate.** After the callback, every poll answers `pending`: no identity, no `confirm`, no token. Licence, device and audit row counts are unchanged until approval. After approval, the next poll is `ready` and exactly one device row is written.
2. **Deny and Not you?** The poll answers `error`, nothing is written and `identity` is gone. A second decision gets the `303`.
3. **The complete-URI attack.** The two `OPEN (R1-07 / R8-03, P1-07 claim|migrate)` cases become `FIXED (… attach retired on device code)`: `attachable: false`, and a forced `attachLicense: true` merges nothing. A new `RESIDUAL (R1-07)` case asserts the approved-phish outcome: one seat-checked device, no claim and no migrate.
4. **Forgery.** Each is refused generically with nothing written: no binder, a foreign binder or a cross-site `Sec-Fetch-Site`; a missing, replayed, stale or foreign token; an expired flow; a flow confirmed but not signed in; a request handle or `__Host-pk_req` alone; an altered label.
5. **Races.** Approve against approve, approve against deny, approve against expiry, and a poll during approval each produce exactly one outcome.
6. **Legacy records.** A record with a device id but no `viaDeviceCode` reaches DeviceConfirm and never `activateFromIdentity`. A called-back record with no `approvedAt` answers `pending` and then `timeout`.
7. **Chooser.** A choice sets `approvedAt` atomically, and `cancel` equals Deny.
8. **Other routes.** `/verify` answers start-again with no store read. Neither entry page names a product before the code resolves (B9.3). `authDeviceApprove` fails closed.
9. **The page's output.** No device code, `state` or handle appears in the HTML or the `Location`. The label is escaped. The place comes from `request.cf` only. The mismatch callout shows when the countries differ. The headers are exactly those in §6.3.
