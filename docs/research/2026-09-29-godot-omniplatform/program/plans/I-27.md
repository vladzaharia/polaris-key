## 1. Summary

- **One authorization server per product.** `<origin>/<p>/identity` becomes an issuer shaped like
  OAuth 2.1, with three endpoints:
  - `authorize`: code with PKCE S256, plus `client_id`, `scope`, `nonce` and `login_hint`;
  - one `token` endpoint, where `grant_type` selects code redemption (I-08), token exchange (I-13,
    I-32) or, later, refresh (I-21);
  - a pushed request (RFC 9126, I-15).

  I-04's `redirect/token` and I-21's `oauth/*` tree are never built. I-08 has not shipped, so no
  deployed client changes.

- **One connection concept.** A connection is an upstream OIDC provider at platform or product
  scope. It has DNS-verified email domains (each optionally enforced), an audience and a claim map
  that carries groups.
  - Pocket ID's env trio becomes a seeded platform connection.
  - `oidc.provider: custom` and I-22 become product connections (I-32).
  - Three hand-rolled relying-party copies become one client.
- **The account profile.**
  - "Screen name" is the UI word for `accounts.display_name`.
  - An optional birth date is stored only when the person accepts it, and never sent to an app.
  - Platform terms are recorded, dormant until the owner publishes reviewed terms.
  - Consent can be granted in part.
  - Email code, magic link and passkeys are always available, except for an enforced domain.
- **Credentials and sign-in surfaces.**
  - `pkeyp_` personal tokens carry exactly one scope, packages or admin.
  - The console and `pkey login` use the same card.
  - One table (§2.1) fixes the entry point for every experience.
- **W-ID train:** I-27 → I-09 → I-08 → I-10a and I-10b, with LX-39 as the tail. `licenses.sub`
  and `oidc_config` stop being read in I-32b (release N), and the drops ship in I-32c (release
  N+1).

## 2. Contract

### 2.1 One authorization server per product (amends I-04 §2.5, §2.6, §2.8; I-08 writes WIRE-CONTRACT-V4 §12.5)

**Why now.** I-04 planned two authorization servers:

- `redirect/token`, for I-08;
- a separate OP under `/<p>/identity/oauth/*`, for I-21 (`plans/I-04.md:831-838`).

Neither exists: `I/routes.ts:61-107` has no `authorize`, `token` or `oauth` route. Shaping them
like OAuth now costs nothing, and I-21 then adds OIDC to the same endpoints.

**Issuer.** The issuer is `<origin>/<p>/identity`. I-08 adds `issuer` to discovery's identity
fragment, beside the `authorize` and `token` endpoints.

**Clients.** Layer 1 has no client table.

- `client_id` is the product slug: the product's own public client. It has no secret and must use
  PKCE.
- `ClientRecord` (`shared-protocol/src/identity.ts:73-88`, `I/passthrough/client.ts:33-70`) is
  unchanged. Its `kind` follows the redirect URI.
- I-21 adds registered third-party clients, with confidential `cl_…` ids, by extending
  `ClientRecord` (`plans/PX-W13.md:215-222`).
- Any other value is `invalid_client`.

**`GET /<p>/identity/authorize`** (I-08):

| Parameter                                                                         | Rule                                                                                                                                                                                                                                                                            |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `response_type`                                                                   | Required, `code`                                                                                                                                                                                                                                                                |
| `client_id`                                                                       | Required. Layer 1 accepts only the product slug                                                                                                                                                                                                                                 |
| `redirect_uri`                                                                    | Required. The origin must be in `core.web.origins` and the path in `identity.redirectPaths`, both exactly (I-04 §2.5). I-15 adds loopback, claimed-HTTPS and scheme URIs                                                                                                        |
| `state`                                                                           | Required, 16 to 512 characters                                                                                                                                                                                                                                                  |
| `code_challenge`, `code_challenge_method`                                         | Required. `S256` only                                                                                                                                                                                                                                                           |
| `scope`                                                                           | Optional, space-delimited: `profile` (name and picture), `email` and `cloudSync`. When absent, it is the product's whole `identity.claims` set. Unknown values are ignored. `openid` answers `invalid_scope` until I-21 ships, so no relying party can mistake layer 1 for OIDC |
| `nonce`                                                                           | Optional, at most 255 characters. Kept on the code record for I-21's `id_token`                                                                                                                                                                                                 |
| `login_hint`                                                                      | Optional email, normalised as PX-W18 says. It prefills the card and never verifies anything                                                                                                                                                                                     |
| `name_hint`, `purpose` (`signin` or `attach`), `license_choice` (`card` or `app`) | Polaris extensions: PX-W18's name hint and attach copy, and I-04 §G.2's choice mode                                                                                                                                                                                             |
| `request_uri`                                                                     | From `request` (I-15). Only `client_id` may accompany it                                                                                                                                                                                                                        |

- **Errors the card shows.** A bad `client_id` or `redirect_uri` makes the card render
  `invalid_client` or `redirect_uri_mismatch`, and it never redirects.
- **Errors sent back to the app.** Every later error is
  `302 redirect_uri?error=…&state=…&iss=<issuer>`, with one of:
  - `invalid_request` (this replaces I-04's card `bad_request` for `plain` PKCE);
  - `invalid_scope`;
  - `access_denied` (Cancel, I-04 §F.8);
  - `server_error`.
- **Success** is `302 redirect_uri?code=…&state=…&iss=<issuer>` (RFC 9207). The code lives 60 s
  and is single use in I-02's store. It is bound to the product, `client_id`, `redirect_uri`,
  `code_challenge` and the granted scope.

**`POST /<p>/identity/token`.** The body is form-encoded, the answer is `no-store`, and CORS
answers only `core.web.origins`, without credentials. Layer 1 requires `X-PKey-Device` and the
metadata headers. A JSON body is `invalid_request`.

| `grant_type`                                                 | Parameters                                                                                                                                                                                                                                                      | WP                                                               |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `authorization_code`                                         | `client_id`, `code`, `code_verifier`, and `redirect_uri` (compared exactly when sent)                                                                                                                                                                           | I-08. It replaces I-04's `redirect/token`, which was never built |
| `urn:ietf:params:oauth:grant-type:token-exchange` (RFC 8693) | `client_id`, `subject_token`, `subject_token_type` and `license_choice`. The token type is `urn:ietf:params:oauth:token-type:id_token` for Apple, Google and product connections, and `urn:polaris-key:token-type:<kind>` for Steam, Game Center and Play Games | I-13 and I-32. It replaces I-04 §2.8's JSON `{kind, token}`      |
| `refresh_token`                                              | —                                                                                                                                                                                                                                                               | I-21                                                             |

**A `200` answer** is an OAuth token response. It carries exactly these members:

- `access_token`: the `pkeyt_` device token. This is the activation response's `token` under its
  OAuth name, and it is not repeated as `token`;
- `token_type`: `"Bearer"`;
- `scope`: the granted subset;
- from the activation response (`W/services/license/activation.ts:225-238`): `schemaVersion`,
  `device`, `license` (`null` on a licence-less device), and `keyEntries` only when the flow
  entered a key (§12.2 rule 5);
- `subject`, as on the device-code `ready` answer (I-04 §2.4);
- after a token exchange, also `issued_token_type: "urn:polaris-key:token-type:device"`.

There is no `expires_in` (optional in RFC 6749 §5.1) and no `refresh_token` before I-21.

Two answers from I-04 §G keep their place:

- I-04 §G.4's `{status:"choose", grant, expiresIn, choices}` is unchanged and comes only with
  `license_choice=app`;
- §G.5's `choice/complete` now answers this same token response, so an SDK parses one shape.

**Error bodies.** Here I-04's rule that new routes answer the nested `PolarisErrorBody`
(`plans/I-04.md:723-726`) is amended, for `token` only. RFC 6749 §5.2 requires the flat body
`{"error", "error_description"?}`:

- `400 invalid_request`;
- `401 invalid_client`;
- `400 invalid_grant`;
- `400 unsupported_grant_type`;
- `400 invalid_scope`.

The Polaris refusals on `token` are flat too, as they are on `license/activate`: `403
not_entitled`, `device_limit`, `license_owned`, `key_entry_limit`, and `429 rate_limited` with
`retryAfter`. I-04 §2.8's reserved `403 interstitial_required` with `url` stays reserved for I-13.
It is a flat Polaris refusal on token exchange, and I-13 registers it.

The `choice/*` routes are Polaris JSON routes, not RFC 6749's token endpoint. Their errors stay
nested, as I-04 §G.5 planned, including `400 invalid_grant`. SDKs already parse both shapes.

**`POST /<p>/identity/request`** (I-15, RFC 9126).

- **Body:** the `authorize` parameters, form-encoded, plus `device_name` under the §12.7.1 rules.
- **Answer:** `201` with `request_uri` = `urn:ietf:params:oauth:request_uri:<22 base64url>` and
  `expires_in` = 60. The URI is used once, at `authorize`.
- It replaces the `{request, authorizeUrl}` shape in `plans/PX-W13.md:215-222`.
- `authorize` still mints §12.7.2's browser-bound `rq_` handle.

**Device code** stays on its shipped routes: `auth/device/start` and `auth/device/poll`, which
`devicecode-*.json` pins in six SDKs. `auth/device/start` gains optional `scope`, `loginHint`,
`nameHint` and `purpose` members (I-08).

**What I-21 adds on the same routes:**

- the `openid` scope, which yields an `id_token`: a separate RS256 keyring, `sub` = the pairwise
  subject, `aud` = `client_id`, with the `nonce`;
- `/<p>/identity/.well-known/openid-configuration`, the JWKS and userinfo;
- `refresh_token`, revocation and end-session;
- registered clients.

I-08 deletes "I-21 appends `oauth/authorize`" from WIRE-CONTRACT-V4 §12.8 rule 3
(`WIRE-CONTRACT-V4.md:1406`).

**Sign-in surfaces.** Every experience uses one card and one server:

| Surface                                                | Entry                                                                           | Server | SDK                                   |
| ------------------------------------------------------ | ------------------------------------------------------------------------------- | ------ | ------------------------------------- |
| The portal and key.plrs.im pages                       | The card and the account session                                                | built  | —                                     |
| A product's web app                                    | `authorize`, then `token` (`authorization_code`)                                | I-08   | React (I-10a)                         |
| Desktop and mobile apps                                | `request`, then `authorize` (loopback, claimed HTTPS or a scheme), then `token` | I-15   | All six (I-15)                        |
| A product's TV, console, game, CLI and terminal builds | Device code on the card, with a QR code                                         | I-08   | Built; `signIn.start` in I-10a, I-10b |

| The console                                            | The card in console context, then the account session and a role check (ST-28)  | ST-30  | —                                     |
| The `pkey` CLI                                         | Account device login (PX-W14), which issues a `pkeyp_` token (§2.5)             | ST-34  | `packages/cli`                        |
| Sign in with <Product>, for third-party sites          | `authorize` and `token` with `openid`                                           | I-21   | —                                     |

The console and the CLI act for the **account**, not for a product's pairwise subject. So they use
the account surfaces of the same card, and never a product's `authorize` or `token`.

### 2.2 First automatic licence (D4; amends I-04 §A.4 and delegated decision 3)

This applies when the account has no candidate licence (I-04 §A.1) and the product's policy grants
one.

- The card skips LicenseChoiceStep.
- ConsentStep is then always shown. Its licence line reads "New: <Tier> license, created when you
  continue", and its primary button is the explicit Continue that D22 requires.
- That press mints the licence and binds the device, in that order.
- In app mode no choice is due, so `token` answers the token response.

**Wire: none.** `GET …/licenses` still answers `state: "autoIssue"`.

**What I-08 mints with, before LX-36 and LX-38.** Today the only guard on an automatic mint is
`idx_licenses_sub` (`0001_init.sql:82`), which Discover relies on (`I/portal/discover.ts:470-480`).
It protects only `sub`-keyed rows, and I-04's delegated decision 2 already stops the card's
`sub`-keyed mint. So I-08 builds D4 on primitives that exist when it starts:

- **Policy.** Today's `identityTier` (`I/oidc.ts:790`), in the form P0-20 extracts it
  (`identityIssuePolicy`): the product's `autoIssue` (`oidcDefault` or `both`), or a
  `groupRoleMap` group. The groups are the ones `discoverIdentity`
  (`I/portal/store/obtain.ts:326`) reads from the account's platform link. An email-only account
  has no groups, so only `oidcDefault` can grant it a licence.
- **Mint.** P0-20's `issueLicense(product, holder, via, target, device?)` with an account holder
  writes origin `oidc`, with `account_id` set in the insert, `sub` NULL and no key. I-09's
  `bindSignedInDevice(…, {kind: "create"})` then binds the device in the same press. If P0-20
  ships only the identity holder, I-08 adds the account arm.
- **Uniqueness.** I-08 adds a claim in I-02's store: a new `SingleUseKind` `"license-mint"`,
  addressed by `<product>:` and a peppered hash of the account id. It is written with
  `putArtefact(…, 30, {ifAbsent: true})` (`W/core/singleUse.ts:133`).
  - The press that wins the claim re-reads `rankAnchorCandidates`, mints only if there is still no
    candidate, then deletes the claim.
  - A press that loses mints nothing. It answers I-09's `409 license_choice_required`, and the
    card re-reads `GET …/licenses`. That shows the winner's licence as the one candidate (I-04
    §A.3's one-tap confirm).
  - An unreachable store throws, so the press fails closed and nothing is minted.
  - Discover's `issueIdentityLicense` (`I/portal/discover.ts:456`) takes the same claim and
    re-checks inside it. A Discover add that races a Continue therefore also mints once.

**What LX-38 swaps in.**

- `accessFor(SignInFacts)` (LX-36) replaces `identityTier`.
- The account-keyed `issueLicense` takes the same signature.
- A unique partial index arrives on `licenses(product, account_id)`, filtered by
  `origin = 'oidc' AND account_id IS NOT NULL AND ended_reason IS NULL`. Inserts use
  `ON CONFLICT` and answer the existing licence. The index ships only after LX-38's P0-49
  duplicate report is clean.
- LX-38 then deletes the `"license-mint"` kind, and re-runs I-08's concurrency test against the
  index (its own acceptance).

### 2.3 Connections (I-30 builds them, I-31 adds the console, I-32 adds product scope)

**Fields.**

- `id` and `label`.
- `scope`: `platform`, or `product:<slug>`.
- `issuer`: https only (`isSafeIssuerUrl`). A product connection must also pass
  `OIDC_ISSUER_ALLOWLIST`, which fails closed for new rows.
- `client_id` and a sealed client secret.
- An optional `jwks_uri`, for token-only issuers such as Firebase (I-32).
- `audience`: `customers`, `operators` or `both`. A product connection is always `customers`, so
  only platform connections can be operator connections (ST-28 SM-2). Setting `operators` or
  `both` is a Superadmin-only write with step-up and an L2 confirm (ST-28 G2, built by ST-32).
  Until ST-32 lands, I-30's and I-31's console writes refuse those two values. The `source: env`
  seed is exempt.
- A claim map with three kinds of target:
  - `groups`;
  - the `claims[]` that access rules may name;
  - `name`, `picture` and `birthdate`, which feed only the sign-in's imported profile (see
    Links). None of them is stored on the link.
- `exchange`: product connections only.
- `status`, and `source` (`env`, `console` or `manifest`).

Google, Apple and Steam are built-in connections defined in code. Steam stays OpenID 2.0.

**One relying-party client: `core/oidc/client.ts`.**

- **Discovery and keys.** Discovery goes through the gated fetch (`I/providers/net.ts`). The JWKS
  is fetched through it too, cached, and verified with `createLocalJWKSet`, as
  `I/providers/discovery.ts:238` does.
- **No `createRemoteJWKSet`.** jose's `createRemoteJWKSet` fetches outside the gated door, which
  matters because product issuers are supplied by tenants. Its three call sites go:
  `W/admin/auth.ts:185`, `I/portal/auth.ts:453` and `I/oidc.ts:2214`.
- **Checks.** The client handles PKCE, state, nonce and RFC 9207, and checks `aud` and `azp`
  exactly.
- It replaces three copies that hard-code Pocket ID's paths (`/authorize`, `/api/oidc/token`,
  `/.well-known/jwks.json`):
  - `W/admin/auth.ts:168,185,274`;
  - `I/portal/auth.ts:344,434,453`;
  - `I/oidc.ts:1549,2181,2214`.

  Today a custom issuer that is not shaped like Pocket ID cannot work at all.

- `providers/{google,apple}.ts` move onto it.
- **Gated hosts.** A connection's allowlist is its issuer host and its `jwks_uri` host. Product
  connections also need `OIDC_ISSUER_ALLOWLIST`.

**Redirect URI.** It is `<origin>/callback`, the portal's SSO callback (`I/portal/auth.ts:326`,
`I/portal/index.ts:124`), generalised so that `state` names the connection. The redirect URI
registered at Pocket ID keeps working.

**The rewritten `/callback`.**

- For the seeded Pocket ID row, it first applies `platformSignInPolicy`
  (`I/accounts/platformMigration.ts:139`) exactly as `I/portal/auth.ts:479` does today: `ended`
  refuses, and `linkedOnly` refuses an unknown subject.
- It then hands every connection identity to `beginProviderSignIn` (`I/card/gate.ts:279`). An
  identity whose address is not vouched for therefore reaches the email gate, never an email-less
  account.

**Links.**

- **The key.** `issuer_key` is `portalIdentityIssuerKey(issuer)` (`I/portal/repo.ts:228-230`).
  That is the key Pocket ID links already carry, with one exception: links created before I-01
  are still keyed by the literal `oidc` (`LEGACY_OIDC_ISSUER`, `I/accounts/repo.ts:55`).
  - Today those are re-keyed only at sign-in (`I/portal/auth.ts:496-497`,
    `I/accounts/platformMigration.ts:291-292`).
  - The connection callback keeps that re-key for the platform scope until I-28 removes the
    helpers.
  - `seed-platform-connection`'s dry run counts the rows with `issuer_key = 'oidc'`.
- `tenant_scope` is `''` for a platform connection, and `product:<slug>` for a product connection.
  A product connection's link is recognised only inside that product
  (`I/accounts/signIn.ts:149-152`).
- **What a link stores.**
  - Groups come only from the mapped claim: at most 100 names, each matching `GROUP_NAME_RE`.
    They go into `account_links.groups_json` (migration 0071).
  - A new `account_links.claims_json` holds only the `claims[]` values that access rules name.
  - Both are replaced at each sign-in through that link, in one `UPDATE` that also sets
    `account_links.asserted_at` (ST-28 §2.4: root and rule freshness key on it). `asserted_at` is
    ST-30's column; whichever of I-30 and ST-30 lands second wires it into that `UPDATE`, and
    nothing else writes it.
  - `name` and `picture` keep their existing home, `account_links.profile_json` (migration 0079,
    through `importProfile`).
- **The birth date** is never stored on a link. It rides in the gate record's imported profile
  (I-02's store, 15 minutes) as a FinishStep suggestion. It reaches `accounts.birthdate` only when
  the person accepts it (§2.4).
- `account_sessions.amr_json` records `connection:<id>`, which ST-28's strong-method rule reads.

**Domains.**

- **Proof.** A TXT record at `_pkey-challenge.<domain>` must hold
  `pkey-domain-verification=<token>`, with one token per connection and domain. The Worker reads it
  over DNS-over-HTTPS (`https://cloudflare-dns.com/dns-query`, JSON). That host is an entry on the
  gated fetch's allowlist and is used for nothing else.
- **Exact domains only.** A verified `example.com` does not cover `sub.example.com`, which needs
  its own TXT record.
- **Re-check.** The existing cron re-checks every domain daily. An answer without the token
  unverifies the domain at once. Resolver errors keep the current state for 72 h, then unverify it.
- **Fail closed.** An unverified domain does not route, vouch or enforce.
- **Ownership.** Each `(scope, domain)` has at most one verified owner.

**Routing** happens in `POST /api/signin/email/start`.

- **When it routes.** The address's domain is verified by a connection whose audience covers the
  surface. In product context the product's connections come first, then the platform's.
- **The answer** gains `next: {kind: "sso", connection: {id, label}, enforced}`. No email goes out
  until the person picks the code, and on an enforced domain they cannot pick it.
- **Enumeration.** The answer depends on the domain only, never on whether an account exists
  (`I/card/emailSignIn.ts:28-35`). Today's Turnstile check and rate limits stay.
- **Buttons.** Every active platform connection with a customers audience also gets a
  "Continue with <label>" entry on the card.

**Enforce.** On an enforced domain, the card never sends that domain's addresses an email code or
a magic link, and the identifier step offers only the connection. The one exception is the join
offer's proof code, which stays until the owner answers Q1 (Owner decisions). Passkeys and the
other links already on an account still sign it in. Everywhere else, email code and magic link
are always offered. I-29 retires the per-product toggles only once this exists.

**Trust in `email_verified`.** `providerVouchesForEmail` (`I/providers/vouch.ts:29-41`) today
vouches for any provider's address except Google's (line 35).

- **The narrowed rule** is a new `connectionVouchesForEmail(connection, identity)`. Only
  `beginProviderSignIn` uses it, on the card's connection buttons and routing, and on the
  rewritten `/callback`. Every one of those paths ends at the email gate:
  - a platform connection vouches only for addresses inside its verified domains;
  - a product connection never vouches, so the email gate's code applies (I-32);
  - the built-in providers are unchanged.
- **The legacy engine keeps today's rule.** `claimPlatformSubject`
  (`I/accounts/platformMigration.ts:297-300`) keeps `providerVouchesForEmail({kind: "oidc"})` for
  the env-path Pocket ID until I-32b retires that engine. It is reached from the legacy product
  callback (`I/oidc.ts:2378`), which has no email gate. Narrowing it there would land each
  member's claim on an account with no email. That would mean:
  - no join offer, so a second account for anyone who already has an email account;
  - no LX-26 association by verified email;
  - an inflated email-less count, which drives the I-17 and I-32b sunsets and C-52's Discover.

  djdl's members use consumer domains, so verifying a domain would never repair this.

Auto-linking is Q1.

**Pocket ID.** A P0-49 job (§6) seeds one platform connection from `PLATFORM_OIDC_*`
(`W/platformOidc.ts:36-38`):

- **The row.** `source: env`, and groups from the `groups` claim.
- **Audience.** `both`. It becomes `operators` when `PLATFORM_OIDC_MIGRATION` is `operators-only`,
  or once the sunset date has passed. I-32b retires both names. It first writes the row's audience
  once from their last value, and records that in P0-24's ledger. From then on, the audience is a
  plain column, changed only in I-31's console, by a Superadmin (ST-28 SM-2).
- **No domains.** On the gate paths (the card and `/callback`), Pocket ID stops vouching until the
  owner verifies a domain. A new identity, or an account with no confirmed email, sees one email
  code at the gate. An account that has already confirmed its email signs in as before
  (`I/card/gate.ts:316-319`). The legacy product callback is unchanged (see above).
- **The env trio.** From I-30's release, the seeded row is the connection's only source: the
  card, `/callback` and the console read the row, not the env. There is no override window
  (owner, 2026-10-07). The legacy engine (`I/oidc.ts`, I-17's report) keeps reading the trio until
  I-32b deletes the engine. I-32b then removes the three names from `Env`, the platform inventory
  and `adminOidcConfig`'s fallback (`W/platformOidc.ts:45-47`). It first confirms that
  `ADMIN_OIDC_*` is set in production, because `console-idp` must no longer fall back.
- **The I-17 switch.** `PLATFORM_OIDC_MIGRATION` and `_SUNSET` keep their meaning for the legacy
  engine until I-32b. The owner step `PLATFORM_OIDC_MIGRATION=claim`, due before LX-38, stands.
- **No console seed.** `ADMIN_OIDC_*` is not seeded: it is ST-30's break-glass.

**`SignInFacts`.** This Core type is the only input to `accessFor()` (LX-36) and to
`console.access` (ST-32). It holds:

- the method (the `amr`);
- each verified email, with how it was verified (`code`, `provider` or `connection:<id>`);
- the groups and the mapped `claims[]`, each per connection.

Group and claim rules are issuer-bound: every one names its connection.

**Secret custody.**

- A platform connection seals its secret in its own row, under `PLATFORM_KEK`, with the AAD
  `pkey:v2:_platform:identity-connection:<id>`. This is the `platform_credentials` pattern
  (`W/core/platformCredentials.ts:18-22`).
- The built-ins follow the same rule from I-31: each gets an `identity_connections` row whose `id`
  is its kind (`google`, `apple`, `steam`). The row seals the credential set its module needs:
  Google's client id and secret; Apple's services id, team id, key id and private key; and Steam's
  Web API key. The code keeps their endpoints.
- **The `SIGNIN_*` names go in I-31's release** (owner, 2026-10-07: no windows). A P0-49 job,
  `seed-builtin-connections`, seals each provider's env values into its row. The Worker then
  stops reading the names, and `Env` and the platform inventory drop them. The lead deletes the
  Worker secrets once a later release is the rollback target, so a revert of I-31 still finds
  them.
- A product connection names a product secret, as `oidc_config.client_secret_secret` does today
  (`I/oidc.ts:345-352`).
- P0-28's single store absorbs all three.

### 2.4 The account profile, consent and terms

**Screen name.** It is the UI word for `accounts.display_name` (`0068_a_accounts.sql:28`). Only
the copy keys change (`signin.register.*`, `portal.profile.*`). An account has one public name,
and it is not unique. Apps receive it as `name`.

**Birth date** (I-33).

- **Columns.** `accounts.birthdate` (`YYYY-MM-DD`) and `birthdate_source` (`user` or
  `connection:<id>`), both optional.
- **Where a value comes from.**
  - A connection's mapped `birthdate` claim is carried only in the gate record (§2.3).
  - FinishStep shows the field only when a source offered a value.
  - The value is written only when the person accepts it there.
  - The account profile can add, change or remove it.
  - Nothing else stores it: not `account_links`, not the audit, not the sign-in flow once it ends.
- **Where it never goes.** No consent item, device response, developer API, Users page, developer
  export or `id_token` carries it. The person's account profile and their full export (I-11) are
  the only places that show it.
- **Not built yet.** Age booleans, `minimumAge` and `identity.minimumAge` wait until a product
  gates content.

**FinishStep** (the API in I-33, the UI in PX-21). One finish API serves both new-account paths,
extending the state machine in `I/card/gate.ts`. The steps:

1. The email, with a code unless the provider or connection vouches for it.
2. The screen name, with chips for each source.
3. The picture.
4. The birth date, as above.
5. The terms.

**Terms.**

- **Product terms.**
  - The setting is `identity.terms {version, url?}`, and `url` defaults to the listing's `eulaUrl`
    (`W/core/storefront/listingModel.ts:131-133`).
  - The listing's `privacyUrl` is linked beside it. A privacy notice informs: it is not a
    contract, so it gets no acceptance row.
  - Acceptances are stored as today, in `account_terms_acceptances` (migration 0091), whose single
    `url NOT NULL` holds the terms URL.
- **Platform terms.**
  - The platform setting is `identity.platformTerms {version, termsUrl, privacyUrl}`.
  - An acceptance is a `_platform` row. Its `url` is `termsUrl`, and `privacyUrl` is linked
    beside it on the same rule.
  - The setting is unset by default, so no step shows and no row is written until the owner
    publishes reviewed terms (Q2; `docs/legal/README.md:3-4`).

**Consent** (I-34).

- **The declaration.** `identity.claims {required, optional}`, over `name`, `picture`, `email` and
  `cloudSync`. The default makes all four optional.
- **The step.** ConsentStep shows toggles for the optional items inside the requested `scope`, and
  Continue posts the granted subset.
- **The contract text.** I-34 amends WIRE-CONTRACT-V4 §12.7.3, additively:
  - the `profile` item gains `required` (the subset of its `claims` the app requires);
  - the `cloudSync` item gains `required: boolean`;
  - the Continue body carries `granted`, the optional items the person left on.
- **`scopeHash` does not change.**
  - Its canonical form stays `{"claims":[…],"services":[…],"v":1}`
    (`I/passthrough/routes.ts:78-89`).
  - `cloudSync` stays in `services`, although `identity.claims` lists it. Moving it into `claims`
    would change every hash and ask everyone again.
- **Storage.**
  - `account_product_grants.claims_json` (`0068_a_accounts.sql:134-141`) holds the granted
    subset.
  - `scope_hash` (migration 0087) still hashes the set the person was **asked**.

  So a declined item is not asked again, and today's grants (all granted) need no re-ask and no
  migration.

- **What reaches the app.** The device-code poll's `identity` and the `token` answer's `scope`
  carry only granted items (D19).
- **Cloud Sync.** U-05 refuses sync for an account that declined `cloudSync` for that product.
- **Connected apps.** A new portal page changes or revokes a consent through I-11's revocation
  hook.

### 2.5 Credentials (F-33 and ST-34; AGENTS.md rule 8 gains `pkeyp_`)

- **Format.** A token is `pkeyp_` and 32 random bytes in base64url. It is stored as an HMAC under
  `KEY_HASH_PEPPER` (F-20's pattern), shown once, and listed and revocable by the person and by
  Superadmins.
- **One scope per token.**
  - `packages:read`: 90 days by default, at most 365.
  - `admin`: at most 30 days. Minting needs ST-28's step-up, and the token is bounded by the
    holder's roles **at use time**.

  The registry host refuses `admin` tokens. The admin API accepts only `admin` tokens, and only as
  bearer.

- **`pkey login`.**
  - The CLI starts PX-W14's account device login (`I/portal/deviceLogin.ts:1-12`) with
    `purpose: "cli"` and a scope.
  - Approval happens on the card. An `admin` request always needs step-up, and the approval page
    names the CLI, the requesting device and the scope.
  - The poll then answers `{token: "pkeyp_…", scope, expiresAt}` instead of setting a session.
  - An `admin` token from `pkey login` lasts 7 days and is kept in the OS keychain.
  - `pkey feeds setup --write` asks for `packages:read` the same way (C-29).

**The edge-mint approval basis.** `identityWidened` (`W/core/edgeMintApproval.ts:176-190`)
compares an approval's `oidc_provider`, `oidc_issuer`, `oidc_client_id` and
`oidc_group_role_map_json` with the product's `oidc_config` row. That leaves two bad options:

- **Remove the read**, and every existing approval mismatches, so edge mint stops.
- **Drop the comparison**, and approvals come silently unbound from the inputs that now decide
  issuance.

- **LX-36: the policy half.** `accessFor()` already lists edge-mint approval as a consumer.

  connections as sorted `{id, issuer, client_id, exchange}`, and replaces the provider, issuer and
  client comparisons. Platform connections stay out of it, as the env-held Pocket ID is today:
  only platform admins change them, and a tenant push cannot.
- **What still invalidates an approval.** A new or changed product connection, or a widened rule,
  invalidates it as before. The sweep in `invalidateWidenedEdgeMintApprovals` keeps running.
  `packages/docs/src/content/docs/services/config/edge-mint.md:171` changes with each half.

## 11. Risks, what is left out, and open questions

**Risks.**

- **Pocket ID stops vouching on the gate paths.** Until a domain is verified, a new Pocket ID
  identity at the card or `/callback` sees one email code at the gate. That is a deliberate
  tightening, and it is announced in the I-30 release notes. The legacy product callback keeps
  today's rule until I-32b, so I-17's claims keep their email.
- **The `/callback` rewrite** carries the console and the portal at once. It is covered by I-30's
  tests and by a code revert (the env trio stays set until I-32b). There is no env override
  window (owner, 2026-10-07).
- **Flat errors on `token`** differ from the nested body other new routes use. SDKs already parse
  both shapes (`device_limit`).
- **The interim claim** (§2.2) serialises one account's first licence per product for at most
  30 s. A store outage refuses the press rather than risking a second licence.

**Deliberately left out:**

- RFC 8628's grant on `token`: device code stays on its shipped routes;
- RFC 8414 metadata, `id_token`, refresh and registered or dynamic clients: these are I-21's;
- SCIM and deprovisioning: enforce does not revoke the links or sessions an account already has;
- age booleans and `minimumAge`;
- a second, "real" name, and unique screen names;
- a Policies page, and per-product method toggles;
- auto-linking through product connections;
- JSON bodies on `token`;
- a separate authorization server for the console or the CLI.

**Questions.** Each is answered in
[Owner decisions](#owner-decisions-delegated-to-claude-2026-10-08) at the end.

1. **Auto-link through a verified domain.** This narrows the owner's 2026-10-04 rule "never by
   email match".
   - **Why it comes up.** On an enforced domain, an email-only account cannot join: the join's
     proof is an email code, and enforce forbids sending one.
   - **Recommendation: yes, narrowly.** It applies only to a platform connection, a DNS-verified
     domain, and an exact match on an address verified on exactly one account. The person is
     emailed "<Org> SSO was added as a way to sign in", and the link is audited. It never applies
     to a product connection.
   - **Alternative.** Keep the join offer, and allow the join's proof code even on an enforced
     domain.
2. **Platform terms.** `docs/legal/README.md:3-4` says the drafts must not be published.
   - **Recommendation:** I-33 ships the mechanism dormant (`identity.platformTerms` unset). The
     owner sets it after a legal review, which is a new owner step. Backlog I-33's acceptance
     "Platform terms acceptance recorded for every new account" becomes "…once
     `identity.platformTerms` is set; none is shown or recorded while it is unset".
   - **Alternative:** record acceptance of the drafts now, at a legal risk.
3. **End users on Pocket ID.** Should the I-17 sunset still end customer sign-in through Pocket ID?
   - **This changes a recorded decision, and an owner statement.** README §8's D2 records "the
     end-user Pocket ID sunset only after Pocket ID runs as a connection and djdl's group mapping
     lives in `license.access`". The I-17 brief records the owner's "end users leave Pocket ID,
     operators stay" (`wp/I-17-pocket-id-migration.md:44`). The recommendation drops that sunset
     instead of deferring it.
   - **Recommendation: no sunset.** Pocket ID stays a connection with audience `both`, and
     `PLATFORM_OIDC_SUNSET` is never set. djdl's group rule (`products/djdl/product.json:35-47`)
     keeps working in `license.access`. The operator/customer split now lives in RBAC and the
     strong-method rule.
   - **Alternative: keep D2's sunset,** after LX-36. djdl's members keep the automatic licences
     they already have, but a new member then needs an email-domain rule or a manual licence.
4. **Who writes the `identity:` manifest block.** The backlog has I-35 write all of it, which
   leaves `redirectPaths` and `terms` unsettable from I-09 until I-35, which waits for LX-36.
   - **Recommendation: I-09 writes the paths of the settings it registers** (§3). That is I-09's
     approved §3 in the final key shape, and `I/settings.ts:104-107` already expects it. I-35
     adds `methods`, `connections` and `claims`.
   - **Alternative: keep the split.** The web redirect then works only for products whose paths
     are set by a console route that does not exist yet. ST-05 would have to widen the settings
     API to keys without a manifest path, or the redirect stays unusable until I-35.
