## 1. Summary

- **The feed carries content.** `packSets` holds P4-12's rows for the app deliverable (one row per
  group, keyed by `contentApi`, platform, engine and variant), a release table, deduplicated sets
  and per-outlet narrowing and gates. `packFloors` holds the effective floor per pack and live
  level with the pack's version scheme. `revocations` lists the revocation records in force by
  hash, with their targets. A device composes its set from one row per group, then its pins and
  holds, and resolves nothing.
- **Revocation is a CI-signed `kind: revocation` release record** naming the revoked pack record
  by hash and an optional replacement. Only a pinned release key verifies it. The Worker cannot
  sign one, so it can withhold content but never condemn or substitute it. Ingest also yanks the
  target, and resolution skips revoked releases.
- **The decision gains `packs`, `prestage`, `content-floor` and `revoked-content`.**
  `blocked {revoked-content}`, for a **required** pack only, is the first answer that gives the
  boot value `required`. Floors still never stop play; a revocation of required content can
  (decision 4, which amends P3-01 decision 1 and the AT-3 invariant).
- **No existing verdict moves.** Every new member is parsed by a function beside the claims. A
  malformed one makes that member unusable and never refuses the feed or record. So three existing
  cases keep their verdicts: `feed-valid-unknown-fields-ignored` (`packSets: []`),
  `record-valid-kind-revocation-verify-only` (a revocation with `deliverable: "app"`) and
  `stamp-forward-members-ignored` (a malformed hold). The corpus is append-only: new sections,
  three appended `feedCases`, four appended `stampCases`, and two vocabulary arrays extended.
- **Split.** P4-13 does the contract, `client-core` (Node, React), the corpus, the Worker and
  the CLI. Python and Swift move to P4-23 (after P4-07), and Godot to P4-24 (after P4-08). The
  critical path drops from 9.5 to 9 weeks, and P4-13 leaves it (§8.3).

## 2. Contract

### 2.1 Versions, and what a pre-P4-13 client does

V4 §2.4 lists `packSets`, `packFloors` and `revocations` as reserved members that "a v4 verifier
ignores". §2.5 lists `revocation` as a reserved kind, "verified, never acted on". §2.5.2 lists
`content.holds` as reserved and ignored. P4-13 fills these slots. It adds **no claim**, because a
claim would flip the three existing cases above, and a malformed content member must never stop app
updates. Each new member has a **usability function** instead, in the pattern of V4 §3.2 for pack
records:

- `feedContent` covers the three feed members;
- `revocationOf` and `verifyRevocation` cover the revocation body;
- `holdsOf` covers `content.holds`.

Integer members inside them follow the §3.1 token rule, read from the verifier's
`nonWireIntegers`. A failure makes that member unusable, the way it does in a side object (§2.6);
it is never a claims step.

`selector` gains no key, because a v4 client refuses any selector key it does not know. The
payload cap stays 65,536 bytes. **`PROTOCOL_VERSION` stays 4.**

**Clients already in the field.**

- **v3 SDKs** are untouched.
- **v4 SDKs that predate P4-13** (P3-04 to P3-08, and P4-06's Node `PackEngine`) behave as
  follows:
  - They verify every new feed byte for byte as today; the three new `feedCases` prove it.
  - They never fetch a revocation, and **they keep mounting a revoked release until the host
    upgrades its SDK**.
  - They never take a compatible pack from the feed, so they run pinned packs only, as before.
  - They see the yank that ingest writes only as a release that is no longer served.
- **Python, Swift and Godot** build on P4-13's regenerated constants: `packs`, `content-floor`
  and `revoked-content` join their enums. No P4-13 code path produces those values in those SDKs
  before P4-23 and P4-24 (§5).

### 2.2 The feed's content members (V4 §2.4, new §2.4.1, [C] via `feedContentCases`)

```jsonc
"packSets": {
  "releases": { "<recordSha256>": { "pack": "diceroll.foes", "version": "1.3.4", "seq": 12 } },
  "sets":     { "<packSetId>": ["<recordSha256>", …] },          // members sorted by pack-id bytes
  "rows": [ { "contentApi": 3, "platform": "android", "engine": "godot-4.4", "variant": { "texture": "astc" }, "set": "<packSetId>" } ],
  "outlets":  { "<outletId>": { "pinned": ["diceroll.foes"],
                                "gates": { "<recordSha256>": { "halted": false, "rollout": { "bp": 2500, "salt": "<32 hex>" }, "fallback": "<recordSha256>" | null } } } }
},
"packFloors":  [ { "pack": "diceroll.foes", "contentApi": 3, "minVersion": "1.3.4", "versionScheme": "semver" } ],
"revocations": [ { "record": "<sha256>", "pack": "diceroll.foes", "target": "<sha256>", "version": "1.3.3", "seq": 10 } ]
```

`feedContent(doc, nonWire) → {packSets, packFloors, revocations}` returns each member parsed, or
`null` when it is absent or unusable. All three are independent: an unusable `packSets` leaves the
floors and revocations in force. A member is unusable when any rule below fails. Unknown members
are ignored at every level.

| Member        | Rule (all patterns whole-string, lengths in bytes, V4 §3.3)                                                                                                                                                                                                                                                                              |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packSets`    | an object with `releases`, `sets`, `rows` (all required) and an optional `outlets`                                                                                                                                                                                                                                                       |
| `releases`    | an object; each key is 64 lowercase hex; each value is `{pack: a pack id (isPackId), version: V4 §2.5's version pattern, seq: integer ≥ 1}`                                                                                                                                                                                              |
| `sets`        | an object; each key is 64 lowercase hex; each value is an array of strings, each a key of `releases`, with no pack named twice in one set                                                                                                                                                                                                |
| `rows`        | an array of `{contentApi: integer ≥ 1, platform: FEED_PLATFORM_PATTERN, engine: "" or ENGINE_PATTERN, variant: 0–4 members (VARIANT_AXIS_PATTERN names, VARIANT_VALUE_PATTERN values), set: a key of sets}`. (contentApi, platform, engine, variantKey(variant)) is unique. When `selector.platform` is set, every row has that platform |
| `outlets`     | absent, or an object keyed by `OUTLET_ID_PATTERN`. Each value is an object: `pinned` is absent or an array of unique pack ids; `gates` is absent or an object keyed by keys of `releases`, each `{halted: boolean, rollout?: {bp: integer 0–10 000, salt: 32 lowercase hex}, fallback: null or a key of releases}`                       |
| `packFloors`  | an array of `{pack, contentApi: integer ≥ 1, minVersion: version pattern, versionScheme: string}`, with (pack, contentApi) unique. An entry whose `versionScheme` is not in `FEED_VERSION_SCHEMES` is **ignored** (a forward value), not fatal                                                                                           |
| `revocations` | an array of `{record: 64 hex, pack: a pack id, target: 64 hex, version: version pattern, seq: integer ≥ 1}`; `record` is unique                                                                                                                                                                                                          |

The pack-part integer pointers, decided by the token rule, are:

- `/packSets/releases/*/seq` (minimum 1);
- `/packSets/rows/*/contentApi` (1);
- `/packSets/outlets/*/gates/*/rollout/bp` (0, at most 10,000);
- `/packFloors/*/contentApi` (1);
- `/revocations/*/seq` (1).

A set's key is the `packSetId` of its members. The Worker and the generator assert that; clients
do not check it.

**What the Worker puts there** (§6.3):

- **Rows.** The stored `release_sets` rows of `appDeliverable: "app"` on the canonical channel.
  An `unsatisfied` pack is simply absent from its row. `unsatisfied` itself is **not on the
  wire** (decision 6); P4-15 reads it from the hook.
- **Floors.** For each live level, `max(level-free min_supported, release_pack_floors)` per pack
  deliverable, pinned packs included.
- **Narrowing.** `pinned` lists the compatible and standalone packs whose transport on that
  outlet cannot float (`TRANSPORT_FLOATS[t] === false`). Today that is only `play-pad`.
- **Gates.** Per-outlet pack rollouts and halts are composed by P4-14. P4-13 emits none, but its
  rows pin what they mean.

### 2.3 The revocation record (V4 §2.5, new §2.5.3, [C] via `revocationCases`)

A `pkey-release+jws` with `kind: "revocation"`. It is **signed in CI by a release key**, the same
key `pkey release publish` uses (`PKEY_RELEASE_KEY`). A product key cannot sign one: §3.5 step 13
refuses a release key whose bytes are in the product trust set. A delegated content key cannot
either (P4-19 adds that refusal). The common claims are unchanged; `version` and `seq` are the
**target's**, so the record names exactly what it revokes:

```jsonc
{
  "schemaVersion": 1,
  "aud": "diceroll",
  "deliverable": "diceroll.foes",
  "kind": "revocation",
  "version": "1.3.3",
  "seq": 10,
  "issuedAt": 1760000000,
  "revokes": "<64 hex: the revoked pack record's hash>",
  "replacement": { "sha256": "<64 hex>", "seq": 11, "version": "1.3.4" }, // optional, same deliverable
  "reason": "Exploit in foes spawn tables",
} // 1–512 bytes, display only
```

`revocationOf(doc, nonWire)` is usable when:

- `deliverable` is a pack id (revoking an app build is License's compatibility window, not this);
- `revokes` is 64 lowercase hex;
- `replacement` is absent, or `{sha256: 64 hex and not equal to revokes, seq: integer ≥ 1 by token, version: version pattern}`;
- `reason` is a string of 1 to `REVOCATION_REASON_MAX_BYTES` (512) bytes.

`builds` and `content` are ignored.

`verifyRevocation(jws, {releaseKeys, productTrust, expectedAud, entry})` runs these steps:

- §3.5 steps 12–14 with `entry.record` as the pin hash;
- step 15 with pin `{kind: "revocation", deliverable: entry.pack, version: entry.version, seq: entry.seq}`;
- a new step 16, `revocation`: `revocationOf` is usable, and `revokes === entry.target`.

A replacement is verified as a pack record with
`verifyReleaseRecord(…, {expectedHash: replacement.sha256, pin: {kind: "pack", deliverable, version, seq}})`.
A record of another deliverable fails `cross-check`. The replacement is **usable** when it
verifies, is not itself revoked, and `selectVariant` picks a variant for the host (engine and
axes). The contentApi range is guaranteed at ingest (§6.2), never checked by a client.

**Revocations are permanent; a later one may supersede the replacement.** CI may sign a further
revocation of the same target that adds or changes `replacement` (or `reason`). It can never
remove the revoked status: there is no un-revoke, and a wrong revocation is fixed by a newer
release. Among revocations of one target, the **newest `issuedAt` wins** (ties by record hash
bytes, higher wins) on the Worker (§6.2 updates the row) and on the device (§2.5 step 11
re-fetches when `entry.record` differs from the stored one, and replaces the stored entry only with
a verified revocation of the same target that `newerRevocation` ranks above the stored one).
**`newerRevocation(a, b)`** in client-core `record.ts` (ported in every SDK: `newer_revocation`,
`newerRevocation`, `PKeyRecord.newer_revocation`) returns the winner of two verified revocations
of one target: the higher `issuedAt`, else the higher record hash by bytes; the Worker uses the
same function. A device keeps every target it has verified as revoked, up to 256 (§2.5), so a
Worker that later withholds the revocation cannot resurrect the target.

### 2.4 Holds (V4 §2.5.2)

`holdsOf(content, nonWire?) → ContentHold[] | null` reads holds as follows:

- `holds` absent reads `[]`.
- Otherwise it is an array of 0–256 entries, each
  `{pack: a pack id, unique and not pinned, release {sha256, seq ≥ 1 by token, version}, reason?: string}`.
- Anything else reads `null`, which means unusable: the device then takes **no feed target for any
  unpinned pack** (decision 9).

The hold type is P4-12's `ContentHold`, **moved** from `shared-manifest/src/descriptor.ts` to
`@polaris-key/protocol/packs` and re-exported by `shared-manifest` under the same name, so there
is one type (`client-core` cannot depend on `shared-manifest`). Holds reach a device in its
**content stamp**. The stamp is the record's `content` (P4-01 decision 25). `parseContentStamp`'s
result is **unchanged**; the caller applies `holdsOf` to the parsed stamp separately (the stamp's
own `nonWireIntegers` give the token rule). CI writes them with
`pkey release content-stamp --hold <packId>@<version>[=<reason>]`, resolved through the uploads
preflight as `--pin` is (§6.5).

### 2.5 Client order: verifying and applying content (V4 §3.4 steps 10–14, informative; P3-05's `runUpdateCheck`)

10. `feedContent` over the committed feed.
11. **Relevant revocations.** Let H be:
    - the device's active pack records (installed or embedded, from the pack state);
    - its stamp's pins and holds;
    - the feed targets that §2.6 selects, gate fallbacks included.

    For each `revocations` entry whose `target` is in H, and that is either not yet stored or
    stored with a different `record` (a superseding revocation, §2.3):
    - fetch `release.endpoints.record` by `entry.record`, at most `MAX_FEED_REVOCATIONS` (64) per
      check;
    - run `verifyRevocation`;
    - on success, store it (below) when the target is new, or when its `issuedAt` is newer than the
      stored one's.

    A failed fetch retries at the next check. A failed verification is ignored and logged, and is
    never trusted.

12. For each stored revocation whose target is in H and that names a replacement: fetch it,
    verify it, and run `selectVariant`. The result is `replacementUsable`. **A failed replacement
    fetch retries at the next check like a failed revocation fetch**: until the replacement is
    fetched and verified, it is neither usable nor judged unusable, and the decision treats it as
    not yet available (so a required pack still blocks, C27, until it arrives; the Worker can delay
    it, §9's AT-3 line). Only a replacement that fetched and failed verification or `selectVariant`
    is `replacementUsable: false` for good.
13. The rollout bucket for each gate `salt`, with P3-01's formula.
14. `decideUpdate` with `content` (§2.6).

**Applying a `packs` answer.** The boot's FETCH (P4-06's `runBootFetch`) installs the entries of
`packs.install` whose pack is `required` or `essential` before mount, with the usual consent and
progress events; it installs the other entries in the background (activation per the pack type:
`hot` now, `restart` next boot). Packs in `packs.revoke` are deactivated and never mounted.

**Persistence: a sibling document, `revocations.json`.** Revocations live beside P4-06's pack
state, never inside it, so an unparseable `state.json` cannot lose them and a lost revocation file
cannot touch the install state. The document is
`{v: 1, revoked: {[targetSha256]: {jws, pack, version, seq, record, issuedAt}}, relearn: [packId]}`:
each entry holds the winning revocation's compact JWS verbatim, the pin it was verified with (the
feed entry's `pack`, `version`, `seq`), its hash and its `issuedAt`. It has its own atomic replace
(temp + rename, or the host's equivalent) and P4-06's hardening, through the same `PackStorage`
seam with a second key:

- **Written only with a first entry.** `revocations.json` is created when the first entry is
  stored, never as an empty document. In the same atomic write sequence the engine sets
  `revocationsStored: true` in P4-06's `state.json` (written first, then the sibling file; a crash
  between them leaves the flag set and the file absent, which reads as the empty document). **A
  product with no revocations always has no such file and no flag.** An absent file is the empty
  document.
- **Unreadable `revocations.json`** (the store cannot read it): the same rule as an unreadable
  `state.json`. The engine writes nothing to it for the life of the process, mounts as P4-06 does,
  and refuses only an embedded baseline that a feed verified in this process lists as a verified
  revocation target. For refusals while offline it reads `state.json`'s flag: when
  `revocationsStored` is `true`, it refuses the **embedded mount** of every pack in the stamp's
  `pins` and `embeds` (`pack-revoked`, detail `relearn`); when the flag is absent, it refuses
  nothing.
- **Torn `revocations.json`** (it exists but does not parse): quarantined as P4-06 does, then
  replaced by a fresh file whose `relearn` holds every pack in the stamp's `pins` and `embeds` (and
  whose `revoked` is empty). From then on only the `relearn` rules below apply.
- **Parsed per entry.** On load each entry is re-verified with `verifyRevocation` against the
  **currently pinned release keys** and the stored pin (`target` = the map key, `record` = the
  stored hash). A failing entry is dropped alone. When the failure is a key that is no longer
  pinned (the key-rotation recovery lever for a stolen release key), the target is simply
  forgotten. For **any other** failure (bad JWS bytes, a pin mismatch, an unparseable entry), the
  entry's `pack` is added to `relearn`.
- **`relearn`** is persisted. It is cleared, per pack, only when steps 10–12 succeed on a fresh,
  network-verified feed **whose `revocations` member is present and usable** (the device has
  re-learned every revocation that feed lists for that pack's targets); a feed that omitted
  `revocations` (size step 4, §6.3) or carries an unusable one clears nothing. `recoverState()`
  clears it wholesale. While a pack is in `relearn`, offline, the
  device refuses that pack's **embedded** mounts (`pack-revoked`, detail `relearn`); downloaded
  installs of it mount only if their record hash is not in `revoked`. A `required` pack in
  `relearn` therefore blocks offline (it was revoked once), consistent with decision 4.
- **Bounded, never by H.** Entries are kept **regardless of H** (a target leaving H is still
  revoked, and a later reinstall or baseline must still be refused), up to
  `MAX_STORED_REVOCATIONS` = 256 targets. Beyond the cap the oldest by `issuedAt` is dropped first
  (its pack is **not** added to `relearn`: dropping at the cap is deliberate). Stated in AT-3:
  more than 256 revocations can push an old one out of a device's memory.
- **Unreadable `state.json`** (P4-06's own case) keeps P4-06's behaviour exactly: P4-06 does not
  rebuild state from a feed and writes nothing while the state is unreadable, and mounts as it does
  today. P4-13 adds one rule only: within the process, an embedded baseline is refused when a feed
  **verified in this process** lists its record hash as a revocation target and the revocation
  verified (steps 10–11). Residual: with both `state.json` unreadable and no network, a revoked
  embedded baseline that `revocations.json` does not list can mount; the threat model states it.
- **`recoverState()`** clears `relearn` and releases a quarantined `revocations.json` (the held
  text is discarded, as P4-06 does for `state.json`), after which revocations are re-learned from
  the next feed.
- **Amendment (implementation review, recorded in the brief's corrections).** `relearn`, and
  `revocationsStored` with an unreadable `revocations.json`, refuse embedded mounts at **every
  boot, online or offline**, not only offline: online the pack is fetched instead, and when no
  copy can be fetched the engine raises `pack-revoked` (detail `relearn`). `relearn` clears once
  step 11 has fetched, verified and stored every revocation of the pack whose target is in H; an
  entry for a release outside H never keeps it set.
- **No revocations, no change.** A product that has never had a revocation has no
  `revocations.json`, no `revocationsStored` flag and no `relearn`, so no rule above can refuse a
  mount: its devices mount, activate and boot **exactly as P4-06 does today**, offline included,
  even when the store cannot read the (absent) sibling file.

The `PackEngine` (and the P4-23 and P4-24 engines) **refuses to activate or mount a release whose
hash is in `revoked`** (new client code `pack-revoked`). This covers embedded baselines and
pinned packs. The boot's FETCH treats such a pack as missing.

### 2.6 The update decision (V4 §11.1; P3-01 §2.8 extended)

**Input.** `UpdateDecisionInput` gains an optional `content`. When it is absent, every v4 rule and
answer is exactly P3-01's (all 65 rows unchanged).

| `content.*`   | Type                                                                                                                                        | Source                                                        |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `stamp`       | `AppContent` with `holds` (`holdsOf`; `null` when unusable)                                                                                 | the running build's content stamp                             |
| `active`      | `{[pack]: {sha256, version, seq}}`                                                                                                          | the pack state's active installs, embedded baselines included |
| `axes`        | `{[axis]: string[]}`                                                                                                                        | the host's variant preferences (`VariantPrefs.axes`)          |
| `revocations` | `[{target, pack, replacement: ReleasePin \| null, replacementUsable: boolean}]`, **one entry per target (the winner of `newerRevocation`)** | the stored, verified revocations (§2.5 step 12)               |
| `buckets`     | `{[salt]: integer \| null}`                                                                                                                 | §2.5 step 13                                                  |

The decision stays pure and synchronous: the caller does every fetch, hash and signature check.

`replacementUsable` is false while a replacement is still unfetched (§2.5 step 12 retries it), so
the decision blocks until it arrives rather than judging it unusable.

**Row selection.** The level L is `stamp.contentApi`, the platform is `installed.platform`, and
the engine E is `installed.engine ?? ""`.

1. Candidate rows are those with (L, platform) and `engine === E`, **exact match only, with no
   fallback** to `""` rows (the approved P4-12 amendment: `""` rows serve builds that declared no
   engine). This is the engine selector key (decision 7).
2. Group the candidates by their variant's sorted axis names.
3. In each group, pick the row `selectVariant`'s rule picks: every axis is in `axes`, with the
   lowest tuple of preference indexes over axis names in byte order. An axis-less group has one
   row. A group with no eligible row contributes nothing.
4. The **feed target** of pack p is the release that the selected rows' sets name for p. A pack
   named by two selected rows gets no feed target.
5. The outlet entry is P3-01 step 3's `entry`, and its id selects `packSets.outlets[id]`:
   - p in `pinned` gets no feed target;
   - when a gate is keyed by p's target, `halted` or an out-of-bucket rollout (a null bucket is
     out) replaces the target with `fallback`.

**Composition, per pack p** (`rep(x)` is x when x is not revoked; else the revocation's
replacement when `replacementUsable` and the replacement is not revoked; else null):

- **base** comes from the first rule that applies:
  1. the stamp's pin for p;
  2. the stamp's hold for p;
  3. null, when p is narrowed, when holds are unusable, when `caps.dataUpdates` is false, or when
     `packSets` is null;
  4. p's feed target.
- **cand** is `rep(base)`. When cand is null and `active[p]` is revoked, cand is `rep(active[p])`.
  A replacement counts as usable only when `caps.dataUpdates` is true and p is not narrowed.
- **install p** when all of these hold:
  - cand is not null, and its hash differs from `active[p]`;
  - p is in active, `required` or `essential`;
  - p is pinned or held, or `active[p]` is absent or revoked, or `cand.seq > active[p].seq`.

  **A feed target never downgrades a pack** (decision 10).

- **eff(p)** is the install target, else `active[p]` when it is not revoked, else cand.
- **revoked without a fix:** cand is null, and either `active[p]` is revoked or (base is
  revoked and `active[p]` is absent).
- **floor:** a `packFloors` entry for (p, L) with a known scheme exists, p is in active or
  `required`, p is not revoked without a fix, and either eff(p) is null or
  `compareVersions(scheme, eff.version, minVersion)` is below 0 or null.
- **R** holds when a `required` pack is revoked without a fix. **F** holds when some pack meets the
  floor condition. **block** is `revoked-content` if R, else `content-floor` if F.

**Prestage.** The offered `record` must have `content`, and its `contentApi` L′ must differ from L.
Then `prestage` lists, for each pack in L′'s record `expects` that is required or essential and
not in the chosen build's `embeds`:

- the release from the record's pin, else its hold (`holdsOf(record.content, recordNonWire)`),
  else the feed target selected at (L′, platform, the build's `requires.engine` or E), after
  `rep`;
- only when that release differs from `active[p]`.

Entries are `{pack, release}`, sorted by pack-id bytes. Otherwise `prestage` is `[]` (decision
12).

**Order.** A is P3-01's answer, unchanged. The first rule that applies decides:

1. A is `none {stale}` or `none {unknown-version}`. R is computed by the composition above with
   `packSets` treated as null (so no feed target), still applying the stored revocations **and
   their usable replacements** (pins, holds and active installs as usual). If R, the answer is
   `blocked {revoked-content}`; otherwise A. A revoked pin whose replacement is already active is
   not blocked (C43, `none {stale}`). Floors are not evaluated on this path (C38).
2. A is `blocked {app-floor}`: the answer is A, plus `contentBlock: block` when there is a block.
3. A is `binary`, `store` or `platform`:
   - With a block, the answer is A with `mandatory: true` and `contentBlock: block`. A content
     block makes an offer mandatory, as an app floor does.
   - Without one, a mandatory A, or any `binary`, is the answer (binary supersedes content).
   - `binary` always carries `prestage`.
4. With a block, the answer is `blocked {reason: block}`.
5. A is `code-ready`: the answer is A.
6. When `caps.dataUpdates` holds and the install or revoke list is non-empty, the answer is
   `packs`. The revoke list is the packs that are revoked without a fix, not required, and active.
7. Otherwise the answer is A: a non-mandatory `store` or `platform`, or a `none`.

This keeps P3-01 §8's order exactly: `blocked(app-floor)` → mandatory offers →
`blocked(revoked-content)` → `blocked(content-floor)` → `binary` with `prestage` → `packs` →
`none`. A content block makes an offer mandatory, as an app floor does, so the "mandatory offers"
step also covers a content-blocked offer. A non-mandatory store or platform offer yields to
`packs`: a store update waits for the player, and content must not wait with it (decision 11).

**Outputs** (new members are optional, so the 65 existing rows stay byte-identical):

| Action              | Members                                                                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `packs` (new)       | `install: [{pack, release {sha256, seq, version}}]`, `revoke: [packId]`, `set: [{pack, sha256}]` (eff over every known pack), `discardStaged` |
| `binary`            | P3-01's, `prestage` now filled; optional `contentBlock`                                                                                       |
| `store`, `platform` | P3-01's; optional `contentBlock`                                                                                                              |
| `blocked`           | `reason` ∈ `app-floor`, `content-floor`, `revoked-content`; optional `contentBlock`, on `app-floor` only                                      |

The lists are sorted by pack-id bytes. `discardStaged` keeps P3-01's rule.

**`bootDecision`** maps the answers like this:

| Answer                                                                            | Boot value |
| --------------------------------------------------------------------------------- | ---------- |
| `blocked {revoked-content}`, or any answer with `contentBlock: "revoked-content"` | `required` |
| `packs`                                                                           | `none`     |
| `blocked {content-floor}`, and any answer with `contentBlock: "content-floor"`    | `optional` |
| everything else                                                                   | as P3-01   |

`required` stops the boot at `blocked {update-required}`, a confirmed boot with no rollback loop.
It fires **only for a `required` pack** (stamp `expects[].required`) that is revoked with no fix,
so it can never be produced without a CI-signed revocation. A revoked **optional** pack is
unmounted and play continues (`packs.revoke`, C30). Floors never give `required`. This amends
P3-01 decision 1 and the AT-3 invariant (decision 4).

**Host copy.** For a `required` boot caused by `revoked-content`, the host shows its own text, not
the generic update-required text: "Some of this game's content was withdrawn by its developer and
can't be used. Update the app to keep playing." (with the offer's button when the answer is an
offer, and no button for `blocked`). The React `UpdatePrompt` and the Godot UI kit carry the
string; `useUpdateDecision` exposes `reason: "revoked-content"` so hosts can localise it.

**Vocabularies** (P3-01's reserved names, added together to the constant, enum, matrix key and
type):

- `UPDATE_ACTIONS` and `updateAction` gain `packs`.
- `BLOCKED_REASONS` and `updateBlockedReason` gain `content-floor` and `revoked-content`.
- `RECORD_KINDS` becomes `["app", "pack", "revocation"]`, and `RESERVED_RECORD_KINDS` becomes
  `["delegation"]`.
- `required` loses its coverage exemption.

**Reference for simulators** (V4 §11.1, informative). Resolution is P4-12's per-component
semantics: within a row, a pack is left out only when the packs its own dependencies and conflicts
link it to cannot keep it. A device's set is the composition above. P4-15's console simulator and
any SDK-side simulator reproduce both; the corpus pins the composition.

### 4.2 `cases.json`

**Appended `feedCases`** (every runner, the compatibility proof):

- `feed-valid-content-members-populated`: channel-wide, all three members, every row kind;
- `feed-valid-content-members-per-platform`: `selector {platform}`;
- `feed-valid-content-at-cap`: a payload of exactly 65,536 bytes. The generator pads `packSets`
  rows to hit it and asserts the length.

Each expects `ok`. The third is the generator's at-cap test; an over-cap payload is already
`jwsCases`' oversize case.

**`feedContentCases`.** Each case has `feedCases`' shape plus
`expect: {verify: "ok", content: {packSets, packFloors, revocations}}`, each member being the
parsed value or `null`. Every case is a signed, valid feed, built from one base by one mutation;
the generator proves each mutation changes only its member. The cases:

- **Valid:**
  - each member alone;
  - absent members;
  - unknown members ignored;
  - an unknown floor scheme, where only that entry is dropped;
  - an empty `sets` value;
  - `engine: ""` rows.
- **Unusable `packSets`:**
  - not an object;
  - `packSets: []`, matching the existing case;
  - a missing `releases`, `sets` or `rows`;
  - a bad release key, pack, version or `seq`;
  - a set naming an unknown release;
  - a set naming one pack twice;
  - a row with a bad `contentApi`, platform, engine, variant (5 members) or set;
  - duplicate row keys;
  - a row platform that differs from `selector.platform`;
  - bad `outlets`: a key pattern, a duplicate `pinned` entry, a gate key not in `releases`, a bad
    `halted`, `bp` 10,001, a bad salt, a dangling `fallback`.
- **Unusable `packFloors` and `revocations`:** shape, and a duplicate key.
- **Token rule:** a token case (`3.0`) and a minimum case (0, or `bp` −1) for each of the five
  integer pointers.

**`revocationCases`** (release key `djdl-release-test-2026`, P3-02's two-key set). Each case has
`releaseRecordCases`' shape plus `entry` (the feed entry) and `mode: "revocation" | "replacement"`.
`expect` is `{verify: "ok", revocation: {pack, target, replacement, reason, issuedAt}}` or
`{verify: "fail", step: "hash|jws|claims|cross-check|revocation"}`. The cases:

- **Valid:**
  - with a replacement;
  - without one;
  - `reason` of exactly 512 bytes;
  - signed by the second (2027) key.
- **`jws`:**
  - **signed by the product key**;
  - a non-pinned `kid`.
- **`hash`:** the body does not match `entry.record`.
- **`cross-check`:**
  - the entry's pack, version or `seq` is wrong;
  - `kind: app`.
- **`revocation`:**
  - `deliverable: "app"`;
  - `revokes` missing, bad, or not equal to `entry.target`;
  - `replacement.sha256 === revokes`;
  - `replacement.seq` given as the token `1.0`, or as 0;
  - `reason` missing, or 513 bytes.
- **`replacement` mode:** a replacement record of **another deliverable** fails `cross-check`; a
  valid one passes.
- **Superseding** (`revocation-supersedes-replacement`): a second revocation of the same target
  with a newer `issuedAt` and a different `replacement` verifies against an entry naming it; the
  case's `expect.supersedes` names the earlier case, and runners check the newer-`issuedAt`-wins
  selection over the pair with `newerRevocation`. A superseding record cannot omit `revokes`
  (still step `revocation`).
- **`revocation-supersede-tie`**: equal `issuedAt`; the higher record hash wins.
- **`revocation-supersede-older-loses`**: an older `issuedAt` with a different replacement loses
  to the stored one, which stays the winner.

`releaseRecordCases` is untouched. A revocation still verifies there as a reserved kind would,
which `record-valid-kind-revocation-verify-only` keeps pinning.

## 6. Worker

### 6.1 Migration, tables, hooks

- **Migration** (numbered at rebase): `release_revocations(product, deliverable_id,
target_release_id, target_sha256, record_sha256, kid, jws, replacement_release_id NULL,
replacement_sha256 NULL, reason, issued_at, ingested_at)`, with `PRIMARY KEY (product,
record_sha256)` and `UNIQUE (product, target_sha256)`: one **current** row per target, which a
  superseding revocation updates in place (§6.2).
  - `TABLE_OWNERS.release` gains it.
  - `data-model.mdx` is regenerated.
  - Revocation records stay out of `release_records`: its `UNIQUE (product, deliverable_id, seq)`
    would collide with the target's row.
- **Hooks** (`core/hooks.ts`, no new service edge):
  - `ReleaseCatalog.revocations(): CatalogRevocation[]`;
  - `Delivery.transports(): {deliverable, outlet, transport}[]`, which Distribution implements
    over `dist_transports`.

### 6.2 Ingest (the CI submit route, `kind: revocation`)

A submit that carries a revocation needs no ticket and no descriptor.

**Checks, in order** (each refusal is `release_record_rejected`, with the reason in brackets):

1. The record verifies: the shared checks, against the product's **release keys**.
2. `revocationOf` is usable [`revocation-body`]. Superseding (step 4) ranks with client-core's `newerRevocation`.
3. The target is a stored `kind: pack` record of `deliverable` whose version and `seq` match
   [`revocation-target`].
4. **Superseding.** When the target already has a revocation: a byte-identical resubmit succeeds
   and changes nothing; a revocation with a **newer `issuedAt`** (ties: the higher record hash)
   **updates the row** (`record_sha256`, `jws`, `kid`, replacement, reason, `issued_at`), adding or
   changing the replacement; an older one is refused [`revocation-stale`]. No submit ever deletes
   the row: there is no un-revoke.
5. Any replacement is a stored, non-yanked, non-revoked record of the same deliverable
   [`revocation-replacement`].
6. The replacement covers the target [`revocation-replacement-incompatible`]:
   - every variant key of the target exists in the replacement, with an equal `requires.engine`;
   - for compatible packs, every level that the target's `requires.contentApi.<app>` admits
     and that is live, or belongs to an app release that pins or holds the target, is admitted by
     the replacement's range.

**One D1 batch** writes the following, then re-resolves (P4-12's trigger pattern):

- the `release_revocations` row (insert, or the superseding update);
- a `release_yanks` row for the target (reason `revoked`, by `ci:<kid>`, `INSERT OR IGNORE`), so
  even a rolled-back Worker stops serving it;
- the clear of the product's sets.

**App publishes** gain `pin-revoked` and `hold-revoked`, refusing a pin or hold of a revoked
release. App releases already stored keep their signed pins; devices handle them (§2.6).

**The record route** serves revocation records by hash too. Access rule (1) governs them, as it
does pack records.

### 6.3 Resolution and composition

- **Resolution.** P4-12's `resolve.ts` drops revoked releases from every candidate list, a pinned
  pointer included. `sets.ts` loads them.
- **Composition.** `compose.ts` gains `composePackParts(channel)` per §2.2. It exports
  `effectivePackBindings` for P4-15. The revocation list:
  - drops a revocation only when **no stored app release on the channel, live or not**, pins,
    holds or embeds its target, and no stored row lists it (a device on an old, unlisted app release
    must still be told);
  - then, above 64, truncates **unreferenced revocations first**, then the oldest by `issuedAt`,
    with an audit row `update.feed.revocations_truncated`.
- **Size** (`feedDoc.ts`). The channel-wide document is signed while it fits. Otherwise the
  per-platform document is signed, holding:
  - its rows;
  - only the sets and releases those rows reference;
  - every floor and revocation;
  - its target's outlets.

  When that per-platform document is still over 65,536 bytes, the Worker sheds content in this
  fixed order, re-measuring after each step and auditing each (`update.feed.packs_omitted`,
  `update.feed.floors_omitted`, `update.feed.revocations_trimmed`,
  `update.feed.revocations_omitted`):

  1. omit `packSets` (devices keep their content; floors and revocations still apply);
  2. omit `packFloors`;
  3. keep only the revocations whose target a stored app release on the channel pins, holds or
     embeds, or a row lists;
  4. omit `revocations` (devices keep the revocations they already store);
  5. only then P3-03's `500 feed_not_composable`, which content can never cause on its own: with
     all three content members gone, the document is P3-03's.

  **Content never stops app updates.** A Worker test composes the legal worst case (64 packs with
  64-byte ids × 3 live levels, every pack floored at every level, and 64 referenced revocations
  with 64-byte ids) on the largest app target P3-03's tests use, and asserts a signed document
  with the app part intact. A second test forces step 4 with a named fixture,
  `appTargetNearCap` (a per-platform app part padded with outlets to 60,000 bytes), and asserts
  `revocations` omitted, `update.feed.revocations_omitted` audited, and the document signed. The pack part is checked with
  `feedContent` before signing, and a member that would be unusable is omitted and audited, never
  signed.

- **Computed sizes** (a throwaway script over the frozen shape, outside the repo):

  | Product shape                                                                                | Channel-wide | Per platform                       |
  | -------------------------------------------------------------------------------------------- | ------------ | ---------------------------------- |
  | Diceroll: 20 packs (5 textured ×3), 2 levels, 4 platforms, 1 engine, 4 floors, 5 revocations | ≈ 15.1 KB    | —                                  |
  | 64 packs in 3 axis groups ×4, 2 levels, 1 engine, 64 floors, 64 revocations                  | —            | ≈ 56 KB                            |
  | the same with 3 levels, 2 engines and 6 platforms                                            | —            | ≈ 120 KB, so `packSets` is omitted |

  A Worker test covers each case and the guard at the cap.

- **Cost.** One composition reads the sets, floors, revocations and transports once each. A test
  at 64 packs × 3 levels × 6 platforms stays inside the CPU budget, on Node and on `test:workerd`.
- **Discovery.** The Release fragment gains `revocations: true`, which the CLI requires before
  `revoke`.

### 6.4 Rule 10, transcripts, boundaries

- **Rule 10.** No new route. The OpenAPI schemas of the submit body and its refusal reasons, the

### 6.5 CLI

`pkey release revoke <packId>@<version> [--replacement <version>] --reason <text> [--dry-run]`:

- resolves both records through the uploads preflight (`seqs[].recordSha256`);
- signs with `recordSigner`;

## 7. Rollout

1. **P4-13's PR merges** in the corpus lane, before P4-10. Existing runners stay green.
2. **The Worker deploys:**
   - migration;
   - ingest;
   - the yank;
   - resolution;
   - composition;
   - discovery.

   Old SDKs ignore the new members (§2.1).

3. **The CLI and Action release** (`revoke`, `--hold`). Against an old Worker, `revoke` refuses
   (no discovery flag).
4. **SDKs release:** Node and React (P4-13), then Python and Swift (P4-23), then Godot (P4-24).
   Diceroll (D-04) adopts P4-24.

**Old clients.** They keep a revoked release until upgraded. That residual is stated in the threat
model, and why every SDK release note must say so.

**Old Workers, on rollback.** The table stays. The yank keeps the target out of an old Worker's
sets. Devices that learned a revocation still refuse the target. A P4-13 SDK against an old Worker
sees no content members and makes no content decision.

**Feature flags.** None. Nothing changes for a product until it has a compatible pack or a
revocation.

### 8.2 Risks

1. **Old SDKs never stop using revoked content.** This is inherent to "verified, never acted on".
   The release notes and the RUNBOOK say so; revocation and yank together at least stop new
   installs.
2. **Large products overflow the per-platform cap**: 64 packs × 3 levels × 2 engines. They lose
   compatible updates on that platform until fewer levels are live. The audit and P4-15 surface it.
   A future per-level split needs a capability the client advertises, not a selector key.
3. **A stolen release key can revoke everything.** Recovery is a binary that pins a rotated key.
   Until then, devices that verified revocations of required packs are stopped (`required`).
4. **SDK downgrade.** A host that downgrades its SDK below P4-13 ignores `revocations.json` and may
   mount a revoked release again. Stated in the threat model; not defended.
5. **A withheld replacement keeps a required pack stopped.** The Worker can refuse to serve a
   replacement record; the device then keeps `blocked {revoked-content}` (stated in AT-3).
6. **Lane.** P4-10 rebases on the four stamp cases.
