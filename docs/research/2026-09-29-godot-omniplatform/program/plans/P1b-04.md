## 1. Summary

- **Header values become contract (new WIRE-CONTRACT-V3 §5.2).**
  - `X-PKey-Platform` is `macos`, `ios`, `android`, `windows`, `linux` or `web`.
  - `X-PKey-Arch` is `arm64`, `x86_64`, `armv7` or `wasm32`. Both describe the running binary.
  - `X-PKey-SDK` is a short id: `node`, `react`, `python`, `swift`, `godot`.
  - Each SDK maps its runtime's own spelling through two tables in `@polaris-key/protocol/core`
    (`PLATFORM_SPELLINGS`, `ARCH_SPELLINGS`), generated into every SDK. It omits a header it
    cannot map.
- **`headers.json`** pins both tables as 31 platform and 31 arch spellings (`platformCases`,
  `archCases`). Every SDK and the Worker run all 62, and a later SDK reuses them without a corpus
  change.
- **The Worker converges stored rows.**
  - `deviceMetadata` stores the canonical value for any listed spelling and the id for each of
    the five old SDK names. An empty value is absent, and any other value is stored as sent.
  - A data-only migration rewrites the rows already stored, so the console's device summary
    stops splitting `darwin` from `macos`.
- **`config-matrix.json`** pins config resolution (new §2.2.1) in 24 `resolveCases`, 79
  `envValueCases` and 8 `listCases`.
  - Each case gives an `expectNoEnv` answer where a host without an environment layer (React)
    differs.
  - Member names compare by Unicode scalar value, as in P3-01's rule 6. So Swift's scan keys
    names by scalars, because Swift's `String` equality is canonical equivalence (§5.4). One
    row pins it. Swift's `[String: …]` maps still merge two canonically equivalent names, which
    is declared as a representation limit in WIRE-CONTRACT-V3 §10.
  - Numbers are judged from their decimal digits, with P3-01's rule 8 range: zero, or a
    magnitude of at least 10^−307 and below 10^308. Godot's number parser is not correctly
    rounded, and it wraps a long exponent, so a test on the parsed value would give Godot other
    verdicts (D9). What a number reads as in Godot is a third declared limit in §10. Twelve
    rows pin the range.
  - Measured against it, the SDKs disagree today (§4.2):
    - on environment values, five ways: Swift accepts trailing commas; duplicate keys are
      last-wins in JS and Python but first-wins in Swift; JS and Python accept infinite numbers
      and lone surrogates; Python accepts `NaN`; and past 512 levels of nesting Swift keeps the
      raw string while Node parses any depth and Python raises `RecursionError` from 9,998
      levels, a 20 KB value;
    - on keys named after `Object.prototype` members (`constructor`, `toString`), which the
      catalog allows: `client-core` finds the prototype's member, so Node reports
      `remote-default` for a key the document lacks, and React throws `TypeError`;
    - React also lists keys that only a local override supplies, which no other SDK does.
  - This package fixes all seven. Rule 2 bounds nesting at 64, and no SDK throws on any input.
    Every input gets the same verdict, parsed or raw, in every SDK, because every verdict is
    decided from the text alone. The parsed values agree too, except where §10 declares a limit.
- **`client-core` stays loadable where it loads today.** It ships in `@polaris-key/react`'s
  browser bundle, so the new code uses no lookbehind or other newer syntax or built-in (§2.4).
- No signed document, claim, `typ`, route or cache record changes, so `PROTOCOL_VERSION` stays 3
  (§2.5).

## 2. Contract

### 2.1 `docs/security/WIRE-CONTRACT-V3.md`

**§2.2.1 Resolution [C]**, new after §2.2 (`:68-80`), pinned by `config-matrix.json`:

> A client resolves a config key from the verified document's `config` map (absent before the
> first document), the host's local overrides and the environment, in this order:
> `enforced | hidden (remote) > local override > environment > remote default > fallback`. The
> source is reported as `enforced`, `hidden`, `local`, `env`, `remote-default` or `fallback`. A
> layer holding JSON `null` answers `null`; only `fallback` means that no layer answered. A layer
> answers only for a key it holds itself, so a key named like a language built-in
> (`constructor`, `toString`) is an ordinary key.
>
> 1. **Variable name.** The prefix (default `PKEY_CONFIG_`, §8), then the key with every `.`
>    replaced by `__`. Nothing else changes, case included. A variable that is set counts even
>    when it is empty. The SDK looks up exactly this name. A host's environment may match names
>    more loosely (Windows ignores case), and Swift's environment map is covered in §10.
> 2. **Variable value.** It is the parsed value when the raw string is one I-JSON text
>    (RFC 7493) nested at most 64 deep, and otherwise the raw string, unchanged. That means:
>    - RFC 8259 JSON, with whitespace limited to space, tab, LF and CR (no trailing comma, `NaN`,
>      `Infinity`, leading zero or byte order mark);
>    - no object with two members of the same name, at any depth. Names compare as sequences of
>      Unicode scalar values after unescaping (RFC 7493 §2.3). So `"a"` and `"\u0061"` are one
>      name, and `"\u00e9"` and `"e\u0301"` are two;
>    - no escaped lone surrogate, in a value or in a member name;
>    - every number in range, judged exactly from its decimal digits, with no floating point.
>      Its exponent part has at most six significant digits, and the number is zero or has a
>      magnitude of at least 10^−307 and below 10^308 (P3-01's rule 8 for documents). So
>      `9.99e307`, `1e-307` and `0e5` qualify; `1e308`, `1e-308`, `5e-324`, `1e400`, a 309-digit
>      integer and `0e1000000` do not;
>    - at most 64 arrays and objects open at any point (`[[1]]` nests 2 deep), so a deeper text
>      is the raw string, whatever its length.
>
>    Reading a variable never fails: every input has one of these two answers, decided from the
>    text alone. The parsed value is pinned except in four cases:
>    - an integer beyond ±(2^53 − 1) keeps the language's own number type;
>    - Godot's number parser is not correctly rounded, so a number can read as another value
>      there (§10);
>    - a string or member name holding U+0000 (written `\u0000`) is read by Godot with U+FFFD in
>      its place (§10);
>    - of two canonically equivalent member names, Swift keeps only the first (§10).
>
> 3. **No environment.** A host with no environment layer resolves as though no variable were
>    set. This covers React in a browser and in a desktop renderer.
> 4. **The user-visible list.** Every document entry except `hidden` ones, each with its resolved
>    value. `enforced` is true exactly when the state is `enforced`. A key supplied only by a
>    local override or by the environment is not listed. The order is not specified.

**§5**, the "Client metadata headers" bullet (`:147`): append "Their values are §5.2."

**§5.2 Client metadata header values [C]**, new after §5.1 (`:150-218`), pinned by
`headers.json`:

> `X-PKey-Platform` and `X-PKey-Arch` describe the running binary: the OS family and the CPU
> architecture it was built for. For example:
>
> - an x86_64 build under Rosetta 2 or Windows-on-Arm emulation sends `x86_64`;
> - a Mac Catalyst build sends `macos`;
> - an iPad app running on a Mac or on visionOS sends `ios`.
>
> | Header               | Value                                                                                                                    |
> | -------------------- | ------------------------------------------------------------------------------------------------------------------------ |
> | `X-PKey-Platform`    | `macos`, `ios` (iPadOS too), `android`, `windows`, `linux`, `web`                                                        |
> | `X-PKey-Arch`        | `arm64`, `x86_64`, `armv7`, `wasm32`                                                                                     |
> | `X-PKey-SDK`         | the SDK id: `node`, `react`, `python`, `swift`, `godot`; a later SDK registers its id in `conformance/parity/enums.json` |
> | `X-PKey-SDK-Version` | the SDK's package version (unchanged)                                                                                    |
>
> 1. **Spellings.** An SDK reads its runtime's own report: Node `os.platform()` and `os.arch()`,
>    Python `platform.system()` and `platform.machine()`, Swift's compilation conditions, Godot
>    `OS.get_name()` and `Engine.get_architecture_name()`. It looks the report up in
>    `PLATFORM_SPELLINGS` or `ARCH_SPELLINGS` (`@polaris-key/protocol/core`, generated into every
>    SDK):
>    - after ASCII case folding (A–Z only, never a locale-dependent lowercase);
>    - with no trimming;
>    - reading the table's own entries only.
> 2. **Omission.** A spelling the table lacks has no value, and the SDK omits the header rather
>    than inventing one (`unknown`, `x86`, `freebsd`). A browser sends `web` and no `X-PKey-Arch`.
> 3. **Server.** The Worker stores:
>    - the canonical value of any listed spelling;
>    - the id for each pre-§5.2 SDK name (`@polaris-key/node`, `@polaris-key/react`,
>      `polaris-key-python`, `PolarisKeySwift`, `polaris-key-godot`);
>    - any other value as sent.
>
>    It treats an empty value as absent. No server decision reads these headers.
>
> 4. A `POST /<p>/devices/report` body that carries `platform`, `arch` or `sdk` uses the same
>    values. The `engine` object that an engine SDK adds carries an `id` of the form
>    `<engine>-<major>.<minor>`, in lowercase ASCII, such as `godot-4.7`.

**§9** (`:322`): add "`headersVersion = 1` (§5.2) and `configMatrixVersion = 1` (§2.2.1)" to the
counters. **§10** (`:326`): append "client metadata header values (§5.2, `headers.json`), config
resolution and environment values (§2.2.1, `config-matrix.json`)" to the classes with corpus
coverage.

**§10** also gains two declared representation limits after the U+0000 entry (`:328-334`). The
first:

> **Declared representation limit: canonically equivalent names in Swift.** Swift's `String`
> equality and hashing are canonical equivalence. Swift holds a decoded object as
> `[String: JSONValue]` and the environment as `[String: String]`, so two names that differ but
> are canonically equivalent are one key. Swift is conformant only under this rule.
>
> - **Member names in an environment value (§2.2.1 rule 2).** `"\u00e9"` and `"e\u0301"` are two
>   names, and Swift keeps the first. The verdict does not change, because Swift's duplicate scan
>   compares scalar values, so the text is parsed as everywhere else. `config-matrix.json` pins
>   that verdict in one row whose two members hold equal values. The generator refuses any row
>   where such members hold different values.
> - **Variable names (§2.2.1 rule 1).** Swift reads a variable whose name is canonically
>   equivalent to the built name as that name. With an ASCII prefix this happens only through
>   U+212A KELVIN SIGN, which is equivalent to `K` (in `PKEY_CONFIG_`, and allowed in keys). No
>   row holds a variable name outside ASCII.
> - Signed documents are outside this entry (P3-01).

The second:

> **Declared representation limit: number values in Godot.** Godot's JSON parser
> (`built_in_strtod`) is not correctly rounded. It keeps the first 18 digits of a number,
> leading zeros included, as an integer, and multiplies or divides that integer by a power of
> ten built from inexact factors. Godot is conformant only under this rule. Measured on 4.7.2:
>
> - a number with a fraction or an exponent can differ in its last bits: `1e-307` reads as
>   1.0000000000000001e-307, and `9007199254740991.0` as 9007199254740990;
> - a number whose first 18 digits are all zeros reads as 0 (`0.00000000000000000001`), or as
>   NaN when the power of ten passes 10^308 (`0e999`,
>   `0.00000000000000000000000000000000000000001e348`);
> - a number divided by a power of ten above 10^308 reads as 0 (`100000000000000000e-309`, which
>   is 10^−292).
>
> The verdict of §2.2.1 rule 2 does not depend on any of this, because every SDK judges each
> number from its digits. Every SDK, Godot included, reads a number as the nearest double when
> it has at most 18 digits before its exponent part (leading zeros included), those digits form
> an integer of at most 2^53, and its exponent minus its count of fraction digits is within
> ±22. `config-matrix.json` compares the value only of such numbers.
>
> Signed documents are outside this entry. P3-01's V4 §10 declares the same limit for their
> values.

The closing sentence (`:336`) becomes "These are the only declared representation limits. The
first covers no character but U+0000. **[C]**".

### 2.4 `packages/client-core`

- **New `src/headers.ts`**, added as the `./headers` subpath in `package.json` and re-exported
  from `src/index.ts`.
  - It exports `canonicalPlatform(raw: string): ClientPlatform | null` and
    `canonicalArch(raw: string): ClientArch | null`.
  - Both fold A–Z, then look up with `hasOwn(table, key)`, so `constructor` and `__proto__` map
    to nothing. `hasOwn(o, k)` is `Object.prototype.hasOwnProperty.call(o, k)`, not
    `Object.hasOwn` (see "Runtimes" below). It lives in a new internal `src/own.ts`, which
    `config.ts` also uses and no subpath exports.
- **`src/config.ts`:**
  - **Own properties only.** `resolveSource` and `resolveValue` (`:80`, `:97`) read an entry
    only when `hasOwn(ctx.remote, key)`. `readEnvValue` (`:56`) reads a variable only when
    `hasOwn(ctx.env, name)`, which also holds for `process.env`.
    - Today a key such as `constructor` finds `Object.prototype`'s member. Node then reports
      `remote-default` for a key the document lacks.
    - React's `ctxFor` passes `env: {}` and `envPrefix: ""` (`sdk-react/src/core/adapter.ts:45-50`),
      so the variable lookup finds a function. `configSource`, `resolveConfigValue`,
      `listUserConfig` and `projectState`'s `resolveConfig` then throw `TypeError` (measured).
      React picks up the fix through `ctxFor`. The rows are in §4.2.
  - `readEnvValue` (`:55-59`) implements §2.2.1 rule 2 in three steps. Any failure keeps the raw
    string.
    1. Two iterative passes over the raw text. Both skip string contents (a backslash skips the
       next code unit), and both are exact for every text `JSON.parse` accepts; any other text
       is raw anyway.
       - `nestingExceeds(raw, 64)` stops at the 65th open array or object.
       - `numbersInRange(raw)` takes, at each `-` or digit outside a string, the run of digits,
         `.`, `e`, `E`, `+` and `-`, which is the whole number token, and judges it with
         `numberTokenInRange(token)`. An exponent part with more than six digits after its
         leading zeros is out of range. Otherwise E, the power of ten of the first non-zero
         digit, is the count of integer digits, minus one, minus the zeros before that digit,
         plus the exponent. The token is in range when all its digits are zero, or when E is
         from −307 to 307. This is integer arithmetic on the token's characters, so no floating
         point decides the verdict. A scratch copy agreed with a `BigInt` reference on 300,000
         random tokens (measured).
       - A run that is not one well-formed number, such as `1e5-5`, occurs only in a text
         `JSON.parse` refuses. The judge may answer either way for it, but it must never throw,
         and Swift's must never trap on arithmetic.
    2. `JSON.parse(raw)`, then `hasDuplicateKeys(raw)`, which is iterative. After step 1 every
       number `JSON.parse` returns is finite.
    3. A walk requires no lone surrogate in any string value or member name. After step 1 it
       recurses at most 64 deep. Without step 1 it would throw: Node 22's `JSON.parse` takes
       1,000,000 levels, but a recursive walk throws `RangeError` by 5,000 (measured).
    - The surrogate test is `hasLoneSurrogate(s)`, a loop over UTF-16 code units with no
      regular expression:
      - a high surrogate (`0xD800`–`0xDBFF`) followed by a low one (`0xDC00`–`0xDFFF`) is a
        pair, and the loop steps over both;
      - any other surrogate is lone.

      On Node 22.13 it agrees with `!s.isWellFormed()` on ten strings (measured): a pair; a lone
      high or low surrogate at either end; a reversed pair; a pair followed by a lone low
      surrogate; two highs then a low; the empty string; and plain text.

    - **Runtimes.** `client-core` runs in `@polaris-key/node`, on Node 22 or later (the root
      `engines`). It also runs in `@polaris-key/react`'s bundle, in these browsers and webviews:
      - Safari and every iOS browser;
      - Chromium: Chrome, Edge, Electron and WebView2;
      - Firefox;
      - the system webviews of Tauri apps (X-02): WKWebView on macOS and WebKitGTK on Linux.
        Their WebKit is the operating system's, so it can be years behind the current Safari.

      No floor is documented. So the new code uses nothing newer than these four packages ship
      today (`client-core`, `protocol`, `jws`, `sdk-react`). Their newest syntax is ES2022's
      public class fields, and their newest language built-in is ES2021's
      `String.prototype.replaceAll`. In particular, the new code uses none of these:
      - a regular-expression lookbehind. Before Safari 16.4 it is an early `SyntaxError`, so the
        whole bundle would fail to parse;
      - `String.prototype.isWellFormed` (Safari 16.4, Node 20);
      - `Object.hasOwn` or `Array.prototype.at` (Safari 15.4).

      Verifying a document needs WebCrypto Ed25519 (Safari 17). On an older engine that fails
      only at run time: `verifyJws` catches the rejected `importKey` and reports a failed
      verification. A lookbehind instead stops the whole bundle from parsing, the app's own code
      included.

    - New `tools/runtime-floor.test.ts` keeps that true. It reads every `.ts` and `.tsx` file
      under the `src/` of those four packages, except `*.test.*` files, and fails on `(?<=`,
      `(?<!`, `isWellFormed(`, `toWellFormed(` or `Object.hasOwn(`. None of these tokens occurs
      there today.

  - `looksLikeJson` and `safeJsonParse` (`:61-76`) are removed: with a strict parser they never
    change an outcome (checked on all 79 cases).
  - `listUserEntries(ctx: ResolveContext)` replaces `listUserEntries(remote)` (`:112-121`) and
    implements rule 4: the document's entries minus `hidden`, each valued by
    `resolveValue(ctx, key)`. Node and React both call it (§5.1, §5.2).
  - The comments at `:1-12`, `:46-48`, `:53-54` and `:110-111` change to match.

- `README.md`: the subpath table (`:51-55`) and the config section (`:108-119`).

### 2.5 Compatibility and `PROTOCOL_VERSION`

- **No bump** (AGENTS rule 2). §5 named the seven headers but never their values, and no signed
  document, `typ`, claim, envelope, route or cache record changes.
- **Header values are telemetry.** Nothing in the Worker branches on them. The admin device filter
  compares the stored string (`admin/repo.ts:252-254`), and the migration makes those strings
  canonical (§6.1).
- **An old SDK against the new Worker:** the normaliser stores canonical values. **A new SDK
  against an old Worker:** the values are stored as sent, and they are already canonical. Neither
  direction fails a request.
- **Environment values** change only for inputs the SDKs disagreed on, for text nested 65 to 512
  deep, and for numbers outside rule 2's range such as `1e308`, `1e-400` and `0e1000000`. Node,
  Python and Swift all parsed the last two kinds (§4.2). Nothing on the wire changes.
- **`client-core`'s `listUserEntries`** changes signature, which surfaces as a type error rather
  than a silent change. Nothing is published yet: every JS package is `0.0.0`.
- **Browsers and webviews** that load `@polaris-key/react` today still parse it (§2.4,
  "Runtimes").

## 4. Corpus

### 4.1 `headers.json`

```jsonc
{
  "headersVersion": 1,
  "description": "…", // §5.2's rules, the meaning of null, and the append-only policy
  "platformCases": [
    {
      "id": "node-win32",
      "description": "Node os.platform() on Windows; the old Node and Swift header.",
      "raw": "win32",
      "expect": "windows",
    },
  ],
  "archCases": [
    { "id": "…", "description": "…", "raw": "x64", "expect": "x86_64" },
  ],
}
```

### 4.3 Generator (`tools/sign-corpus.ts`)

- **`buildHeadersCorpus()`** writes literal `PLATFORM_CASES` and `ARCH_CASES`. Its self-check
  throws `corpus self-check failed: headers/<section>/<id>` unless:
  - ids are unique;
  - rows whose folded `raw` is equal have the same `expect`;
  - every non-null `expect` is a value of the `platform` or `arch` enum in
    `conformance/parity/enums.json`;
  - each such value has an identity row (`raw` equal to the value);
  - every non-null row's folded `raw`, so every table key, matches `^[a-z0-9_-]+$`.

  Because of the third and fourth checks, adding a vocabulary value needs a corpus case, and so a
  plan. The fifth keeps Swift's lookup exact: its `Dictionary` compares keys by canonical
  equivalence, and no other scalar sequence is canonically equivalent to such a key. The only
  ASCII characters a non-ASCII scalar is equivalent to are `K`, `;` and `` ` `` (U+212A, U+037E,
  U+1FEF).

- **`buildConfigMatrix()`** writes literal case lists; the `envValueCases` come from a compact
  `[raw, value]` list, whose depth rows are built with `repeat`.
  - **Reference.** Three generator-local functions check every expectation: `refResolve` and
    `refList` (each run with and without the environment) and `refEnvValue`. They sit on a small
    recursive-descent I-JSON parser. It refuses a 65th level before descending into it, so the
    10,000-level row never recurses past 64. It compares member names as JS strings, which is
    scalar comparison once lone surrogates are refused, and never normalizes them. It judges
    each number token from its digits with its own copy of rule 2's range, and reads an
    in-range token with `Number`.
  - **Independence.** They import nothing from `client-core` or `shared-jws`, for the reason
    stated at `:3657-3664`. Like §2.4, they read own properties only.
  - **Self-check.** Generation fails on any disagreement, or if:
    - `expectNoEnv` is present where it equals `expect`, or absent where it differs;
    - a list `expect` is unsorted;
    - some source value, JSON type or `enforced` value is used by no row;
    - an object anywhere in the file has two sibling member names that differ but are equal
      after `normalize("NFC")`, and their values differ under the comparison of §4.2. Equal
      values make it irrelevant which one Swift keeps (§10). At least one `envValueCase` must
      hold such a pair, so the scalar-comparison row cannot be dropped;
    - a string or member name holds U+0000, raw or escaped (rule 2 leaves it unpinned);
    - a variable name, which is an `env` key, is not ASCII (§10);
    - a number is outside the forms every SDK reads as the same double. This covers every
      number in the file, which each runner loads with its own parser, and every number in the
      `raw` of a row that compares a value. The number must have at most 18 digits before its
      exponent part (leading zeros included), and those digits must form an integer of at most
      2^53. Its exponent minus its count of fraction digits must be within ±22. Godot then reads
      the number with one exact multiplication or division, so it gets the nearest double, as
      every other SDK does. That held for 30,000 random numbers in these forms (measured on
      4.7.2). Outside them Godot can differ (§10), as `1e-307` and `9007199254740991.0` do;
    - an `anyNumber` row is not a single non-zero number in range, with at most 18 digits
      before its exponent part and an exponent minus fraction digits within ±308. Godot reads
      such a number as finite and non-zero;
    - rule 2's range is not pinned on both sides of each edge. That needs `anyNumber` or value
      rows at E = 307 and E = −307, raw rows at E = 308 and E = −308, and a raw row whose
      exponent has seven significant digits.
- **`main()`** (`:4308-4359`): both files join the `files` map, so `CORPUS_TARGETS` (`:223`)
  writes them to the source and to both mirrors. The header comment (`:18-21`) lists six files.
- **Versions.** The two counters are not generated constants, as `stageMatrixVersion` is not.
  Each runner asserts the version it implements. Rule 2's limits are likewise literals in each
  SDK and in the reference: `64`, `307` and six exponent digits. The depth rows and the number
  edge rows pin them.

- **`readEnvValue`**, in this order:
  1. It keeps the raw string when the first scalar is U+FEFF or the string contains U+0000.
     `JSONDecoder` skips one leading UTF-8 BOM and guesses UTF-16 or UTF-32 from NUL bytes.
     Measured on Swift 6.4: U+FEFF then `{}` decodes to `{}`, and `[`, NUL, `]`, NUL decodes to
     `[]`. Under rule 2 no JSON text begins with U+FEFF or holds a raw U+0000, so both guards
     are exact.
  2. It keeps the raw string when a new `StrictJSON.nestingExceeds(_:_:)`, the scan of §2.4 over
     UTF-8 bytes, finds more than 64 levels. `JSONDecoder` cannot enforce the bound: it decodes
     512 levels and refuses 513 (measured on Swift 6.4). It also keeps the raw string when a new
     `StrictJSON.numbersInRange(_:)`, §2.4's number scan over the same bytes, finds a number out
     of range. `JSONDecoder` would read `1e308`, `5e-324` and `0e1000000` (measured). The scan
     checks each byte is a digit before it subtracts `0x30`, so a run such as `1e5-5` cannot
     trap on `UInt8` underflow.
  3. It refuses input that fails a new `StrictJSON.hasDuplicateScalarKeys(_:)` or a new
     `StrictJSON.hasTrailingComma(_:)`.
     - Today's scanner (`JWSVerifier.swift:209-256`) becomes a private function that is generic
       over the key it stores for each name (`Set<K>` instead of `Set<String>`, `:211` and
       `:242`).
     - `hasDuplicateScalarKeys` keys each name by `Array(name.unicodeScalars)`, which is rule 2's
       comparison and P3-01's (its plan keys the JWS scan the same way).
     - `hasDuplicateKeys` keeps keying by `String`, for the JWS path (D14). Swift's `String`
       `==` and hashing are canonical equivalence, so that key would make `"\u00e9"` and
       `"e\u0301"` one name and keep the raw string where every other SDK parses (§4.2).
  4. It decodes with `JSONDecoder`, which already refuses lone surrogates (member names
     included) and the other non-JSON rows.
     - `JSONValue.object` is a `[String: JSONValue]`, so of two canonically equivalent names it
       keeps the first (measured: one member, U+00E9). That is WIRE-CONTRACT-V3 §10's declared
       limit, and the verdict is unchanged.
     - `JSONValue` tries `Int` before `Double` (`JSONValue.swift:27-30`), and that order must
       stay. `JSONDecoder` refuses `0e1` to `0e9`, `0.000e3` and `-0.0e21` as a `Double`, but
       decodes each as the `Int` 0 (measured on Swift 6.4). The
       `env-value-number-zero-with-exponent` row fails if the order changes.

  The variable lookup stays a subscript of `env`, a `[String: String]`. So it also compares by
  canonical equivalence, and §10 declares that too (only U+212A, against `K`, can differ).

  No row holds U+0000, raw or escaped. No environment can carry a raw one, and Godot reads an

  `package static` (tools 6.0). `StrictJSON.decode` and `hasDuplicateKeys`, the JWS path, do not
  change (D14).

## 7. Rollout

- **One PR**, committed in §5's order. Deploys and publishing are human steps.
- **Deploy order.** The Worker goes first: a `v*` tag runs `deploy.yml`, which applies the
  migration and then deploys. Then the SDKs are published: the Changesets PR for npm, then
  `python-v*` and `swift-v*` tags.
  - Nothing is published yet: every JS package is `0.0.0`, and no SDK tag exists. "Old clients"
    therefore means apps built from this repository.
  - Production runs v0.5.3 (`HANDOFF.md`, 2026-10-01), with migrations up to P5-01's `0034`
    applied, so this package's `0035` is the next one.
- **What changes for deployed clients and Workers:**
  - **An old SDK against the new Worker:** the Worker stores canonical values. Existing rows
    converge with the migration, and every later write is canonical.
  - **A new SDK against the old Worker:** the values are stored as sent, and they are already
    canonical. Old SDKs keep writing old spellings until the Worker deploys, so the device summary
    shows both kinds meanwhile. No request fails.
  - **Between the migration and the new Worker,** an old SDK can store an old spelling again. That
    device's next call rewrites it.
  - **Environment values:** a host now gets the raw string where it relied on any of these:
    Swift's trailing commas; JS or Python duplicate resolution; Python's `NaN` or `Infinity`; a
    number of magnitude 10^308 or more, or a non-zero one below 10^−307; or a value nested more
    than 64 deep. The release notes say so.
  - **React:** `listUserConfig()` no longer lists keys that only a local override supplies.
  - **Keys named after `Object.prototype` members:** Node reports `fallback` rather than
    `remote-default` for one the document lacks. React stops throwing on them, which today
    happens as soon as `projectState` meets one in a document.
  - **Constants:** Swift's `POLARIS_SDK_NAME`, Python's `SDK_NAME` and Godot's
    `PKeyHeaders.SDK_NAME` change value. Node and React keep `SDK_NAME` as the package name.
  - **Older browsers and webviews** keep loading `@polaris-key/react`, because the new code adds
    no syntax or built-in that they lack (§2.4).
- **Rollback.** Redeploying the previous Worker stops the mapping. Canonical rows stay canonical,
  and old SDKs write old spellings again. Rolling back an SDK means pinning its previous version.
  There is **no feature flag**: a flag would be a second code path for the corpus to pin.
- **Changeset** `.changeset/canonical-headers-config-matrix.md`: `@polaris-key/protocol`,
  `@polaris-key/jws`, `@polaris-key/client-core`, `@polaris-key/node` and `@polaris-key/react`
  take a `minor` bump. The Python and Swift release notes repeat §7 when they are tagged.

## 8. Decisions and risks (resolved as recommended unless the lead overrides)

- **D1 Versions.** `PROTOCOL_VERSION` stays 3 (§2.5). The new counters are `headersVersion` 1 and
  `configMatrixVersion` 1, and neither is a generated constant.
- **D2 Platform values.** `macos`, `ios`, `android`, `windows`, `linux`, `web`, describing the
  running binary.
  - iPadOS is `ios`, as is an iPad app on a Mac or on visionOS. Mac Catalyst is `macos`.
  - visionOS, tvOS and the BSDs have no value: adding one is a new spelling and a case.
  - The binary is what an update replaces, so the values agree with Release's per-build platform.
- **D3 Arch values.** `arm64`, `x86_64`, `armv7`, `wasm32`. An unrecognised spelling is omitted,
  as the brief recommends.
  - `arm` (Node, Rust, .NET) and `armv8l` map to `armv7`, the only 32-bit Arm value; Node's
    official 32-bit Arm builds are ARMv7.
  - A browser sends no arch: its JavaScript has none. Godot's web export does send `wasm32`, which
    is its binary's arch.
- **D4 `X-PKey-SDK`: short ids**, in `enums.json` as `sdkId`, as the brief recommends. A later SDK
  adds its own id (`kotlin`, `dotnet`, …) when it lands; that edits `enums.json` and the generated
  constants, not the corpus. The package version stays in `X-PKey-SDK-Version`.
- **D5 Compatibility: the normaliser is in this package**, plus a data migration, so stored rows
  converge for devices that never return. Unknown values stay verbatim, and an empty one is absent.
  Capping header length (R10-11, still open) is left out: it is a security fix with its own test,
  and no package owns it yet (see the follow-ups below).
- **D6 Engine: `engine.id` is pinned in the contract, not the corpus.** P1-05 has landed. There
  is no engine header. `engine` is a `/devices/report` object, which the Worker bounds and keeps in
  `devices.reported_json` (`core/devices.ts:881-907`).
  - As the brief asks once P1-05 has landed, §5.2 rule 4 pins its `id` as
    `<engine>-<major>.<minor>` (`godot-4.7`). `PKeyFacts.engine()` already sends that
    (`core/facts.gd:174-180`), and `tests/devices/test_facts.gd:87` checks it.
  - A corpus section would pin a format string that one SDK writes and no server reads.
  - The registry title drops "engine".
- **D7 The `headers.json` shape** differs from the brief's proposal: spelling rows instead of
  per-SDK input rows, and no `canonical` block.
  - One rule then serves every SDK and the Worker, and rows that describe one machine agree by
    construction.
  - Kotlin, .NET and Tauri, none of them plan-mode packages, reuse the rows without a corpus
    change.
  - Choosing which API to read is one line per SDK, proven by each SDK's captured-request test.
  - A `canonical` block would copy `enums.json` and force a corpus regeneration for every edit to
    it; the generator checks the rows against `enums.json` instead (§4.3).
- **D8 The tables live in `@polaris-key/protocol/core`** and are generated into every SDK, as
  `CHANNEL_ALIASES` is. The Worker imports them directly; it does not depend on `client-core` at
  run time (`core/bundles.ts:109-111`).
- **D9 Environment values follow I-JSON, nested at most 64 deep.** This fixes the five measured
  disagreements (§4.2) in the strict direction, as R2-06 did for documents. Trailing commas and
  the duplicate rule match §1, and the lone-surrogate rule matches P3-01's direction for
  documents.
  - JS drops its look-first gate.
  - Swift replaces its gate with two exact guards, a leading U+FEFF and any U+0000, because
    `JSONDecoder` skips a leading BOM and guesses UTF-16 and UTF-32 from NUL bytes (§5.4).
  - **Why 64.** It is twice `MAX_MANIFEST_DEPTH` (32, `shared-manifest/src/index.ts:526`), so any
    value a manifest can carry fits. It is an eighth of Swift's 512, so the corpus file's own
    three levels around the 64-level row fit too. It is also `System.Text.Json`'s default: on
    .NET 8, 64 levels parse and 65 throw `JsonException` (measured), which X-01 inherits.
  - Every SDK here enforces the bound with its own scan before parsing (§2.4, §5.3, §5.4, §5.5),
    because none of their parsers stops at 64: Swift's stops at 512, Godot's at 1,025, CPython
    3.12's at about 10,000 (as `RecursionError`), and Node's never.
  - **Alternative:** leave depth above 64 unpinned, as big integers are. That still needs every
    scan, because without one Python throws, so it saves only the depth rows.
  - **Names compare by scalar value**, as RFC 7493 §2.3 and P3-01's rule 6 say. JS, Python and
    Godot already compare that way. Swift's `String` does not, so Swift's scan keys names by
    scalars (§5.4), and one row pins it (§4.2).
    - Pinning the raw string for canonically equivalent names instead would need Unicode
      normalization in every SDK, and GDScript has none.
    - Leaving the case unpinned would let a `String`-keyed Swift scan keep the raw string where
      the others parse, and nothing would catch it.
    - Swift's `[String: …]` maps still merge such names. That affects the value Swift holds, not
      the verdict, so WIRE-CONTRACT-V3 §10 declares it, as it already declares U+0000 for Godot.
  - **Numbers are judged from their digits, with P3-01's rule 8 range.** A verdict that depends
    on a parser's rounding cannot agree across SDKs, because Godot's `built_in_strtod` is not
    correctly rounded (§10). A test on the parsed value, such as "finite as binary64", gives
    Godot other verdicts in three ways (measured on 4.7.2):
    - it reads `1.7976931348623158e308` as infinity where the others read the largest double;
    - it reads a zero with an exponent of 309 or more (`0e999`, `0e1000000`) as NaN;
    - it reads `1e4294967297` as 10, because its exponent wraps at 2^32, so it would parse a
      text that every other SDK keeps raw.

    Judged from the token, the verdict needs no floating point, and every SDK reaches it exactly:
    - Python's `parse_float` and `parse_int` hooks already receive the token;
    - JS, Swift and Godot scan for it (§2.4).

    The range is P3-01's for documents. P3-01's plan also has the Worker refuse a catalog value
    outside it at write (`representabilityIssue`, `number-out-of-range`), so an environment
    value can hold exactly the numbers a document can. The six-digit exponent cap keeps the
    arithmetic in small integers, and it also covers Godot's wrap.
    - The cost: every non-zero number below 10^−307 and every number from 10^308 up becomes the
      raw string. Node, Python and Swift all parse `1e-400` and `1e308` today, but no config
      value plausibly needs such a number.
    - **Alternative:** keep "finite as binary64", and declare Godot's verdict unpinned for any
      number outside the forms it reads exactly. That needs no number scan, but it leaves
      Godot's three divergences in place, one of which parses where every other SDK does not.
      §1 could then no longer promise one verdict per input.

  - **U+0000** in a string or member name stays unpinned: Godot reads it as U+FFFD (§10), and
    P3-01 decides member names for documents.

- **D10 The list holds document entries only.** Node, Python and Swift already behave this way, as
  do the docs ("every remote entry minus the hidden ones") and P1-10's settings panel, which
  renders one row per entry.
  - A key that only a local override supplies has no catalog metadata to render.
  - A key that only the environment supplies cannot be enumerated anywhere.
  - React changes. `listUserEntries` takes a context so that Node and React share one
    implementation.
- **D11 Hosts without an environment** get a per-row `expectNoEnv`, rather than an N/A, as the
  registry note says. React runs it, and so does Godot whenever its layer is off.
- **D12 Godot's headers are in this package.** P1-02 is `done` and cannot take them. Godot's
  manifest names P1b-04 for `core.headers`, so leaving it `planned` would fail rule 4 the moment
  this package is marked done. The change is small: the SDK id, two lookups and a runner section.
  - Godot's config matrix follows D17.
  - P1-05 is `done` as well, so no other package can take them. Its report already reads
    `PKeyHeaders` (§5.5).
- **D13 Proof-level `wp` (P1b-01's wave-1 sync).** A proof that is missing while its owner is
  `done`, or names an unknown owner, is a violation. An active proof keeps its `wp` as provenance,
  and the parity page hides it (§6.4).
- **D14 The JWS path has four differences of the same kind, left to P3-01 and P3-02.**
  - **Trailing commas.** `StrictJSON.decode` runs `JSONDecoder` after the duplicate scan, so a
    validly signed header or payload with a trailing comma verifies in Swift and fails in TS,
    Python and Godot.
  - **A leading BOM**, measured at each decoding function:
    - one BOM is accepted by TS (`new TextDecoder()` strips it), Swift (`JSONDecoder` skips it)
      and Godot (`PKeyJson.parse_bytes` drops it);
    - Python refuses it: `raw.decode("utf-8")` keeps U+FEFF, and `json.loads` rejects it;
    - two BOMs are accepted only by Godot, where `get_string_from_utf8` drops one and
      `parse_bytes` the other.

    RFC 8259 §8.1 lets a parser ignore a BOM, so the verdict is P3-01's.

  - **Nesting depth.** A validly signed text nested 513 to 1,025 deep verifies in TS, Python and
    Godot, and fails in Swift (`JSONDecoder` stops at 512). Past 1,025 Godot fails too. Python
    fails closed from about 10,000, because `verify_jws` catches `Exception` around the parse
    (`core/jws.py:231-232`), and TS accepts any depth.
  - **Canonically equivalent member names.** `StrictJSON.hasDuplicateKeys` keys a
    `Set<String>` (`JWSVerifier.swift:211`). So Swift refuses a validly signed header or payload
    whose sibling names are U+00E9 and U+0065 U+0301, which TS, Python and Godot accept as two
    names. P3-01's plan already settles it: its rule 6 compares scalar values, and its
    `valid-canonically-equivalent-member-names` vector expects `ok`.
  - Only the signer can produce such bytes, so the risk is low.
  - None is fixed here. WIRE-CONTRACT-V3 §10 asks for a corpus case before a fix, and those
    cases belong with P3-01 and P3-02's JSON edge vectors (this plan's §10). That is why the
    environment path gets its own scalar-keyed entry point (§5.4).
  - This package's `hasTrailingComma`, `nestingExceeds`, `numbersInRange` and
    `hasDuplicateScalarKeys` are the building blocks for the fixes. `numbersInRange` is already
    rule 8 of P3-01's plan.

- **D15 Facts stay as they are.** `os.name` in `/devices/report` keeps each SDK's Node-style family
  (`darwin`, `win32`, `linux`, and `ios` for Swift). Node, Python, Swift and now Godot
  (`core/facts.gd:24-35`, from P1-05) already agree there, and facts are a separate surface.
- **D16 One package, not two.** The two files share the generator change, the regeneration, the
  docs, the manifests and the corpus lane. If the lane is congested, the lead may split along §4.1
  and §4.2 (headers with the Worker and Godot; then the config matrix).
- **D17 Sequencing with P1-04: whichever merges second brings Godot's config to §2.2.1.**
  - **Where P1-04 stands.** It is implemented and unmerged (`wp/P1-04-godot-config` at
    `ff96a696`), so it will probably merge first.
    - Its `read_env_value` runs `looks_like_json`, then `PKeyJson.parse`, with no number or depth
      check: 64 of the 79 rows (§4.2).
    - Its static `list_user_entries(remote)` returns document values. The public
      `list_user_config()` already resolves each row.
  - **P1-04 first (expected).** P1b-04 does §5.5's config part as a Godot commit in §5's step 4.
    The size includes it.
  - **P1b-04 first.** Godot's config proofs are still `planned` on `main`, so nothing fails. When
    P1-04 rebases onto the new file, parity:check rule 2 refuses its implemented proofs until a
    tagged test loads `config-matrix.json`. So P1-04 does §5.5's config part itself.
  - **P1-04's brief.** The lead adds that second case to P1-04's brief when approving this plan
    (§10). It is conditional, so P1-04 is not reworked if it merges first.
  - **No graph edge.** Making P1-04 depend on P1b-04 would hold a finished package for about 1.5
    weeks. Making P1b-04 depend on P1-04 would fix the expected order, at the cost of waiting for
    P1-04's merge. The lead may choose that instead; §5.5's config part then stops being
    conditional, and P1-04's brief needs no edit.
- **D18 `client-core` keeps today's runtime floor.** It ships in the React bundle, and Tauri's
  system webviews (X-02) run whatever WebKit the operating system has. So the new code adds no
  syntax or built-in, and `tools/runtime-floor.test.ts` enforces that (§2.4).
  - The lone-surrogate test is a loop over code units. `/[\uD800-\uDFFF]/u` would also be exact
    and is ES2015, but the loop needs no regular-expression engine and reads like Python's check.
  - Own-property reads use `hasOwnProperty.call`. With `Object.hasOwn`, every config read would
    throw on Safari before 15.4.
- **Residual risks:**
  - real-host values are proven only by the spelling rows and CI's linux-x86_64 and macOS-arm64
    hosts (§9, H2);
  - Python's `platform.machine()` may report the native arch under Windows-on-Arm emulation, or a
    model id on iOS. Either is omitted or reported as the hardware rather than the binary;
  - keys `a.b` and `a__b` share one variable name. The catalog allows both, and the rule is
    unchanged;
  - the migration scans `devices` once, which is fine at today's scale;
  - the transcript replayers check header presence, so a host outside the vocabulary would fail
    them;
  - with two canonically equivalent member names in one variable, a Swift host holds a smaller
    object than other hosts (§10). Only such names cause it;
  - a Godot host can hold a different number than other hosts for a number outside the forms it
    reads exactly, and 0 or NaN for a few absurd spellings such as `0e999` (§10). The verdict is
    the same;
  - the runtime-floor test looks for tokens and does not parse code. It catches the constructs it
    names, not every newer feature.
- **Follow-ups (unowned):**
  - assert header values in the transcript replayers (P1b-03's harness);
  - cap metadata header length (R10-11);
  - let Release's `normalizeArch` (`services/release/assets.ts:17-35`) adopt `ARCH_SPELLINGS`
