## 1. Summary

- **A pack release is one CI-signed `pkey-release+jws` record with `kind: pack`**, variants
  inside. Every object it names is pinned by an object ref `{sha256, bytes, size, codec}` over the
  stored bytes, and per-file detail lives in hash-pinned side objects: the `pkey-files/1` index,
  one zstd frame with a blob ref per file, and for the per-entry delta set a `pkey-patch/1`
  descriptor plus one packed data object. A record with three variants and two deltas each is
  4,136 bytes, whatever the entry count (§2.3).
- **App records fill the reserved `content: {contentApi, pins[], expects[]}`, and builds gain
  `embeds[]`.** The running build learns its own pins from an embedded content stamp
  (`pkey-content/1`) and its embedded packs from markers (`pkey-marker/1`, the compact pack record
  beside the payload), so required-set checks are local and offline (CONTENT F11). No new `typ`,
  feed field or route: `PROTOCOL_VERSION` stays 4, and a v4 SDK that predates packs keeps every
  verdict it acts on (§2.1).
- **Claims stay forward-compatible.** They check structure, patterns, presence, uniqueness and the
  integer rule. A value outside an extensible vocabulary (type, method, scope, codec, layout,
  delivery, axis) only makes a variant, delta or pack unusable on an SDK that lacks it, never the
  record invalid, so v2 and v3 records verify in v1 SDKs (§2.2).
- **Corpus.** `conformance/corpus/v2/content/` (`cases.json` and `blobs/`, about 2.7 MB, kept in
  the source tree only), `plan-matrix.json` (A7's 23 rows plus 2, `variantCases`, `targetCases`),
  `cases.json` gains `packRecordCases` and `markerCases`, and `stage-matrix.json` goes to version 3
  (consent, progress and a playable offline). `tools/gen-content-corpus.ts` regenerates everything
  from committed blobs, decoding with the decoder-only libzstd WASM that P4-04 lands as
  `@polaris-key/zstd-wasm` (§4).
- **Order.** P3-02 → P4-04 → P4-02 and P4-03 (after P3-03) → P4-05; SDKs P4-06, then P4-07 and
  P4-08. `packs` stays a reserved decision name, which P4-13 adds with the rows that produce it; v1
  adds no `update-matrix.json` row. Error codes are A7's registry, spelled in kebab case (§2.9).

### 2.2 What a claim refuses, and what only makes a thing unusable

A P4 verifier refuses a record at step 14 (`claims`) only for these, which no later package
relaxes: a wrong JSON type, a pattern miss, a missing required member or a present `null` where
the type has none, a duplicate where uniqueness is stated, an integer-rule failure (V4 §3.1), a
count outside its bound, and the structural invariants written in §2.3 and §2.4 (`codec: none`
means `bytes === size`; `gaps` exactly when the layout is `container`; a `payload`-scope delta
only on a container; one axis set per record; `full.size === payload.size`).

Everything a later package extends is checked only for its pattern. A value the SDK does not know
makes the governed thing unusable on that SDK, and the record still verifies:

| Field                    | v1 values                                                                   | An unknown value makes                                                                      |
| ------------------------ | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `type`                   | `godot.pck`, `files.tree`                                                   | the pack unusable (`pack-type-unsupported`)                                                 |
| `formatVersion`          | per handler (`godot.pck`: the PCK header's format version; `files.tree`: 1) | the pack unusable (`pack-type-unsupported`)                                                 |
| `handler.activation`     | `restart`, `hot`                                                            | the pack unusable (`pack-type-unsupported`)                                                 |
| `files.format`           | `pkey-files/1`                                                              | the variant's index unusable: no `file` or `files`-scope delta, and a tree variant unusable |
| `files.layout`           | `container`, `tree`                                                         | the variant unusable                                                                        |
| any object ref's `codec` | `zstd`, `none`                                                              | that object unusable (§2.9's `planTarget` drops it)                                         |
| `deltas[].method`        | `zstd-patch-from`                                                           | the delta infeasible (the planner's method check)                                           |
| `deltas[].scope`         | `payload`, `files`                                                          | the delta skipped                                                                           |
| variant axis names       | `texture`, `locale`, `quality`                                              | the variant ineligible unless the host supplies preferences for that axis                   |
| `expects[].delivery`     | `essential`, `prefetch`, `on-demand`                                        | the pack read as `on-demand`                                                                |

Cross-record rules (every expected pack is pinned, `embeds` ⊆ pins, a required pack has no
entitlement, a variant's axes are declared) are publish rules, enforced by the CLI and by ingest,
never by a client: P4-12 makes unpinned `expects` valid, and a v1 client must verify the app
records that P4-12-era CI signs.

### 2.3 The pack record (`kind: pack`, V4 §2.5.1)

The common members are V4 §2.5's, unchanged for every kind. A pack record never carries `builds`.

| Field                 | JSON type  | Req.            | Claims check                                                                                                                                                                                                                                      |
| --------------------- | ---------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deliverable`         | string     | yes             | the pack id: `DELIVERABLE_ID_PATTERN` `^[a-z][a-z0-9-]*(\.[a-z0-9-]+)*$`, at most 64 bytes, not `app`                                                                                                                                             |
| `builds`              | —          | absent          | refused when present                                                                                                                                                                                                                              |
| `type`                | string     | yes             | `PACK_TYPE_PATTERN` `^[a-z][a-z0-9-]{0,31}\.[a-z][a-z0-9-]{0,31}$`                                                                                                                                                                                |
| `formatVersion`       | integer    | yes             | ≥ 1                                                                                                                                                                                                                                               |
| `handler`             | object     | no              | absent or an object: `mountOrder` integer ≥ 0; `prefixes` 1–32 unique strings, each `HANDLER_PREFIX_PATTERN` `^res://([A-Za-z0-9_][A-Za-z0-9 ._@+-]*/)+$` and at most 256 bytes; `activation` a string. Each member optional                      |
| `entitlement`         | string     | no              | `ENTITLEMENT_PATTERN` `^[A-Za-z0-9._:-]{1,64}$`: the licence flag that gates the pack's objects. An SDK whose licence lacks the flag leaves the pack out of its plans (CONTENT §6.7 item 9)                                                       |
| `variants`            | array      | yes             | 1–32 (`MAX_PACK_VARIANTS`); variant keys unique; every item declares the same axis names                                                                                                                                                          |
| `variants[].variant`  | object     | yes             | 0–4 members; names `VARIANT_AXIS_PATTERN` `^[a-z][a-z0-9-]{0,15}$`; values `VARIANT_VALUE_PATTERN` `^[A-Za-z0-9][A-Za-z0-9-]{0,34}$`                                                                                                              |
| `variants[].payload`  | object     | yes             | `{size, sha256}`: integer ≥ 0; 64 lowercase hex. | `variants[].full`     | object ref | yes             | `size === payload.size`. One object holding the whole payload; a tree's holds its files concatenated in index order                                                                                                                               |
| `variants[].files`    | object     | yes             | `{format, layout, sha256, bytes, size, codec, gaps?}`: `format` and `layout` non-empty strings; the ref members as an object ref with `bytes`, `size` ≥ 1; `gaps` an object ref, required when `layout` is `container`, refused when it is `tree` |
| `variants[].deltas`   | array      | no              | 0–16 (`MAX_VARIANT_DELTAS`); delta ids unique within the variant (a `payload` delta's id is its `artifact.sha256`, a `files` delta's its `patch.sha256`; a delta of another scope has none)                                                       |
| `deltas[].method`     | string     | yes             | `PATCH_METHOD_PATTERN` `^[a-z][a-z0-9-]{0,31}$`                                                                                                                                                                                                   |
| `deltas[].scope`      | string     | yes             | non-empty                                                                                                                                                                                                                                         |
| `deltas[].from`       | string     | yes             | 64 lowercase hex: the base release's `payload.sha256`                                                                                                                                                                                             |
| `deltas[].memBytes`   | integer    | yes             | ≥ 1 (§2.7)                                                                                                                                                                                                                                        |
| `deltas[].artifact`   | object     | `payload` scope | `{sha256, bytes}`: 64 hex; integer ≥ 1. A `payload` delta is refused on a `tree` variant                                                                                                                                                          |
| `deltas[].patch`      | object ref | `files` scope   | the `pkey-patch/1` descriptor                                                                                                                                                                                                                     |
| `deltas[].data`       | object     | `files` scope   | `{sha256, bytes}`: the packed frames and blobs                                                                                                                                                                                                    |
| `variants[].requires` | object     | no              | absent or an object; `engine`, when present, a string matching `ENGINE_PATTERN` `^godot-[0-9]+\.[0-9]+$`. Other members are not claims                                                                                                            |
| reserved              | —          | —               | `variants[].chunks` (P4-10: `{format: "pkey-chunks/1", sha256, bytes, size, codec, params}`), `variants[].conflicts` and `requires.{contentApi, packs, features}` (P4-12), record-level `provides` and `removes` (P4-20). Ignored by v1           |

An **object ref** is `{sha256, bytes, size, codec}`: the lowercase hex SHA-256 and the length of
the stored bytes (so the blob route's `ETag` and `Repr-Digest` equal them, README §3.5), the
decoded length, and the codec. `zstd` means exactly one zstd frame with its content size; `none`
means stored raw and is refused unless `bytes === size`. All four members are required, even for
`none`, because Godot's `decompress` needs the size (A7 §5).

The **variant key** is the canonical string of a variant: its `axis=value` pairs sorted by axis
name bytes and joined with `;` (`locale=fr;texture=astc`), and the empty string for `{}`.

**Size (brief item 3).** The record names no file, so the entry count never enters it. Measured on
records built to these shapes: the envelope is 457 bytes, a variant without deltas 600, a
`payload` delta 244 and a `files` delta 364. The acceptance worst case, a Diceroll-sized pack of
625 entries with three variants and one delta of each scope per variant, is
457 + 3 × (600 + 244 + 364 + 14) = **4,136 bytes**, 6.3% of the 65,536-byte cap (5,697 bytes as a
compact JWS, inside `MAX_RECORD_JWS_BYTES`). The 625 entries live in the files index: about
263 bytes each raw with the blob ref, 164 KB, and about 52 KB as one zstd frame (measured 3.1×). The
bounds alone do not keep a record under the cap (32 variants of 16 deltas would be about 206 KB),
so the cap is the limit, as for app builds: the CLI refuses to sign and ingest refuses to store a
record over it (P3-01 §2.4). `MAX_RECORD_JWS_BYTES` is unchanged.

### 2.5 New integer claims and their minimums (V4 §3.1)

minimum to 2^53 − 1, decided from the token through the pointer sets), and gets a token case, a
bound case and a minimum case unless the "implied by" column names a check that already implies
the bound or the minimum (P3-01 §4.3).

### 2.6 Verification order

**Pack records.** The device fetches a pinned pack record by its pin's `sha256` from
`release.endpoints.record` (P3-03's `GET /{product}/release/records/{sha256}`, which serves every
stored record), and runs V4 §3.5's steps 12–15 with `pin: {kind: "pack", deliverable: <pack id>,
version, seq}`. Step 15 becomes: "`kind` equals the pin's `kind`, `app` when the pin names none;
`deliverable`, `version` and `seq` equal the pin's". The refusal codes stay P3-01's
`record-rejected` (`hash`, `jws`, `claims`) and `record-mismatch`. Pack records verify against the
pinned release keys only, as app records do; P4-19's content keys come later.

**Markers (V4 §3.7, [C] via `markerCases`).** The marker's `release` member is a compact pack
record:

1. The marker file's bytes pass V4 §1.2's strict JSON (`format`).
2. `format === "pkey-marker/1"`; `packId` matches the pack-id pattern; `version` matches
   `VERSION_RE`; `release` is a string (`format`).
3. Steps 12–14 with `release` as the body and its own SHA-256 as the pin hash: the 88,844-byte
   ASCII bound (`hash`), key selection from the pinned release keys and `verifyJws` (`jws`), the
   record claims (`claims`).
4. Cross-check: `kind === "pack"`, `deliverable === packId`, `version === version`
   (`cross-check`).

It returns `{record, recordSha256}`. The host then matches its bytes (unit tests in P4-06 to P4-08,
not corpus): a single-file payload's SHA-256 and size equal some variant's `payload`; a tree's
`treeDigest`, computed from the files under its directory minus `.pkey/`, equals some variant's
`payload.sha256`. When the content stamp pins that pack, `recordSha256` must equal the pin's
`sha256`, or the embedded copy is not the pinned release and is not used. A refusal is the client
code `marker-rejected` with `detail` set to the step.

**The content stamp** (§2.8) is parsed with strict JSON; `format === "pkey-content/1"`; its
`contentApi`, `pins` and `expects` pass §2.4's `content` claims. Otherwise `content-stamp-invalid`.

### 2.7 Side objects and byte rules (V4 §2.6, [C] via the content corpus)

**Where bytes come from.** Every pack object is a blob of the product's blob store,
`blobs/sha256/<sha256>` (or under `gated/` for an entitled pack), named by the SHA-256 of its
stored bytes, served by `distribution.endpoints.blobs` with `{sha256}` substituted (P2b-04's
`GET|HEAD /{product}/distribution/blobs/sha256/{sha256}`). P2-01's `deltas/<from>/<to>.<method>`
keys are not used in v1. A device checks the stored SHA-256 and length against the object ref
before it decodes anything, and the decoded length against `size`.

**`pkey-files/1`** (A7 §3.3, plus one member per entry):

```jsonc
{
  "format": "pkey-files/1",
  "layout": "container", // or "tree": no offsets, no gaps
  "payload": { "size": 5256232, "sha256": "b994…" }, // equal to the variant's payload
  "files": [
    {
      "path": ".godot/imported/t512_05.png-….s3tc.ctex",
      "offset": 1234, // container only; ascending, non-overlapping
      "size": 174828,
      "sha256": "…", // of the file's bytes
      "blob": { "sha256": "…", "bytes": 61230, "codec": "zstd" }, // the stored object of this file
    },
  ],
}
```

- CI publishes a blob for every file of every release, deduplicated by hash, so the `file`
  strategy works from any older release (brief item 5). A `none` blob has `bytes === size` and
  `blob.sha256 === sha256`.
- Container entries are in ascending offset order. Tree entries are in strictly ascending path
  byte order.
- `parseFilesIndex(stored, ref, variant)` returns the first failure, in order:
  1. stored SHA-256 or length differs from the ref, the decode fails, or the decoded length
     differs from `size` → `files-index-invalid`;
  2. strict JSON or the integer rule fails → `files-index-invalid`;
  3. `format`, `layout` (equal to the ref's), `payload` (equal to the variant's), more than
     `MAX_INDEX_FILES` (100,000) entries, a mistyped or missing entry member, a `none` blob that
     breaks the rule above → `files-index-invalid`;
  4. the path rules below, in index order → `files-unsafe-path`, `files-duplicate-path`,
     `files-case-collision` or `files-path-conflict`, with `path`;
  5. a container whose offsets are not ascending and disjoint, whose last entry ends past
     `payload.size`, or whose gap bytes (`payload.size` − Σ sizes) differ from `gaps.size` →
     `files-layout-mismatch`; a tree whose paths are not strictly ascending, whose sizes do not
     sum to `payload.size`, or whose `treeDigest` differs from `payload.sha256` →
     `files-index-invalid`.
- The Worker decodes indexes too, at ingest (§6), so a decoded index is at most 32 MiB
  (`MAX_FILES_INDEX_BYTES`, 33,554,432).

**Path rules** are A7 §3.3's, with one addition: a first segment equal to `.pkey` (any case) is
`files-unsafe-path`, because a tree's marker lives there.

**`treeDigest`** is the lowercase hex SHA-256 of the UTF-8 text made of one line
`<sha256hex> <size> <path>\n` per file, sorted by path bytes (A7 §3.3); size is decimal without
leading zeros, and an empty tree hashes the empty string.

**`pkey-patch/1`**, the descriptor of a `files`-scope delta set, packed now (brief item 7):

```jsonc
{
  "format": "pkey-patch/1",
  "scope": "files",
  "method": "zstd-patch-from",
  "from": "088b…", // the base release's payload.sha256 (a tree's treeDigest)
  "to": "b994…", // this variant's payload.sha256
  "data": { "sha256": "8898…", "bytes": 314899 }, // equal to the record's data
  "entries": [
    {
      "path": "…/t1024_03.png-….ctex",
      "op": "delta",
      "from": "<base file sha256>",
      "to": "<file sha256>",
      "size": 349656,
      "offset": 0,
      "length": 21313,
    },
    {
      "path": "assets/data/level_120.json",
      "op": "blob",
      "to": "<file sha256>",
      "size": 4410,
      "codec": "zstd",
      "offset": 21313,
      "length": 1203,
    },
  ],
}
```

- Entries cover exactly the target files whose hash is not in the base: an `op: "delta"` entry for
  a path the base has with another hash (a bare `--patch-from` frame against the base file), an
  `op: "blob"` entry for an added file. Removed files vanish. A frame that is not smaller than the
  file's blob is published as a blob entry. Entries are in target index order; their byte ranges
  are ascending, disjoint and inside `data`.
- Any failure of the descriptor or the data object against its ref, of strict JSON, or of these
  members (`format`, `scope`, `method`, `from`, `to` and `data` equal to the record; every path in
  the target index with that entry's `sha256` and `size`) is `delta-artifact-mismatch`.
- Packing turns A7's 33-object per-file set into four requests (index, gaps, descriptor, data): on
  the measured set the data object is 314,899 bytes (35 frames, 179,951; 9 added blobs, 134,948)
  and the descriptor 4,009 bytes as one zstd frame.

**Codec, publish and decode rules** (A7 §3.2; brief items 4 and 8):

1. Every compressed object is exactly one zstd frame with the content-size flag, or stored raw
   (`codec: "none"`). CI stores raw when the frame is not smaller. There is no second codec
   (README decision 21).
2. `zstd-patch-from` frames are bare `zstd --patch-from=<base> <target>` output: content size and
   checksum on, the whole base as a raw-content prefix. The stored artifact is the bare frame; an
   edge may add the RFC 9842 `dcz` header later (P4-18).
3. Decoders decode them in raw-content prefix mode only (`ZSTD_DCtx_refPrefix` and its
   equivalents), never by dictionary auto-detection, with `windowLogMax` set to
   `min(31, ⌈log2(memBytes)⌉)`.
4. `memBytes` is the most memory one frame needs: a `payload` delta's base size plus the payload
   size; a `files` set's largest entry, base file plus new file (a blob entry counts its size).
   The planner drops a delta whose `memBytes` exceeds the device's budget.
5. CI never publishes a `zstd-patch-from` delta whose base (payload or file) starts with
   `37 A4 30 EC`. An SDK whose decoder cannot decode such a frame reports `delta-apply-failed`,
   and the host falls back to the next strategy.

### 2.8 The marker and the content stamp

**Marker** (`pkey-marker/1`; no new `typ`: the signature is the pack record's own):

```json
{
  "format": "pkey-marker/1",
  "packId": "diceroll.core3d",
  "version": "1.4.0",
  "release": "eyJhbGciOiJFZERTQSIsInR5cCI6InBrZXktcmVsZWFzZStqd3MiLCJraWQiOiJkaWNlcm9sbC1yZWxlYXNlLTIwMjYifQ.…"
}
```

It sits **beside** a single-file payload `X` as `X.pkey.json` (so `diceroll.core3d.pck` and
`diceroll.core3d.pck.pkey.json`; inside, it would change the hash it pins), and **inside** a tree
payload rooted at `D/` as `D/.pkey/pack.json`, which no files index lists. One marker covers every
variant: the device picks the variant whose `payload` its bytes match. A detached JWS was rejected:
it needs a new `typ` and a `PROTOCOL_VERSION` event for what the record's signature already gives.
CI writes markers for every embedded pack, and platform transports (P5-08) ship them in the
delivered unit.

**Content stamp** (`pkey-content.json`, `pkey-content/1`): the app record's `content`, written by
CI before the export and embedded in every build. The running build reads its pins, `required`
and `delivery` from it, never from the network: a store build lagging behind its channel cannot
learn its own record's hash from the feed (the feed pins the channel head, and an outlet's `live`
carries no hash), and the record cannot be embedded in the build it hashes. The build is the
running code, so an unsigned stamp inside it is as trustworthy as the code. `pkey release publish
--deliverable app --content-stamp <file>` signs that same object as the record's `content` (§6).

```json
{
  "format": "pkey-content/1",
  "contentApi": 4,
  "pins": [
    {
      "pack": "diceroll.core3d",
      "release": { "sha256": "…", "seq": 12, "version": "1.4.0" }
    }
  ],
  "expects": [
    { "pack": "diceroll.core3d", "required": true, "delivery": "essential" }
  ]
}
```

Where it lives: in Godot, `res://pkey_packs/pkey-content.json` beside the embedded payloads and
markers (P4-08); in Node, Python and Swift, a file the host ships and names in the client options
(P4-06, P4-07). A host without a stamp has no packs.

### 2.9 Selecting, planning and applying (V4 §11.4, informative; the corpus pins it)

**`selectVariant(variants, {engine, axes})`** (`variantCases`). A variant is eligible when its
`requires.engine` is absent or equals the host's `engine` (`godot-<major>.<minor>`, null outside
Godot), and every axis it declares has a host preference list (`axes.texture`, `axes.locale`, …,
in preference order) that contains its value, compared by bytes. Among eligible variants the lowest
tuple of preference indexes over the axis names in byte order wins; the record's single axis set
makes the order total. None eligible → `pack-no-variant`.

**`planTarget(variant, recordSha256, filesIndex | null)`** (`targetCases`) maps a variant onto A7
§4.1's planner input:

| Planner member | Value                                                                                                                                                                                                                                                                                                            |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `release`      | `recordSha256`                                                                                                                                                                                                                                                                                                   |
| `payload`      | the variant's `payload`                                                                                                                                                                                                                                                                                          |
| `full`         | `{bytes: full.bytes, requests: 1}` for a container; `{bytes: full.bytes + files.bytes, requests: 2}` for a tree, which needs its index to split; null when `full` or (for a tree) the index is unusable                                                                                                          |
| `platform`     | null (P5-08 sets it for a platform-bound pack)                                                                                                                                                                                                                                                                   |
| `chunks`       | null (P4-10, P4-11)                                                                                                                                                                                                                                                                                              |
| `files`        | with `filesIndex`: `{indexBytes: files.bytes, gapsBytes: gaps?.bytes ?? 0, files: [{sha256, blobBytes: blob.bytes}]}` in index order; else null                                                                                                                                                                  |
| `deltas`       | in record order, keeping usable ones: a `payload` delta (container) as `{id: artifact.sha256, method, from, memBytes, artifacts: [artifact]}`; a `files` delta (with `filesIndex`) as `{id: patch.sha256, method, from, memBytes, artifacts: [files, gaps (container), patch, data]}`, each as `{sha256, bytes}` |

The client fetches the target files index before planning when the layout is `tree`, or when any
release of the pack is installed (its index is kept at install); a first install of a container
plans with a null index and takes `full`. The planner counts the index in every candidate that
needs it, fetched or not, so every SDK computes the same costs.

**`plan(input)`** is A7 §4.2 exactly, `REQUEST_WEIGHT` = `PLAN_REQUEST_WEIGHT` = 16,384, with one
generalisation: `full` is `{bytes, requests?}` and costs `requests ?? 1` requests. A7's 23 rows keep
their inputs. v1 capabilities never list `chunk` (P4-06); the planner still costs chunk candidates
from inline records, so P4-11 never touches it. Its results (`plan-transport-unsupported`,
`plan-insufficient-disk`, `plan-no-strategy`) are verdicts it returns, never throws (brief item
12); a pipeline raises them only when it cannot proceed.

**Appliers** (A7 §3.4; the first failure is the verdict; counters are part of it):

- `applyFull`: the `full` ref → `full-corrupt`; decode to exactly `payload.size` → `full-corrupt`;
  a container's SHA-256 equals `payload.sha256` → `full-corrupt`. A tree first validates its index
  (§2.7's codes), then splits the bytes by entry sizes in index order and checks every file's
  SHA-256 → `full-corrupt`.
- `applyDelta` (`payload` scope): the artifact ref → `delta-artifact-mismatch`; the base's SHA-256
  equals `from` → `delta-base-mismatch`; the raw-prefix decode, its length and its SHA-256 against
  `payload` → `delta-apply-failed`.
- `applyFile`, for the `file` strategy and for a `files`-scope set: the target index (§2.7), the
  gaps ref of a container (a failure is `files-layout-mismatch`, as A7's `file-gaps-short`), the
  descriptor and data of a set (`delta-artifact-mismatch`). Then for each target file in index
  order: reuse an installed file with the same SHA-256; else the set's `delta` entry (no installed
  file with its `from` → `delta-base-mismatch {path}`; decode → `delta-apply-failed {path}`); else
  its `blob` entry, or for the `file` strategy the file's own blob by its ref (ref, decode or hash →
  `file-corrupt {path}`); else `file-source-missing {path}`. A container's payload SHA-256 →
  `payload-hash-mismatch`; a tree checks every file, reused ones included (`file-corrupt {path}`),
  and reports its `treeDigest`. Counters: `reusedFiles`, `deltaFiles`, `blobFiles`, and
  `downloadedBytes`, the bytes of the objects fetched for the strategy except the index and gaps
  (the file blobs, or descriptor plus data).

**`packSetId(entries)`** (`packSetIdCases`; brief item 11): the lowercase hex SHA-256 of the UTF-8
lines `<packId> <releaseSha256>\n` sorted by pack-id bytes, where `releaseSha256` is P3-01's
record hash. An invalid pack id, a release that is not 64 lowercase hex, or a pack listed twice
gives null; the empty set hashes the empty string. A device reports the id of its **active set**:
the pack releases activated in the running process (restart packs mounted at this boot, hot packs
active, embedded baselines included). P4-12 stores the same function's value for resolved sets.

**Error registry** (brief item 12). The codes are A7 §3.5's, renamed to kebab case because
`errors.schema.json`'s code pattern (`^[a-z][a-z0-9]*([_-][a-z0-9]+)*$`) has no dot, plus the new

| Required missing | Essential missing | `result`       | Next                                                         |

### 2.12 The feed and the update decision (brief item 14)

Pinned packs need no feed entry (CONTENT §6.3), so v1 adds no feed field: `packSets`,
`packFloors`, `revocations`, `deltas` and new `selector` keys stay reserved for P4-12, P4-13 and
P4-17, and a v4 or P4 client never asks for one. CONTENT §16's v1 row says the same ("pinned packs
come from the app record, so v1 needs no feed entry").

**`packs` stays reserved.** P3-01 asked this plan to add `packs` to `UPDATE_ACTIONS`, the
`updateAction` enum, `vocabulary.actions` and `UpdateDecision` together with the rows that produce
it. In v1 nothing produces it: the running build's set is fixed by its stamp and only an app
update changes it, which `binary`, `store` and `platform` already decide; first fetches are the
boot's FETCH, background prefetch and `ensure()`. A listed value no row produces would fail P3-01's
coverage self-check (§4.9 there). So P4-13, which brings the feed's pack sets, adds `packs` with
`prestage`, `content-floor` and `revoked-content`, and `update-matrix.json` is unchanged here.

### 4.2 The generator (brief item 19)

- **`tools/gen-content-corpus.ts`** (new), a TypeScript port of A7's `gen/gen.py`, `planref.py`
  and the reference applier in `runners/python/pkey_content.py`, called from
  `tools/sign-corpus.ts`'s `main`, so `pnpm gen:corpus` and `--check` cover both corpora. It
  imports nothing it checks (P3-02's rule): its reference `parseFilesIndex`, appliers, planner,
  `selectVariant`, `planTarget`, `packSetId`, path rules and content claims are its own.
- **Blobs are inputs.** zstd output is not stable across libzstd versions, so normal and `--check`
  runs never compress: they read `content/blobs/`, decode with `@polaris-key/zstd-wasm` (the
  pinned Node, 22.13.1, has no `node:zlib` zstd, and only a raw-prefix decoder handles every base),
  hash with `node:crypto`, and rebuild `content/cases.json` (its `blobs` table included) and
  `plan-matrix.json`. `--check` also fails on a missing blob, a blob not in the table, and a stray
  file in `content/` or a `content/` directory in a mirror.
- **`--rebuild-content-blobs`** (explicit, never in the gate) rebuilds every blob from the decoded
  payloads (v1 from its full blob, v2 by the `file` strategy) with the zstd CLI, and refuses unless
  `zstd -V` reports exactly 1.5.7.
- **Seeding** (once, in P4-04): run A6's `prototype/patching/build.sh` and A7's
  `gen/gen.py small`, re-encode the result to §2.7's formats with the rebuild mode, and commit.
  The figures here come from S-04's regeneration of that set; P4-04's exact bytes will differ and
  its PR lists them.
- **The JWS side.** `sign-corpus.ts` takes the content set's hashes from the content generator and
  signs the pack records, app records and markers of §4.6 with P3-02's `djdl-release-test-2026`
  (and `-2027` for rotation), so the corpora join by hash and no key enters `content/` (A7 §11.5).
- **Self-checks** (each throws, so `gen:corpus` fails): every positive apply case is `ok` and every
  negative one fails with the code it names; the payloads rebuilt by `full`, `delta` and `file`
  equal each other byte for byte; every plan row, variant case and target case is recomputed;
  every pack record case differs from its valid twin in the one property under test; each of
  §2.5's 16 paths has its token, bound and minimum cases, proved by switching that path's rule off
  in the generator's own claims (P3-01 §4.9); every `nonWireIntegers` member equals the
  generator's scan; the valid pack records pin exactly the content set's objects; stage matrix
  version 3 covers every `accepts` cell, including the two new keys.
- **Hygiene** (brief item 21): `.prettierignore` gains `conformance/corpus/v2/content/blobs/`;
  `.gitattributes` gains `conformance/corpus/v2/content/blobs/** binary` (the Godot Windows leg runs
  with `core.autocrlf=true`, and a small raw text blob would otherwise change its hash).

## 6. Worker

**Routes (rule 10):** none new. Pack records are served by P3-03's record route, pack objects by
P2b-04's blob route (P4-05 adds `HEAD` and the gated branch with their OpenAPI and
`routeCoverage` entries only if missing). Body schemas change in the OpenAPI spec: the submit body
for a pack, the uploads answer's `seqs[].recordSha256`, the report's `content` and discovery's
`release.packs`.

**P4-02** (worker lane; imports `client-core`'s claims and `@polaris-key/zstd-wasm`):

- **Manifest sync** writes pack rows to `release_deliverables` (`kind` `pack`, `pack_type`,
  `def_json`, `def_source`, the operator guard).
- **Pack submits** are `{ticket, record, dryRun?}` with no descriptor (the record is the whole
  truth, and every pack object is a blob). The ticket for a pack deliverable takes up to 25,000
  objects and a 4 MiB uploads body, so a 20,000-entry pack (P4-03's lint ceiling) publishes in one
  submit. A pack submit's body is at most `MAX_RECORD_JWS_BYTES` + 4 KiB (P3-03 sizes the app
  submit's, which also carries a descriptor).
- **Ingest**, refusing with P3-03's `release_record_rejected` and a `reason`: P3-03's checks
  (`typ`, `kid`, `product-key`, `signature`, `claims` with the extended claims, `scheme` under the
  pack's scheme, `seq`), then `pack-unknown` (not a declared pack), `pack-type` (type differs from
  the declaration), `pack-variant` (a variant outside the declared axes and values), `pack-index`
  (an index fails `parseFilesIndex`, read from the blob store and decoded with the WASM decoder,
  at most `MAX_FILES_INDEX_BYTES`), and `pack-object` (an object named by the record or by a files
  index is not stored with that size and SHA-256, or the product may hold no ref to it: P2-01's
  rule, promoted from this ticket or already referenced; a `files` set's added blobs live inside
  its data object, so ingest never reads a patch descriptor). It writes `release_metadata`
  (`deliverable_id`, `seq`), one `release_builds` row per variant (`build_id` the variant key or
  `default`, `platform` NULL, `arch` `any`, `format` the pack type, `variant_json`,
  `requires_json`), one `release_artifacts` row per object with its role, and `blob_refs` with ref
  kind `pack-object` and the release id.
- **App records with `content`**: `content-api` (missing while packs are declared), `pin-unknown`,
  `pin-mismatch` (the stored record's deliverable, version or `seq` differ), `pin-yanked`,
  `pin-missing` (an expected, required or `baseline: embedded` pack without a pin, or a pin
  without an expect) and `embeds` (an embedded pack not pinned). It writes `release_pins` and
  `release_metadata.content_api`, and each build's `embeds_json`.
- **Tables** (migrations numbered at rebase): `release_pins` with `product`, `app_release_id`,
  `pack_deliverable`, `pack_release_id`, `record_sha256`, `required`, `delivery` and `created_at`,
  primary key (`product`, `app_release_id`, `pack_deliverable`), indexed on (`product`,
  `pack_release_id`); `release_metadata` gains `content_api INTEGER`; `release_builds` gains
  `embeds_json TEXT`. `release_artifacts.role` has no
  CHECK (0027_f), so the roles of §2.14 need no rebuild; `PACK_OBJECT_ROLES` lives in
  `@polaris-key/manifest` beside `ARTIFACT_ROLES`, which app artifact maps keep using.
  `TABLE_OWNERS.release` (`gen-reference.mjs:312`) gains `release_pins`; `data-model.mdx`
  regenerates.
- **The record route**: for a `kind: pack` record the `entitled` version-window check (an app
  version rule) does not apply; the metadata mode's request-level check governs, and the pack's
  bytes are gated by P4-05.
- **Hook** (`releaseCatalog`, the name P2b-01 landed; README §10's `buildCatalog` is not it):
  `packDeliverables()`, `packRelease(deliverable, releaseId)` (variants and objects),
  `pins(appReleaseId)`, `pinnedBy(packReleaseId)`, `embeds(appReleaseId, buildId)`.
- **Discovery:** the Release fragment gains `packs: true`; the CLI refuses to publish a pack or
  stamp `content` without it, so no app record carries pins a Worker did not mirror.
  `pnpm gen:transcripts` re-records discovery.
- **Upload answer:** `seqs[]` gains `recordSha256` for an existing release, which resolves
  `--pin <packId>@<version>`.
- **Telemetry:** `REPORT_KEYS` gains `content` (§2.11).
- **Docs:** `services/release/packs.md`; the glossary terms (pack, pack release, variant, payload,
  files index, binding, `contentApi`, marker, content stamp, pack set) in `start/concepts.md`.
- **Threat model:** two-signer property unchanged (the Worker signs no record); the WASM decoder at
  ingest is a new parser of CI-supplied bytes, bounded by size; refs follow P2-01's rule.

**P4-03** (CLI; no Worker change): `--deliverable <packId>` builds, per variant, the stripped
payload, the files index, every file blob, the gaps object, the whole and the packed `files`
deltas against `patch.deltaBases` stored releases fetched by hash, the marker, and the record;
self-checks with `releaseRecordClaims`, `parseFilesIndex` and a byte-for-byte rebuild; uploads only
missing objects. `pkey release content-stamp --embedded <dir> [--pin <packId>@<version>]… --out
pkey-content.json` writes the stamp from the markers in `<dir>`, the pins and `.pkey/release`;
`--deliverable app --content-stamp <file>` signs it as the record's `content`, with each build's
`embeds` from the artifact map. `--dry-run` prints all of it.

**P4-05**: serves every pack object through the blob route (`Range`, `If-Range`, `ETag` = SHA-256,
`Repr-Digest`, no `Content-Encoding`), the gated prefix for an entitled pack (authorised by the
licence's entitlement flag, `private, no-store`; `entitledBlobRefusal` gains the pack branch), and
availability (`pkey-cdn` and `web` live when every object is stored; `embedded` per build from
`embeds`).

### 8.2 Risks

1. **P3-02 is not merged.** Names here follow its branch at `9dfaed3c`. A rename before it merges
   is followed by P4-04 and recorded in a small amendment to this plan.
2. **zstd versions.** Blobs are inputs; only the rebuild mode compresses, with zstd 1.5.7, and it
   refuses any other version. A rebuild changes hashes, so it is a deliberate PR of its own.
3. **The WASM decoder** is a committed binary in the generator, the Worker, React and the Node
   fallback. Its recorded SHA-256 and reproducible `build.sh` guard the supply chain; other SDKs
   decode with other libraries, so a decoder bug cannot make the whole corpus agree with itself.
4. **The content set's provenance.** It is seeded once from A6's Godot exports; a regeneration
   gives other bytes (S-04's differs from A7's). After seeding, the committed blobs are the inputs.
5. **A host that ships no content stamp has no packs.** P4-06 to P4-08 make the stamp option and
   `res://pkey_packs/` the documented setup, and their docs pages say so.
6. **Consent confirms a boot.** A crash after a consented download rolls back one launch later
   (§2.10). P3-10 keeps P3-01's confirmation rule.
7. **Godot's GDDL route is engine-internal**: P4-08 advertises `zstd-patch-from` only on pinned
   engine versions, and `file` and `full` need nothing internal.
8. **Forward compatibility is a promise.** A later package that must refuse what §2.2 lets v1 accept
   changes a verdict and is a plan-mode event.
9. **The Worker parses CI-supplied indexes.** Bounded by `MAX_FILES_INDEX_BYTES` and run through the
   same `parseFilesIndex` SDKs run; refs follow P2-01's possession rule.
10. **Reading the checkout from the Swift and Godot runners** is a new pattern; if the lead prefers
    full mirrors, adding `content/` to the reconcile loop is mechanical and costs ≈ 5.2 MB.
