## 1. Summary for the owner

You asked for three things: apps that sign people in by themselves, devices that find each other
and talk directly, and a Cloud Sync that handles files. Three planners each wrote one plan. This
file joins them into one program: about 70 work packages, roughly 47–63 engineer-weeks, in four
waves with a release after each wave.

**Order.** Polaris Locker comes first.

- **Wave 1:** the server half of automatic sign-in, the "link your Google or Apple account" offer,
  and the device keys that all three features share.
- **Wave 2:** automatic sign-in in the Apple, Android, web and Godot SDKs, then release. Cloud
  Connect's server side and Cloud Sync's encryption core are built in parallel.
- **Wave 3:** nearby approval, Cloud Connect in every SDK, and encrypted sync in every SDK.
- **Wave 4:** synced files in every SDK, background transfer, the kits' sync screens and the
  console's Data tab. The security sign-offs come last, before anything reaches production.

**What changed so the three plans agree:**

- **One cipher everywhere, AES-256-GCM.** Browsers and Godot web exports have it built in, so no
  JavaScript crypto library is added. Android keeps its API 24 floor. Cloud Connect had chosen
  ChaCha20, which browsers lack.
- **One nearby approval.**
  - The new device asks. Your signed-in phone shows "Sign in <device>?" with three codes, and you
    tap the code the new device shows.
  - It works only on the same network, never through the relay.
  - The same tap also hands over your sync key.
- **A flaw in two of the plans is fixed.** A short code taken straight from the connection
  handshake can be forged by someone on the same Wi-Fi who tries about a million keys. The fix is
  the standard one, used by Bluetooth pairing: each side commits to a random value before the code
  is shown. It adds three small messages.
- **Device keys are built once.** One Core package (CC-03) is built first, and each SDK gets one
  key store (the new CC-26), so no plan builds keys twice.
- **Wire version 5 lands first**, as a document and a constant. The sign-in and sync changes are
  then written into the v5 contract. Shipped apps are unaffected, because no SDK checks the
  version.

**What you trade:**

- **Cloud Connect trusts the Worker.** Channels between your own devices rely on device
  certificates that the Worker signs, so a compromised Worker could add a device to your account.
  Sync keys never travel on those channels, so Cloud Sync stays end-to-end (Q6).
- **Web unlock needs the recovery code.** In v1, a new browser unlocks encrypted sync only with the
  recovery code (Q8).
- **Godot on Linux is slow at encryption.** It encrypts in GDScript, at about 1 MB/s, so synced
  files there are capped at 32 MiB until a Linux native lane exists.

**What you do.** Answer the 12 questions in §3; each is a yes or a choice between options. Then do
the owner steps in §3.2: Google Cloud clients, Sign in with Apple, three R2 buckets, billing
alerts, test devices and an external cryptographer.

**What starts now (§5; none of it touches the wire):**

- the overdue Cloud Sync security review (U-19);
- I-10a and I-10b, the SDK identity packages that automatic sign-in waits on;
- writing the I-15 plan;
- the Godot crypto speed test (CC-13);
- two read-only checks in production.

## 2. Decisions resolved by the reconciler (the lead may overrule)

**R-1 One AEAD: AES-256-GCM, for every layer.** This covers:

- **Noise:** `Noise_XXpsk0_25519_AESGCM_SHA256` for mode `a` and `Noise_XX_25519_AESGCM_SHA256` for
  modes `v` and `p`. Noise's AESGCM is AES-256.
- **HPKE:** KEM 0x0020, KDF 0x0001, AEAD 0x0002.
- **Cloud Sync:** `pkey-sync-value/1`, `pkey-sync-file/1`, `pkey-sync-chunk/1` and the recovery wrap.

The table compares the two candidates on each platform.

| Platform                                   | AES-256-GCM                                                                                                                                                                                                                                                                       | ChaCha20-Poly1305                                                                               |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Browser (client-core, React, Godot web)    | WebCrypto, native; derived keys stay non-extractable (CS Q8)                                                                                                                                                                                                                      | Not in WebCrypto: needs `@noble/ciphers`, a new dependency with raw keys in the JS heap (CC C9) |
| Node, Python, JVM                          | node:crypto, `cryptography`, JCA                                                                                                                                                                                                                                                  | the same                                                                                        |
| Android (minSdk 24)                        | JCA (Conscrypt) on every API level, constant-time without AES hardware                                                                                                                                                                                                            | JCA from API 28 only (CC §3: "Connect needs API 28")                                            |
| Swift; Godot macOS and iOS                 | CryptoKit. Godot's Apple binding already links Swift: `native/macos/build_apple.sh` and `native/ios/build.sh` compile `PolarisKeyPlatform` and its `@_cdecl` surface `PolarisKeyPlatformC` (`pkp_call`). CC §3's "CryptoKit cannot be called from Objective-C" is therefore wrong | CryptoKit                                                                                       |
| Godot Windows                              | BCrypt, part of the OS. Monocypher 4.0.3 stays for X25519 and Ed25519 only, because CNG has no Ed25519                                                                                                                                                                            | Monocypher                                                                                      |
| Godot Linux and the editor (GDScript lane) | The keystream comes from native `AESContext` ECB over a batch of counters; GDScript does the XOR and a constant-time GHASH. About 1 MB/s (estimate)                                                                                                                               | All in GDScript, add-rotate-XOR. About 2 MB/s (estimate; research §4.5 says "~1 MB/s or less")  |

- **Cost.** The GDScript lane runs at about half the speed. It carries only handshakes and small
  messages (L-10), plus Sync files of at most 32 MiB (CS Q9).
- **Rejected:**
  - Two suites: double vectors, two GDScript AEADs, and a negotiation step that adds a downgrade
    surface. This is CC D6's own argument against an AESGCM suite.
  - AES-CTR with HMAC-SHA256: native in GDScript, but a bespoke construction in every SDK.
- **If CC-13 fails** on the AES-GCM lane, the fix is a Linux GDExtension, not a second cipher.

**R-2 One nearby approval flow, `pkey-peer/1` mode `v`, LAN only.** D is the new device and M is a
signed-in device of the same account.

1. **D starts the request.** D creates its P-1 keys if it has none. It calls
   `POST /<p>/identity/nearby/start {signKey, agreeKey, deviceName?, proof}` (proof purpose
   `nearby-start`) and gets back `{request: "nr_…", expiresIn: 300, interval: 3}`. The server
   stores both keys, the label and the start network.
2. **D finds M.** D browses `_pkeypeer._tcp` for adverts with `m=v` and its product tag `h` (R-4),
   then connects out. When more than one approver answers, D lists them by their HELLO label and
   sends a request only to the one the person picks, so no one else gets a prompt.
3. **Handshake.** `Noise_XX_25519_AESGCM_SHA256` with one-time static keys on both sides. The
   prologue is `pkey-peer/1‖0‖slug‖0‖v‖0`, and HELLO goes each way.
4. **Code.** The commit-reveal of R-3 produces the 6-digit `sas`.
5. **Request.** D sends M `VOUCH_REQ` (0x8010):
   `{v: 1, request, signKey, agreeKey, label, platform, sig}`. `sig` is `pkey-proof/1` with purpose
   `vouch` and value `<b64url h>.<request>`. M checks it.
   - There is no `userCode`: SI C7 shows that a code a victim can be told to type is exactly the
     proof I-37 rejects.
   - There is no separate `pop`.
6. **Approval on M.** M shows `NearbyApproval`: "Sign in {label}?" with three 6-digit codes, one
   of them `sas`. D shows `sas`. Tapping any other code, or "Not now", denies.
7. **Server decision.** M calls
   `POST /<p>/identity/nearby/approve {request, signKey, agreeKey, decision, choice?, proof}` with
   its bearer and its own P-1 proof (`nearby-approve`). The server checks:
   - the keys equal the start's keys;
   - `clientNetwork(approve) == clientNetwork(start)`, or it answers `403 not_nearby`;
   - I-37's approval rules, with a single decision per request (CAS);
   - the licence is chosen on M.

   It then writes D's device row, calls `registerDeviceKeys(…, {via: "nearby"})`, binds the seat,
   audits and emails. D never gets a grant (§12.5.1 rule 5).

8. **Result and keys.** M sends `VOUCH_RESULT` (0x8011) with status `approved`, `denied`,
   `expired`, `not_nearby` or `device_limit`; it is for display only. If the product is E2E and M
   holds R, M also:
   - sends `KEYRING_WRAP` (0x0030): `{ringId, epoch, kid, kem, enc, ct}`, an HPKE wrap to the
     `agreeKey` from step 5;
   - PUTs the same wrap to `/devices/keyring/wraps/{D}`.
9. **D finishes.** D polls `nearby/poll {request, proof}` until it gets a token. It opens R from the
   channel copy and ignores a server copy that differs. Its form shows "Signed in as {email}" with
   "Not you?"; this answers a hostile approver on the same LAN signing D into another account
   (login CSRF; new THREAT-MODEL row).

**R-3 The code needs commit-reveal (a new finding, against CC §2.5 and SI §10).**

- **The flaw.** In XX, whoever sends the last handshake message chooses it after seeing the other
  side's keys. A man in the middle on the LAN can finish one session, then grind its static key in
  the other session until both 6-digit codes match. That takes about 10^6 X25519 operations:
  seconds on a few cores. CC's `HKDF(h)` code and SI's "values derive from the handshake hash" both
  allow it.
- **The fix**, as in ZRTP and Bluetooth numeric comparison:
  1. D → `SAS_COMMIT` (0x8014) `{c: SHA-256(nD)}`, where nD is 32 random bytes.
  2. M → `SAS_NONCE` (0x8015) `{nM}`.
  3. D → `SAS_REVEAL` (0x8016) `{nD}`. M checks `c`.
  4. `sas = u32be(HKDF-SHA256(salt=h, ikm=nD‖nM, info="pkey-peer/1 sas"‖0x00‖mode)[0..4]) mod 10^6`.
- **Limits.** M accepts at most 5 handshakes a minute per advert. A man in the middle then succeeds
  with probability about 10^-6 per attempt.
- **Scope.** It applies to modes `v` and `p`, and its vectors go in `peer-matrix.json` `sas`.

**R-4 M advertises; D connects out.** D needs no listener, so there is no Windows firewall prompt
(SI D-A14); CC §2.4 had D advertise. M advertises an approver instance (`m=v`, a random name, the
`h` tag, renewed every 300 s while in the foreground) only when all of these hold:

- it is signed in;
- the product's `identity.nearby` is on;
- the Local Network permission was already granted, on platforms that ask for one.

Otherwise it advertises after the person picks "Approve a nearby device" in the account menu,
which asks for the permission (L-11). D prefers the OS DNS-SD browser where one exists. Mode `p`
keeps CC's design, in which both sides open pairing.

**R-5 Device keys: one Core package and one store per SDK.**

- **CC-03 (Core) owns:**
  - `device_keys` and `PUT /<p>/devices/keys`;
  - `registerDeviceKeys(db, product, deviceId, {signKey, agreeKey}, {via: "put"|"exchange"|"nearby"})`;
  - `deviceSignKey`, `accountDeviceKeys` and `verifyDeviceSignature`;
  - the lifecycle event (R-7) and the proof (R-6).
- **It lands before I-13.4 and I-40.** SI §6's "a no-op before CC-key" goes away.
- **Every registration carries both keys.** SI's `nonce` and `nearby/start` send
  `{signKey, agreeKey}`, not `deviceKey` alone.
- **New CC-26: the device-key store in each SDK.**
  - API: `ensure()`, `publicKeys()`, `sign(bytes)` and `dh(peerPublic)`. Noise uses `dh`; Sync
    builds HPKE open on it, so the private key is never exported.
  - Storage follows CC §3's table. Keys are generated on first need.
  - Slices: .1 client-core port, proof helper and browser IndexedDB store; .2 Node; .3 Python;
    .4 Swift; .5 Kotlin JVM and Android; .6 Godot GDScript Ed25519 sign (RFC 8032 vectors; CC C14)
    and X25519 (research: verify takes 6.3–7 ms in GDScript, so sign is fast enough); .7 Godot
    native key ops.
  - I-44–I-48, CC-08–CC-14 and U-38–U-40 depend on their SDK's slice and drop their own key steps.

**R-6 One device proof, `pkey-proof/1`.** SI §2.1's line format is the only format.

- **Lines:** `pkey-proof/1`, purpose, slug, deviceId, value, and the token hash or `-`, joined by
  `\n`. Every field is pattern-checked to hold no newline.
- **Purposes:**
  - `keys`: replaces CC's binary `pkey-devkey/1`; the value is `<signKey>.<agreeKey>.<issuedAt>`;
  - `nonce`, `exchange` and `link`;
  - `nearby-start`, `nearby-poll` and `nearby-approve`;
  - `vouch`;
  - `restore`.
- **Corpus.** One generated file, `device-proof.json` (`tools/corpus/deviceProof.ts`, with a Godot
  mirror), replaces SI's `identity-proof.json` and CC's `peer-matrix.json` `pop` section.
- **Owner.** CC-03.4 owns it; it absorbs I-13.6.

**R-7 One device lifecycle.**

- **The dispatcher.** CC-03.3 adds `core/devices/lifecycle.ts`, called after every bind, unbind,
  deauthorise, purge and key upsert. It is modelled on `contributes.onAuthorization`
  (`core/authorizationListeners.ts`) and never fails the request.
- **Core's key ring (U-36) subscribes inside Core.** It drops a removed device's wraps. On `keys`
  it drops the device's wrap, and the device re-wraps to its new key.
- **Services subscribe through `contributes.onDeviceChange`.** Connect uses it to bump the ring.
- **Not built:** CS §2.9's separate "Core clearing hook".
- **Routes.** `deviceKeys` and `keyring` are both `CORE_ROUTES` rows in `src/publicRoutes.ts`,
  matched before `/devices/{deviceId}`.

**R-11 Platform backup and sign-out.**

## 3. Owner questions

Each question lists the recommended option first. They are numbered most important first.

1. **Approve the combined program?** This means §2, the waves and scope in §4, and the three plans
   as edited by §6.
   - Wire version 5 lands first, and the sign-in and Sync amendments are written into the v5
     contract.
   - Automatic sign-in ships first. Inter-account links and Direct Transfer come in wave 4.
   - WebRTC, fast reconnect (IK), QR and CPace pairing, the relay mailbox and native fast paths
     stay unscheduled.

   Options: (a) **Yes.** (b) Yes, but with no version bump: the two new document types enter v4.
   (c) No.

2. **Nearby approval as one flow.**
   - It works on the same network only (a LAN channel plus a same-public-network check), never
     through the relay.
   - The signed-in device shows "Sign in <device>?" with three 6-digit codes, and you tap the code
     the new device shows.
   - The licence is chosen on the signed-in device, and the same tap hands over the sync key.
   - There is no remote approval in v1.

   Options: (a) **Yes.** (b) No: allow remote approval through the relay with a code, which reopens
   R1-07 phishing.

3. **Nearby approval without Cloud Connect.** It works for every product with sign-in on (a
   developer switch, on by default), without turning on Cloud Connect. Cloud Connect stays opt-in
   for linking your devices, the relay, Direct Transfer and inter-account links.
   Options: (a) **Yes.** O-3 then holds in every app, and encrypted sync unlocks nearby even
   without Connect. (b) No: nearby approval only where Cloud Connect is on.

4. **Silent seat binding (SI D-A2).** On a new device, in an app the person already allowed: if
   they hold exactly one licence with a free seat, the app binds it with no tap. This amends
   SIGN-IN.md O-1's one-tap confirm, on the automatic path only. Two or more licences, a full
   licence, Keep, or a first mint still ask.
   Options: (a) **Yes.** (b) No: keep the one-tap confirm everywhere.

5. **Scope of a link made inside an app (SI D-A3).**
   - Google: a Google account linked from inside an app signs the person in to every Polaris Locker
     app only if its email is already verified on their account. Otherwise it works only in that
     developer's apps.
   - Apple: links always stay within one developer.
   - The link offer says which applies. This narrows O-5's "Google identities match across
     developers".

   Options: (a) **Yes.** It closes a takeover in which a malicious app links an attacker's Google
   account to the person's account (SI C5). (b) No: always global.

6. **O-1 for device channels.**
   - Cloud Connect's channels between a person's own devices are end-to-end against the relay and
     the network, but they trust device certificates the Worker signs.
   - A compromised Worker could add a device and receive app data sent to the person's devices.
   - Sync keys never travel on those channels, so Cloud Sync stays end-to-end.

   Accept this for v1, with a later package that binds channels to the sync key?
   Options: (a) **Yes.** (b) No: build device-signed rosters now, which costs about 2 engineer-weeks
   and a second roster format in every SDK.

7. **Quotas and hard caps (O-2).**
   - **Relay:** 256 MiB a day per person (16 MiB without a licence), at most 4 GiB a day per person,
     and 500 GiB a month per product.
   - **Cloud Sync per person:** the tier's `pkey.cloudSync.bytes`, at most about 1.06 GiB.
   - **Cloud Sync files:** up to 1 GiB each (32 MiB by default).
   - **Cloud Sync per product:** 50 GiB and 100,000 people.
   - "Product tier" means the product's own tiers.

   Options: (a) **Yes.** (b) Change the numbers (give them).

8. **Recovery for encrypted sync.**
   - Platform key backup (iCloud Keychain, Google Block Store) is on by default, and a developer
     can turn it off.
   - There is one recovery code per app.
   - Keys do not rotate automatically when a device is removed; Reset encryption is manual.
