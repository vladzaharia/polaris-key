# Lead contract: Cloud Connect, automatic sign-in and Cloud Sync files (2026-10-24)

The lead owns the shared primitives so three planners can work in parallel without inventing three key systems. Planners may challenge a primitive with evidence; they may not fork it. Research inputs: `research-identity-devices.md`, `research-cloud-sync.md`, `research-device-linking.md` (all in this directory).

## Owner request (verbatim intent)

1. **On-device automatic account linking.** If the device's Google and/or Apple account is linked to the person's Polaris Locker account, launching the app signs in with no login screen and finds — or auto-mints — a licence. The device screen (device limit, licence choice) still shows when it applies.
2. **Automatic inter-device linking (optional data transfer).** Same-app, same-account devices find each other automatically on the LAN, pair, exchange keys, open channels — direct on the LAN or through a relay. Developers can opt into inter-account links (LAN + approval). Native protocols where the SDK has them, plus a platform-neutral method; cross-OS and cross-language.
3. **Cloud Sync actually built**, including small and large file uploads, multipart and patched (delta) files.

## Owner decisions (2026-10-24)

- **O-6 Release (owner, 2026-10-26):** Cloud Connect, Cloud Sync and Direct Transfer, with the fixes that come with them, launch as **0.10.0**, a new minor version, once they ship.
- **O-7 Direct Transfer (owner, 2026-10-26):** the name of Cloud Connect's peer-to-peer data transfer (CC-20): information moves between two clients that have already authenticated with each other through Cloud Connect (same-account peers, or an inter-account link), directly on the LAN or through the relay. It is a feature of the Cloud Connect service, not a separate service, and it launches in 0.10.0 with Cloud Connect and Cloud Sync.

- **O-1 Encryption:** end-to-end by default for Cloud Sync data and device channels. Keys live only on the person's devices; Polaris Key stores and relays ciphertext. A product may opt into **server-readable** sync (server-side merge, console views). This reverses U-17's drop.
- **O-2 Cost:** relay and file storage run on Polaris Key's Cloudflare (Durable Objects, R2) with **included quotas per product tier and hard caps**; LAN is preferred automatically and costs nothing.
- **O-3 Desktop/web sign-in:** where the OS can't sign in silently, a **nearby signed-in device of the same account approves the new device with one tap**; the new device shows no login screen.
- **O-4 Service name (owner, 2026-10-24):** device linking and transfer (direct on the LAN or through the relay) ship as one opt-in service, **Cloud Connect**. It is a new row in `tools/services.json` (proposed slug `connect`, label `Cloud Connect`, `requires: ["identity"]`, coherence code `connect_requires_identity`, its own console feature group and accent), built through the "Adding a service" checklist (`packages/docs/src/content/docs/contribute/layout.md`). It owns device certificates, the roster, discovery keys, the relay Durable Object, pairing and inter-account links. Cloud Sync's E2E key ring (P-3) and the nearby vouch (P-5) use Cloud Connect's device keys and channels through Core descriptor hooks (rule 6), never by importing it.
- **O-5 No linked account (owner, 2026-10-24):** when automatic sign-in finds no linked account, the app shows the **regular sign-in**. After it succeeds, if the device has a platform identity (Apple, Google) that is not yet linked, the kit **offers to link it** so later launches in this and other apps sign in automatically. One tap links it. The fresh sign-in counts as the step-up, and the link is audited and emailed like every account-link change; `link_conflict` still applies. Declining is remembered on the device, so the app does not ask again. The copy must not promise more than the link gives: Google identities match across developers, but Apple identities match only within one developer team (`tenant_scope`; L-4).

## Shared primitives (lead decisions; challenge with evidence, don't fork)

- **P-1 Device keys.** Every install generates, on device, an Ed25519 signing key and an X25519 agreement key (hardware-backed where the platform allows: Secure Enclave/Keychain, Android Keystore/StrongBox, TPM/DPAPI, libsecret; web: non-extractable WebCrypto). Private keys never leave the device. The public keys are registered against the existing device row (pairwise subject + device id).
- **P-2 Device certificate.** The Worker issues each registered device a short-lived signed **device certificate** (proposed `typ` `pkey-peer+jws`, 7-day lifetime, plus a signed monotonic **roster** `pkey-ring+jws` for revocation (spike §4.2, Matter-like), signed by the product key, verified against the app's pinned trust like every other document): `{ iss, aud: product, sub: ps_ subject, deviceId, signKey, agreeKey, issuedAt, expiresAt }`. Two devices prove "same app, same account" to each other **offline** by exchanging certificates. This is a new signed document → a wire change (rule 2): plan the `PROTOCOL_VERSION` decision, the catalog, the corpus vectors and every SDK's verifier. Revocation: removing a device or signing out stops renewal; certificates are short (hours–days) and peers refuse expired ones.
- **P-3 Account key ring (E2E root).** Per (product, subject): a symmetric **sync root key** created by the first device, wrapped to each device's X25519 key (HPKE) and stored server-side only as wrapped blobs the server cannot read. A new device obtains it from another device (P-5 one-tap, or a LAN/relay pairing) or from a recovery secret the person keeps (platform key backup where available: iCloud Keychain, Android Block Store; else a printed/typed recovery code). Cloud Sync E2E keys and the LAN discovery key derive from the root key (HKDF, distinct labels). Products that opt into server-readable sync skip E2E for data but keep device certificates.
- **P-4 Channels.** One platform-neutral channel protocol for every transport: a Noise handshake (XX for first contact, IK once peers know each other) authenticated by the device certificates, then length-prefixed encrypted frames with a version byte and message types. Transports: TCP on the LAN (native discovery finds the peer), and a WebSocket **relay** Durable Object that forwards ciphertext between two authenticated device sessions (per-pair rooms; quotas per O-2). Native fast paths (Multipeer/Network.framework, Nearby Connections on the Play flavour) are optional adapters that carry the same frames.
  - **Note (2026-10-26, plan-combined.md):** one AEAD everywhere: Noise_XXpsk0_25519_AESGCM_SHA256 for mode a and Noise_XX_25519_AESGCM_SHA256 for modes v and p, AES-256-GCM (R-1). XX only in v1; IK is optional CC-25 (CC D3). The account mode uses a PSK from K_disc (CC D4). The short code is commit-reveal, not taken from the handshake hash (R-3). CC C1.
- **P-5 Nearby one-tap approval.** A device with no session (desktop/web/or a phone whose OS can't sign in silently) asks nearby same-app devices to sign it in; the signed-in device shows "Sign in <device label>?" with the requesting device's label and a short code both screens display; one tap → the signed-in device asks the Worker to register the new device under its subject (a server-recorded approval, audited and emailed like other account changes), then hands over the wrapped root key over the channel. Must satisfy I-37 / R1-07: no proof a starter can obtain by instructing a victim (the approver is physically near and sees the matching code on both screens; same-LAN proximity + code, never a link).
  - **Note (2026-10-26, plan-combined.md):** one flow, `pkey-peer/1` mode v, LAN only, never the relay (R-2). The new device D asks; the signed-in device M shows three 6-digit codes and the person taps the one D shows (R-3). The key hand-over is `KEYRING_WRAP` (0x0030), mode v only (R-9). Gated by `identity.nearby`, on by default, so it works with Connect off (R-13).
- **P-6 Discovery adverts.** DNS-SD service `_pkeypeer._tcp` (and the platform equivalents). Same-account instances advertise a **rotating name**: `p1-` + 16 base32 chars of HMAC-SHA256(K_disc, "pkey-peer/1 disc" ‖ u64be(epoch900)) — 15-minute epochs; K_disc rotates when the roster changes (spike §8), TXT minimal (protocol version only). No device names, ids, subjects or hashes in the clear (rule 7). Devices without the root key (P-5 requesters, inter-account pairing) advertise a short-lived random "pairing" instance only while the person has opened pairing in the app.
  - **Note (2026-10-26, plan-combined.md):** the approver M advertises (m=v) and D connects out, so D needs no listener and no firewall prompt (R-4). The account-mode name also covers `deviceId`: every same-account device would otherwise advertise the same name (CC C1, D5).
- **P-7 Inter-account links.** Developer opt-in per product. Both people open pairing; the devices run a PAKE over the short code both screens show (CPace or SPAKE2), then exchange certificates and each side approves. The link is a local, revocable trust between two devices (optionally recorded server-side for the product's records); it never merges accounts or moves licences.
- **P-8 Silent sign-in (feature 1).** Built as I-13: a native-token grant on `POST /<p>/identity/token` accepting an Apple identity token (bundle-id audience) or a Google ID token (Android client-id audience), verified once and never stored. Silent only when the provider link and the product grant already exist (SIGN-IN.md §4.4); otherwise `interstitial_required` → the normal flow. Licence: an existing usable licence, else auto-mint under the product's auto-issue policy (`oidcDefault`/`both`, fails closed, `license-mint` claim) or restore a store purchase the store verifies; `device_limit` and `license_choice_required` still show. Apple: `ASAuthorizationController` with `.preferImmediatelyAvailableCredentials`; Android: Credential Manager `GetGoogleIdOption(filterByAuthorizedAccounts = true, autoSelectEnabled = true)`; web: FedCM auto-reauthn / GIS `auto_select` where the browser supports it; everything else → P-5.

## Lead decisions on the spike's open questions (research-device-linking.md §10; lead authority, owner may veto)

- **L-1 Consent (D22):** the first sign-in to an app with a verified platform token shows an **in-app confirm**, drawn by the kit and system-style ("Continue to <App> as a…@…"), never a login screen. It enters no credentials, so D17 holds. A vouch tap on the approving device also counts as consent. The browser interstitial stays only for unverified email and link conflicts. Later launches are silent.
- **L-2 "Automatic"** means no login screen drawn by the app, at most one OS sheet (Sign in with Apple has no silent mode), and the L-1 confirm only once per app.
- **L-3 Vouching** always needs a tap on the approving device (O-3). A silent vouch would let anyone on the LAN who runs the app collect licences.
- **L-4 Apple across developers:** accept tenant scoping for v1. Locker-domain passkeys inside apps (Locker's AASA and assetlinks generated from product data) are phase 5, as a separate plan.
- **L-5 Google audience:** per-product client ids, held as product data (rule 5). A Locker-owned Google project is deferred.
- **L-6 Wire:** `pkey-peer+jws` and `pkey-ring+jws` are new signed documents (rule 2). The Cloud Connect planner recommends a v5 bump or additive types under v4, citing how `pkey-feed+jws` and `pkey-release+jws` entered the set. The owner approves the plan.
- **L-7 Scope:** peers link only within one product, over the pairwise subject. There is no developer-wide ring, because that would be a cross-product correlator.
- **L-8 Relay:** app data may cross the relay within the tier quota (O-2). The LAN is preferred automatically. The mailbox is phase 5.
- **L-9 Inter-account:** SAS or QR first, over the LAN. CPace and a server-recorded contact link come later.
- **L-10 Godot:** GDScript may do the handshake and control messages on desktop, but only after a measured speed and constant-time check on desktop and ARM. Bulk data and mobile and web exports use the native or WebCrypto lane.
- **L-11 Permissions** (iOS/macOS Local Network, Android 17 `ACCESS_LOCAL_NETWORK`, Chrome Local Network Access) are requested on first use of a nearby feature, never at launch. The copy needs a UX review.
- **L-12 Auto sign-in ladder** (spike §7): stored session, then platform silent restore, then platform silent identity, then one OS sheet, then the nearby vouch, then device code, QR or redirect. The regular sign-in (O-5) is the last rung, followed by the link offer.

- **L-13 Ownership:** device public keys (P-1) and the account key ring (P-3) live in **Core** (`core/devices`, a new `core/keyring`), because Cloud Connect, Cloud Sync E2E and the vouch all use them. Cloud Sync E2E therefore does not require Cloud Connect: an approving device wraps the root key to the new device's agreement key and uploads the blob. Cloud Connect owns the certificates, the roster, discovery, channels, the relay, pairing and inter-account links. The Cloud Connect planner designs P-1; the Cloud Sync planner designs P-3. The spike's server-delivered K_disc, rotated when the roster changes, replaces the old "derive from the root key" idea unless the Cloud Connect planner shows otherwise.
  - **Note (2026-10-26, plan-combined.md):** nearby belongs to Identity and the engine is shared: `identity.nearby` gates mode v, `services.connect` gates mode a, mode p and the relay, and the `pkey-peer/1` engine and LAN adapters ship in a module both load (R-13). Device keys are one Core package (CC-03) with one key store per SDK (CC-26), R-5.

## Cloud Sync files (feature 3) — lead positions

- Build the planned U-09 (records) and U-10 (files) on the existing CloudSyncDO + R2, adding E2E per O-1/P-3 (client-side encryption of record values and file bytes; the server sees sizes, hashes of ciphertext, timestamps). Settings policies that need plaintext on the server (`max`, `min`, `merge`) run client-side in E2E mode; the server keeps ordering (HLC), idempotency and quotas.
- Uploads: small (single request ≤ the zone body limit) and large via R2 multipart (adapt `services/release/packages/ociUpload.ts`), resumable, per-person upload state, SHA-256 of ciphertext verified on finalize, quotas per O-2.
- Patched files: a chunked, content-defined file format so an edit uploads only changed chunks (reuse `pkey-chunks/1` ideas and `pkey-patch/1` apply where it fits), designed so it works with E2E (chunk ids are keyed hashes, not plaintext hashes). A plan-mode wire decision with corpus vectors.
- The six SDK transports (U-06/07/20/21), conflict vocabulary (U-08), saves (U-22/23), background transfer per platform (URLSession background, WorkManager, etc.), progress, the console Data tab (U-11a), docs (U-15a), privacy cascade (U-12) and the open U-19 security review are all in scope for "actually built".

## Constraints every plan honours

- AGENTS.md hard rules (wire → plan first; corpus/transcripts regenerated; GENERATED files; terminology; products are data; layers and table ownership; rule 7 privacy; naming — end users see **Polaris Locker**; validators need mutation-table entries; routes need OpenAPI + descriptor surface).
- Security first: one Sonnet security review per security-bearing slice, plus a threat-model update per new surface (R1-07 relay/phishing, relay abuse, LAN spoofing, downgrade, key loss/recovery, revocation).
- Every new dependency pinned exactly, ≥14 days old; no public-registry publishing.
- Slices ≤60 minutes of builder time, scoped tests only, CI runs the matrix.
