## 1. Summary

- **Two stores on one principal.** _Synced settings_ ride the shipped `config.*` API. Every
  Editable catalog `config` key syncs, and undeclared _open settings_ sync within one budget.
  _Records_ live in declared collections, and any record may carry one file. `saves` and `session`
  are record templates, and the v1 SDK surface is saves only.
- **One conflict vocabulary**, `lastWrite | max | min | merge | union | revision`, for both
  stores. `onAttach` is gone: the first sign-in is an ordinary sync.
- **The quota is the entitlement `pkey.cloudSync.bytes` alone.** The registry default is 256 MiB
  and tiers override it. A device with no usable licence gets 1 MiB and no files. The operator
  has one ceiling setting and one kill switch, and the device-trust bar moves into Core's trust
  policy.
- **The config chain is five layers.** Synced settings fill the device's `local` slot
  (WIRE-CONTRACT-V4 §2.2.1). They never enter the server merge, and licence overrides stay
  layer 4.
- **Contract slice (U-01b, the W-SYNC slot).** WIRE-CONTRACT-V4 §13 in full, `sync-scenarios.json`
  v2, the catalog and validator vocabulary, client-core's reference machine (routes, the `local`
  store, the import) and the parity rows. It also ships a lenient trust-policy reader, the expand
  step for U-05's `cloudSyncWrite`. U-05's `cloudsync-*` transcripts follow.

- **`@polaris-key/protocol/sync`** (U-05) is as U-01 §2.6 describes, with these changes: no

  1048576 added. `SYNC_MAX_VALUE_BYTES` moves here from client-core. U-05 moves the numbers here
  from `@polaris-key/catalog`, which then re-exports them, so they live in one place.
- **`client-core/src/cloud-sync.ts`** (U-01b). The machine stays pure. It does not import
  `@polaris-key/catalog` (its only dependencies are `jws` and `protocol`). The host passes it the
  routes from `syncedSettings(catalog)`.
  - **Routes in.** `CloudSyncCatalog.settings` becomes `SettingRoute[]`, which is
    `{key, route: "synced", scope: "user" | "platform", policy, schema?}` or
    `{key, route: "local" | "locked" | "refused"}` (`:57-74`). A key with no route is an open
    setting.
  - **`SyncTarget`** gains `scope: "platform"` (`:83-85`). A `synced` key is pushed with its
    route's scope, and an open setting with `user`. Today both push sites hard-code `"user"`
    (`:532`, `:942`).
  - **`set` and `clear`** replace `setConfig` and `clearConfig`, which are deleted with no alias
    (owner, 2026-10-07: remove, don't deprecate). `edit` (`:892-899`) answers in this order,
    journalling nothing on a refusal:
    - `refused` (a declared `secret` or `flag`): `bad_request`;
    - `locked` (catalog-locked), or locked by the current document: `managed_by_admin`;
    - a value over `SYNC_MAX_VALUE_BYTES` (8192, added to client-core now; U-05 moves it):
      `bad_request`;
    - `local`: written to the new persisted `CloudSyncPersisted.deviceLocal`. Sign-in never moves
      it and no push reads it. An SDK backs `deviceLocal` with its existing `config.local` store;
    - otherwise the key is drafted as today, and an undeclared key becomes an open setting.
  - **State.** `SettingState` becomes `{sync: "local" | "pending" | "synced", invalid, locked}`
    (`:205-209`). `sync` is `local` with no principal or for a `local` key, `pending` while a
    draft or journal op exists, and `synced` otherwise. This replaces `pending`.
  - **Import.** `importLocal(values)` is called once per install, with the legacy `config.local`
    contents. It filters by route:
    - `synced` and undeclared keys go into the local partition at the HLC floor
      `000000000000:0000`, without `preContact`, so rule 8 never re-stamps them;
    - `local` keys go into `deviceLocal`, which is the same `config.local` store, so they never
      move;
    - `locked` and `refused` keys are not imported. They stay in `config.local`, read as today
      and never synced;
    - why the floor: any cloud value or tombstone beats it under `lastWrite` (the push gets
      `conflict` and the client takes the server copy), so a device that upgrades last cannot
      overwrite newer cloud values. The server accepts the floor, because it clamps only future
      stamps (U-01 §2.3). A `max`/`min` key is decided by value, as it should be. The store's
      mtime was rejected because not every platform's store keeps per-key times.
  - **Records.** `CollectionDecl.policy` gains `lastWrite`, `max`, `min` and `merge`, plus
    `field`.

    and 64 KiB in total. Never signed, never read by any server path, and exported and deleted
    with settings. A synced value fills §2.2.1's `local` slot on **every device of the person**.

    local store the person cannot edit. The bound is the person: no push reaches another
    principal. Mitigations: an app treats an undeclared key as untrusted input, and a key that
    matters is declared with a schema, routed `local`, or locked (locks beat the `local` slot).
    The authoring docs and both skills say so.

    cannot. It is resolved per device (§13.1), so a device cannot borrow another device's quota.

  (`services/config/admin/catalog.ts:146-151`), so after a revert the old validator would refuse
  the next publish of any such product. The new vocabulary means: `template`, a collection
  `conflict` of `max` or `min`, `conflictField`, a `user` block without `sync`, or a `user` block
  on a locked key. Before reverting, the lead runs the §7 precondition query with those
  patterns. If any active catalog matches, roll forward instead. Otherwise the revert is pure,
  and v1 of the scenario file comes back with it.
- U-01b's lenient trust-policy reader is never reverted while U-05 is deployed. A U-05 revert
  leaves it in place (§6.1).
- After U-05, the order is: `cloudSync.writesPaused`; then the product's Cloud Sync switch
  (`404`, and SDKs stay local); then a code revert. The directory tables stay, unread.
