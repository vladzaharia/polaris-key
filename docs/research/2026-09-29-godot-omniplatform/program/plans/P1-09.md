## 1. Summary

- **One new unsigned corpus file**, `conformance/corpus/v2/stage-matrix.json`
  (`stageMatrixVersion: 1`), written by `buildStageMatrixV1()` in `tools/sign-corpus.ts`. It holds
  29 hand-authored flow rows and 7 boot-guard cases. Each row is an ordered list of host events
  with the exact emits each event produces. The file is mirrored into the Swift test bundle (and
  into Godot's, once P1-01 creates that mirror) and guarded by `pnpm gen:corpus -- --check`.
- **One new pure module**, `packages/client-core/src/stages.ts`, exported from the barrel and as
  `@polaris-key/client-core/stages`. It provides `initialBootState(options)`,
  `bootTransition(state, event) → { state, emits }` and the boot-guard decision
  `bootGuardAction({ staged, failedBoots })` with `MAX_FAILED_BOOTS = 2`.
- **Ports and runners.** Python (`polaris_key/core/stages.py`) and Swift
  (`PolarisKeyCore/Stages.swift`) get a port and a runner over the same file. Node and React use
  `client-core` directly. Godot follows in P1-10.
- **No wire, Worker, catalog or manifest change.** `cases.json`, `gate-matrix.json` and
  `fingerprint.json` stay byte-identical.
- The plan resolves the brief's five open decisions and one more (§8), and makes six changes to
  the brief's proposed shape (§2.4).

## 2. Contract

### 2.1 Wire contract, `shared-protocol`, `shared-jws`

Nothing normative changes. The stage machine never crosses the wire or the disk (the
WIRE-CONTRACT-V3 scope line), so there is no new `[C]` rule. `PROTOCOL_VERSION`, `CACHE_VERSION`,

`shared-protocol` and `shared-jws` are untouched. `stages.ts` imports only the `LicenseStatus`

### 2.2 The `client-core` API

```ts
// packages/client-core/src/stages.ts, also exported as @polaris-key/client-core/stages
export const BOOT_STAGES = [
  "idle",
  "shell",
  "guard",
  "sync",
  "gate",
  "decide",
  "fetch",
  "mount",
  "ready",
  "background",
  "offline",
  "blocked",
  "error",
] as const;
export const BOOT_OUTCOMES = [
  "running",
  "waiting",
  "ready",
  "blocked",
  "offline",
  "error",
] as const;
export type BootStage = (typeof BOOT_STAGES)[number];
export type BootOutcome = (typeof BOOT_OUTCOMES)[number];
export interface BootOptions {
  allowOffline?: boolean; // default true
  allowGrace?: boolean; // default true
  requiredPacks?: readonly string[]; // default []; copied, compared by exact string
}
export interface BootState {
  readonly stage: BootStage;
  readonly outcome: BootOutcome;
  readonly options: Readonly<Required<BootOptions>>;
  readonly sync: "pending" | "ok" | "offline" | "error"; // latest sync result; a timeout is "offline"
}
export function initialBootState(options?: BootOptions): BootState; // idle, running, sync "pending"
export function bootTransition(
  state: BootState,
  event: BootEvent,
): { state: BootState; emits: BootEmit[] };
export const MAX_FAILED_BOOTS = 2;
export type BootGuardAction = "none" | "apply-staged" | "roll-back";
export function bootGuardAction(input: {
  staged: boolean;
  failedBoots: number;
}): BootGuardAction;
```

`BootEvent` and `BootEmit` are unions discriminated on `type`. Their JSON form is the corpus form,
byte for byte, in every language, and no port renames a string:

- event types are dotted (`sync.done`);
- emit types are snake_case (`stage_changed`), matching the signal names renderers expose;
- payload keys are camelCase and payload values are kebab-case.

| Event `type`                          | Payload                                                      | Accepted in                                         |
| ------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------- |
| `start`                               | none                                                         | `idle`                                              |
| `shell.done`                          | none                                                         | `shell`                                             |
| `guard.done`                          | `result`: `ok`, `applied` or `rolled-back`                   | `guard`                                             |
| `sync.done`                           | `result`: `ok`, `offline` or `error`                         | `sync`                                              |
| `sync.timeout`                        | none (sent by the host's own timer)                          | `sync`                                              |
| `gate.status`                         | `status`: a `LicenseStatus` from `licenseState`              | `gate`, waiting or not                              |
| `decide.done`                         | `decision`: `none`, `optional` or `required`                 | `decide`                                            |
| `fetch.done`                          | `result`: `ok`, `offline` or `failed`; `installed`: pack ids | `fetch`                                             |
| `mount.done`                          | none                                                         | `mount`                                             |
| `background.start`, `background.done` | none                                                         | `ready` and `background` respectively               |
| `retry`                               | none                                                         | `gate` while waiting, `offline`, `blocked`, `error` |
| `play-offline`                        | none                                                         | `offline` (refused on every v1 path)                |
| `fail`                                | `code`: a host error code                                    | `shell` to `mount`, except `gate` while waiting     |

| Emit `type`        | Payload                                                        | When                                       |
| ------------------ | -------------------------------------------------------------- | ------------------------------------------ |
| `stage_changed`    | `stage`, `previous`                                            | on every stage change, always first        |
| `waiting`          | `status`                                                       | the gate needs the player                  |
| `update_available` | none                                                           | `decide.done optional`                     |
| `blocked`          | `reason`: `update-required` or `not-available`                 | a gate block, or `decide.done required`    |
| `offline`          | `canPlayOffline`: `false` on every v1 path                     | the boot cannot continue without a network |
| `error`            | `code`: `sync-failed`, `fetch-failed`, or the code from `fail` | the boot stopped on an error               |
| `boot_rolled_back` | none                                                           | `guard.done rolled-back`                   |
| `ready`            | none                                                           | `mount.done`, once per boot                |

### 2.3 Transition rules

The normal path runs `idle → shell → guard → sync → gate → decide → fetch → mount → ready`. Every
stage is entered even when it has nothing to do (decision 1).

General rules:

- An event that is not accepted in the current stage is **ignored**: the same state comes back with
  no emits. The common case is a late `sync.timeout` (row 26).
- A transition emits `stage_changed` first when the stage changes, then at most one other emit.
- `retry` returns to `sync` and resets `sync` to `pending`. `shell` and `guard` run once per
  launch.
- `fail {code}` moves to `error` and emits `error {code}`.
- `mount.done` moves to `ready` and emits `ready`. `background.start` and `background.done` move
  between `ready` and `background`, and the outcome stays `ready`.
- `guard.done` moves to `sync`. `rolled-back` also emits `boot_rolled_back`.

**Sync.** How the result of the sync stage decides what happens next:

| Event                                  | `allowOffline: true`                             | `allowOffline: false`                    |
| -------------------------------------- | ------------------------------------------------ | ---------------------------------------- |
| `sync.done ok`                         | go to `gate` (`sync: ok`)                        | the same                                 |
| `sync.done offline`, or `sync.timeout` | go to `gate` using local state (`sync: offline`) | go to `offline`, `canPlayOffline: false` |
| `sync.done error`                      | go to `gate` using local state (`sync: error`)   | go to `error`, `code: sync-failed`       |

**Gate.** How `gate.status` decides what happens next:

| Status                                            | After `sync: ok`                        | After `sync: offline` or `error`                                           |
| ------------------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------- |
| `ok`, `not-applicable`, `grace` (if `allowGrace`) | go to `decide`                          | the same                                                                   |
| `needs-activation`, `revoked`                     | stay in `gate`, waiting; emit `waiting` | the same                                                                   |
| `expired`, `grace` (if not `allowGrace`)          | stay in `gate`, waiting; emit `waiting` | the stop for that sync result: `offline {false}`, or `error {sync-failed}` |
| `version-too-old`                                 | go to `blocked`, `update-required`      | the same                                                                   |
| `version-too-new`, `channel-not-entitled`         | go to `blocked`, `not-available`        | the same                                                                   |

A stop caused by a failed sync reports what failed, at the sync stage and at the gate alike:
`offline {canPlayOffline: false}` after `sync.done offline` or a timeout, and
`error {code: sync-failed}` after `sync.done error` (rows 5 and 29).

The pass set equals `isUsable` (with `allowGrace: true`), and a unit test pins that equality.

**Decide.** `none` goes to `fetch`. `optional` goes to `fetch` and emits `update_available`.
`required` goes to `blocked` with `update-required`.

**Fetch.** The missing set is `requiredPacks` minus `installed`:

- If nothing is missing, go to `mount`, whatever the `result` (a failed optional download never
  blocks play).
- If something is missing and `result` is `offline`, go to `offline` with `canPlayOffline: false`.
- If something is missing otherwise, go to `error` with `fetch-failed`.

**Purity.** `bootTransition` does no I/O, reads no clock, uses no randomness and never mutates its
input. `bootGuardAction` is equally pure.

**Boot guard.** `bootGuardAction` decides what happens at launch:

- `failedBoots ≥ MAX_FAILED_BOOTS` gives `roll-back`;
- otherwise, `staged` gives `apply-staged`;
- otherwise, it gives `none`.

The host defines the two inputs, so P3-10 counts exactly this way:

- `staged` means the host has a staged update that it has already verified (size and SHA-256
  against its record) and that is still eligible (same channel and engine, newer than the binary).
- `failedBoots` counts the launches of the active slot that passed the guard and were never
  confirmed. The host resets it to 0 when a boot is confirmed and whenever the active slot changes.

Under this rule, two crashed launches roll back on the third, as Diceroll does (notes/A4 §1.5).
One deliberate difference: a rollback is not combined with applying a staged update in the same
launch. That keeps `guard.done` single-valued, and the staged update is considered at the next
launch.

### 2.4 Changes from the brief's proposed shape

1. `start` carries no payload. The options go to `initialBootState(options)`, which is a row's
   `init`, so `retry` reuses them.
2. `shell.done {cache}` is dropped, and `shell.done` has no payload in v1. The gate already says
   whether local state is usable. A separate cache flag would stop an unlicensed product's first
   offline launch, and would hide offline bundle import behind an offline card (rows 12 and 13).
3. `gate.resolved` is merged into `gate.status`, which the host sends again while the machine is
   waiting. One event means one code path in every port.
4. `fetch.done` carries `installed` instead of `missingRequired`. The host reports facts, and the
   machine derives what is missing from `requiredPacks`, so `requiredPacks` is not dead input.
5. Additions:
   - the `allowGrace` option, which mirrors React's `<LicenseGate allowGrace>` and P1-10's
     `allow_grace`;
   - the `waiting {status}` emit, because renderers draw only what the machine says;
   - `fail {code}` and `background.start`;
   - the stages `idle`, `offline`, `blocked` and `error`.
6. Rows use per-step emits instead of one flat list. This pins which event produced each emit.

## 4. Corpus

### 4.1 The file

The file is plain JSON, like `gate-matrix.json`: it has no signature, no `typ` and no key.

```jsonc
{
  "stageMatrixVersion": 1,
  "description": "…", // the reducer, the event and emit forms, the ignore rule, append-only
  "maxFailedBoots": 2, // runners assert it equals MAX_FAILED_BOOTS
  "vocabulary": {
    "stages": ["idle", "shell", "…", "error"], // BOOT_STAGES, 13
    "outcomes": ["running", "…", "error"], // BOOT_OUTCOMES, 6
    "events": ["start", "shell.done", "…", "fail"], // the 14 event types
    "emits": ["stage_changed", "…", "ready"], // the 8 emit types
    "guardActions": ["none", "apply-staged", "roll-back"],
  },
  "rows": [
    {
      "name": "…",
      "init": { "allowOffline": true, "allowGrace": true, "requiredPacks": [] },
      "steps": [
        {
          "event": { "type": "start" },
          "emits": [
            { "type": "stage_changed", "stage": "shell", "previous": "idle" },
          ],
        },
      ],
      "expect": { "stages": ["shell", "…"], "outcome": "ready" },
    },
  ],
  "guardCases": [
    {
      "name": "…",
      "input": { "staged": false, "failedBoots": 0 },
      "expect": { "action": "none" },
    },
  ],
}
```

`expect.stages` lists every stage entered, in order. The last entry is the final stage. A runner
asserts four things:

- each step's emits;
- the stage sequence built from the actual `stage_changed` emits;
- the final `state.stage` and `state.outcome`;
- that its own stage, outcome and event names equal `vocabulary`.

### 4.3 The rows

Every row's stages begin `shell, guard, sync`. The notation used below:

- **`P`**: the prefix `start`, `shell.done`, `guard.done ok`.
- **`T`**: the tail `decide.done none`, `fetch.done ok []`, `mount.done`. It adds the stages
  `decide, fetch, mount, ready` and the emit `ready`.
- **`gate X`, `sync X`, `fetch X [ids]`**: the events `gate.status`, `sync.done` and `fetch.done`
  with that status, result or `installed` list.
- **`init` values:**
  - `D` is `{ allowOffline: true, allowGrace: true, requiredPacks: [] }`;
  - `D-O` is `D` with `allowOffline: false`;
  - `D-G` is `D` with `allowGrace: false`;
  - `D+K` is `D` with `requiredPacks: ["core"]`;
  - `{}` means every option is omitted, which pins the defaults.

Every row has been replayed through a scratch prototype of §2.3, and all 29 reach the stages,
emits and outcomes shown.

### 4.5 Drift gate and versioning

- `pnpm gen:corpus -- --check` guards the source file and every mirror, file for file (rule 1).
  Nobody edits the JSON by hand.
- **The file is append-only**, like `CARRIED_MATRIX_ROWS`. Adding rows that use only v1 semantics
  keeps `stageMatrixVersion: 1`. The version is bumped when:
  - the vocabulary changes;
  - any existing row's expectation changes;
  - `canPlayOffline` can become `true`.
- **Every runner asserts the exact version**, so a bump is a deliberate change in all languages.
- **Extensions come from plan-mode packages** (decision 3):
  - P3-01 plans the boot-confirmation rows and P3-02 emits them;
  - P4-01 plans the pack rows and P4-04 or P4-06 emits them.

## 8. Decisions and risks

Each decision is resolved below, with its reason. Approving this plan approves them.

| #   | Question                                  | Resolution                                                                                                                                   | Why                                                                                                                                                                                                                          |
| --- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Are stages with nothing to do entered?    | Yes, in order. P1 hosts send `guard.done ok`, `fetch.done ok []` and `mount.done` at once                                                    | Every renderer can rely on one sequence, and P3-10 and P4-08 fill the stages without changing it                                                                                                                             |
| 2   | Where does the file go?                   | `conformance/corpus/v2/stage-matrix.json`, unsigned, with its own `stageMatrixVersion: 1`                                                    | The runners keep one directory, and the file's version is independent of `corpusVersion`                                                                                                                                     |
| 3   | How do later phases extend it?            | Append-only rows. Bump the version when the vocabulary or an existing expectation changes. Extensions come through plan-mode packages (§4.5) | P3-10 and P4-08 are not plan-mode, so they cannot own an extension                                                                                                                                                           |
| 4   | Who owns timeouts?                        | The host, which sends `sync.timeout`. A late timeout is ignored (row 26)                                                                     | The matrix stays clock-free and deterministic                                                                                                                                                                                |
| 5   | Pin the boot guard now?                   | The launch decision, yes (`bootGuardAction`, G1–G7, rows 24–25). The confirmation criterion, no: that moves to P3-01 item 20                 | The launch decision is Diceroll's tested rule. When a boot counts as confirmed interacts with the skip-version rule (`update-matrix.json`) and the pack state's `confirmedBootSeq`. A wrong criterion causes false rollbacks |
| 6   | Do Python and Swift stay in this package? | Yes                                                                                                                                          | Each port is about 200 lines, and the estimate holds                                                                                                                                                                         |

**Risks.**

1. **Deferring confirmation leaves a known trap to P3-01.** If a boot counts only at `ready`, a
   player who quits twice at the activation screen rolls back a good update. The never-re-offer
   rule then skips that version for good.
2. **`canPlayOffline` is `false` on every v1 path.** The first `true` path (a playable pack
   subset) changes semantics, so P4-01's plan bumps the file to `stageMatrixVersion: 2`.
3. **A renderer that decides transitions itself drifts silently.** P1-10's acceptance already
   drives `PKeyBoot` through every row.
4. **Decoding.** Row 10's `init: {}` is the only place a field is omitted, and runners decode
   strictly everywhere else. Godot parses JSON numbers as floats, so its port compares
   `failedBoots` numerically.
5. **The parity checker.** P1b-01's rule 4 fails if a manifest still says `planned` under P1-09
   after this package is done. Flip `ui.stages` in the same PR.

**Briefs this plan changes.**

- **P1-09** (corrected in this plan's PR): the Godot mirror exists only after P1-01; the rows run in
  the Node runner, not in the `client-core` unit suite; §2.4 supersedes the proposed names.
- **P1-01:** mirror every file in `corpus/v2/`, which will be four, through the shared mirror list.
- **P1-10:**
  - port the machine to `core/stages.gd` (`PKeyStages`) rather than `ui/boot/`, so headless
    exports can use it;
  - `PKeyBoot` also emits `waiting(status)`, `update_available()` and `boot_rolled_back()`;
  - add an `allow_grace` option;
  - there is no `gate.resolved`; send `gate.status` again instead;
  - `fetch.done` carries `installed`.
- **P3-01 (item 20) and P3-02:** only the confirmation rows remain to plan and emit, plus mapping
  the `decideUpdate` outputs onto `decide.done` (or extending it under version 2).
- **P3-10:** `guardCases` exist from P1-09. P3-10 implements the slots and the counting against
  `bootGuardAction`, and P3-02's confirmation rows.
- **P4-01, with P4-04 or P4-06:** plan and emit the pack rows (a `true` `canPlayOffline`, fetch
  consent and progress). P4-08 only implements them.
- **P1b-01:** its draft already plans `ui.stages` under P1-09 and leaves `update.bootguard`
  unowned. Keep both, and flip `ui.stages` when this package is done (risk 5).
- **Program README §9:** add the unowned terminal renderers and the boot-protocol docs page.
