## 1. Summary

- **One new unsigned corpus file**, `conformance/corpus/v2/stage-matrix.json`
  (`stageMatrixVersion: 1`), written by `buildStageMatrixV1()` in `tools/sign-corpus.ts`. It holds
  39 hand-authored flow rows, 7 boot-guard cases, and an `accepts` table with one probe event per
  event type. Each row is an ordered list of host events with the exact emits each event
  produces. Every runner also sends every probe at every state a row reaches, so the whole ignore
  rule is pinned in every language. The file is mirrored into the Swift test bundle (and into
  Godot's, once P1-01 creates that mirror) and guarded by `pnpm gen:corpus -- --check`.
- **One new pure module**, `packages/client-core/src/stages.ts`, exported from the barrel and as
  `@polaris-key/client-core/stages`. It provides `initialBootState(options)`,
  `bootTransition(state, event) → { state, emits }`, the boot-guard decision
  `bootGuardAction({ staged, failedBoots })` with `MAX_FAILED_BOOTS = 2`, and five vocabulary
  constants that every runner compares with the file.
- **Ports and runners.** Python (`polaris_key/core/stages.py`) and Swift
  (`PolarisKeyCore/Stages.swift`) get a port and a runner over the same file. Node and React use
  `client-core` directly. Godot follows in P1-10.
- **No wire, Worker, catalog or manifest change.** `cases.json`, `gate-matrix.json` and
  `fingerprint.json` stay byte-identical.
- The plan resolves the brief's five open decisions and seven more (§8), makes eight changes to
  the brief's proposed shape (§2.4), and fixes which event a host sends for each result of its
  work (§2.2).

## 2. Contract

### 2.1 Wire contract, `shared-protocol`, `shared-jws`

Nothing normative changes. The stage machine never crosses the wire or the disk (the
WIRE-CONTRACT-V3 scope line), so there is no new `[C]` rule. `PROTOCOL_VERSION`, `CACHE_VERSION`,
`corpusVersion` (2), `gateMatrixVersion` (2) and `fingerprintVersion` (1) keep their values.

One informative clause is appended to the counter list in WIRE-CONTRACT-V3 §9:
"`stageMatrixVersion = 1` (client boot behaviour outside this contract, owned by
`client-core/src/stages.ts`)". It keeps that list and the table on `/docs/build/wire/` complete.

`shared-protocol` and `shared-jws` are untouched. `stages.ts` imports only the `LicenseStatus`
type from `@polaris-key/protocol/license`.

### 2.2 The `client-core` API

**Vocabulary.** Five ordered lists, exported under these names in every language and repeated in
the file's `vocabulary`:

| Constant             | Values, in order                                                                                                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BOOT_STAGES`        | `idle`, `shell`, `guard`, `sync`, `gate`, `decide`, `fetch`, `mount`, `ready`, `background`, `offline`, `blocked`, `error`                                                                         |
| `BOOT_OUTCOMES`      | `running`, `waiting`, `ready`, `blocked`, `offline`, `error`                                                                                                                                       |
| `BOOT_EVENT_TYPES`   | `start`, `shell.done`, `guard.done`, `sync.done`, `sync.timeout`, `gate.status`, `decide.done`, `fetch.done`, `mount.done`, `background.start`, `background.done`, `retry`, `play-offline`, `fail` |
| `BOOT_EMIT_TYPES`    | `stage_changed`, `waiting`, `update_available`, `blocked`, `offline`, `error`, `boot_rolled_back`, `boot_ready`                                                                                    |
| `BOOT_GUARD_ACTIONS` | `none`, `apply-staged`, `roll-back`                                                                                                                                                                |

```ts
// packages/client-core/src/stages.ts, also exported as @polaris-key/client-core/stages.
// Its only import: import type { LicenseStatus } from "@polaris-key/protocol/license".
export type BootStage = (typeof BOOT_STAGES)[number]; // likewise BootOutcome, BootGuardAction
export const MAX_FAILED_BOOTS = 2;

export type BootEvent =
  | { type: "start" | "shell.done" | "sync.timeout" | "mount.done" }
  | { type: "background.start" | "background.done" | "retry" | "play-offline" }
  | { type: "guard.done"; result: "ok" | "applied" | "rolled-back" }
  | { type: "sync.done"; result: "ok" | "offline" | "error" } // classified as below
  | { type: "gate.status"; status: LicenseStatus } // from licenseState
  | { type: "decide.done"; decision: "none" | "optional" | "required" }
  | {
      type: "fetch.done";
      result: "ok" | "offline" | "failed";
      installed: readonly string[];
    }
  | { type: "fail"; code: string }; // a host error code

export type BootEmit =
  | { type: "stage_changed"; stage: BootStage; previous: BootStage }
  | { type: "waiting"; status: LicenseStatus }
  | { type: "update_available" | "boot_rolled_back" | "boot_ready" }
  | { type: "blocked"; reason: "update-required" | "not-available" }
  | { type: "offline"; canPlayOffline: boolean } // false on every v1 path
  | { type: "error"; code: string }; // "sync-failed", "fetch-failed", or fail's code

export interface BootOptions {
  allowOffline?: boolean; // default true
  allowGrace?: boolean; // default true
  requiredPacks?: readonly string[]; // default []; copied, compared by exact string
}
export interface BootState {
  readonly stage: BootStage;
  readonly outcome: BootOutcome;
  readonly options: Readonly<Required<BootOptions>>;
  readonly sync: "pending" | "ok" | "offline" | "error"; // latest sync result; a timeout is "offline"
  readonly resume: "shell" | "guard" | "sync"; // where retry goes (§2.3)
}
export interface BootTransition {
  readonly state: BootState;
  readonly emits: readonly BootEmit[];
}
// initialBootState: stage idle, outcome running, sync "pending", resume "shell".
export function initialBootState(options?: BootOptions): BootState;
export function bootTransition(
  state: BootState,
  event: BootEvent,
): BootTransition;
export function bootGuardAction(input: {
  staged: boolean;
  failedBoots: number;
}): BootGuardAction;
```

The string forms are the corpus's in every language, and no port renames a string:

- event types are dotted (`sync.done`);
- emit types are snake_case (`stage_changed`) and are the signal names renderers expose. No emit
  may share a name with a member of Godot's `Control`. That rules out `ready`, so the emit is
  `boot_ready` (decision 10);
- payload keys are camelCase and payload values are kebab-case.

| Event `type`                          | Accepted in                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------------- |
| `start`                               | `idle`                                                                          |
| `shell.done`                          | `shell`                                                                         |
| `guard.done`                          | `guard`                                                                         |
| `sync.done`, `sync.timeout`           | `sync`; the host's own timer sends `sync.timeout`                               |
| `gate.status`                         | `gate`, waiting or not                                                          |
| `decide.done`                         | `decide`                                                                        |
| `fetch.done`                          | `fetch`; `installed` lists the pack ids present after the fetch                 |
| `mount.done`                          | `mount`                                                                         |
| `background.start`, `background.done` | `ready` and `background` respectively                                           |
| `retry`                               | `gate` while waiting, `offline`, `blocked`, `error`; it goes to `resume` (§2.3) |
| `play-offline`                        | nowhere in v1, because `canPlayOffline` is never `true` (decision 12)           |
| `fail`                                | `shell` to `mount`, except `gate` while waiting                                 |

The file repeats this table as `accepts` (§4.1), and every runner checks every cell of it.

| Emit `type`        | When                                       |
| ------------------ | ------------------------------------------ |
| `stage_changed`    | on every stage change, always first        |
| `waiting`          | the gate needs the player                  |
| `update_available` | `decide.done optional`                     |
| `blocked`          | a gate block, or `decide.done required`    |
| `offline`          | the boot cannot continue without a network |
| `error`            | the boot stopped on an error               |
| `boot_rolled_back` | `guard.done rolled-back`                   |
| `boot_ready`       | `mount.done`, once per boot                |

**What a host sends.** The machine sees only events, so this mapping is normative for every host
and renderer (PKeyBoot, `<PolarisBoot>`, `PolarisBootView`, a terminal). A host reports a result
with the stage's own event whenever that event can express it. It sends `fail {code}` only for a
failure the event cannot express: an exception or a broken invariant in its own work.

| Stage    | The result event                                                                                                                                                                                                                                  | `fail` only for, for example                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `shell`  | `shell.done`, also when the SDK discarded a cache that did not re-verify                                                                                                                                                                          | a store it cannot read, which would make an activated device look new                |
| `guard`  | `guard.done` with the outcome of `bootGuardAction`: `none` sends `ok`, `apply-staged` sends `applied` and `roll-back` sends `rolled-back`, each once done. A staged update that fails re-verification is discarded and does not count as `staged` | a slot swap or a rollback that threw                                                 |
| `sync`   | `sync.done`, classified below. A device with no token first registers inside `sync` when it can do that without the player (below). The host's own timer sends `sync.timeout`, and it covers the registration too                                 | an exception from `register()` or `sync()` itself, such as a cache write that failed |
| `gate`   | `gate.status` from `licenseState`. While waiting, the host sends it again after each activation, enrolment, sign-in or bundle import, whatever its result. The gate's Retry sends `retry`                                                         | computing the status threw. Never while waiting: the gate UI shows activation errors |
| `decide` | `decide.done optional` when the update check says this build is behind, otherwise `none`, also when the check failed or the service is off. P1 has no source of `required` yet                                                                    | an exception                                                                         |
| `fetch`  | `fetch.done` with `installed`. A download that failed is `result: failed`, or `offline` when there was no network                                                                                                                                 | the pack store threw                                                                 |
| `mount`  | `mount.done`                                                                                                                                                                                                                                      | a pack that did not mount                                                            |

**Classifying a sync.** The host counts each signed document the product runs (license, config),
and the keyless registration below when it makes one. For a document it takes the final answer,
after the SDK's single 401 re-acquire and its half-life refetch. Trust and discovery failures do
not count, because `sync()` already keeps the previous state for them.

| Class     | The document's final answer                                                                             | The gate then reads                                          |
| --------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| answered  | 200 with a document that verified, 304, 401, a 403 build block, or 429 (the SDKs' `device-cap` outcome) | the new or held document, `revoked` (401) or `blocked` (403) |
| no answer | no HTTP response at all: a DNS, connect, TLS or reset failure, or the SDK's own request deadline        | local state                                                  |
| unusable  | any other status (a 5xx, an unexpected 4xx), or a 200 whose document did not verify                     | local state                                                  |

**A device with no token.** `sync()` fetches nothing without a token
(`packages/sdk-node/src/core/sync.ts:93`, `sdks/python/src/polaris_key/core/sync.py:101-102`,
`sdks/swift/Sources/PolarisKeyCore/CoreContext.swift:816`), and no SDK registers by itself
(`packages/sdk-node/src/client.ts:151-155`,
`sdks/swift/Sources/PolarisKey/PolarisKeyClient.swift:146-149`; Godot's `register()` is P1-05's).
So the host decides where the token comes from:

- **Without the player.** A product without License whose registration policy is `open` gets its
  token by keyless registration. `open` is the WIRE-CONTRACT-V3 §6 default when neither License
  nor Identity runs, and discovery's `core.registration` states the policy when the host has it.
  The host calls `register()` inside `sync`, before `sync()`, and counts the registration:
  - no answer is `offline`, and an answer that minted no token (403 `registration_closed`, 404,
    429, a 5xx, a malformed 200) is `error`. Either way the host skips `sync()`, which has no
    token to use;
  - a minted token is followed by `sync()`, whose documents count as above.

  So an offline first launch of a config-only product sends `sync.done offline`. It continues on
  its defaults (row 13), or stops at `offline` under `allowOffline: false` (row 15).

- **With the player.** A token from activation, enrolment or sign-in needs the player, so nothing
  is counted. A product with License never registers first, because `/license/document` answers a
  token without a licence with 401 (`packages/worker/src/services/license/document.ts:109-110`).
  Its gate reads `needs-activation` and shows those steps. A product without License continues on
  its local state, because sign-in is not a boot stage.

**The result.**

- The host sends `sync.done ok` when everything counted was answered, including when nothing was
  counted because the token needs the player.
- It sends `offline` when anything counted got no answer, and `error` otherwise.
- **A host that cannot tell no answer from unusable sends `error`**, the result that claims less.
  The SDKs know the difference at the transport, where no answer is `DocumentResult.error` with
  `status: 0` (`packages/sdk-node/src/core/context.ts:328-329`,
  `sdks/python/src/polaris_key/core/context.py:399-400`,
  `sdks/swift/Sources/PolarisKeyCore/CoreContext.swift:439-442`). Their `sync()` results then
  drop it, because `DocOutcome.error` carries no status (`packages/sdk-node/src/core/sync.ts:43-64`,
  `sdks/python/src/polaris_key/core/sync.py:56-79`,
  `sdks/swift/Sources/PolarisKeyCore/CoreContext.swift:100-122`). `RegisterResult.error` merges
  the two in the same way (`packages/sdk-node/src/devices/client.ts:122-124,133`,
  `sdks/python/src/polaris_key/devices/client.py:184-185,201`,
  `sdks/swift/Sources/PolarisKeyCore/CoreContext.swift:679-682,698-699`). P1-02 keeps the status
  in Godot's `PKeySyncResult` and P1-05 in its registration result. A package that builds a
  renderer on another SDK surfaces it in both places first (§5).
- So even with `allowOffline: false`, a sync answered with a 401 reaches `waiting {revoked}` and
  one answered with a 403 reaches `blocked`, never `error {sync-failed}` (report §6.3: "one clear
  screen … not a generic error").

### 2.3 Transition rules

The normal path runs `idle → shell → guard → sync → gate → decide → fetch → mount → ready`. Every
stage is entered even when it has nothing to do (decision 1).

General rules:

- An event that is not accepted in the current stage is **ignored**: the input state comes back
  unchanged (the same object where the language has references) with no emits, and nothing is
  logged. The common case is a late `sync.timeout` (row 26). Rows 17, 30 and 31 show other cases,
  and the probes (§4.1) pin every cell of the "Accepted in" table in every runner.
- **Malformed input** is ignored the same way: an unknown `type`, a missing payload field, or a
  payload value outside the vocabulary or of the wrong type (`installed` not a list of strings,
  `code` not a string) (decision 7). Extra keys do not make an event malformed. TypeScript and
  Swift rule malformed events out at compile time. At runtime the TypeScript reducer and the
  Python and GDScript ports ignore them too, and a unit test in each pins that. The corpus holds
  only well-formed events.
- A transition emits `stage_changed` first when the stage changes, then at most one other emit.
  Every accepted event emits something, so an empty list always means the event was ignored.
- **`retry`** goes to `resume` and resets `sync` to `pending`. `resume` starts at `shell`, becomes
  `guard` on `shell.done` and `sync` on `guard.done`, and stays `sync` for the rest of the launch
  (decision 9):
  - after a failure in `shell` or `guard`, a retry redoes that stage's work (the cache load, the
    slot choice). The gate never reads state the shell failed to load, and a rollback that is due
    still runs (rows 34 and 35);
  - every other retry syncs again (rows 6, 9, 17, 27 and 36–39);
  - once `guard.done` is sent, `shell` and `guard` do not run again in the launch.
- `fail {code}` reports that the host's work for the current stage failed, as §2.2 defines it. It
  moves to `error`, emits `error {code}` and leaves `resume` as it is (decision 8). It is not
  accepted while the gate waits, because the pending work is then the player's and activation
  errors belong to the gate UI. It is not accepted after `ready`, because background work never
  ends a boot (row 31).
- `mount.done` moves to `ready` and emits `boot_ready`. `background.start` and `background.done`
  move between `ready` and `background`, and the outcome stays `ready`.
- `guard.done` moves to `sync`. `rolled-back` also emits `boot_rolled_back`.

**Sync.** How the result of the sync stage decides what happens next (§2.2 says which result the
host sends):

| Event                                  | `allowOffline: true`                             | `allowOffline: false`                    |
| -------------------------------------- | ------------------------------------------------ | ---------------------------------------- |
| `sync.done ok`                         | go to `gate` (`sync: ok`)                        | the same                                 |
| `sync.done offline`, or `sync.timeout` | go to `gate` using local state (`sync: offline`) | go to `offline`, `canPlayOffline: false` |
| `sync.done error`                      | go to `gate` using local state (`sync: error`)   | go to `error`, `code: sync-failed`       |

**Gate.** How `gate.status` decides what happens next:

| Status                                            | After `sync: ok`                        | After `sync: offline` or `error`                                           |
| ------------------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------- |
| `ok`, `not-applicable`, `grace` (if `allowGrace`) | go to `decide`                          | the same                                                                   |
| `needs-activation`, `revoked`                     | stay in `gate`, waiting; emit `waiting` | the same                                                                   |
| `expired`, `grace` (if not `allowGrace`)          | stay in `gate`, waiting; emit `waiting` | the stop for that sync result: `offline {false}`, or `error {sync-failed}` |
| `version-too-old`                                 | go to `blocked`, `update-required`      | the same                                                                   |
| `version-too-new`, `channel-not-entitled`         | go to `blocked`, `not-available`        | the same                                                                   |

A stop caused by a failed sync reports what failed, at the sync stage and at the gate alike:
`offline {canPlayOffline: false}` after `sync.done offline` or a timeout, and
`error {code: sync-failed}` after `sync.done error` (rows 5 and 29).

The pass set equals `isUsable` (with `allowGrace: true`), and a unit test pins that equality.
`stages.ts` restates the set rather than importing `gate.ts`, so it keeps its single type import.

**Decide.** `none` goes to `fetch`. `optional` goes to `fetch` and emits `update_available`.
`required` goes to `blocked` with `update-required`.

**Fetch.** The missing set is `requiredPacks` minus `installed`:

- If nothing is missing, go to `mount`, whatever the `result` (a failed optional download never
  blocks play).
- If something is missing and `result` is `offline`, go to `offline` with `canPlayOffline: false`.
- If something is missing otherwise, go to `error` with `fetch-failed`, even when `result` is
  `ok`.

Rows 13, 20–23 and 32 pin every cell.

**Purity.** `bootTransition` does no I/O, reads no clock, uses no randomness and never mutates its
input. `bootGuardAction` is equally pure.

**Boot guard.** `bootGuardAction` decides what happens at launch:

- `failedBoots ≥ MAX_FAILED_BOOTS` gives `roll-back`;
- otherwise, `staged` gives `apply-staged`;
- otherwise, it gives `none`.

The host defines the two inputs, so P3-10 counts exactly this way:

- `staged` means the host has a staged update that it has already verified (size and SHA-256
  against its record) and that is still eligible (same channel and engine, newer than the binary).
- `failedBoots` counts the launches of the active slot that passed the guard and were never
  confirmed. A launch counts once, when the host sends `guard.done`, which happens at most once
  per launch because `resume` never returns to `guard` after it. The host resets the count to 0
  when a boot is confirmed and whenever the active slot changes. It counts only while an applied
  update is active, because the content the binary shipped with has nothing to roll back to.
- If applying the staged update needs a restart (P3-10's sidecar swap), the host restarts before
  it sends `guard.done`, and the next launch starts a new machine.

Under this rule, two crashed launches roll back on the third, as Diceroll does (notes/A4 §1.5).
One deliberate difference: a rollback is not combined with applying a staged update in the same
launch. That keeps `guard.done` single-valued, and the staged update is considered at the next
launch.

### 2.4 Changes from the brief's proposed shape

1. `start` carries no payload. The options go to `initialBootState(options)`, which is a row's
   `init`, so `retry` reuses them.
2. `shell.done {cache}` is dropped, and `shell.done` has no payload in v1. The gate already says
   whether local state is usable. A separate cache flag would stop an unlicensed product's first
   offline launch, and would hide offline bundle import behind an offline card (rows 12 and 13).
3. `gate.resolved` is merged into `gate.status`, which the host sends again while the machine is
   waiting. One event means one code path in every port.
4. `fetch.done` carries `installed` instead of `missingRequired`. The host reports facts, and the
   machine derives what is missing from `requiredPacks`, so `requiredPacks` is not dead input.
5. Additions:
   - the `allowGrace` option, which mirrors React's `<LicenseGate allowGrace>` and P1-10's
     `allow_grace`;
   - the `waiting {status}` emit, because renderers draw only what the machine says;
   - `fail {code}` and `background.start`;
   - the stages `idle`, `offline`, `blocked` and `error`;
   - `resume` in `BootState`, so that `retry` redoes a failed shell or guard;
   - the constants `BOOT_EVENT_TYPES`, `BOOT_EMIT_TYPES` and `BOOT_GUARD_ACTIONS`, and the file's
     `accepts` and `probes`, so a runner can compare every list with the file and check the whole
     ignore rule.
6. Rows use per-step emits instead of one flat list. This pins which event produced each emit.
7. The emit `ready` becomes `boot_ready`, because a Godot `Control` cannot declare `signal ready`
   (decision 10). The stage and the outcome keep the name `ready`.
8. The brief's "play-offline reaches ready only when the required set is present and the gate is
   usable" has no v1 path. Every v1 `offline` has a required pack missing, an unusable gate, or
   `allowOffline: false`, so v1 accepts `play-offline` nowhere (decision 12).

## 4. Corpus

### 4.1 The file

The file is plain JSON, like `gate-matrix.json`: it has no signature, no `typ` and no key.

```jsonc
{
  "stageMatrixVersion": 1,
  "description": "…", // the reducer, the event and emit forms, the ignore rule, the probes, append-only
  "maxFailedBoots": 2, // runners assert it equals MAX_FAILED_BOOTS
  "vocabulary": {
    "stages": ["idle", "…", "error"], // BOOT_STAGES, 13
    "outcomes": ["running", "…", "error"], // BOOT_OUTCOMES, 6
    "events": ["start", "…", "fail"], // BOOT_EVENT_TYPES, 14
    "emits": ["stage_changed", "…", "boot_ready"], // BOOT_EMIT_TYPES, 8
    "guardActions": ["none", "apply-staged", "roll-back"], // BOOT_GUARD_ACTIONS
  },
  // §2.2's "Accepted in" table. A key is a stage, or "gate:waiting" for the gate while waiting.
  "accepts": {
    "idle": ["start"],
    "shell": ["shell.done", "fail"],
    "guard": ["guard.done", "fail"],
    "sync": ["sync.done", "sync.timeout", "fail"],
    "gate": ["gate.status", "fail"],
    "gate:waiting": ["gate.status", "retry"],
    "decide": ["decide.done", "fail"],
    "fetch": ["fetch.done", "fail"],
    "mount": ["mount.done", "fail"],
    "ready": ["background.start"],
    "background": ["background.done"],
    "offline": ["retry"],
    "blocked": ["retry"],
    "error": ["retry"],
  },
  // One well-formed event per type, in vocabulary.events order.
  "probes": [
    { "type": "start" },
    { "type": "shell.done" },
    { "type": "guard.done", "result": "ok" },
    "…",
    { "type": "fail", "code": "probe" },
  ],
  "rows": [
    {
      "name": "…",
      "init": { "allowOffline": true, "allowGrace": true, "requiredPacks": [] },
      "steps": [
        {
          "event": { "type": "start" },
          "emits": [
            { "type": "stage_changed", "stage": "shell", "previous": "idle" },
          ],
        },
      ],
      "expect": { "stages": ["shell", "…"], "outcome": "ready" },
    },
  ],
  "guardCases": [
    {
      "name": "…",
      "input": { "staged": false, "failedBoots": 0 },
      "expect": { "action": "none" },
    },
  ],
}
```

The 14 probes are, in order: `start`, `shell.done`, `guard.done ok`, `sync.done ok`,
`sync.timeout`, `gate.status ok`, `decide.done none`, `fetch.done ok []`, `mount.done`,
`background.start`, `background.done`, `retry`, `play-offline` and `fail probe`.

`expect.stages` lists every stage entered, in order. The last entry is the final stage. A runner
asserts six things:

- `stageMatrixVersion` is 1, and `maxFailedBoots` equals its `MAX_FAILED_BOOTS`;
- its five vocabulary constants equal `vocabulary`, in order;
- each step's emits, compared as values rather than as text;
- the stage sequence built from the actual `stage_changed` emits equals `expect.stages`, the final
  `state.stage` is its last entry, and `state.outcome` equals `expect.outcome`;
- **the probes.** At each row's initial state and after each of its steps, the runner sends every
  probe to `bootTransition` from that state. It must get the same state (by value) and no emits
  exactly when the probe's type is not in `accepts[key]`. The key is `gate:waiting` when the
  state's stage is `gate` and its outcome `waiting`, and the stage otherwise. Probe results are
  discarded, and the row continues from its own steps. That is about 5,000 transitions per
  runner;
- `bootGuardAction(input)` equals each guard case's `expect.action`.

### 4.5 Drift gate and versioning

- `pnpm gen:corpus -- --check` guards the source file and every mirror, file for file (rule 1).
  Nobody edits the JSON by hand.
- **The file is append-only**, like `CARRIED_MATRIX_ROWS`. Adding rows that use only v1 semantics
  keeps `stageMatrixVersion: 1`. The version is bumped when:
  - the vocabulary or the `accepts` table changes (the probes follow the vocabulary);
  - any existing row's expectation changes;
  - `canPlayOffline` can become `true`.
- **Every runner asserts the exact version**, so a bump is a deliberate change in all languages.
- **The package that adds rows makes them pass.** Every runner reads every row. The package that
  appends rows or bumps the version therefore updates `client-core` and every port that exists by
  then (Python, Swift, Godot) in the same PR. Rows that use only v1 vocabulary pass with no port
  change. This answers the last question of P3-01's item 20.
- **Extensions come from plan-mode packages** (decision 3). A planning-only package plans the
  rows, and a package gated on the corpus and on all SDKs emits them:
  - P3-01 plans the boot-confirmation rows and P3-02 emits them;
  - P4-01 plans the pack rows and P4-04 emits them.
- **The other packages implement only the host side of those rows:** P3-10 for the confirmation
  rows, and P4-06, P4-07 and P4-08 for the pack rows. None of them is plan-mode, and P4-06's Gates
  row requires `pnpm gen:corpus -- --check` unchanged.

**Risks.**

1. **Deferring confirmation leaves a known trap to P3-01.** If a boot counts only at `ready`, a
   player who quits twice at the activation screen rolls back a good update. The never-re-offer
   rule then skips that version for good.
2. **`canPlayOffline` is `false` on every v1 path.** The first `true` path (a playable pack
   subset) changes semantics, so P4-01's plan bumps the file to `stageMatrixVersion: 2`, and
   P4-04 emits it.
3. **A renderer that decides transitions itself drifts silently.** P1-10's acceptance already
   drives `PKeyBoot` through every row.
4. **Decoding.** Row 10's `init: {}` is the only place a field is omitted, and runners decode
   strictly everywhere else. Godot parses JSON numbers as floats, so its port compares
   `failedBoots` numerically.
5. **The parity checker.** P1b-01's rule 4 fails if a manifest still says `planned` under P1-09
   after this package is done. Flip `ui.stages` in the same PR.
6. **The ignore rule hides host bugs.** An event sent in the wrong stage is dropped silently. A
   host can detect it, because the input state comes back unchanged with no emits, and every
   accepted event emits something. P1-10's fake-host tests drive every row.
7. **Hosts that cannot tell send `error`.** Until an SDK surfaces the transport status, a player
   whose licence has lapsed offline sees "sync failed" rather than "offline", and so does one who
   first launches a config-only product offline under `allowOffline: false`. Both cards offer
   Retry. Godot has the status once P1-02 and P1-05 have landed.

**Briefs this plan changes.**

- **P1-09** (corrected in this plan's PR): the Godot mirror exists only after P1-01; the rows and
  the probes run in the runners, not in the `client-core` unit suite, and its acceptance rows

  this package lands first, append `GODOT_V2_RESOURCES` to the list it creates.
- **P1-02:** `PKeySyncResult` keeps, for each document, whether the fetch got no answer (status 0)
  or an unusable one, so that PKeyBoot classifies a sync as §2.2 says without guessing.
- **P1-05:** the result of `register()` keeps a request that got no answer (status 0, as P1-02's
  transport reports it) apart from a refusal or an unusable answer, so that PKeyBoot classifies a
  keyless registration as §2.2 says.
- **P1-10:**
  - port the machine to `core/stages.gd` (`PKeyStages`) rather than `ui/boot/`, so headless

  - `PKeyBoot`'s signal is `boot_ready()`, not `ready()`, because a `Control` cannot redeclare
