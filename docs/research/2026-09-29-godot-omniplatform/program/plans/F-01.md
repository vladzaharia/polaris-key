## 1. Summary

- **A new host, `pkg.plrs.im`, with its own isolation dispatcher.** It is the same Worker on a third
  custom domain, beside `key.plrs.im` and `dl.plrs.im`. `core/registryHost.ts` copies the bytes
  host's compensations: no cookies, `nosniff`, a `sandbox` CSP, no CORS and JSON 500s. It widens
  the type allowlist to registry JSON, `text/x-swift` and PNG/JPEG. The only HTML it serves is
  the inert PyPI page. OCI sits at `/v2/`, and every other ecosystem sits at `/<ecosystem>/<owner>/`.
- **A package is a Release deliverable of a third kind, `package`, and each version is a release
  of it.** `.pkey/release` declares it (rule 9). `pkey release publish` sends a descriptor with
  `kind: "package"` and a `package` block. Release ingests it into a new `release_packages` table
  (unique forever, tombstoned). Distribution renders each ecosystem's index documents into R2 when
  something changes, and serves them.
- **No wire change.** Package releases carry no `pkey-release+jws` record. The Worker refuses one.
  `RECORD_KINDS`, `PROTOCOL_VERSION`, the corpus, the transcripts, discovery and every SDK's
  generated constants stay byte-identical. The descriptor is a CI↔Worker shape in
  `@polaris-key/manifest`, so its change is rule 9 plus the Action-bundle drift gate, not a wire
  event.
- **Every read goes through one `authorizeFeedRead`.** It admits only `public` today. Its
  credential extractor is built and tested now, so registry auth (F-20, F-21) is a settings change.
- **Platform packages belong to a system product, `polaris-key`.** Its `.pkey/` sits at the root of
  this monorepo. F-10 moves all six SDK families onto the feeds and stops publishing to GitHub
  Packages and PyPI (owner decision: feeds only). Swift releases are signed with an X.509
  certificate held in CI.

### 3.1 `.pkey/release`: the `package` deliverable

```jsonc
"deliverables": {
  "npm.node": { "kind": "package", "ecosystem": "npm",   "name": "@polaris-key/node",
                "artifacts": { "tarball": { "match": "dist-pkg/polaris-key-node-*.tgz" } } },
  "swift.polariskey": { "kind": "package", "ecosystem": "swift", "name": "polaris-key.PolarisKey",
                "artifacts": { "archive": { "match": "build/swift-registry/*.zip" } } }
}
```

- `DELIVERABLE_KINDS` becomes `["app", "pack", "package"]`. Its pinning test
  (`index.test.ts:1672`) is updated.
- `PACKAGE_ECOSYSTEMS = ["npm", "pypi", "swift", "maven", "oci", "godot"]` is exported and is
  open for `cargo | go | nuget` in tier 3. Each new ecosystem is its own rule-9 change.
- **A product may declare packages without `deliverables.app`.** The system product has no app.
  The "packs need an app" rule (`index.ts:2849`) is unchanged.
- The `artifacts` map reuses today's `{ match }` entries. `platform`, `arch`, `format`, `content`,
  `binding`, `type` and `packType` are refused on a package.

| Code                              | Rule                                                                                                                                                                                                                                                                                | `schema`  |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| `invalid_deliverable_kind` (kept) | `kind` ∈ `DELIVERABLE_KINDS`; the message lists three values                                                                                                                                                                                                                        | `rejects` |
| `invalid_package_ecosystem`       | `ecosystem` ∈ `PACKAGE_ECOSYSTEMS`                                                                                                                                                                                                                                                  | `rejects` |
| `invalid_package_name`            | `name` matches the ecosystem's grammar: npm scoped `@scope/name` (≤ 214, lower case); PyPI PEP 508 name; Swift `scope.Name` (SE-0292: scope `[A-Za-z0-9-]{1,39}`, name `[A-Za-z0-9_-]{1,100}`); Maven `groupId:artifactId`; OCI repository path components; Godot `[a-z0-9_]{1,64}` | `rejects` |
| `package_name_collision`          | no two package deliverables share `(ecosystem, normalised name)`. PyPI normalises with PEP 503 and npm and Maven compare case-insensitively                                                                                                                                         | `accepts` |
| `invalid_package_field`           | the app and pack fields named above are absent                                                                                                                                                                                                                                      | `rejects` |
| `too_many_package_deliverables`   | at most `MAX_PACKAGE_DELIVERABLES = 64`, counted first, like packs (`:2782`)                                                                                                                                                                                                        | `accepts` |

The schema expresses the name grammar through `if`/`then` on `ecosystem`. Collision and the count
are validator-only. The manifest **declares** packages and never **enables** a feed (§6.3).

### 3.2 The release descriptor: `kind: "package"`

```jsonc
{
  "descriptorVersion": 1,
  "product": "polaris-key",
  "deliverable": "npm.node",
  "kind": "package",
  "version": "1.4.0",
  "channel": "stable",
  "seq": 12,
  "package": {
    "ecosystem": "npm",
    "name": "@polaris-key/node",
    "files": [
      {
        "name": "polaris-key-node-1.4.0.tgz",
        "role": "payload",
        "type": "npm-tarball",
        "sha256": "…",
        "size": 48213,
        "locations": [{ "provider": "r2", "key": "blobs/sha256/…" }],
      },
    ],
    "metadata": {
      /* the extractor's output, ≤ 16 KiB serialised, shape per ecosystem (§6.8) */
    },
  },
}
```

- `builds` is absent on a package and `package` is absent on an app. Each mix-up is
  `invalid_descriptor`.
- `files[]` reuses `DescriptorArtifact` and adds a required `type` from a per-ecosystem
  vocabulary:
  - npm: `npm-tarball`;
  - PyPI: `wheel`, `sdist`, `core-metadata`;
  - Swift: `source-archive`, `manifest`, `source-archive-signature`;
  - Maven: `maven-file`, with `classifier?` and `extension`;
  - OCI: `oci-blob`, `oci-manifest`, `oci-index`, with `mediaType`;
  - Godot: `godot-zip`, `godot-icon`.
- **Locations are `r2` only.** A package's bytes are always ours to serve under the feed prefix.
- At most 4,096 files for OCI and 64 for every other ecosystem. The 64 KiB descriptor cap still
  applies (`MAX_DESCRIPTOR_BYTES`).
- **The Worker never unzips** (the P2b-05 rule). The CLI extracts the metadata, and the Worker
  checks its shape, its bounds and that it agrees with the declaration: `ecosystem` and `name`
  equal the deliverable's, and `version` equals the descriptor's.
- `release-descriptor.schema.json` gains the `package` branch. The refusals use the existing codes
  `invalid_descriptor` and `unsupported_deliverable_kind`, each with a new mutation row.

### 3.3 `.pkey/distribution`

### 5.3 Swift signing (owner decision: sign)

- **CI secrets** (F-10 adds them as consumers; the owner provides the values later):
  - `SWIFT_REGISTRY_SIGNING_KEY`: a PEM private key, base64;
  - `SWIFT_REGISTRY_SIGNING_CERT`: the DER leaf, base64;
  - `SWIFT_REGISTRY_CERT_CHAIN`: the DER intermediates and root, base64, separated by commas.
- **Fail clearly without them.** The job's first step checks all three and stops with
  `::error::Swift registry releases are signed (owner decision 2026-10-04). Set
SWIFT_REGISTRY_SIGNING_KEY, SWIFT_REGISTRY_SIGNING_CERT and SWIFT_REGISTRY_CERT_CHAIN.` It never
  falls back to unsigned.
- **Signing** uses `swift package-registry publish … --dry-run --private-key-path <key.pem>
--cert-chain-paths <leaf.der> <chain…>`. That produces the `cms-1.0.0` source-archive signature
  and signs `Package.swift` and every `Package@swift-*.swift`; SwiftPM embeds the manifest
  signature as a trailing comment. `--dry-run` writes everything into the scratch directory and
  contacts no registry. The key files are written to the runner's temp directory and deleted in an
  `always()` step.
- **Publishing.** The CLI's Swift extractor reads the scratch directory and uploads:
  - `source-archive`, the zip;
  - `source-archive-signature`, the raw CMS bytes;
  - one `manifest` file per signed manifest.

  The Worker serves the **signed** manifest copies, never manifests re-extracted from the zip,
  whose copies are unsigned.

- **The Worker** stores the signature format and serves it as specified by SE-0292:
  - the release metadata's `resources[].signing {signatureBase64Encoded, signatureFormat}`;
  - `X-Swift-Package-Signature-Format` and `X-Swift-Package-Signature` on the archive download.

  It checks only presence and `signatureFormat == "cms-1.0.0"`. Verifying X.509 in the Worker is
  out of scope; SwiftPM verifies. The Swift feed setting `requireSigned` defaults to `true` and is
  locked `true` for the system product. Publishing an unsigned Swift release to such a feed is
  `invalid_descriptor`, reason `swift-unsigned`.

- **Tests.** F-06 tests with a throwaway CA generated in the test (never committed) and SwiftPM set
  to `onUnsigned: error` and `onUntrustedCertificate: error` after trusting that root. The
  certificate type for production is open question **Q1**.

```
  swift/<owner>/<scope>/<name>[/<version>[.zip | /Package.swift]]   and  swift/<owner>/identifiers?url=

  godot/<owner>/asset-library/api/{configure,asset,asset/<id>}        Godot ≤ 4.6

```

- `<owner>` is the product slug. For platform packages it is `polaris-key`.
- Ecosystem names are a closed list in `registryHost.ts`, so a product slug can never shadow one.
- **Byte URLs embed the SHA-256** wherever the protocol lets the server choose: PyPI files, Godot
  zips and icons, and OCI blobs. Those URLs are immutable by construction. npm tarballs, Swift
  archives and Maven files have protocol-fixed names. They are immutable because a version is
  never republished (§6.3).

### 6.3 Data model (F-03)

**Package deliverables and releases.** A package release is an ordinary row in Release's release
tables, with `release_id` set to `<deliverable>@<version>`, as for tagless descriptor releases. It
has no builds. Its files are `release_artifacts` with role `payload`, held by `blob_refs` as today,
so the blob collector keeps them. A new Release-owned table holds what is package-specific:

```sql
CREATE TABLE IF NOT EXISTS release_packages (
  product        TEXT NOT NULL REFERENCES products(slug),
  ecosystem      TEXT NOT NULL,
  name_norm      TEXT NOT NULL,          -- PEP 503 / lower-cased key; the uniqueness key
  version        TEXT NOT NULL,
  deliverable_id TEXT NOT NULL,
  release_id     TEXT NOT NULL,
  name           TEXT NOT NULL,          -- as declared
  state          TEXT NOT NULL DEFAULT 'live' CHECK (state IN ('live','yanked','deprecated')),
  state_message  TEXT,                   -- npm deprecation / PEP 592 yank reason
  files_json     TEXT NOT NULL,          -- [{name, type, sha256, size, mediaType?, classifier?, extension?, sha1?, sha512?, md5?}]
  metadata_json  TEXT NOT NULL,          -- the validated extractor output (§3.2)
  source_json    TEXT NOT NULL,          -- {kind: 'oidc'|'static'|'console', publisher?, runUrl?, tokenId?}
  published_at   INTEGER NOT NULL,
  PRIMARY KEY (product, ecosystem, name_norm, version)
);
```

- **Unique forever.** Rows are never deleted. There is no delete in tier 1, and Release's admin
  delete refuses a package release. A yank changes `state`, and the version can never be
  published again (`release_exists`, reason `package-version-taken`).
- **Integrity.** At ingest, after promotion, Release streams each `npm-tarball` and `maven-file`
  once through `crypto.DigestStream`:
  - SHA-512 and SHA-1 for npm;
  - SHA-512, SHA-1 and MD5 for Maven.

  The results go into `files_json`. SHA-256 is already the blob key and is R2-verified, which is

### 6.5 Render-on-write index documents (F-02 framework, F-03 trigger, F-04 to F-09 renderers)

- **What is rendered:**
  - npm packuments, in full and abbreviated form;
  - PyPI project pages (JSON and HTML) and the project list;
  - Swift release lists and per-version metadata;
  - `maven-metadata.xml` with its sidecars;
  - OCI tag lists and tag → digest pointers;
  - Godot `configure`, `asset/<id>`, `assets/…`, `releases/…` and `index.json`.

  Each is written to R2 under `registry/<ecosystem>/<owner>/<key>`. That prefix is unlocked and
  separate from the bucket-locked `blobs/`, `bundles/`, `deltas/` and `gated/`, and from
  `staging/`. DEPLOYMENT §3 records that `registry/` must never get an age lock.

- **The trigger, across the service boundary.** **[correction]** S-12 said Distribution
  re-renders on publish, but Release cannot call Distribution (rule 6), and the hooks are
  read-only (`hooks.ts` rule 2). Instead:
  - Release enqueues into the Core-owned `registry_render_queue(product, deliverable_id, reason,
enqueued_at)` through `core/registryQueue.ts` `enqueuePackageRender()`. It does so in the
    same D1 batch as each publish, yank, unyank, deprecate or channel move of a package release.
  - Distribution's settings writes and `packageFeeds` toggles enqueue too.
  - The composition root drains the queue. `dispatch.ts` calls `ctx.waitUntil(drainRegistry())`
    after any request that enqueued, and `scheduled.ts` drains on every cron run. Both reach
    Distribution's `materialise(product, deliverable)` through a new optional descriptor member,
    `registryMaterialiser`, registered in `mount.ts`.
  - The materialiser reads Release's state only through `releaseCatalog.packageVersions`.
  - This is open question **Q3**.
- **Atomicity and recovery.** A render writes every object of a package, then deletes the queue
  rows it consumed, matched on `enqueued_at ≤ start`. A crash leaves the rows queued, and the next
  drain retries.
- **Self-check.** The cron re-renders any package whose stored `x-pkey-render-stamp` (R2 custom
  metadata: a hash of the package's rows) differs from the D1 state, at most 50 packages per run.
- **Read path.** A missing object is rendered from D1 on read, written back and counted
  (`registry.render_miss`), so a lost object heals itself.
- **Admin.** `POST …/feeds/:eco/rebuild` enqueues every package of the owner's feed, and the
  action is audited.

### 6.6 The `authorizeFeedRead` ladder (F-02)

```ts
feedPrincipal(req): FeedPrincipal            // tier 1: always {kind: "anonymous"}; the extractor is built and tested
authorizeFeedRead(ctx, principal, owner, ecosystem, deliverableId | null)
  : { ok: true, cache: "public" | "private" } | { ok: false, challenge: ChallengeKind }
```

1. The platform kill switch (`dist_registry_policy.enabled`) is checked. If it is off, the answer
   is not-found.
2. The owner's Distribution and `packageFeeds`, and the feed's `enabled`, are checked. If one is
   off, the answer is not-found.
3. The mode is `stricter(feed.access_mode, dist_access(deliverable).mode)`, reusing
   `distribution/access.ts`'s ladder `public < authenticated < licensed < entitled`. For a list
   document, such as the PyPI project list or OCI `_catalog` (not served in tier 1), the
   deliverable is `null` and only the feed's mode counts. Packages stricter than the list are
   omitted from it.
4. `public` admits `anonymous` with `cache: "public"`.
5. Every other mode refuses `anonymous` in tier 1, with the client's native challenge:
   - `401` with `WWW-Authenticate: Basic realm="pkg.plrs.im"` for npm, PyPI, Maven, Swift and Godot;
   - for OCI, `401` with `WWW-Authenticate: Bearer realm="https://pkg.plrs.im/v2/token",service="pkg.plrs.im",scope="repository:<owner>/<repo>:pull"`
     (the token endpoint 404s until F-21).

   F-21 adds token principals and maps them onto this same function.

6. Anything not `public` is `Cache-Control: private, no-store` and never enters the Cache API.

`feedPrincipal`'s extractor parses:

- `Authorization: Bearer <t>`;
- the raw `Authorization: <t>` (Cargo);
- `Authorization: Basic base64(user:t)`, where the token is the password, or the username when the
  password is empty.

It returns `{kind: "anonymous"}` in tier 1 whatever it parses, and never logs the value. Its
unit tests cover every shape.

**Order matters.** Steps 1 to 3 run **before** the Cache API lookup. A disabled feed or a
tightened mode therefore takes effect within the 30 s settings cache, even for bytes cached at the
edge for a year.

### 6.7 Caching, immutability and dependency confusion

| Answer                                                                                                              | `Cache-Control` (public mode)                   | ETag                     |
| ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------ |
| content-addressed bytes (tarballs, wheels, zips, OCI blobs and manifests by digest, icons)                          | `public, max-age=31536000, immutable`           | `"<sha256>"`             |
| index documents (packuments, simple pages, release lists, metadata XML, tag lists, Godot JSON, OCI manifest by tag) | `public, max-age=60, stale-while-revalidate=60` | strong, the body SHA-256 |
| not-found and refusals                                                                                              | `no-store`                                      | —                        |
| any non-public mode                                                                                                 | `private, no-store`                             | —                        |

- Public answers go through the Workers Cache API, keyed by the normalised URL plus `Accept` for
  PyPI and npm. A publish shows up within 60 s.
- Settings are held per isolate for 30 s.
- **Immutability:**
  - content-addressed bytes are never overwritten;
  - `(product, ecosystem, name_norm, version)` is unique forever;
  - an OCI version tag equal to a release version never moves; only channel tags move;
  - a Swift archive never changes after publish (SwiftPM TOFU);
  - Maven `-SNAPSHOT` versions are refused (`invalid_descriptor`, reason `maven-snapshot`).
- **Dependency confusion:**
  1. **Owner prefix in every URL.** A token or trusted publisher publishes only under its own
     product (`requireCiScope`).
  2. **A namespace is required per feed and enforced at ingest.**
     - npm: the name's scope equals `namespace.scope`.
     - Swift: the scope equals `namespace.scope`.
     - Maven: the groupId starts with one of `groupPrefixes`.
     - PyPI: the normalised name matches `prefixes` or `names`.
     - OCI: the repository is under the owner.
     - Godot: the publisher equals `namespace.publisher`.

     A feed cannot be enabled with an empty namespace. The system product's namespaces are
     `@polaris-key`, `polaris-key`, `im.plrs.key`, the PyPI name `polaris-key`, and `polaris-key`
     for Godot.

  3. **No upstream proxying.** `upstream` is pinned to `'none'` by a CHECK.
  4. **Strict-router snippets only:** npm scope, uv `explicit = true`, Gradle `exclusiveContent`,
     SwiftPM `--scope`, a fully qualified OCI reference.
  5. **Public-name claims.** The owner decided against publishing to public registries and
     against placeholder packages. The `claims_json` setting records any account-level claim the
     owner makes (open question **Q2**), and the setup page warns pip users that
     `--extra-index-url` has no routing.

### 6.11 Threat-model additions (`docs/security/THREAT-MODEL.md` §3)

F-02 adds a new section, "The registry host and package feeds (F-02/F-03)", and F-03 extends it.
It covers:

- **Same-site exposure.** The host is a third sibling. Its compensations are listed against
  `dl.plrs.im`'s, and its single deliberate widening is the type allowlist, which is reviewed here.
- **Tenant-supplied text.** POMs, `.module` files, `package.json`-derived fields and Godot
  descriptions never render as HTML, and the PyPI HTML page escapes everything.
- **Ingest abuse.** Size ceilings, the namespace rule, unique versions and no Worker-side unzip.
- **Cache poisoning.** The access check runs before the cache, the cache key carries `Accept`, and
  non-public answers are never cached.
- **Dependency confusion.** The defences of §6.7, and the residual risk that no public names are
  claimed (Q2).
- **Supply chain of our own SDKs.** Trusted publishing only, and Swift signatures. Godot 4.7+ and
  PyPI fragment hashes give no authenticity, and the SDK's own update path still verifies signed
  records.
- **Kill switches.** The platform policy per ecosystem, `packageFeeds` per owner, and `enabled` per
  feed.

Review trigger (§9): any change to `REGISTRY_HOST_TYPES` or to the HTML fallback.

### 7.2 Deploy order and what happens to what is deployed

- **Clients in the field:** nothing changes (§2).
- **Workers older than F-03** refuse package descriptors with `invalid_descriptor`. F-10's

  mode always does a dry-run submit first (it already supports `--dry-run`). It maps an old

## 8. Risks and open questions

**Q1. Which certificate signs Swift releases?** SwiftPM verifies the CMS chain against its trusted
roots and, by default, prompts for an untrusted certificate (`onUntrustedCertificate: prompt`). A
self-issued or private-CA certificate therefore stops unattended adopter builds, just as unsigned
releases would.

- **Recommendation:** an Apple-issued code-signing certificate (Developer ID Application) under the
  existing Apple developer account. SwiftPM's default certificate policy recognises Apple's roots
  [I].
- **Alternative:** a commercial code-signing certificate. It works on macOS through the system
  trust store. On Linux, adopters may have to add the root to
  `~/.swiftpm/security/trusted-root-certs/`.
- F-06 confirms the recommended chain on macOS and Linux with a test certificate before F-10 relies
  on it.

**Q2. Claim the public names at account level, publishing nothing?** The owner ruled out
publishing to npmjs, PyPI and Maven Central, and ruled out placeholder packages. Without claims,
an attacker can register `@polaris-key` on npmjs or the `im.plrs.key` namespace on Central. A
misconfigured adopter would then resolve the attacker's package. pip has no per-index routing, but
`polaris-key` on PyPI is already ours through its existing releases.

- **Recommendation:** register the npm organisation `polaris-key` and verify the `im.plrs.key`
  namespace on Central (DNS TXT), with no package published to either. This is not a placeholder
  package, and both claims are recorded in `claims_json`.
- **Alternative:** no claims. The threat model then records the residual risk, and the setup page
  warns.

**Q3. The render trigger: a Core-owned queue, or a notify hook?** Hooks are read-only by rule
(`hooks.ts` rule 2), so Release cannot ask Distribution to render.

- **Recommendation:** the queue of §6.5. It is atomic with the Release write, it survives a crash,
  and the hook rules stay as they are.
- **Alternative:** a write-allowed `onPackageChanged` hook. It is simpler, but it is the first
  exception to rule 2 and loses atomicity.

**Risks** (each mitigated in this plan):

- **The `release_deliverables` rebuild** touches a table with FKs: §6.4's replay test.
- **`DigestStream` support** for SHA-1, SHA-512 and MD5 in workerd: F-02's workerd test, with the
  JS fallback.
- **The XML-as-octet-stream assumption:** F-07's matrix, which stops if it fails.
- **The OCI per-blob ceiling** of 5 GiB through tickets: documented; native push is F-23.
- **Godot 4.7+ verifies no hash:** documented in the threat model.
- **Stale indexes for up to 60 s** after a publish: documented, and acceptable for registries.
- **Graph encoding.** F-02 and F-03 execute this plan, but they are not flagged `planMode` in
  `workpackages.json`, per the lead's instruction. Their briefs say so.
