## 1. Summary

- **New unsigned HTTP only.** `POST /<p>/identity/request` (RFC 9126 pushed request) answers a
  `request_uri`. `authorize` accepts `request_uri` and three native redirect classes, and `token`
  checks the pushed device. `GET /signin/return` serves the hosted desktop ReturnStep shell.
  `PROTOCOL_VERSION` (5 after CC-04.1), `DISCOVERY_VERSION` 2 and `corpusVersion` 2 do not change,
  and no signed shape changes.
- **Native classes, chosen by registration.** Loopback `http://127.0.0.1:<port>/pkey/callback`
  needs no registration and can be turned off per product. A scheme URI
  `<scheme>:/pkey/callback` and claimed HTTPS `https://<web.origins entry><claimed path>` must be
  registered in `identity.nativeRedirect`. Native classes are accepted only through the pushed
  request.
- **`signin-fresh` lands here.** I-43.1 is absorbed. Same-device code redemptions (web, loopback,
  scheme, claimed) write the step-up marker that I-43's link offer consumes. The native sign-in
  therefore ends on the link offer (SI §2.3, O-5).
- **Changes to the error registry and the transcripts.** One new wire code
  (`invalid_request_uri`) and one new client code (`redirect-unavailable`). Five new transcripts
  and two re-recorded. No corpus file changes.
- **SDKs (I-15b).** `signIn.start({channel: "redirect"})` and `signIn.handleRedirect(url)`:
  - Node, Python, Kotlin JVM and Godot desktop use loopback;
  - Swift uses ASWebAuthenticationSession (iOS) and loopback (macOS);
  - Kotlin Android uses Auth Tab, else Custom Tabs;
  - React is N/A (`web`), and its desktop bridge forwards to Node.

## 2. Contract (into WIRE-CONTRACT-V5 §12, after CC-04.1; merge lane after I-13.1)

- **§12.4 `authorize`.**
  - **The `request_uri` parameter.** When present, only `client_id` may accompany it. It is
    resolved first: unknown, expired, malformed or already taken renders the branded
    `invalid_request_uri` page (400) and never redirects. A `client_id` that differs from the
    record renders `invalid_client`. Any other parameter alongside it is
    `302 …?error=invalid_request`, and the record is kept.
  - **No native URI on a direct `authorize`.** A native `redirect_uri` sent straight to
    `authorize` stays `redirect_uri_mismatch`.
  - **The handle.** Success mints the browser-bound `rq_` handle with `kind: "native"` and the
    pushed `deviceName` as its label.
- **§12.4 Continue and Cancel.**
  - On a loopback redirect they append `request=<rq_ handle>`.
  - Continue takes the pushed record in the same atomic step, so one pushed request yields at
    most one code.
  - Bind on redemption already holds for every code (I-08b). I-15 adds tests for the native
    classes.
- **§12.5 `token`.**
  - A code from a pushed request carries the pusher's `deviceId`. A different `X-PKey-Device` is
    `invalid_grant`.
  - Every `200` for `authorization_code`, and `choice/complete` on a grant with
    `origin: "code"`, write `signin-fresh` (SingleUseDO, keyed `(product, deviceId)`, 300 s).
  - Device code, exchange (I-13), nearby (I-40) and restore (I-49) never write it. Grants gain
    `origin: "code" | "exchange"`. A grant without `origin` (one issued before the deploy) writes
    nothing.
- **New §12.12 Native redirect.**

  | Item         | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
  | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `request`    | `POST`, form-encoded: the §12.4 parameters plus `device_name` (§12.7.1) and optional `return_uri`.   - `NativeRedirectDiscovery`;
  - the new view members and the discovery endpoints.

  `shared-jws` and `client-core`'s verify, trust and gate floor are untouched. client-core gains

## 7. Rollout

- **Deploy order.** The Worker (I-15) ships first, in R1 beside I-43. The SDKs (I-15b) ship in R2.
- **Shipped SDKs** (v0.9.x) never call `request` and ignore the new discovery members, so nothing
  changes for them.
- **A new SDK against an old Worker** finds no `request` and uses device code. No flag is needed;
  the endpoint's presence is the switch.
- **Rollback.**
  - Pushed requests and `signin-fresh` expire in at most 600 s, and codes in 60 s.
  - A native handle in flight answers `404`.
  - A loopback `303` to a missing `/signin/return` shows a 404 page, but the app has already
    redeemed.
  - An older Worker or `pkey` refuses `identity.nativeRedirect` with `invalid_identity`, so a
    manifest that uses it publishes only after the Worker ships. A rollback leaves the stored
    settings rows unread.

## 8. Risks and open questions

**Owner questions (recommended option first):**

- **Q1 Where claimed HTTPS lives.**
  - (a) **On the product's own `web.origins`**, with association files the developer hosts
    (the brief's "on the product's domains").
  - (b) A Polaris links domain, with files generated from new product data (Android SHA-256 cert
    fingerprints). This means a new package (+0.4–0.6 weeks) and a domain to buy.
  - Never on `key.plrs.im` or `polaris.locker`. Apple's `.https` callback needs the
    `webcredentials` service. Listing a developer's app there would let that app request
    assertions for Polaris Locker passkeys, which is an account takeover.
- **Q2 The mobile default.**
  - (a) **A registered scheme inside ASWebAuthenticationSession or Auth Tab.** The callback
    returns to the starting app only, so it cannot be hijacked; claimed HTTPS applies when it is
    registered.
  - (b) Claimed HTTPS by default. Every mobile product would then need its own domain. This
    amends the rung-6 cells of SI §1 that say "claimed HTTPS".
- **Q3 Pushed-request lifetime.**
  - (a) **600 s, resolvable until Continue or Cancel takes it**, so **Open browser again**
    reopens the same sign-in (closes SIGN-IN §8's I-15 row). RFC 9126 §4 allows reuse on reload.
    This amends I-27 §2.1's "60 s, used once".
  - (b) 60 s and once: **Open browser again** pushes a new request, and the listener keeps up to
    three live states.

**Lead decisions (delegated):**

- **D-4** Native classes only through `request`. This keeps the label and device binding on one
  path.
- **D-5** Reverse-DNS schemes only. SIGN-IN's `tidewater://` examples become
  `com.tidewater.studio:/…`.
- **D-6** The card keeps the return state in `sessionStorage` under the handle, so there is no
  return API, no artefact and no transcript. Alternative: a `signin-return` artefact and
  `GET /api/signin/requests/:h/return`.
- **D-7** Godot mobile redirect goes in I-48, which already edits `native/ios` and `:platform`.
  Godot mobile keeps device code until then.
- **D-8** The I-15 / I-15b split, and I-43.1 folded into I-15.5.
- **D-9** Loopback is on by default with an off switch. Desktop SDKs are useless without it.

**Risks:**

- **Top-level navigation from HTTPS to `http://127.0.0.1`** under Chrome's Local Network Access
  rollout. It is a main-frame navigation, which LNA exempts today; I-15b.2 tests it in Chrome,
  Firefox and Safari.
- **Desktop scheme handoff to a running instance** (Windows starts a second process). It is
  documented per OS, and the SDK exposes `handleRedirect`; it does not do the IPC itself.
- **The Godot `TCPServer` ephemeral port** is unverified [U].
