## 1. Summary

- One Core pipeline, `W/core/ingest/`, plans and applies a parsed `.pkey/` to a product. Core and
  each service contribute through one descriptor facet, `contributes.manifest`. Core orders the
  contributions, runs every check before the first write, writes one batch and then runs the
  after-commit steps.
- Link, resync (webhook, console and link-existing), the deploy hook and the three dry runs all
  call it. Release keeps the GitHub reads and `release_config`, and becomes the GitHub source
  adapter. The GitHub reads are the coordinates, the installation token, the pinned `.pkey/`
  fetch, the repository ids and the blob lookups.
- Nothing changes behaviour. The PR's first commit captures golden "statements produced" tests
  from today's code. They pass unchanged after the move (§4), except the three deltas D5 lists.
- Every P0-26 seam goes. Six `SEAMS` rows and eight `WRITE_SEAMS` rows are deleted, and six rows
  are retagged to the package that removes them (D7).
- There is no wire, corpus, SDK, route, migration or `TABLE_OWNERS` change.

## 6. Worker

### 6.1 The pipeline (`W/core/ingest/pipeline.ts`)

`ingestFor(registry): Ingest` returns `{ plan(env, db, input), apply(env, db, input) }`.

The input is `{ mode: "create" | "apply", scope: "full" | "system", product, manifest, warnings,
source, now, create? }`. `create` holds ST-42's choices.

`apply` runs these phases in order. `plan` runs phases 1–3 and returns every refusal as a
conflict (D5).

1. **Read.**
   - The product row is read once, into `before`. When the caller holds one, it is P0-22's
     `ProductContext.row`.
   - `claimsForApply` and the previous snapshot's row ids are read.
   - The effective services are worked out. They are the stored set when
     `services_source = 'admin'`, and the manifest's set otherwise. Under the `system` scope
     they are always the stored set.
   - The memoised shared reads go in `ctx.read`: tiers, profiles, the active schema and
     `release_config`.
2. **Prepare.** Core's contributor runs first, then each mounted service's contributor in
   `SERVICE_SLUGS` order. Each is told whether its service is enabled (`ctx.enabled`). This
   phase only reads and checks.
3. **Refuse.** Any refusal returns before the first write. The first refusal is reported in
   today's check order (`REFUSAL_ORDER`).
4. **Sweep (apply, `full` scope only).** `invalidateWidenedEdgeMintApprovals` runs, as it does
   today after the checks.
5. **Finalize.** Late re-reads run, such as Config's profile secret carry-forward (R2), as close
   to the batch as today. A late re-read can still refuse.
6. **Batch.** One `db.batch` writes Core's statements, then each service's statements, then
   every deferred audit row, then the snapshot.
7. **After commit.** These steps never throw.
   - Core: the service transitions (PX-W17, apply mode) and hosted assets (HA-05).
   - Release: the store sync (create mode); the generation bump, pack sets and mirrors (apply
     mode).
8. **Final sweep (apply, `full` scope only).** The widening sweep runs again in a `finally`, as
   `resyncRepo` does today.

`updated` ids keep today's order (`UPDATED_ORDER`), and plan items keep today's order
(`PLAN_AREA_ORDER`). The console's `ResyncDialog` labels and plan list therefore do not change.

### 6.2 The contributor facet (`W/core/ingest/types.ts`)

```ts
// ServiceContributions.manifest (core/contributions.ts:155); Core's own is core/ingest/core.ts
interface ManifestContributor {
  prepare(ctx: IngestContext): Promise<ManifestContribution>;
}
interface ManifestContribution {
  refusals: IngestProblem[]; // { area, check, file, path, message, id? }
  plan: ManifestPlan; // apply / skipClaimed / delete / conflicts (moved from linkExisting.ts)
  statements: DbStatement[];
  audits: DbStatement[];
  updated: UpdatedId[];
  claimed?: string[];
  conflicts?: PlanConflict[];
  refused?: Refused[];
  finalize?(): Promise<
    | { statements: DbStatement[]; audits: DbStatement[] }
    | { refusal: IngestProblem }
  >;
  afterCommit?(): Promise<Partial<IngestOutcome>>;
}
```

- **Every mounted service's contributor runs, whatever its enablement**, as `productDeletion`
  does. It reads `ctx.enabled` and decides for itself (D1).
- **The two old hooks are deleted** from `ServiceDescriptor`. Their three users move their
  statements into the facet unchanged. A part that ran only while the service was enabled now
  checks `ctx.enabled`.
- **The contract rules:**
  - read only in `prepare` and `finalize`;
  - write only your own tables (`tableCrossings` proves it);
  - be idempotent;
  - never write an operator-owned column;
  - put each claim guard in the SQL.

## 8. Decisions for the lead

**D1. Enablement of the moved rows.** Tiers, profiles, the catalog, edge mint, OIDC, provisioning
and `release_config` are written today whatever their owner's enablement. Turning a service on
runs no ingest, so its rows must already be current, which is the same reason
`manifestIngestAlways` exists.
**Recommend:** keep today's behaviour with one facet that is told `ctx.enabled`, and retire both
hooks.
The alternative is to write only while enabled: a product that later turns License on would have
no tiers until its next push.

**D2. How the pipeline is handed in.**
**Recommend:** inject it, as today (`ingest`), but make it required everywhere. Today an omitted
`ingest?` would silently skip the owners' rows.
The alternative is P0-19's bound registry. It has less wiring, but it is global state, and every
suite then depends on `mount.ts`.

**D3. The deploy hook.**
**Recommend:** a `system` scope that writes exactly today's subset.
Applying the full manifest would let the root `.pkey/` rewrite the system product's services,
catalog and tiers, which `ensureSystemProduct` and the operator own. That is a separate decision
for ST-17 or later.

**D4. The golden rule.**
**Recommend** the rule in §4: per-table order, audits as a multiset, the end state, results,
plans, and no more reads than today. Every result and plan id keeps today's order.
The alternative, one global statement order, would force the pipeline to interleave owners as
Release happens to today.

**D5. Three declared deltas.**
**Recommend** all three, each pinned by its own golden scenario:

- link screens the catalog for delivery issues, as resync and the console already do (a secret
  with a default no longer gets in through link);
- the create dry run parses with `reservedDisplayNames`, as the create does;
- the resync and link dry runs list every policy refusal, not only the first.

The alternative is zero deltas, with the drift filed as a follow-up.

**D6. Validator warnings.**
**Recommend:** add the field to `ParseManifestResult` (§3) and carry it as `manifestWarnings` on
the pipeline's plan and result. No HTTP response changes in P0-26; ST-17 publishes the warnings.
The alternative is to leave the parser alone and let ST-17 call the validator a second time.

**D7. Six P0-26 rows this plan does not remove.**
**Recommend** retagging them, which keeps P0-26 at 1–1.5 weeks:

| Row                                                                    | New tag     | Why                                                                                     |
| ---------------------------------------------------------------------- | ----------- | --------------------------------------------------------------------------------------- |
| `core/edgeMintApproval.ts` → `edge_mint_approvals`                     | `permanent` | P0-12's widening rule has four callers across Core, the console, License and the ingest |
| `core/ops/settingsBackfill.ts` → `product_schema`, `profiles`, `tiers` | P0-49       | A one-shot migration, which belongs to the runner                                       |
| `core/settingsClaims.ts` → `product_schema`                            | ST-17       | Revert and the break-glass apply are ST-17's Revert and Keep                            |
| `core/products/store.ts` → `profiles`                                  | ST-43       | `stmtInsertConsoleProfile`, used by the manual create                                   |

The alternative is to take all six, which adds 0.5–1 week.

**D8. Creating from documents.**
**Recommend:** a source with no `repo`, tested in P0-26, with no route and no migration.

- The snapshot origin stays `link`, with `applied_sha` NULL.
- A declared `trustedPublisher` without a repository is refused, failing closed.
- The release-store sync and repository asset paths are skipped, with today's warnings.

ST-43 wires the console side.

**Risks:**

- **Size.** If commit 2 overruns, the lead may split commit 3 into P0-26b. The acceptance line
  "the deploy hook calls one pipeline" then moves with it.
- **Security-sensitive moves.** The move touches R6-05 (ref pinning), R9-01 (the issuer gate),
  P0-12 (approvals), R2 (secret carry-forward), P3-03 (release keys) and F-03 (the system
  product). Their checks move verbatim and the attack suites pass unchanged. One
  `pkey-security-reviewer` pass on the PR is recommended.
