## Goal

Make Core the single orchestrator for service-owned manifest ingestion on product link and resync: it selects contributors through the service registry, collects statements in canonical order, and lets the existing link/resync transaction commit them atomically with Core's own manifest work. Services keep ownership of their tables and never import one another.

## Evidence and non-negotiable invariants

- The brief's registered source is DX consolidation Track B, integration decision record and `audits/cq-worker-services.md`; the work-package graph marks the lane `worker`, plan mode, and dependencies P0-17/P0-18.
- The current implementation establishes the required shape in `packages/worker/src/core/registry.ts:478-534`: `ManifestIngest` accepts `(parsed, product, services, now)`, `manifestIngestStatements` returns `{ slugs, statements }`, visits `SERVICE_SLUGS` canonically, calls `manifestIngest` only when a service is enabled, and always follows it with `manifestIngestAlways`.
- `packages/worker/src/services/release/resync.ts:888-904` puts those statements in the release resync batch and resolves service enablement from the stored source of truth. It says Release must not import responding services (AGENTS rule 6).
- Registry descriptor comments at `packages/worker/src/core/registry.ts:233-270` define the contributor contract: `DbStatement` only, idempotent, no reads, no writes to operator-owned columns. `manifestIngestAlways` is the narrow exception for records that must already be correct at enablement and must do nothing while a service is disabled.
- `packages/worker/src/core/rowSettings.ts:15-23` demonstrates the ownership consequence: Core knows no service settings; each service supplies its own manifest-row statements, with manifest omit-clears and console claims preserved.

## Preconditions and decisions

1. **Verify P0-17 and P0-18 first.** This package must use their approved Core boundaries and shared context/registry design. If either dependency changed an interface or transaction boundary, update this plan before implementing rather than retaining two orchestration paths.
2. **Inventory actual ingress sites.** Repository evidence visibly shows webhook, platform-deploy, product-link and release-resync callers binding `manifestIngestFor(SERVICES)`. Before cutover, enumerate all manifest mutation/link/resync paths and identify the one transaction/batch each uses. No caller may be silently omitted.
3. **`manifestIngestAlways` admission decision.** The existing comments define its exception but no general approval mechanism. Before adding or moving a contributor, the implementer must document why a record is unread while the service is disabled, why enabling does not ingest, and why a stale/missing row would be unsafe. Otherwise use enabled-only `manifestIngest`.
4. **No unmet requirement is inferred.** The source evidence does not prescribe a new manifest syntax, service-specific table schema, audit wording, or retry policy. Those are out of scope unless the owning service brief supplies them.

## Design and implementation sequence

1. Establish one Core-owned `ManifestIngest` interface and collector adjacent to the service registry. The collector receives parsed manifest data, product slug, effective service map and operation timestamp; it returns only service slugs and `DbStatement`s. Do not expose D1 prepared statements or a service registry to callers.
2. Require every descriptor contribution to be pure statement generation. Enforce the existing semantics with targeted tests:
   - canonical `SERVICE_SLUGS` ordering independent of mount order;
   - missing descriptor and absent hook contribute nothing;
   - disabled services do not run `manifestIngest`;
   - registered services run `manifestIngestAlways` after their enabled hook;
   - the returned slug list names only services producing one or more statements.
3. Bind the collector at the composition root (`manifestIngestFor(SERVICES)`), not inside Release, a service handler, or a feature-specific import. Preserve rule 6: Core routes, services own statements, and a service imports neither siblings nor Core-owned mutation details beyond the declared contract.
4. Route every inventoried ingress site through the same bound collector and append statements to the caller's existing batch. Maintain each caller's own validation, snapshot, audit and error behavior; this package does not create a second transaction or an asynchronous post-commit ingest.
5. Migrate existing service-owned manifest writes one service at a time. For each, document input block, owned tables/columns, enabled versus always decision, idempotence, omit behavior, and test fixture. Delete the old parallel write path in the same change once the caller is migrated.
6. Keep ownership intact: a contributor may not write a Core table except through the established Core contract, another service's table, or an operator-owned/console-claimed column. Keep manifest omit-clears and console-claim survival where an owning service already specifies them.

## Tests and migration proof

- Unit-test the collector's ordering, enablement, always semantics, empty contributions and statement/slugs result.
- Add one integration test per ingress family proving its service rows enter the same batch as Core rows and rollback together if the batch fails.
- For every migrated service, prove repeated ingest is idempotent and a disabled service does not mutate service-only rows through its enabled hook.
- Add an architecture test or lint-level assertion that Release/other ingress code uses the bound Core collector rather than importing feature services to write their tables.

## Explicitly out of scope

- A new manifest grammar or validation rule.
- New service settings, release semantics, table schemas, retries, queueing or audit vocabulary.
- Changing service enablement policy; this plan consumes the effective map selected by the existing owner.
- Admin dry-run UX (ST-17), the new-product wizard (ST-43), and update resolver design (P2-12), which consume this pipeline.

## Acceptance criteria

- [ ] Exactly one Core collector is the supported route for service manifest ingestion, with a registry-bound composition-root adapter.
- [ ] Every manifest ingress caller identified in the inventory appends collected statements to its existing atomic batch; no feature imports sibling services.
- [ ] Enabled-only and always contributions obey the documented contracts and deterministic order, backed by unit tests.
- [ ] Migrated service writes are idempotent, preserve service/column ownership and preserve existing console-claim/omit behavior.
- [ ] Parallel legacy service-ingest paths are removed and focused integration rollback tests demonstrate atomicity.
