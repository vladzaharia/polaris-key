## 1. Summary

- **`variants[].chunks` becomes a claim-checked object ref**
  `{format, sha256, bytes, size, codec, params}` naming a binary `pkey-chunks/1` index exactly as A7 §3.1, stored as one zstd frame when
  smaller (§2.2, §2.3). Unknown `format` or `codec` only makes the chunk strategy unusable; members
  of `chunks` other than these are ignored, so an index delta can arrive later inside v4.
- **CI chunks once, with frozen parameters**: FastCDC 2016 NC1, file-aware with S-03's padding
  rule, 64 KiB average for every payload, per-chunk zstd -19 frames or raw, and bundles of about
  4 MiB **shared along one deliverable's variant chain**, so an N−1 sync is the index plus one run
  (§2.4). Every container variant of 4 MiB or more gets an index (S-03 retired the 16 MiB clause).
- **Content corpus v2** adds `chunkIndexCases` (22), 8 chunk `applyCases`, the chunk blobs (about
  0.9 MB), `plan-matrix.json` v2's three `plan-real-chunk-*` rows (records inline, P4-01 §4.5)
  and eight chunk `targetCases` over a four-record synthetic index. P4-04's ids and bytes stay as
  they are, and the source set is about 4.46 MB, under the 4.6 MB target and the 5 MB budget (§4).
- **`client-core` gains `parseChunkIndex` and `planTarget`'s chunk rule**, which the Node runner,
  the CLI self-check and the Worker's ingest share. Applying chunks stays with P4-11 in every SDK.
- **Order**: P4-10 lands the format and corpus. The new P4-22 lands the CLI and the Worker
  (ingest of `chunks`, discovery `release.chunks`, the `chunk` patch strategy). Then P4-11 adds
  chunk sync in five SDKs. No deployed client or Worker changes behaviour (§7).

### 2.3 `pkey-chunks/1` and `parseChunkIndex` (V4 §2.6)

The layout is A7 §3.1 byte for byte (all little-endian):

- a 64-byte header: `PKEYCHNK`, `version` u16 1, `recordSize` u16 48, `flags` u32 with bit 0
  `fileAware` (informative), `chunkCount` u32, `bundleCount` u32, `payloadSize` u64, then
  `payloadSha256`;
- `chunkCount` records `id[32] | len u32 | clen u32 | bundle u32 | offset u32`, in payload order;
- `bundleCount` records `sha256[32] | size u64 | reserved u64`.

`id` is the SHA-256 of the uncompressed chunk. `clen == len` means the chunk is stored raw.
`clen < len` means one zstd frame whose content size is `len`. Duplicate ids share one location.

`parseChunkIndex(stored, ref, payload | null, {decode, maxBytes = MAX_CHUNK_INDEX_BYTES})` returns
the first failure, in this order:

0. One of these → **`chunks-ref-mismatch`** (new; see decision 8):
   - `ref.size > maxBytes`, checked before anything is fetched or decoded;
   - the stored SHA-256 or length differs from the ref;
   - a `zstd` ref fails to decode;
   - the decoded length differs from `ref.size`.
1. length < 64 → `chunks-bad-length`. 2. magic → `chunks-bad-magic`. 3. version ≠ 1 →
   `chunks-unsupported-version`. 4. recordSize ≠ 48 → `chunks-bad-record-size`. 5. `flags & ~1` →
   `chunks-bad-flags`.
2. length ≠ 64 + 48 × (chunkCount + bundleCount), computed in 64 bits → `chunks-bad-length`.
3. Bundle records, in order: reserved ≠ 0 → `chunks-reserved-nonzero {bundle}`.
4. Chunk records, in order:
   - `len == 0` → `chunks-zero-length {chunk}`;
   - `clen == 0 || clen > len` → `chunks-bad-clen {chunk}`;
   - `bundle ≥ bundleCount` → `chunks-bad-bundle-ref {chunk}`;
   - `offset + clen > bundles[bundle].size` → `chunks-bad-bundle-range {chunk}`.
5. Σ len ≠ payloadSize → `chunks-size-mismatch`.
6. If `payload` is given, (`payloadSha256`, `payloadSize`) ≠ (`payload.sha256`, `payload.size`) →
   `chunks-payload-mismatch`.

On success it returns `{ok: true, index: {fileAware, payloadSize, payloadSha256, records,
bundles}}`. **The u64 rule:** every SDK reads a u64 as `hi × 2^32 + lo` from two u32 reads (low
word first), saturated at 2^53; no SDK uses a native 64-bit read (Godot's `decode_u64` is not
used). Reads go through a `DataView` (JS) or an aligned copy, never a typed-array view at an
unaligned offset. With
`MAX_CHUNK_INDEX_BYTES` = 16 MiB (349,523 records), Σ len stays below 1.5 × 10^15 < 2^53. So a
saturated value never compares equal by accident, and no SDK needs an integer wider than a double
or GDScript's `int` (A7 trap: Godot reads every JSON number as a float). `MAX_CHUNK_INDEX_BYTES`
is a client limit, like `MAX_FILES_INDEX_BYTES`. CI and the Worker read at most
`MAX_PUBLISHED_INDEX_BYTES` (8 MiB, 174,761 records, about 10.7 GiB of payload at 64 KiB); a CLI
index above it is not published: the variant omits `chunks` and the publish warns.

**`MAX_CHUNK_BYTES`** = 4 MiB (4,194,304), a protocol constant emitted by `gen constants`, bounds
one chunk's `len`, and so the buffer an applier allocates per chunk. CI's `maxSize` is 256 KiB, a
sixteenth of it. The format does not refuse a longer chunk (A7's twelve parse codes stay as
they are); `planTarget` treats an index holding one as unusable (§2.5), so no SDK ever fetches or
decodes it.

### 2.4 Chunking, bundles and the index on the wire (CI; P4-22 implements)

- **Which variants.** A variant gets `chunks` when all of these hold:
  - its layout is `container`;
  - `payload.size ≥ CHUNK_MIN_PAYLOAD_BYTES` (4 MiB, a CLI constant);
  - `chunk ∈ patch.strategies` (§3);
  - discovery advertises `release.chunks` (§6);
  - the written index is at most `MAX_PUBLISHED_INDEX_BYTES` (otherwise `chunks` is omitted with a
    warning, and the publish goes on).

  This follows S-03 §5 item 3, measured on `extra`: 83 KB in 2 requests against 11.6 MB full.
  Trees get none.

- **Parameters, frozen per release**, signed as `chunks.params`:

  ```json
  {
    "chunker": "fastcdc-2016-nc1",
    "fileAware": true,
    "avgSize": 65536,
    "minSize": 16384,
    "maxSize": 262144,
    "padMerge": 64,
    "bundleTarget": 4194304,
    "bundleLayout": "shared",
    "zstdLevel": 19
  }
  ```

  - `fastcdc-2016-nc1` names exactly A7's `gen/fastcdc.cjs`: the xorshift32 gear table seeded
    `0x9e3779b9`, the masks, min = avg/4, max = avg × 4, and a remainder ≤ min kept as one chunk.
    Changing any of it means a new chunker name.
  - **Segments** are the files index's entries, each with the gaps between them. A gap shorter than
    `padMerge` bytes that directly follows an entry joins that entry's segment. The header, the
    directory and longer gaps stay segments of their own, so no chunk spans two entries.
  - `bundleLayout` is `fresh` when no reusable chain exists (below).
  - Clients never read `params` (CONTENT principle 3). CI never re-chunks a published release.

- **Codec.** A chunk is one `zstd -19` frame with its content size, or raw when the frame is not
  smaller. Frames are compressed with `storeMany` in batches of 400 files per zstd process. The
  index object follows P4-01 §2.7 rule 1: one frame when smaller. On the content set that is
  9,328 → 8,024 B; on Diceroll's 85 MB PCK, 350 → 284 KB (S-03 §4.7).
- **Shared chains (dedupe across releases).** A chain is one deliverable, one variant key and one
  gating class.
  - CI keeps each published index in its base cache: `--out` writes the stored object as
    `<dir>/<packId>/<version>/<variant>/chunks.<sha256>`.
  - It reuses the latest proven cached release of the same variant key and gating class. The
    record is proven by `seqs[].recordSha256` and the object by that record's `chunks.sha256`.
  - A new record reuses that index's location (bundle, offset, clen) for every id it already
    holds, but only in bundles the stage round reports `present`.
  - Every other chunk goes into new bundles, unique chunks in first-use order. A bundle is closed
    before it would pass `bundleTarget`; the 16 MiB cap holds because `maxSize` is 256 KiB.
  - The bundle table lists the bundles in the order records first reference them.
  - A lost cache, a gate change or an absent bundle only costs storage, never a publish: those
    chunks are packed fresh from the current payload, which holds every chunk.
  - A gated and a free pack never share a bundle (CONTENT §12). Their keys differ anyway
    (`gated/`), and ingest's prefix check refuses a mix.
- **Bundles are blobs.** They are stored as `blobKey(sha256, {gated})`, that is
  `blobs/sha256/<hex>` or `gated/blobs/sha256/<hex>`, with no extension, and earn `pack-upload` refs
  in stage rounds, like every pack object (P4-01 §2.7). They are served by the blob route with
  `Range` and `If-Range`, so P4-05 needs no change. P2-01's `bundleKey` and
  `blob_objects.kind = bundle` stay unused (decision 4).
- **Lints** (A7 §11.5). Every new frame's header has a content size equal to `len`; it decodes with
  `@polaris-key/zstd-wasm` `decode(frame, len)`; and its SHA-256 equals `id`. Every reused
  location matches the proven earlier index. The records' lengths equal the chunker's output over
  the payload. The written index passes `parseChunkIndex` bound to the payload, under
  `MAX_PUBLISHED_INDEX_BYTES`. Each new bundle's length equals its table `size`. The same input
  twice gives the same index (for one zstd build).
- **Index on the wire.** The index ships as its own object, compressed when smaller. An index delta
  against the seed (S-03 §4.7: 1.4–9 KB) is deferred (decision 6), and **64 KiB is the average for
  every payload**. This is the average S-03 recommends when the index is not a delta, and under
  per-pack delivery it stays within −1.2% to +5.3% of 32 KiB even with a delta (S-03 §4.10).
- **Repacking** bundles below about 50% live data (CONTENT §11) has **no owner**. The format needs
  no change for it (§8.2 risk 3).

### 2.5 Planning and applying (V4 §11.4; P4-11 implements apply)

- **`planTarget(variant, recordSha256, filesIndex, chunkIndex = null)`.** It maps `chunks` to
  `{indexBytes: chunks.bytes, records: [[idHex, len, clen, bundle, offset], …]}` when every one
  of these holds; otherwise `chunks` stays null:
  - the variant is usable and its layout is `container`;
  - `chunks.format === CHUNKS_FORMAT`;
  - `codec` is usable;
  - `chunks.size ≤ MAX_CHUNK_INDEX_BYTES`;
  - `chunkIndex` is given and bound to `payload`;
  - no record's `len` exceeds `MAX_CHUNK_BYTES` (no new code: the strategy is simply unusable).

  The planner is unchanged: it already costs chunks over inline records (P4-06), and the index
  counts in `indexBytes`.

- **Fetch rule** (informative): fetch the target index before planning when `chunks` is usable,
  `chunk ∈ caps.strategies` and at least one seed index is stored, as P4-01 does for the files
  index. A first install stays `full` and then keeps its index as a seed (S-03 §4.11: the chunk
  store is 28% above one frame).
- **`applyChunk`** is A7 §3.4 with P4-01's kebab codes:
  - Parse the index with `parseChunkIndex` (with `payload`). Build the seed map: first occurrence
    over seeds in order, then over records.
  - For each record: copy from a seed, else from the output if the id was already written, else
    fetch.
  - A run continues while the bundle stays the same and `offset == prev.offset + prev.clen`. A
    seeded or duplicate record between two contiguous fetched records does not break the run.
  - A fetched record with fewer than `clen` bytes available → **`chunk-bundle-truncated {chunk}`**.
    That is a short body, or a range clipped at the object's end. It is checked before the record
    is decoded and after every earlier record.
  - A decode error, a wrong length or a wrong SHA-256 → **`chunk-corrupt {chunk}`**.
  - Then `payload-hash-mismatch`, or with `repair` the A7 repair pass.
  - The verdict is
    `{ok: true, sha256, size, fetchedChunks, fetchedBytes, requests, seedChunks, selfChunks, repairedChunks}`,
    where `requests` counts runs (the planner adds 1 for the index).
- **Memory and `Range` on devices** (constraints P4-11 implements; S-02, S-04):
  - The output streams to a `.part` file at record offsets. A device holds the parsed index (48 B
    a record, about 350 KB for the 85 MB PCK), the seed map and one chunk (`clen + len`, ≤ 512 KiB
    at `maxSize`), never a bundle.
  - Chunk frames decode one-shot to `len`, with no prefix, so P4-01's `frameWindow` check does not
    apply.
  - One single-range request per run, with `If-Range: "<bundle sha256>"` and
    `Accept-Encoding: identity`. A run is at most one bundle (≤ 16 MiB).
  - **Exact `Content-Range`:** for `Range: bytes=o-e` the `206` must say `bytes o-e/<size>`. A
    `206` that starts at `o` but ends at `<size> − 1 < e` (clipped at the object's end) is
    truncation: the records past its end are `chunk-bundle-truncated`. Any other `Content-Range`,
    another `ETag` or a `200` fails the strategy, and the host falls back to the next one. Never
    send multi-range.
  - S-04 sets the boot inline limit at 50 MB natively and 25 MB on the web.

### 4.2 The generator (`tools/gen-content-corpus.ts`, `tools/sign-corpus.ts`)

- **Reference code**, its own (P3-02's rule, no `client-core` import): `refParseChunkIndex`,
  `refApplyChunk` (a port of A7's `refapply.py`/`content.mjs` chunk path with P4-01's codes),
  `refPlanTarget`'s chunk rule, and the `mutate` ops `putU16`, `putU32` and `putU64`
  (little-endian, value < 2^53) beside `truncate` and `xor`.
- **Rebuild mode** (`--rebuild-content-blobs`, zstd 1.5.7 only) gains the reference chunker (a port
  of `fastcdc.cjs` plus §2.4's segments) and the bundle packer. It writes:
  - `chunks/v1.pkc` (stored raw, codec `none`), `chunks/v2.pkc` and its frame `chunks/v2.pkc.zst`;
  - v2's new bundles, laid out shared after v1;
  - the v1 bundle that holds the largest reused chunk (gen.py's choice for the tampered seed);
  - the synthetic `dup` index and its bundle. `dup` is `t1`'s first three files with the first
    repeated, `f0 f1 f0 f2`, so duplicate records exist; padMerge leaves no duplicate in the
    content set.

  The corpus params equal §2.4's but `bundleTarget: 262144`. Runs then cross bundles (A7's
  reason), and only one v1 bundle ships.

  **The additions-only guard (decision 15).** `--rebuild-content-blobs` computes every blob and
  `refs.json` entry in memory first, and throws, writing nothing, if any pre-existing blob's bytes
  or any existing `refs.json` entry would change; it may only add files and entries. P4-10
  implements the guard and tests it (a temporary copy of `content/blobs/` with one existing blob
  altered makes the rebuild throw and leaves the copy untouched).

- **Normal and `--check`** read the blobs, never compress, and rebuild both files. **Self-checks**
  (each throws):
  - `chunk-v1-to-v2` rebuilds v2 byte for byte, equal to the delta and file results;
  - its `requests` equals `refPlan`'s chunk candidate in `plan-real-chunk-v1-v2` minus the index
    request;
  - every `.pkc` parses, `v2.pkc.zst` decodes to `v2.pkc`, and every bundle an apply case names is
    in an index;
  - `pack-valid-chunks`' `chunks` ref equals `chunks/v2.pkc.zst`'s, which is the join by SHA-256;
  - every mutation lands where its case says;
  - the per-check and per-path self-checks pass at 83 checks (95 structure cases, from 92) and 18
    pack integer paths (from 16).

## 6. Worker (P4-22)

- **No route** (rule 10), migration or table (`TABLE_OWNERS` unchanged). `release_artifacts.role`
  has no CHECK.
- **Ingest** (`services/release/packs/ingest.ts`):
  - `packObjects` gains role `chunk-index` (one per variant, `meta {size, codec, format}`), and
    `PACK_OBJECT_ROLES` gains `chunk-index`.
  - The new checks reuse P4-02's reasons. `pack-index`:
    - `chunks.size` or `bytes` above `MAX_PUBLISHED_INDEX_BYTES`, refused before reading;
    - `parseChunkIndex` fails or is bound to another payload (WASM decode, one index at a time);
    - `format` is unknown.

    `pack-object`: the index, or a bundle in its table, is not stored with that size, or has no
    `blob_refs` row held by **this pack**: `ref_kind = 'pack-upload'` and `ref_id = <packId>` (the
    holder `refHolders` reports), on the key under the pack's prefix (`gated/` exactly when the
    record carries an `entitlement`). A ref held by another pack or release of the product does
    not count. P4-22 adds this stricter variant beside `firstMissingObject` (one `json_each`
    batch, the pack id as one more parameter) and uses it for the index and its bundles.

  - **Dry run** (P4-02's `unverified`): an index not yet promoted is judged from its verified staged
    copy as P4-02 does (`PendingObject`); an index that is neither stored nor staged is listed in
    `unverified` and its parse and bundle checks are skipped; a bundle in a parsed index that is
    not yet referenced is listed in `unverified`, never refused, in a dry run.

  - `MAX_INGEST_INDEX_BYTES` counts chunk indexes too.
  - Bundles get no `release_artifacts` rows, as file blobs get none (P4-01 decision 28): their
    `pack-upload` refs hold them. `chunk-bundle` stays an app artifact role only.
  - The `test:workerd` cases: an index exactly at the bound, one a byte over, and a missing bundle.

- **Discovery:** the Release fragment gains `chunks: true`. `pnpm gen transcripts` re-records it and
  the OpenAPI discovery schema follows. The CLI omits `chunks` with a warning when the fragment is
  absent.
- **No `Range` test is added**: bundles are blobs, and `test/blobs.test.ts` already covers `Range`,
  `If-Range`, 416 and multi-range on blob keys. P4-05 covers pack objects.
- `THREAT-MODEL.md` (P4-22), beside P4-02's ingest paragraph:
  - ingest parses one CI-supplied binary index at a time, under 8 MiB, into typed arrays;
  - a record may name earlier releases' bundles, but only ones holding a `pack-upload` ref of the
    same pack, under the same prefix (§6's check);
  - a gated and a free chain never share an object.

## 7. Rollout

1. **P4-10 merges** (after P4-06, and after P4-13 if both are ready; before P4-19). It brings the contract, the
   claims, the parser and the corpus. It needs no deploy. A Worker built afterwards applies checks
   81–83 at ingest, which refuse nothing CI produces.
2. **P4-22 deploys the Worker first**: ingest of `chunks`, then `release.chunks`. Then the CLI and
   Action release. An old CLI publishes no `chunks`. A new CLI against an old Worker sees no
   `release.chunks` and also publishes none, so no record carrying `chunks` lands unchecked. A
   manifest that lists `chunk` fails an old Worker's resync and an old CLI's validation, so
   products add it only after both have rolled out. A manifest without `strategies` gets chunks
   automatically.
3. **P4-11** releases the SDKs that plan and apply chunks. Earlier SDKs keep `delta`, `file` and
   `full` (§2.1).

**Rollback.** A pre-P4-22 Worker keeps serving stored records, indexes and bundles (they are blobs
with refs), and new publishes omit `chunks`. Rolling back the CLI only stops new indexes. **Feature
flags:** none beyond discovery. **CI already deployed:** unchanged until it upgrades.

### 8.2 Risks

1. **Frozen parameters.** A bad default lives in every published release. Mitigated by S-03's real
   history, and by `params` per record, so a later default applies to new releases only.
2. **The CLI chunker must equal the corpus's.** P4-22's test chunks the corpus payloads and
   compares `(id, len)` with `chunks/v{1,2}.pkc`. `clen` and the bundle hashes depend on the zstd
   build, so they are not compared.
3. **Storage grows without repacking**, by each release's new chunks. Liveness comes from live
   indexes (decision 16: bundles a live index names stay). Repacking is unowned. Recommendation: a later CLI policy that
   packs a chain fresh when its live share drops below 50%, scheduled after P4-14.
4. **Duplicate texture variants double bundle storage.** Chains are per variant, by choice, so each
   device class gets contiguous runs. Cross-variant sharing is a later optimisation with no format
   change.
5. **Presence round-trips.** Reuse depends on `present` answers. A wrong one costs a refused
   ingest (`pack-object`), never a bad device install.
6. **Lane contention** with P4-13 (decision 13).
