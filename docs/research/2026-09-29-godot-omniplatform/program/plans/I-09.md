## Owner decision (2026-10-05): licence choice at sign-in

The owner decided on 2026-10-05 that sign-in asks the person which licence to bind and never
chooses silently. The verbatim decision, the "Replace a device" follow-up and the delegated
decisions are in [`plans/I-04.md`](I-04.md), "Owner decision (2026-10-05): licence choice at
sign-in". Where this plan differs from that section, that section wins. **No device-wire change:**
`PROTOCOL_VERSION` stays 4, and there is no new discovery member, poll status or corpus file.

**Effect on this plan.** §2.4 becomes a ranking plus an explicit bind:

- **`core/anchor.ts` `rankAnchorCandidates(db, product, accountId, deviceId, now)`** replaces
  `chooseAnchorInline`.
  - It returns every usable licence of the account for the product, plus I-24a's seat-holder
    licences, each with `seats {used, limit}` and the state `free`, `full` or `blocked`.
  - The order is §2.4 step 2. It is used only to pick `preselected`.
  - It also returns `keep`, which is true when the device already runs on a usable licence (Q1),
    and `create`, which is offered only when the policy auto-issues to this person and every
    candidate is full.
- **`bindSignedInDevice(…, choice)`** takes `{kind: "license", licenseId, replaceDeviceId?}`,
  `{kind: "keep"}` or `{kind: "create"}`.
  - It refuses with `license_choice_required` when there are candidates and no valid choice.
  - Step 3's auto-issue mint now runs only when there are no candidates at all, or on
    `kind: "create"`. That is the rule "never a second auto-issued licence".
  - A `replaceDeviceId` frees the device through I-08's `freeAccountDevice()`, which the portal's
    Remove also calls, before the seat-checked `authorizeDevice`.
- **Q1 (keep the anchor)** now sets only the preselected row. **Q2 (attach never re-anchors)** is
  unchanged.
- **Attach** (§2.2) is unchanged on the wire. The card's chooser never lists the device's floating
  licence (P1-07). Attach stays the device-side **Add to your Library** step, offered after
  **Keep**.
- LX-10 later swaps the ranking body behind the same signature.
- **Sign-in alignment (2026-10-05, `plans/I-04.md` §F).** `rankAnchorCandidates` marks the
  device's own candidate `current` and sets `keep` only when the device's licence is not a
  candidate (§F.1); preselection is the current row, else Keep, else the first free row, never a
  higher rank over the current one (§F.2). It reports each candidate's `access` through
  `licenseAccess(db, license)`, the fact behind the origin "From signing in" and the mixed rule,
  never a displayed type (owner decision, 2026-10-05: no 'Account-wide' label; origin shown as
  plain words, store named with the key). **Owner decision (2026-10-05): sign-in licenses stay
  device-limited**, so `authorizeDevice` is unchanged: a sign-in licence's devices count against
  its effective limit like any other (§F.6). The replace path runs `freeAccountDevice()`'s
  statements and the guarded seat claim in one batch (§F.3). No sign-in-licence THREAT-MODEL row
  (the seat bound stays).
- `license_choice_required` is registered by I-08 in `errors.json`, not by I-09.

### 2.1 Key entry (§12.2)

This follows I-04 §2.2's order on both routes, with two changes. The limit is
`resolveSetting(product, "identity.keyEntry.limit")`. Steps 3 and 4 run only while
`resolveSetting("identity.keyEntryRefusals")` is on.

1. Rate limit, key lookup and licence lookup, as today (`activation.ts:111-130`).
2. If the device is **enrolled** (`devices` row for `(product, device_id)` with this
   `license_id` and `status = 'authorized'`), proceed as today. Never refuse and never count.
3. If `licenses.account_id IS NOT NULL`, answer `license_owned` with `signInUrl`. Nothing is
   counted.
4. If the number of `license_key_entries` rows for the licence is ≥ the limit, answer
   `key_entry_limit` with `manageUrl` and `keyEntries`.
5. Run `authorizeDevice(…, {boundBy: "key"})` as today. On success, insert one row with
   `surface` `app` or `browser` and add `keyEntries` to the response.

Key entry never sets `devices.subject`. Under S-19 decision 4 the device therefore sees its
licence's own slice, whoever owns the licence. With Identity off, step 2 onwards behaves exactly as
today: no row, no member, no refusal. With Identity on and the switch off, step 5 still counts and
answers `keyEntries`. `manageUrl` = `<origin>/activate?product=<slug>` and `signInUrl` =
`<origin>/signin?product=<slug>`. Both are built from the Worker's own origin, never carry
the key, and are not auth failures.

### 2.2 Attach, subject and sign-out (§12.3)

All three take `Authorization: Bearer pkeyt_…` and `X-PKey-Device`, are `no-store`, and answer
CORS for `core.web.origins` without credentials. Identity off → `404 not_found`.

- **`POST /<p>/identity/attach` `{confirm: boolean}`.** The holder is
  `accountForSubject(resolveSubject(devices.subject))`, **never `licenses.account_id`**
  (S-19 decision 4). If it is null, answer `403 account_required`.
  - `confirm: false` answers `200 {status:"confirm", license:{id, tierId, name|null}}` and writes
    nothing.
  - `confirm: true` calls `attachLicenseAccount` (`accountSubjects.ts:168`), rotates the token and
    answers the activation response plus `subject` and `"attached":"claimed"`. Already attached to
    this account → the same with no `attached`.
  - Refusals: `license_owned` (another account; no `signInUrl`); `license_email_bound` (the
    licence has a buyer email, the account has no matching verified email, and
    `identity.keyEntry.claimByKey` is false); `404 not_found` (no licence on the device).
  - **Attach never changes the device's anchor** (§8 Q2). The enroll-supersede re-anchor is
    LX-10's.
- **`GET /<p>/identity/subject`** answers `200 {subject: "ps_…" | null}`.
- **`POST /<p>/identity/signout`** runs `clearDeviceSubjects(…, "signout")` and answers
  `200 {released}`. `released` is true only when `devices.bound_by = 'signin'` and the anchor
  belongs to the signed-out account (I-04 Q3). In that case the device is also deauthorized.

### 2.3 Discovery (§12.6, I-09 part)

With Identity on, the fragment gains `"account": true`, `"keyEntryLimit": n` (from the same
`resolveSetting` call as §2.1) and the endpoints `attach`, `subject`, `signout` and
`accountPortal` (`<origin>/#/p/<slug>`, for `openAccount()`). `accountPortal` moves here
from I-08 so that the `identity.account` row is testable at I-09. I-08 adds `authorize` and
`redirectToken`. SDKs use an endpoint only when it is present.

### 2.4 Sign-in anchor, inline (S-19 decision 3; Core, no wire)

`core/anchor.ts` `chooseAnchorInline(db, product, accountId, now)` works in three steps:

1. Collect the account's usable licences for the product (`accountLicenses`) on which
   `authorizeDevice` would succeed.
2. Order them by no expiry first, then latest `expires_at`, then earliest `activated_at`. Every
   tier ranks 0 until LX-08 adds `tiers.rank`.
3. If there are none, use the auto-issue mint (origin `oidc`) attached to the account. Otherwise
   give today's sign-in refusal, with no new reason value.

`bindSignedInDevice(…)` sets `devices.subject` with `bound_by = 'signin'`. It runs the rule only
when the device has no usable anchor. A device already running on a usable licence keeps it
(§8 Q1). I-08's passthrough sign-in calls this function. LX-10 swaps the body for `chooseAnchor`
without changing the signature.

### 2.5 Clients and Workers already deployed

- **Old SDKs** ignore the new members. They meet the refusals only on a new install of an Identity
  product, and only after an operator turns the switch on (§7). Node maps any 403 other than

  app shows the wrong copy but loses no state. I-10a and I-10b record the old behaviour of each

- **New SDKs on an old Worker** find no `account` member and report the features unavailable.
- **Existing installs** keep their tokens, refresh, offline grace and documents unchanged.
- **Already deployed Identity products (`djdl`)** start counting from zero at deploy. There is no
  backfill (§8 Q4).

### Open questions for the owner

1. **Q1 Sign-in on a device that already runs on a usable licence** (for example a key-entered
   device that then signs in). **Recommend: keep its anchor.** Only set the subject and offer
   attach. The rank-first rule runs only for a device with no usable anchor. This avoids moving
   seats and config silently. LX-10 may revisit it under `anchorPolicy`.
2. **Q2 Does attach re-anchor?** With every tier at rank 0, rank-first could move a device off the
   licence it just attached, to an older licence of the account. **Recommend: no, never in I-09.**
   The enroll-supersede case is LX-10's.
3. **Q3 Resolver dependency.** S-18 wants discovery and enforcement to read through
   `resolveSetting()`, which is ST-04. **Recommend: add ST-04 to I-09's dependencies.** ST-04
   already waits on ST-01b and ST-03, so the delay is small and no throwaway reader is written.
4. **Q4 Counting from zero at deploy.** Today's `devices.bound_by = 'key'` rows could seed the
   count, but they would penalise current customers for entries made before the rule existed.
   **Recommend: start at zero, with no backfill.**
5. **Q5 Scope of `identity.keyEntryRefusals`.** **Recommend: one platform switch (S-18 A.1),
   default off.** Turn it on once after I-10a and I-10b ship. Do not add a per-product override:
   counting already runs everywhere, and a per-product switch would be a second writer.
