## 1. Summary

- **The feed's `deltas` member gets a shape.** It is an object keyed by the target **payload**
  SHA-256 (`to`). Each value lists up to 4 `payload`-scope `zstd-patch-from` deltas to that
  payload: `{from, method, scope, memBytes, artifact {sha256, bytes}}`. The member holds at most
  64 entries. The Worker lists the `ready` rows of P4-17's `release_lazy_deltas` there, and only
  those: CI deltas stay in their records.
- **It is parsed beside the claims, as P4-13's members are.** `feedContent` gains a fourth
  member. A malformed menu is `null` and never refuses the feed, and no existing verdict moves.
- **The planner sees one more candidate.** `withFeedDeltas(variant, deltas)` appends the menu's
  entries for `variant.payload.sha256` after the record's own deltas. `planTarget`, `plan`,
  `applyDelta` and the engine's candidate loop are then unchanged. CI wins a cost tie. Integrity
  rests on the CI-signed record: the applier checks the artifact hash, the base and the output
  hash against `payload`, and falls back on any failure.
- **The Worker serves what it lists.** The blob route resolves a lazy delta by its artifact hash
  through `blob_objects`, under the holding pack's delivery rule (its gate, under `gated/`).
  P4-18's payload URL answers `dcz` from lazy deltas too.
- **The corpus is append-only.** It appends `feedContentCases` and adds new sections
  `feedDeltaCases` (`plan-matrix.json`) and `feedDeltaApplyCases` (`content/cases.json`). No
  version moves, and no blob is added.

## 2. Contract

### 2.1 Why this stays in wire v4

- V4 §2.4 reserves `deltas` (P4-17) and says a v4 verifier ignores it. Every v4 SDK already
  ignores unknown members, and `feed-valid-unknown-fields-ignored` pins that.
- No claim is added. A claim would let a malformed menu refuse the feed and stop app updates,
  and it would change the verdict of the existing cases. A **usability function** reads the
  member instead (V4 §2.4.1's pattern), and its integers follow §3.1's token rule through the
  verifier's `nonWireIntegers`.
- No selector key, no `typ` and no change to signing. The menu adds no trust: every byte a menu
  entry produces is checked against the CI-signed record (§2.4).
- A bump to `PROTOCOL_VERSION` 5 is needed only when a deployed v4 client must refuse something,
  or an existing corpus verdict changes. Neither happens here, which was also the reasoning for
  P4-13 and P4-19.

**Clients already in the field.** v3 SDKs never fetch the feed. v4 SDKs that predate P4-13
ignore the member, and so do those that predate P4-29: `feedContent` ignores unknown members, and
the appended `feedContentCases` prove it (§4.2). Old clients plan with record deltas only, as
they do today.

### 2.2 The member (V4 new §2.4.2, [C] via `feedContentCases`)

```jsonc
"deltas": {
  "<to: target payload sha256>": [
    { "from": "<base payload sha256>", "method": "zstd-patch-from", "scope": "payload",
      "memBytes": 1048576, "artifact": { "sha256": "<frame sha256>", "bytes": 325258 } }
  ]
}
```

`feedContent(doc, nonWire)` now returns `{packSets, packFloors, revocations, deltas}`. `deltas` is
`null` when absent or unusable, and otherwise a `FeedDeltas` value: an object of `to` to
`FeedDelta[]` holding the known members only. The member is **unusable** when any rule fails.
Patterns match the whole string (§3.3).

| Rule                                                                                                                                                                                                                              |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| an object (a present `null`, an array or any other type is unusable); each key 64 lowercase hex                                                                                                                                   |
| each value an array of 1 to `MAX_FEED_DELTAS_PER_TARGET` (4) entries; the member holds at most `MAX_FEED_DELTAS` (64) entries in total                                                                                            |
| each entry an object: `from` 64 lowercase hex and not equal to its key; `method` and `scope` `VOCAB_TOKEN_PATTERN`; `memBytes` an integer ≥ 1; `artifact` an object with `sha256` (64 lowercase hex) and `bytes` (an integer ≥ 1) |
| `artifact.sha256` unique across the member; (`from`, `method`) unique within a key. Both caps and both uniqueness rules count dropped entries too                                                                                 |

**Forward values.** An entry whose `scope` is not `payload` is **dropped alone**, so a later
`files` menu needs no new member. A key whose entries are all dropped is left out. An unknown
`method` is **kept**, and the planner's `caps.patchMethods` decides, as for record deltas (§3.2).
Unknown members are ignored at every level. The integer pointers are `/deltas/<to>/<i>/memBytes`
and `/deltas/<to>/<i>/artifact/bytes`, both with minimum 1; a failure makes the member unusable.

`size` and `windowLog` from P4-17's descriptor are **not on the wire** (decision 3). The target
size comes from the record's `payload.size`, and the window comes from the frame header (§2.6).

### 2.3 Signing

The menu is inside the feed payload, so the product key's JWS covers every byte of it, like every
other member. A network attacker cannot add, alter or remove an entry. A cached feed is
re-verified on load (§4.1), so the menu read offline is a verified menu. The menu carries the
**Worker's** authority only (product key), never CI's. That is why §2.4 anchors every result in
the record.

### 2.4 Client: reader, merge, planner, verification and fallback (V4 §11.4, informative)

1. **Source.** The engine reads the `deltas` of the **most recently committed feed** of the
   canonical channel, fresh or stale. Freshness gates decisions, not integrity, and a stale entry
   that 404s only falls back. `PackEngineOptions` gains `feedDeltas?: () => FeedDeltas | null`.
   `@polaris-key/node`'s `update/client.ts` and React's `packs/browserPacks.ts` wire it to the
   committed feed.
2. **Merge.** `withFeedDeltas(variant, deltas) → {variant, feedIds}` lives in `packs/select.ts`.
   The variant is returned unchanged (with empty `feedIds`) when any of these holds: `deltas` is
   null; the variant is not usable; the layout is not `container`; or `deltas` has no key equal to
   `variant.payload.sha256`. Otherwise each entry, in feed order, is appended to a **copy** of
   `variant.deltas` as `{method, scope: "payload", from, memBytes, artifact}`, unless its
   `artifact.sha256` equals an existing delta id (a record delta wins). `feedIds` is the set of
   appended artifact hashes. The merged list may exceed `MAX_VARIANT_DELTAS`, which is a claim on
   records only.
3. **Planner.** `planTarget(merged, …)` and `plan()` are unchanged. A feed delta is a candidate
   only when `delta` is in `caps.strategies`, its method is in `caps.patchMethods`, its `from` is
   an installed payload, `memBytes ≤ caps.memBudget` and the disk check passes. Record deltas keep
   the lower `ord`, so **CI wins a cost tie**.
4. **Verification.** `applyDelta` and the native payload port are unchanged:
   - artifact length and SHA-256 against the menu entry, else `delta-artifact-mismatch`;
   - the base's SHA-256 equals `from`, else `delta-base-mismatch`;
   - §2.6's window check against `memBytes`, then the decode, bounded by `payload.size` from the
     record;
   - output length and SHA-256 equal the **record's** `payload`, else `delta-apply-failed`.
5. **Fallback.** A failed feed-delta candidate (a fetch error, a 404 or any of the codes above)
   emits the existing `phase: "fallback"` event and moves to the next candidate. **At most one
   feed-offered delta is tried per install** (decision 6): once one fails, the remaining `feedIds`
   are skipped for that install, while record deltas, `chunk`, `file` and `full` continue. That
   bounds a hostile menu's waste to one artifact, which the planner already priced below the
   alternatives.
6. **Resume.** `PackJournal` gains an optional `feedDelta` (the merged entry) when the strategy is
   a feed delta. A resume re-merges it. A journal whose `delta` is in neither the record nor
   `feedDelta` is abandoned and re-planned. The optional member keeps `PACK_STATE_VERSION` 1, as
   P4-19's `PackInstall` member did.
7. **Telemetry.** No change: a feed-delta install reports `strategy: "delta"` in `packInstalls`,
   which keeps the pair warm (P4-17).

`expect.content`. The appended cases keep `expect.content` to those three members and put the
menu in a sibling `expect.deltas`. So every existing runner passes them unchanged, and that is
also the proof that a populated `deltas` refuses nothing. A P4-29 runner compares
`content.deltas` with `expect.deltas ?? null` on **every** case, so the 48 old cases pin `null`.
New sections are ignored until a runner implements them (P4-13's placement rule). The only runner
edit outside the new sections is the count 48 → 76, made in P4-29's PR for every runner:
`conformance/runners/node/suites.ts` `toBe(48)`, `sdks/python/tests/test_content_decision.py`,
`sdks/swift/Tests/PolarisKeyTests/ContentDecisionConformanceTests.swift` and
`sdks/godot/tests/suite_conformance.gd`. The implementer confirms that each compares
`expect.content` only, and edits any that compares the whole `expect`.

**Mirrors and gate.** `CORPUS_TARGETS` is unchanged: `cases.json` and `plan-matrix.json` are
already mirrored to Swift and Godot, and `content/` stays source-only. `pnpm gen:corpus` writes
all three targets, and `pnpm gen:corpus -- --check` is the drift gate. No `--rebuild-content-blobs`
run is needed. The PR shows that every pre-existing case is byte-identical with a canonical-JSON
diff. The budget is about 60 KB of source, about 160 KB with mirrors.

### 4.3 `plan-matrix.json` `feedDeltaCases`

Each case is `{id, description, variant, recordSha256, filesIndex, chunkIndex, deltas, installed,
caps, expect: {feedIds, target, plan}}`. The runner computes
`withFeedDeltas(variant, deltas)` → `planTarget(merged, recordSha256, filesIndex, chunkIndex)` →
`plan({target, installed, caps})`, and compares by canonical JSON. The generator's reference
recomputes every expectation. The cases:

- `feed-delta-only-candidate`: no record delta, base installed → `delta`;
- `feed-delta-beats-unreachable-record-delta`: the record's base is not installed;
- `feed-delta-tie-record-wins`: equal cost, so the record's delta is chosen;
- `feed-delta-duplicate-id-dropped`;
- `feed-delta-other-target-ignored`;
- `feed-delta-tree-variant-ignored`;
- `feed-delta-unusable-variant`;
- `feed-delta-over-mem-budget`: falls back to `chunk` or `full`;
- `feed-delta-unknown-method`;
- `feed-delta-base-not-installed`;
- `feed-delta-platform-target`;
- `feed-delta-null-menu`;
- `feed-delta-real-v1-v2`: the content set's v1 → v2 pair with the record delta removed and P4-17's
  measured frame (325,258 B) offered. The delta beats `chunk` (P4-17's fourth criterion).

### 4.4 `content/cases.json` `feedDeltaApplyCases` (the target-hash proof)

These cases have `applyCases`' payload-delta shape plus `deltas`. The runner merges, then applies
the merged variant's feed delta with `applyDelta`. They reuse the committed v1 → v2 frame:

| Case                                 | Verdict                   |
| ------------------------------------ | ------------------------- |
| `feed-delta-apply-ok`                | ok, the v2 payload        |
| `feed-delta-apply-artifact-mismatch` | `delta-artifact-mismatch` |
| `feed-delta-apply-base-mismatch`     | `delta-base-mismatch`     |
| `feed-delta-apply-target-mismatch`   | `delta-apply-failed`      |

In `feed-delta-apply-target-mismatch`, the record's `payload.sha256` is altered and the menu is
keyed to the altered hash, so a correct frame still fails the check against the record.

## 6. Worker

### 6.1 Composition (`services/update/feedDoc.ts`, through a hook)

- **Hook.** `ReleaseCatalog.lazyDeltas(recordSha256s): CatalogLazyDelta[]` in `core/hooks.ts`,
  implemented by Release over `release_lazy_deltas` with one read on
  `idx_release_lazy_deltas_state`. No migration; Update reads no Release table directly (rule 6).
- **What it returns.** For each named pack record, for each `container` variant, the `ready` rows
  whose `to` is the variant's `payload.sha256`. It drops a row when:
  - the variant has a record delta from the same `from` and `method`;
  - the descriptor fails §2.2's rules;
  - `windowLog > max(10, min(30, ⌈log2(memBytes)⌉))`, which keeps the frame decodable on a
    wasm32 or 32-bit applier.
    It returns nothing while `LAZY_DELTAS` is off or the product's `lazy_delta_settings.enabled`
    is 0, so either switch withdraws the menu at the next compose (decision 9).
- **Which records.** The document's `packSets.releases`, plus the pins and holds of the app
  records its targets pin. A per-platform document names only its own.
- **Order and caps.** Entries are ranked by P4-17's `installedBase(from)` (devices last seen on
  `from`), then by `created_at` (newest first), then by `artifact.sha256` bytes. The cap is 4
  per key and 64 in total. The member is omitted when it is empty.
- **The seq.** `deltas` is part of the hashed content, so a delta turning `ready` or `cold`
  bumps `seq` at the next request. P4-17's daily cap bounds this to about 20 bumps a day per
  product.

### 6.2 Size: the menu never displaces anything

The composer decides which document to sign (channel-wide or per-platform) and runs P4-13's
shedding order **without** `deltas`. It then adds entries in rank order while the payload stays
at or under 65,536 bytes. It drops lowest-ranked entries first, auditing
`update.feed.deltas_trimmed`, or `update.feed.deltas_omitted` when none fit. So the menu can
never turn a channel-wide document into a per-platform one, shed a P4-13 member or cause
`feed_not_composable`. The menu is checked with `feedContent` before signing, and a menu that
would be unusable is omitted and audited. Worker tests cover:

- the cap guard at exactly 65,536 bytes;
- the P4-13 near-cap fixture `appTargetNearCap`, with the menu trimmed;
- a gated pack's entry;
- each of the hook's exclusion rules;
- `test:workerd`.

### 6.3 Serving (gated delivery)

- **Blob route** (`services/distribution/blobAccess.ts` `decideBlob`). When neither
  `blobs/sha256/<hex>` key is held, a third candidate is read: the `blob_objects` rows with
  `sha256 = <hex>` and `kind = 'delta'` that this product holds a `lazy-delta` ref to, using the
  existing `idx_blob_objects_sha256`.
  - `core/blobs.ts` `refHolders` names the holder of a `lazy-delta` ref as its `ref_id` (the pack
    deliverable), as it does for `pack-upload`.
  - `classify` counts that ref as a pack holder, so the pack rules apply unchanged. A
    `gated/deltas/…` key needs the pack's **current gate**. A public `deltas/…` key needs the
    pack's delivery mode, and `entitled` without a gate stays fail-closed.
  - `blobResponse` already accepts a `deltas/` key against the stored checksum.
  - A cold delta (ref dropped) is the plain not-found, so the device falls back.
- **P4-18's payload URL** (`services/distribution/payload.ts`). The hook's `CatalogPackPayload.deltas`
  gains the payload's `ready` lazy deltas, under the same switches. `Available-Dictionary` naming a
  lazy delta's `from` then answers `dcz` from the stored frame, unchanged. Without it, the
  `?via=dcz` guard's 409 sends the SDK to the WASM delta through the blob route.
- **Rule 10.** No new route. `openapi/polaris-key.v3.yaml` changes only the feed schema (the
  `deltas` member) and the descriptions of the blob route and payload URL.
  `routeCoverage.test.ts` is re-run unchanged. `boundaries.test.ts` passes: Update reads
  Release's rows through the hook, and Distribution reads only Core's tables.
- **Transcripts.** No recorded scenario has a ready lazy delta, so
  `pnpm gen:transcripts -- --check` must stay green with no diff. A diff means the composer leaked
  a member into an empty menu.

## 7. Rollout

1. **P4-17 merges.** Deltas are generated, stored and offered to no one.
2. **P4-29's PR merges.** It carries the contract, the corpus, `client-core`, Node, React and the
   Worker. Every existing runner stays green.
3. **The Worker deploys.** The blob route, the payload URL and the composer ship together. No
   product lists a menu until both P4-17 switches are on for it. There is no new flag.
4. **SDKs release.** Node and React (P4-29), then Python and Swift (P4-30), then Godot (P4-31).

**Old clients.** They ignore the member (§2.1). They also never fetch a lazy delta, so they never
reach the new serving path.

**Old Workers, on rollback.** There is no menu, so P4-29 SDKs plan with record deltas only. A
feed composed before the rollback can still list a delta for its TTL. The old blob route answers
404 for it, and the device falls back (§2.4 step 5).

## 9. Risks

1. **A compromised Worker or product key can offer junk deltas.** The cost is bandwidth and CPU,
   never integrity: the output must equal the record's `payload` (§2.4). The waste is bounded by
   decision 6, by `memBudget` and by the declared `bytes`.
2. **Seq churn.** Each `ready` or `cold` transition re-signs the feed. That is bounded by P4-17's
   daily cap, and is harmless to clients.
3. **Composition cost.** One more indexed D1 read per feed request. A Worker test at 64 packs × 3
   levels stays inside the CPU budget on `test:workerd`.
4. **Ordering.** P4-29 rebases on P4-17. P4-17's brief keeps its fourth criterion only by
   pointing here.
