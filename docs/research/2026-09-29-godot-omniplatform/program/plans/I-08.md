## 0. Findings that change the brief

1. **Nothing of this exists yet.** `services/identity/routes.ts` has no `authorize`, `token`, `choice/*`. What is built and reused: PX-W13's request handle and `__Host-pk_req` binder (`passthrough/request.ts`), the client record and consent views (`passthrough/{client,routes}.ts`, portal API `GET /api/signin/requests/:handle[/consent]`), `account_product_grants.scope_hash` (migration `0087`), I-09's `bindSignedInDevice` (`core/licensing/anchor.ts:300`), `attach`/`subject`/`signout` (`services/identity/attach.ts`), the key-entry accounting (`core/licensing/keyEntries.ts`), and I-30's relying-party client (`core/oidc/client.ts`, not needed here: `authorize` is the Worker acting as the _server_, so it does not use it).
2. **`identity.claims` does not exist.** The manifest's `identity` takes only `keyEntry`, `terms`, `redirectPaths` (`shared-manifest/src/index.ts:6264`; I-35 widens it). The default scope is therefore `profile email` (`CONSENT_PROFILE_CLAIMS`, `passthrough/routes.ts:38`) plus `cloudSync` when the product runs it. No catalog or manifest change, so no rule-9 entry.
3. **The device is unknown at `authorize`.** A browser redirect carries no `X-PKey-Device`; only `token` does. So "the press mints then binds the device" (brief, I-27 §2.2) splits: **Continue** records consent and the choice on the code and (first automatic licence) mints the account licence; **`token`** binds the device with `bindSignedInDevice`. See D5.
4. **Device code is I-37's, and it fails closed.** The brief's device-code half (card with app header for `auth/device`, Continue bound to the entering browser, `choose`/`replace`/`autoissue` on device code, poll `subject`/`attachable`, hints on `auth/device/start`) contradicts the approved I-37 ruling D1.A and is removed from I-08 (D4).

## 1. Summary

- Card-side routes on the portal API for the web redirect: request view (exists), licence choice, Continue, Cancel; `login_hint`, `name_hint`, `purpose` carried on the request record (absorbs PX-W18 for `authorize`).
- App-mode licence choice (`license_choice=app`) with the pending sign-in grant, `choice/*` routes, Replace, key-in-card, and the D4 first automatic licence. This is the part D2 proposes to split off.
- Discovery gains `issuer`, `authorize`, `token`, `configured: true` (and, with I-08b, the four `choice*` endpoints). Everything behind the product's Identity toggle.
- Six error codes plus `license_choice_required`; transcripts as §4; **no SDK code**, only parity rows and fixtures for I-10a/I-10b/I-15.

## 3. Contract

**WIRE-CONTRACT-V4:** write §12.4 (`authorize`) and §12.5 (`token`, `choice/*`), add them to the amendment ledger, and update §12.6's identity fragment. Delete "I-21 appends `oauth/authorize`" from §12.8 rule 3 (`authorize` is already in `IDENTITY_NAVIGATION_ENTRIES`, so Core's `identity_disabled` redirect already covers it). `packages/shared-protocol/src/identity.ts` gains the request/response types: `AuthorizeParams`, `TokenResponse` (exactly `access_token`, `token_type: "Bearer"`, `scope`, `schemaVersion`, `device`, `license`, `keyEntries?`, `subject`; no `expires_in`, no `refresh_token`), `TokenError`, and (I-08b) `PendingSignIn`, `LicenseChoiceInput` etc. shared from the card.

**`authorize`** exactly as I-27 §2.1 (parameters, card-rendered `invalid_client` / `redirect_uri_mismatch` before any redirect, 302 errors with `iss`). Implementation shape: `authorize` validates, stores the parameters (client*id, redirect_uri, state, code_challenge, scope, nonce, licenseChoice, purpose, hints) in the PX-W13 request record (`SignInRequestRecord` gains an `authz` member), mints the `rq*`handle with the`\__Host-pk_req`binder, and 303s to the card at`<origin>/signin?request=rq_…`. The binder cookie is the R1-07 callback binding: Continue/Cancel need account session + CSRF + binder, and the code is delivered only by the response to that request.

**Portal API (same-origin JSON, `no-store`):** `POST /api/signin/requests/:handle/continue` (body: `consent` claims, `choice`) and `…/cancel`. Both answer `{ redirect: "<redirect_uri>?code=…&state=…&iss=…" }` or the `access_denied` form; the SPA navigates. I-08b adds `GET …/licenses` and `GET …/licenses/:licenseId/devices`. A handle that fails binder, product or Identity-off answers `404 not_found` as today.

**Code:** new `SingleUseKind` `"signin-code"` (60 s, consumed atomically, keyed by a peppered hash), bound to product, `client_id`, `redirect_uri`, `code_challenge`, granted scope, account, pairwise subject, consent/choice. **`token`:** form-encoded only, `no-store`, CORS `core.web.origins` without credentials, requires `X-PKey-Device` and metadata headers; consumes the code, checks verifier (S256, constant time), `client_id`, `redirect_uri`, binds the device through `bindSignedInDevice`, and answers the activation shape with `subject`. A replayed code answers `invalid_grant`; the already-issued token is not recalled (it was bound to a PKCE-proven redeemer).

**Rate limits and audit:** per-device and per-network limits on `token` and `authorize` using `core/rateLimit.ts`; `429 rate_limited` + `retryAfter` flat. Audit rows for Continue, Cancel and Replace; no code, verifier, state or hint ever logged.

**Errors (`conformance/parity/errors.json` first, `kind: wire`, service `identity`):** `invalid_request`, `invalid_client`, `invalid_grant`, `unsupported_grant_type`, `invalid_scope`, `redirect_uri_mismatch`, `license_choice_required` (409). Then `pnpm gen constants --check`.

**Deployed clients and workers:** no deployed client calls any of these routes. Old SDKs ignore the new discovery members; a new SDK on an old Worker finds no `authorize`/`token` endpoint and reports the feature unavailable. Old Worker rollback: routes vanish; codes (60 s) and grants (300 s) die; web apps show "Sign in again".

## 9. Risks

- Login CSRF: an attacker-started `authorize` lands the victim on the product's own registered origin with a code the app never requested; the app's `state` check rejects it. The attacker never receives the code (redirect is to the product origin only).
- Open redirect: exact origin and path match only; no wildcard; refusal is rendered, never redirected.
- Mix-up: `iss` on success and error (RFC 9207).
- `token` replay of a stolen code needs the PKCE verifier; a verifier mismatch consumes the code (no brute force).
- If D2 is rejected, the 1.2-1.7 week size is optimistic; review in one sitting is not possible.
