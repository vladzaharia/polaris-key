## Consolidation 2026-10-07

Added by the lead on 2026-10-07, after the owner decided that the consolidation ships as the 0.9 line and that 1.0 is decided later, from this review ([README §12](../../../2026-10-07-dx-consolidation/README.md#12-versions-09x-now-10-later)). Its stage, DX consolidation L: Launch, is not a track in `tracks.md`; it depends on every required package in tracks A–K and on P0-50.

## Goal

1.0 readiness review, as scoped below. Done when every acceptance criterion holds and the green gate passes.

## Why

The owner decided on 2026-10-07 that the consolidation ships as the **0.9 line**: batch 6 is the last 0.8 release (v0.8.33), the first consolidation batch is v0.9.0 and every batch after it is a v0.9.x release. **1.0 is decided later**, from this review ([README §12](../../../2026-10-07-dx-consolidation/README.md#12-versions-09x-now-10-later)): when all six parts of the bar pass, the owner can tag v1.0.0, and from then on every SDK follows semver against `conformance/parity/api.json`.

## Read first

- `AGENTS.md` (always), and the skill that applies, if any.
- [README §12](../../../2026-10-07-dx-consolidation/README.md#12-versions-09x-now-10-later) (its 1.0 bar is copied below) and the exit criteria of every track in [`tracks.md`](../../../2026-10-07-dx-consolidation/tracks.md).
- `conformance/parity/api.json`, `backlog-changes.json`'s `uxRows`, P0-24's migration ledger and the production deploy history.

## Scope

**In:**

- A time-boxed review against the 1.0 bar (the consolidation plan's README §12, copied below) that writes `notes/1.0-readiness.md`, with evidence and a recommendation. The owner makes the 1.0 call from it.

**Out** (and where it belongs instead):

- Work owned by the packages in the Depends on and Unblocks rows, and the rest of the plan (→ the ids in [`tracks.md`](../../../2026-10-07-dx-consolidation/tracks.md)).

## The 1.0 bar

Copied from [README §12](../../../2026-10-07-dx-consolidation/README.md#12-versions-09x-now-10-later); if they differ, README §12 wins.

1. **Complete.** Every required package in tracks A–K is done, including the second-release drops (`*b`). Every `UX-*` row is built, parked with a revive condition, or dropped.
2. **Stable API.** `api.json` is the frozen public surface of all six SDKs; no deprecated alias
   exists; no wire change is pending in the corpus lane; `PROTOCOL_VERSION` stays 4.
3. **Secure.**
   - ST-30's security review has passed.
   - A final security review of the consolidated surfaces has no open blocking finding. Those surfaces are: console sign-in on accounts and roles, connections and domain routing, personal and service tokens, the access policy, and automatic licences.
   - P0-50 is done, and no high or medium dependency alert is open.
4. **Proven in production.**
   - The consolidated features have run in production for at least 14 days, with no P1 incident and no rollback.
   - DJDL and the system product run on the new model (tiers, access policy, channels, release tracks), migrated through P0-49 runs.
5. **Experience.**
   - A fresh product goes from wizard to Integration to Verified on every must-tier SDK with no undocumented step.
   - A whole-product audit with the same lenses as 2026-10-07 finds no blocking issue.
   - The docs have one start path, and every generated page is current.
6. **Engineering.**
   - The full CI matrix is green on the launch commit.
   - Lint and debt baselines (strings, page budget, boundary, table crossings) are no larger than at the start.
   - The boundary tests block.

## Design notes

- The review is evidence, not opinion: each part's verdict cites the command, query or link that shows it.
- A gap becomes a proposed package with an id and an owner track, not a note in the recommendation.
- No new copies (tracks.md rule 4): build on the one mechanism this plan names, never beside it.

## Steps

1. Confirm every dependency is `done` (`node check.mjs --show P0-51`).
2. Check each of the six parts of the bar and record the evidence in `notes/1.0-readiness.md`.
3. Recommend tagging v1.0.0 or staying on the 0.9 line with the 1.0 punch list; hand off to the lead. The owner makes the 1.0 call.

## Acceptance criteria

- [ ] `notes/1.0-readiness.md` gives, for each of the six parts of the 1.0 bar, pass or fail with its evidence (commands and their output, links, production checks)
- [ ] It recommends tagging v1.0.0 (all six parts pass) or staying on the 0.9 line with a 1.0 punch list, each gap proposed as a package with its track
- [ ] The green gate passes (`AGENTS.md`), including any drift gate this work package touches.
