# E3 — Distributing a Godot 4.x game on Windows, Linux and Web: what a release/update server must provide

Research date: 2026-09-29. Scope: Polaris Key (Cloudflare Worker, GitHub Releases indexer, channels stable/beta/pr-N, streaming download gateway, Sparkle appcast + /version JSON, Ed25519 signing).
Method: primary docs fetched via WebFetch/WebSearch on 2026-09-29. Where a claim rests on a secondary source, or a summarizer could have garbled a page, it is flagged **[UNVERIFIED]** or **[SECONDARY]**. Page "updated" dates from Microsoft Learn front-matter are quoted where useful.

## 0. Ten findings that change the design

1. **A Godot game cannot use the Microsoft Store's "EXE/MSI URL" path.** Store Policy 10.2.9 (policy v7.20, page updated 2026-09-14) says _"Non-gaming products may submit an HTTPS-enabled download URL"_. Policy 10.2.5 says games _"must be submitted using supported package types … installed and updated only through the Store."_ A game must therefore ship as MSIX (or MSIXVC via the GDK for Xbox), Store-managed updates only. Any self-updater (Velopack/WinSparkle/Sparkle) must be disabled in the Store build. https://learn.microsoft.com/en-us/windows/apps/publish/store-policies
2. **Games must use the Microsoft Store in-product purchase API** for digital goods (10.8.1): no steering to other purchase mechanisms, but previously purchased content may be consumed. Non-game apps may use third-party billing. Store-hosted DLC-with-packages (optional packages) is "restricted set of developers" (contact support).
3. **Policy 10.2.2** forbids "dynamic inclusion of code" that changes/extends described functionality. Godot PCKs can carry GDScript ("Scripts within packs execute normally"). Hot-loading code-bearing PCKs in a Store build is a certification risk; content-only packs are safer. (Inference from the two policy texts.)
4. **`msstore` CLI / GitHub Action can publish updates only for free products today** ("App update operations … currently supported for free products only. Paid products will be supported in a future release", docs dated 2026-08-30 / 2026-09-28). The app and its first submission (incl. age-rating questionnaire) must be created manually in Partner Center first. https://learn.microsoft.com/en-us/windows/apps/publish/msstore-dev-cli/overview
5. **Cloudflare Workers static assets cap files at 25 MiB** (Free and Paid); a stock Godot `index.wasm` is ~35-40 MB raw (Godot 4.3 blog: "40 MB uncompressed / ~5 MB Brotli"), and PCKs are usually larger. Compression does not help: the limit applies to the uploaded file. Web builds must be served from **R2 via a Worker** (or a public R2 bucket/custom domain), not as static assets.
6. **Godot has no Ed25519 and no SHA-512 natively**: `Crypto` is RSA-only (+HMAC SHA-1/256), `HashingContext` is MD5/SHA-1/SHA-256 only. Ed25519 verification of Polaris Key JWS therefore needs a native plugin on desktop (e.g. the MIT GDExtension `freehuntx/gd-ed25519`, Monocypher-based) or WebCrypto through `JavaScriptBridge` on web. Large-file integrity can be plain SHA-256 listed inside a signed manifest (pure GDScript).
7. **WebCrypto Ed25519 is now in all three engines**: Safari 17.0 (Sep 2023), Firefox 129 (Aug 2024), Chrome 137 (May 2025); ~79% of users as of Aug 2025 → fine for a 2026 web build, keep a pure-JS fallback (@noble/ed25519) for stragglers.
8. **winget rejects redirected installer URLs** (`Validation-Indirect-URL`: "URL is not coming directly from the ISV's server … redirector … not allowed"), and requires HTTPS, matching domain, stable hash, non-interactive install. A Polaris Key gateway that _streams_ (200, no 302) from the publisher's own domain satisfies this; a redirecting gateway does not.
9. **Flathub's requirements now include a generative-AI policy**: "AI tools or agents must not open or automate Flathub submission pull requests, or generate their commit messages …; Flathub manifests must not contain AI-generated or AI-assisted content" (docs.flathub.org requirements, fetched 2026-09-29). Automation must be deterministic tooling (x-checker-data / external-data-checker) and human-authored. **[verify current wording before relying on it]**
10. **Godot 4.4+ has first-class patch PCKs; 4.6 added delta-encoded patches**, and the Godot docs themselves recommend _asymmetric-crypto-signed patches for launcher-based patching, public key stored in the main PCK_. This is exactly Polaris Key's signed-artifact model.

## A. WINDOWS

### A1. Microsoft Store

**A1.1 Win32 EXE/MSI (URL) vs MSIX**

- EXE/MSI submission (since 2021): publisher hosts a versioned HTTPS URL, Store downloads/installs silently. Requirements (Policy 10.2.9): .msi/.exe only; the binary **and all PE files** signed with a cert chaining to Microsoft Trusted Root Program CA (self-signed refused); URL must be versioned and the bytes must never change after submission; every update needs a new versioned URL + new submission; silent install required (UAC allowed); standalone offline installer, not a stub; PC only; **non-gaming only**. Store-managed updates NOT available ("Updates are the app's responsibility"). https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/choose-distribution-path ; https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msi/upload-app-packages (says the Store keeps copies of the most recent packages and will re-download+re-certify if the CDN bytes are swapped).
- MSIX submission: Microsoft re-signs (no cert to buy), Microsoft hosts/CDNs, Store-managed updates, gradual rollout, flights, differential downloads. "Recommended path".
- **Better for Godot: MSIX** — the only option a game is allowed to use. Godot 4 has no UWP/MSIX exporter; the practical route is Windows export (embed PCK = single exe, or exe+pck) → wrap with MSIX Packaging Tool / `makeappx` as a **full-trust (`runFullTrust`) Win32 desktop package**. A Godot forum thread reports partial-trust MSIX installs but "nothing happens" on launch; switching to `runFullTrust` fixed it (https://forum.godotengine.org/t/msix-run-with-partial-trust/135238). `runFullTrust` is a restricted capability and needs Partner Center approval steps (https://learn.microsoft.com/en-us/windows/uwp/packaging/app-capability-declarations). MSIX package identity/`user://` virtualization behaviour for Godot is **[UNVERIFIED — needs a spike]**.
- Xbox Play Anywhere path needs ID@Xbox onboarding + GDK + MSIXVC/XVC packages (https://devdocs.xbox.com/paths/play-anywhere/overview) — out of scope for stock Godot.

**A1.2 Publishing automation**

- `msstore` CLI (preview; cross-platform; needs .NET 9 runtime; `winget install "Microsoft Store Developer CLI"` or brew). Auth = Entra ID app with Manager role in Partner Center; `msstore reconfigure --tenantId --sellerId --clientId --clientSecret` (or certificate thumbprint/file). GitHub Action: `microsoft/microsoft-store-apppublisher@v1.1`. `init/package` know WinUI, MAUI, Flutter, Electron, React Native, PWA, UWP — **not Godot**, so use the generic path: `msstore publish <file.msix|.msixupload> -id <productId> [--noCommit] [-f <flightId>] [-prp <0-100>]`. https://learn.microsoft.com/en-us/windows/apps/publish/msstore-dev-cli/commands ; https://learn.microsoft.com/en-us/windows/apps/publish/msstore-dev-cli/github-actions
- Other subcommands: `apps list/get`, `submission status|get|getListingAssets|updateMetadata|update|poll|publish|delete|rollout {get|update <pct>|halt|finalize}`, `flights list|get|create <productId> <name> --group-ids … [--rank-higher-than]|delete|submission … |rollout …`. Gotcha in docs: `publish` deletes any pending draft and recreates it from the last published submission, so publish _before_ editing metadata.
- MSI/EXE apps have a separate REST API (`https://api.store.microsoft.com/submission/v1/product/{productId}/…`; Entra client-credentials token valid 60 min; header `X-Seller-Account-Id`): https://learn.microsoft.com/en-us/windows/apps/publish/store-submission-api ; MSIX uses the older "Microsoft Store submission API" (referenced from the CLI page; not fetched).
- **Flights (beta groups):** "known user groups" (Microsoft-account emails), per-flight rank (highest-ranked flight wins even with a lower version), flights use the same certification (some WACK failures become "passing with notes"), can be combined with gradual rollout; Xbox flight members must update manually. https://learn.microsoft.com/en-us/windows/apps/publish/package-flights
- **Gradual rollout:** percent of _existing_ customers; increase/halt/finalize; **MSIX only**; halted rollout does not roll back installed users. https://learn.microsoft.com/en-us/windows/apps/publish/gradual-package-rollout
- **Certification lag:** "can take up to three business days"; typically hours; once passed, listing visible in ~15 minutes on average; listing-only changes < 1 hour. https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/app-certification-process (MSI/EXE: up to three business days per the search summary).

**A1.3 How Store apps update; in-app update APIs**

- MSIX Store apps: Store handles updates (user setting + policy; users can only pause 1-5 weeks). Package "mandatory update" flag exists but is _not enforced by Microsoft_ — app must enforce it itself.
- API: `Windows.Services.Store.StoreContext` (Win10 1607+): `GetAppAndOptionalStorePackageUpdatesAsync`, `RequestDownloadAndInstallStorePackageUpdatesAsync`; silent variants `TrySilentDownloadStorePackageUpdatesAsync` / `TrySilentDownloadAndInstallStorePackageUpdatesAsync` (1803+; succeed only if "Update apps automatically" is on and connection not metered; check `CanSilentlyDownloadStorePackageUpdates`). https://learn.microsoft.com/en-us/windows/uwp/packaging/self-install-package-updates
- **Non-UWP callers (Godot):** desktop apps with package identity may use `StoreContext`, but must call `IInitializeWithWindow::Initialize(hwnd)` on the StoreContext or "this object will return inaccurate data or errors"; in-app purchase is "not currently supported in elevated applications"; `Windows.Services.Store` has no simulator — the app must be published (can be hidden) and associated to test. https://learn.microsoft.com/en-us/windows/uwp/monetize/in-app-purchases-and-trials . For Godot this means a **C++/WinRT GDExtension** (Godot's main window HWND via `DisplayServer.window_get_native_handle(HWND)`). Detect the Store/MSIX context at runtime with `GetCurrentPackageFullName` (`APPMODEL_ERROR_NO_PACKAGE` = unpackaged) to switch updater backends. https://learn.microsoft.com/en-us/windows/msix/detect-package-identity
- Store-managed receipts: `Windows.Services.Store` provides no client-side receipt; server-side entitlement check via the Microsoft Store collection REST API (Entra auth).

Game revenue share 88/12 since Aug 2021 [SECONDARY: trueachievements]. Sources: https://blogs.windows.com/windowsdeveloper/2025/09/10/free-developer-registration-for-individual-developers-on-microsoft-store/ ; https://blogs.windows.com/windowsdeveloper/2025/05/19/microsoft-store-expands-opportunities-for-windows-app-developers/ ; https://www.windowscentral.com/microsoft/windows-11/microsoft-store-drops-fees-for-individual-developers-apple-still-charges-usd99-per-year/ ; https://www.trueachievements.com/n45372/microsoft-increases-revenue-share-for-developers-microsoft-store

### A2. MSIX + App Installer outside the Store

**A2.1 `.appinstaller` schema** (https://learn.microsoft.com/en-us/uwp/schemas/appinstallerschema/schema-root, .../element-appinstaller)

- Root `<AppInstaller xmlns=".../appinstaller/2017/2" Version="Major.Minor.Build.Revision" Uri="…">` — `Uri` = "Web URI to the redirected appinstaller file" (max 3 redirects; **multi-key/value query strings unsupported**). Only UTF-8, no escapes, no non-ASCII.
- Exactly one of `MainPackage` or `MainBundle` (`Name`, `Publisher`, `Version`, `Uri`, optional `ProcessorArchitecture`) — Name/Publisher/Version must **exactly match** the package identity. Also `Dependencies`, `OptionalPackages`, `RelatedPackages`.
- `UpdateSettings`: `OnLaunch HoursBetweenUpdateChecks="0-255" (default 24) ShowPrompt UpdateBlocksActivation` (BlocksActivation requires ShowPrompt=true); `s4:AutomaticBackgroundTask` (every 8 h, no UI); `s4:ForceUpdateFromAnyVersion` (permits **downgrade**; without it only higher versions); `s4:UpdateUris`/`s4:RepairUris` fallbacks (namespace `…/appinstaller/2021`, Win11/21H2+). Min OS: base 1709; HoursBetweenUpdateChecks/AutomaticBackgroundTask 1803; ShowPrompt/UpdateBlocksActivation/ForceUpdateFromAnyVersion 1903; docs for "auto-update and repair" say Win10 2004+ and all Win11. https://learn.microsoft.com/en-us/windows/msix/app-installer/update-settings ; https://learn.microsoft.com/en-us/windows/msix/app-installer/auto-update-and-repair--overview
- Gotcha (feature-status page, reviewed Aug 2026): Visual Studio emits the **2017/2** schema, which silently ignores ShowPrompt/UpdateBlocksActivation; switch xmlns to `…/appinstaller/2021`. https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/distribution-feature-status
- Differential updates: `AppxBlockMap.xml` holds SHA-256 per 64 KB block; updates fetch only changed blocks (MS App Installer blog: https://learn.microsoft.com/en-us/archive/blogs/appinstaller/differential-updates-for-uwp-apps). Server must support **HTTP/1.1 byte-range requests** and serve MIME types `application/appinstaller`, `application/msix`, `application/msixbundle`. https://learn.microsoft.com/en-us/windows/msix/app-installer/installing-windows10-apps-web
- Settings can also be overridden by PowerShell (`Set-AppxPackageAutoUpdateSettings`) or Intune CSP.

**A2.2 Can Polaris Key serve `.appinstaller` dynamically per channel?** Yes (design inference). The installed package records the `.appinstaller` URI and re-polls that URL; the file is just XML. A Worker can render `/msix/{slug}/{channel}.appinstaller` from the release index (Version quad from semver; `MainPackage/@Uri` → gateway URL of the .msix/.msixbundle). Constraints: `Uri` must equal the URL it is served from (or redirect ≤3 times); at most one query key/value pair; no custom auth headers, so gating is by unguessable path/token only; the gateway must honour Range; use a **different package Identity Name per channel** (e.g. `Studio.Game.Beta`) for side-by-side channels, same Name+Publisher for in-place switching (then use `ForceUpdateFromAnyVersion` for rollbacks).

**A2.3 `ms-appinstaller:` protocol** — **still disabled by default** (since App Installer 1.21.3421.0, 12 Dec 2023; abuse by Emotet/CVE-2021-43890 pattern). Feature-status page last reviewed August 2026 still says disabled; enterprises can re-enable with GPO `EnableMSAppInstallerProtocol`. Link directly to the `.appinstaller` file (download + double-click). https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/distribution-feature-status

**A2.4 Signing**

- MSIX must be signed by a cert users' machines trust; manifest `Publisher` must equal cert subject (else 0x8007000b in signing).
- **Azure Artifact Signing** (renamed from Trusted Signing; GA Jan 2026): Basic **$9.99/month** (5,000 signatures, 1 profile per type, $0.005 per extra), Premium **$99.99/month** (100,000 signatures, 10 profiles); needs a **paid** Azure subscription (free/trial/sponsored rejected). Public-trust eligibility (quickstart updated 2026-09-29): **organizations** in US, Canada, EU, UK, Australia, NZ, Japan, South Korea, Singapore, Switzerland, Norway, Israel; **individual developers only in the US or Canada** (Azure billing account type must be "Individual", legal name/address must match government ID; Verified ID via AU10TIX + Microsoft Authenticator). Org validation takes 1-20 business days. Certs are short-lived (daily renewed; always timestamp via `http://timestamp.acs.microsoft.com`); no EV, ever. Works with SignTool+dlib, PowerShell, GitHub Actions, Azure DevOps task; signs "all file types SignTool supports" incl. MSIX, EXE, DLL. https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart ; https://learn.microsoft.com/en-us/azure/artifact-signing/faq ; https://devclass.com/2026/01/14/code-signing-windows-apps-may-be-easier-and-more-secure-with-new-azure-artifact-service/ ; pricing page https://azure.microsoft.com/pricing/details/artifact-signing/
- **SmartScreen** (docs reviewed 2026): EV no longer bypasses; reputation = file-hash + publisher-cert signals, accumulates ("several weeks and hundreds of clean installs"); Store apps never warned; unsigned files restart at zero per version; Win11 **Smart App Control** blocks unsigned code without reputation. https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation
- **Sparse package / packaging with external location** (Win10 2004+): a tiny identity package registered by your own installer gives an unpackaged exe package identity (notifications, background tasks, etc.) while you keep your own install/update; **cannot itself be Store-submitted**. https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/grant-identity-to-nonpackaged-apps-overview

### A3. Classic installer / portable + self-update frameworks

**A3.1 Velopack** (MIT; Rust core; libs for C#, Rust, JS, C++, Python; Java/Swift/Go "planned"). https://docs.velopack.io/ ; https://github.com/velopack/velopack

- **CLI** `vpk pack --packId --packVersion --packDir --mainExe [--channel] [--delta BestSpeed|…] [--noPortable] [--framework] [--signParams|--azureTrustedSignFile]`. Windows output: `releases.{channel}.json` (+ legacy `RELEASES`/`RELEASES-{channel}`), full `.nupkg`, delta `.nupkg`, `Setup.exe`, `Portable.zip`. Linux output: `.AppImage` (default channel `linux`). Default channels `win`/`osx`/`linux`; docs recommend explicit arch-qualified names (`win-x64-stable`, `win-x64-beta`, …). https://docs.velopack.io/reference/cli/content/vpk-windows ; .../vpk-linux ; https://docs.velopack.io/packaging/channels
- **Feed format** (`releases.{channel}.json`): `{"Assets":[{PackageId, Version, Type:"Full"|"Delta", FileName, SHA1, SHA256, Size, NotesMarkdown, NotesHTML}]}`; "the only way `UpdateManager` can discover releases" (https://docs.velopack.io/distributing/overview ; C# source https://raw.githubusercontent.com/velopack/velopack/master/src/lib-csharp/VelopackAsset.cs).
- **Client behaviour (C# `SimpleWebSource`)**: GET `{baseUri}/releases.{channel}.json` **plus query params** `arch`, `os`, `rid`, and (if already installed) `id` and `localVersion`; asset download = `{baseUri}/{FileName}` or an **absolute URL if `FileName` starts with http(s)** (https://raw.githubusercontent.com/velopack/velopack/master/src/lib-csharp/Sources/SimpleWebSource.cs; summarizer wrote `RELEASES.{channel}.json` casing in one place — **[UNVERIFIED casing]**, docs say lowercase `releases.`). ⇒ **Polaris Key can serve a Velopack-compatible feed dynamically** (per-channel, per-arch, even per-installed-version delta selection using `localVersion`), with `FileName` pointing at the streaming gateway. Client picks the channel it was installed from unless `ExplicitChannel` is set; `AllowVersionDowngrade`, `MaximumDeltasBeforeFallback` (default 10). https://docs.velopack.io/integrating/overview
- **Non-.NET integration:** C++ lib `velopack_libc_{version}.zip`; `Velopack::VelopackApp::Build().Run()` must run at the very start of `main()` (may restart/exit the process); `UpdateManager(url)`, `CheckForUpdates()`, `DownloadUpdates()`, `WaitExitThenApplyUpdate()` then you `exit(0)` yourself (https://docs.velopack.io/getting-started/cpp). Lifecycle hooks re-launch your main exe with `--veloapp-install|--veloapp-obsolete|--veloapp-updated|--veloapp-uninstall <ver>` (timeouts 30/15/15/30 s) and **kill it if it does not exit** (https://docs.velopack.io/integrating/hooks). Packaging docs are .NET-oriented and mention neither non-.NET apps nor Godot.
- **Can Velopack wrap a Godot exe?** Packaging: yes (`--packDir` is just a folder; sidecar or embedded PCK both fine). Runtime: hooks would boot the whole Godot engine for a hook call, so use either (a) a tiny native launcher (Rust/C++) as `--mainExe` that calls `VelopackApp::Build().Run()` and then execs the Godot binary, plus a GDExtension exposing update check/download/apply to GDScript; or (b) a GDExtension that parses argv and calls `Run()` at CORE init level **[UNVERIFIED that this is early enough]**. Recommend (a).
- Velopack Flow (hosted update service by the same authors) exists as a first-class source [SECONDARY, release-notes summary] — it is the competitor a self-hosted feed replaces.

**A3.2 WinSparkle** (MIT; Sparkle-format appcasts; C API; DLL). https://winsparkle.org/ ; releases https://github.com/vslavik/winsparkle/releases

- Appcast is RSS 2.0/Sparkle. `<enclosure sparkle:os="windows|windows-x86|windows-x64|windows-arm64|macos" sparkle:version sparkle:installerArguments length type>`, `<sparkle:minimumSystemVersion>10.0.22000</…>`. Installer args examples: Inno `/SILENT /SP- /NOICONS`, MSI `/passive`, NSIS `/S`. It downloads and **launches an EXE/MSI installer** (not a zip/delta). https://winsparkle.org/guides/publishing-updates/
- **EdDSA (Ed25519) supported since 0.9.0** ("Introduced EdDSA signature support; new `winsparkle-tool`; DSA deprecated"); 0.9.1 fixed public-key validation; 0.9.3 custom HTTP headers on download; 0.9.4 adds VS 2026 support (release page shows day/month only — 0.9.4 is a 2026 release by inference); 0.8.3 gzip/deflate appcasts + multi-enclosure selection. Signature = base64 Ed25519 over installer bytes in `sparkle:edSignature` (same key family as Polaris Key's). API: `win_sparkle_set_appcast_url`, `win_sparkle_set_eddsa_public_key`, `win_sparkle_init`, `win_sparkle_cleanup`, `win_sparkle_check_update_with_ui`; app needs VERSIONINFO (ProductName/ProductVersion/CompanyName). https://winsparkle.org/guides/integrating-winsparkle/
- **No documented channel support** (`sparkle:channel` not mentioned) → one appcast URL per channel, set at runtime. **[UNVERIFIED negative]**
- Godot: GDScript cannot call a DLL; needs a small **GDExtension (C++/Rust) wrapping WinSparkle.dll** + shutdown callback that quits the Godot tree. Polaris Key's existing Sparkle appcast renderer only needs Windows enclosures (`sparkle:os="windows-x64"`, installer URL through gateway, `edSignature` from the existing Ed25519 pipeline).
- Squirrel.Windows: legacy; Velopack's README advertises automatic migration from it. Don't build new work on it.

**A3.3 Installers / portable / signing**

- Inno Setup / NSIS / WiX produce the silent installers needed for WinSparkle, winget (winget auto-supplies silent switches for `inno`/`nullsoft` types) and non-game Store EXE path; portable zip = winget `zip`+`portable` nested type, no self-update.
- **Godot Windows export**: signing via SignTool or osslsigncode configured in Editor Settings + preset; env overrides `GODOT_WINDOWS_CODESIGN_IDENTITY_TYPE|IDENTITY|PASSWORD`; **"code-signed executables cannot have PCK data appended afterward"**, so sign during export or use a **sidecar `.pck`** and sign the exe independently. Embedded PCK limit ~3.89 GB total. Design note: with a sidecar PCK, content-only patches leave the exe hash unchanged, so SmartScreen _file-hash_ reputation survives updates. https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html
- Azure Artifact Signing can be driven from Godot's export via custom signtool arguments (dlib) **[UNVERIFIED in Godot preset UI]**; simplest is a CI post-export sign of exe/dll.

### A4. Package-manager surfaces (winget, Scoop, Chocolatey)

- **winget** — community repo = PR to `microsoft/winget-pkgs`; manifest schema **1.12.0** (InstallerType: msix, msi, exe, inno, nullsoft, wix, burn, portable, zip (+`NestedInstallerType`), font; `Channel` field exists but is **"Not implemented"** → model beta as a separate `PackageIdentifier`). Automation: `wingetcreate update <PkgId> -u <url> -v <ver> -t <GitHub PAT> --submit` (single/multiple URLs). Validation: schema, Defender + multi-AV scan, silent install/uninstall test, URL reputation, then moderator approval; `Needs-Author-Feedback` closes after 10 days; **installer must come directly from the ISV host (no redirector), HTTPS, hash must match, publisher-domain match**. https://learn.microsoft.com/en-us/windows/package-manager/package/manifest ; https://learn.microsoft.com/en-us/windows/package-manager/package/repository ; https://github.com/microsoft/winget-create ; https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.12.0/installer.md
- **winget REST source** (`Microsoft.Rest`: `/information`, `/manifestSearch`, `/packageManifests/{id}`; `winget source add -n X -a https://… -t Microsoft.Rest`) is a documented open contract → Polaris Key could expose a **private/beta winget source** without any PR flow. https://github.com/microsoft/winget-cli-restsource
- WinGet Configuration (`winget configure`, DSC YAML) is a dev-machine setup tool (needs winget ≥1.6.2631) — not a distribution surface; only useful for contributor onboarding. https://learn.microsoft.com/en-us/windows/package-manager/configuration/
- **Scoop** — JSON manifest with `checkver` (`github`, or `url`+`regex`/`jsonpath`) and `autoupdate` (url templates, hash by regex/jsonpath/XPath); official buckets updated by Excavator (Main/Extras hourly; Versions/Java/PHP/Games daily); custom bucket is just a git repo. **A Polaris Key `/version` JSON per channel is directly consumable by `checkver.jsonpath`.** https://github.com/ScoopInstaller/Scoop/wiki/App-Manifest-Autoupdate
- **Chocolatey** — community repo: ~76 validation rules, install/uninstall verification, scan, and **human review of every new version**; 35 days to fix. Private feeds (Nexus/ProGet) possible. Low ROI for a game. https://docs.chocolatey.org/en-us/community-repository/moderation/

## B. LINUX

### B1. AppImage

- Godot Linux export = ELF + `.pck` (or embedded PCK); archs x86_64 (default), arm64, x86_32, arm32, plus rv64/ppc64/loongarch64 with custom templates. https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_linux.html
- **Update information** lives in ELF section `.upd_info` (Type 2). Formats (AppImageSpec draft): `zsync|https://host/path/App-latest-x86_64.AppImage.zsync` (zsync file and AppImage on an HTTP server with **range requests**, URL constant across versions); `gh-releases-zsync|user|repo|tag|filename-pattern` with tags `latest` (no pre-releases), **`latest-pre`**, `latest-all` and wildcards; `pling-v1-zsync|id|pattern`; `bintray-zsync` deprecated. Embed with `appimagetool -u`, which also emits the `.zsync`. https://github.com/AppImage/AppImageSpec/blob/master/draft.md ; https://docs.appimage.org/packaging-guide/optional/updates.html
- Tools: `AppImageUpdate` (GUI) / `appimageupdatetool` (CLI) / `libappimageupdate`; latest release seen **2.0.0-alpha-1-20251018** (Oct 18 2025; "beta-level" per README). https://github.com/AppImage/AppImageUpdate ; https://github.com/AppImage/AppImageUpdate/releases
- **Stable per-channel `.zsync` URL from Polaris Key: yes.** Serve `/dl/{slug}/{channel}/Game-x86_64.AppImage.zsync` from the release index; the `.zsync`'s `URL:` header must be an absolute gateway URL for the _current_ AppImage and the gateway must return 206 for Range. Alternative that needs **zero server work**: `gh-releases-zsync|owner|repo|latest-pre|Game-*-x86_64.AppImage.zsync` maps _beta → latest-pre_ directly on GitHub Releases (Polaris Key already indexes those); pr-N has no such mapping.
- **Signing:** GPG signature embedded via `appimagetool --sign`; verification needs the external `validate` tool; "no enforcement" in the ecosystem — treat as optional; Polaris Key's Ed25519-signed manifest/`/version` is the real integrity story. https://docs.appimage.org/packaging-guide/optional/signatures.html
- Runtime caveat: AppImages built with the old runtime need FUSE 2 (`libfuse2t64` on Ubuntu 24.04); newer runtimes embed FUSE 3 support. https://github.com/AppImage/AppImageKit/wiki/FUSE
- Game-side: **pure GDScript is enough** — read `OS.get_environment("APPIMAGE")`, `OS.execute("appimageupdatetool", [..])` (ship the tool as a bundled AppImage), relaunch. No native plugin needed.

### B2. Flatpak / Flathub

- **Flathub rules** (https://docs.flathub.org/docs/for-app-authors/requirements): source-available apps must build entirely from source with no network during build (all sources as public URL + sha256); **non-redistributable/proprietary payloads use `extra-data`** (downloaded at install; sha256 only) — _but_ "if the submission is being opened by the upstream authors or developers, there is generally no need to use extra-data … redistribution permissions are implicitly granted", so an upstream studio can ship the binary directly in the manifest. Reverse-DNS app-id (`io.github.*` prefixes for hosted forges), domain verification token at `https://{domain}/.well-known/org.flathub.VerifiedApps.txt`, metainfo + .desktop + icon (SVG or ≥256 px PNG). **Monetisation policy:** must give clear benefit, no repeat charging (except subscriptions), disclosed upfront; donations exempt. **Generative-AI policy** (see finding 9).
- **Submission/publishing:** PR to `flathub/flathub` branch `new-pr`; volunteer reviewers, merges in batches; after merge "usually published within 1-2 hours". https://docs.flathub.org/docs/for-app-authors/submission
- **Updates:** a global External Data Checker runs every 2 hours using `x-checker-data` in the manifest (types include `json` (jq queries), `html`, `git`, `rotating-url`, `anitya`, …) and opens PRs; auto-merge via GitHub automerge or `flathub.json` `automerge-flathubbot-prs`. **A Polaris Key `/version` JSON with `version`+`url`+`sha256` per channel is directly consumable by `type: json` checkers.** https://docs.flathub.org/docs/for-app-authors/maintenance ; https://github.com/flathub/flatpak-external-data-checker
- **Beta:** push a `beta` git branch in the app repo → publishes to the Flathub **beta repo**; "not intended to be permanent"; nightly/daily-snapshot software is not allowed on stable/beta. (Maps to PK `beta`; `pr-N` is not publishable.)
- **In-app update:** sandboxed apps do not self-update; they may use the `org.freedesktop.portal.Flatpak` **UpdateMonitor** (`CreateUpdateMonitor`, `UpdateAvailable`/`Progress` signals, `Update` method) via D-Bus/libportal (from search results; official portal doc page 404'd) — needs a GDExtension; otherwise rely on the software center.
- **Self-hosted OSTree repo:** static-file hosting, `archive-z2` = one small object per file (lots of requests → HTTP keep-alive/HTTP2), GPG-signed (`--gpg-sign`), `.flatpakrepo`/`.flatpakref` for one-click add/install, optional **static deltas** (`flatpak build-update-repo --generate-static-deltas`), branches `stable`/`beta` = channels; free on GitHub/GitLab Pages. Cost/complexity: build+sign in CI, then upload to R2; a Worker can serve it (no dynamic logic needed). https://docs.flatpak.org/en/latest/hosting-a-repository.html

### B3. Snap Store, Steam/Steam Deck, itch.io

- **Snap** — channel = `track/risk/branch`; risks `stable|candidate|beta|edge`; closed channels fall back to the next lower-risk release; branches auto-close after 30 days; extra tracks need Store approval; `devel`-grade snaps cannot reach stable/candidate. CI: `snapcraft export-login … --channels=…`, env `SNAPCRAFT_STORE_CREDENTIALS`, `snapcraft upload --release=beta` / `snapcraft release <name> <rev> <channel>` (snapcore/action-publish). snapd checks 4×/day; `refresh.hold` ≤60 days, `refresh.timer` ≥20 min; a snap can hold its own refresh (`gate-auto-refresh` hook + `snapctl refresh --hold`, ≤90 days). **Best channel mapping of all surfaces:** PK stable→stable, beta→beta/candidate, pr-N→`beta/pr-N` branch (30-day life). Snap owns updates; game needs no updater. https://ubuntu.com/docs/snapcraft/latest/reference/channels/ ; https://snapcraft.io/docs/how-to-guides/manage-snaps/manage-updates/ ; https://github.com/marketplace/actions/snapcraft-action
- **Steam** — SteamPipe: `app_build`/`depot_build` VDF, `steamcmd +login … +run_app_build …`; build account needs "Edit App Metadata" + "Publish App Changes To Steam"; **default branch requires manual promotion in the web UI**, other named branches can be auto-set live via `SetLive`; ~1 MB chunk delta; CI reuses login token in steamcmd config (Steam Guard first). https://partner.steamgames.com/doc/sdk/uploading . DLC = its own AppID with depots listed under the base app; ownership via `ISteamApps::BIsDlcInstalled` or server-side `CheckAppOwnership`; buying via store/overlay (`ActivateGameOverlayToStore`). https://partner.steamgames.com/doc/store/application/dlc . In-game purchases must go through the Steam Microtransaction API / Steam Wallet [SECONDARY for the "no third-party payment inside the Steam build" corollary]. https://partner.steamgames.com/doc/features/microtransactions . **Steam Deck Verified:** full controller access, text ≥9 px @1280×800 (12 px recommended), no launcher friction, 30 fps @800p; Valve tests the Linux build if one exists. https://partner.steamgames.com/doc/steamdeck/compat . Godot side: **GodotSteam** (GDExtension or module, Godot 4.x, Windows/Linux/macOS). https://godotsteam.com/ . Game must not self-update in the Steam build.
- **itch.io** — `butler push dir user/game:channel [--userversion X]`; channel names containing `win|windows`, `linux`, `mac|osx`, `android` auto-tag platforms; wharf patches (immediate rsync-style + Brotli patch, later replaced by server-side bsdiff-optimized one); CI with `BUTLER_API_KEY`; HTML5 = set game type "HTML" after first push. https://itch.io/docs/butler/pushing.html . itch app updates downloads itself; game needs no updater.

## C. WEB (HTML5)

### C1. Godot 4.x web export requirements (4.3 → 4.7)

- **Threads:** since **4.3 single-threaded export is the default/preferred** (works on macOS/iOS; needs no special headers). The optional **Thread Support** build needs `SharedArrayBuffer` ⇒ cross-origin isolation: `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp`, HTTPS (localhost exempt). https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html ; https://godotengine.org/article/progress-report-web-export-in-4-3/
- **PWA export** (`progressive_web_app/enabled`): generates `.service.worker.js`, `.offline.html`, `.manifest.json` (+ icons, `display`, `orientation`, `background_color`); `progressive_web_app/ensure_cross_origin_isolation_headers` makes the **service worker inject COOP/COEP** so threaded/GDExtension builds work on hosts you can't configure. SW logic: `CACHE_NAME = CACHE_PREFIX + CACHE_VERSION`, cache-first for cacheable files, network-first for navigation, offline fallback page, **re-exporting bumps `CACHE_VERSION` and `activate` purges old caches**. https://raw.githubusercontent.com/godotengine/godot/master/platform/web/export/export_plugin.cpp ; https://raw.githubusercontent.com/godotengine/godot/master/misc/dist/html/service-worker.js
- **Exported file set:** `.html .js .wasm .pck .png` (+ `.icon.png .apple-touch-icon.png .audio.worklet.js .audio.position.worklet.js`; with extensions: `.side.wasm` + shared objects; PWA: `.service.worker.js .offline.html .manifest.json`).
- **GDExtension on web:** enable **Extensions Support**; requires "dlink" templates (`scons platform=web dlink_enabled=yes` → `web_dlink_release.zip`/`web_dlink_debug.zip`); extensions must be compiled for web; docs say it needs cross-origin isolation like threads. https://docs.godotengine.org/en/latest/engine_details/development/compiling/compiling_for_web.html (also lists `threads=no`, `javascript_eval=no`, and "Emscripten 6.0.1+" for the 4.7 docs).
- **Size/compression:** 4.3 wasm ≈ 40 MB raw / ≈ 5 MB Brotli (official blog); empty 4.4 project ≈ 35 MB wasm [SECONDARY dev.to]; docs: serve `.wasm` as `application/wasm`; gzip → ~25%; Brotli precompression supported. `.pck` loads fully before start (100 MB pck ≈ 30-60 s on slow links [SECONDARY]).
- **Persistence:** `user://` = IndexedDB; needs cookies/site data allowed (third-party cookies in iframes; none in private mode); `OS.is_userfs_persistent()` can false-positive.
- **Networking:** only HTTP client/requests, WebSocket (client), WebRTC; `HTTPRequest` obeys same-origin/CORS and can't use threads. Under COEP `require-corp`, CORS-mode `fetch()` is _not_ blocked but the API must return `Access-Control-Allow-Origin` (+ credentials headers if used); no-cors cross-origin embeds need `Cross-Origin-Resource-Policy`. **COEP `credentialless` is unsupported in Safari** (caniuse through 27.2), so Safari needs `require-corp`. https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cross-Origin-Embedder-Policy ; https://caniuse.com/mdn-http_headers_cross-origin-embedder-policy_credentialless
- **Safari/iOS:** docs: Safari "has several issues with WebGL 2.0 … recommend Chromium or Firefox"; single-thread fixes most macOS/iOS problems; audio autoplay needs a gesture; Sample playback is the default since 4.3. WebKit storage (Safari 17+): browser-app origin quota up to 60% of disk (15% for other apps), LRU eviction by last interaction, `persist()` granted by heuristics (Home-Screen web apps favoured), Home-Screen apps get browser-app quotas. https://webkit.org/blog/14403/updates-to-storage-policy/
- **Godot 4.4-4.7 milestones:** 4.4 patch PCKs; 4.5 wasm SIMD default [SECONDARY]; 4.6 delta-encoded patches (dev5, Dec 2025); **4.7 stable 2026-06-18** (4.7.1 Jul 14, 4.7.2 RC Aug 2026; official 4.7.1 notes list no web/Windows/Linux export fixes) — official 4.7 release page does not mention web changes. **wasm64:** PR #102378 (merged 2026-02-26, milestone 4.7) enables `wasm64` in SCons for web builds but "doesn't enable exporting games with WASM 64-bit support"; Safari has no Memory64. Claims that 4.7 "ships wasm64 exports" and "experimental WebGPU export" come from a third-party aggregator (app.cinevva.com) and **are not confirmed by any official page I read; official 4.7 web docs still say WebGL 2.0 Compatibility only**. Plan on wasm32 + WebGL2. https://github.com/godotengine/godot/pull/102378 ; https://godotengine.org/article/dev-snapshot-godot-4-7-beta-1/ ; https://godotengine.org/article/maintenance-release-godot-4-7-1/

### C2. Hosting on Cloudflare; itch.io hosting

- **Workers static assets:** max **25 MiB/file** (Free & Paid), max files 20,000 Free / **100,000 Paid** (raised 2025-09-02), static-asset requests free & unlimited, `_headers` ≤100 rules & ≤2,000 chars/line, default `Cache-Control: public, max-age=0, must-revalidate` + ETag; **`_headers` do not apply to Worker-generated responses**. https://developers.cloudflare.com/workers/platform/limits/ ; https://developers.cloudflare.com/changelog/2025-09-02-increased-static-asset-limits/ ; https://developers.cloudflare.com/workers/static-assets/headers/ ; https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/
- **Implication:** put `index.html`, small JS, PWA files, icons in static assets (or the Worker), and **`.wasm` + `.pck` (and any file >25 MiB) in R2**, served by a Worker that (a) sets `Content-Type` (`application/wasm`), COOP/COEP/CORP, cache headers; (b) honours `Range` via `R2GetOptions.range` and `onlyIf` conditionals; (c) streams `R2ObjectBody.body`. R2: single PUT ≤5 GiB, multipart ≤5 TiB; Worker CPU up to 5 min (paid), 10,000 subrequests (paid). https://developers.cloudflare.com/r2/api/workers/workers-api-reference/ ; https://developers.cloudflare.com/r2/objects/upload-objects/
- **Compression:** Cloudflare's edge compresses `application/wasm` (plan-dependent algorithm; honours `Accept-Encoding`); origin-supplied `Content-Encoding` is preserved if the client supports it and no body-rewriting feature is on; add `Cache-Control: no-transform` to preserve `Content-Length`. Simplest robust path: **precompress `.wasm`/`.pck`/`.js` to Brotli (and gzip) at publish time, store `*.br` in R2, and let the Worker pick by `Accept-Encoding`** (Godot docs support precompressed Brotli). https://developers.cloudflare.com/speed/optimization/content/compression/
- **Layout / cache-busting:** immutable build prefix `/play/{slug}/{buildId}/…` (`Cache-Control: public, max-age=31536000, immutable`), and a short-TTL channel entry `/play/{slug}/{channel}/` (stable, beta, pr-N) that serves/redirects to the current build's `index.html`. Because SW scope is the directory of the SW file, each channel/build directory gets its own service worker and cache namespace; do not host two channels under one SW scope. Godot's PWA `CACHE_VERSION` handles per-export invalidation; PK should also expose `/play/{slug}/{channel}/version.json` (signed) for the SDK to compare.
- **itch.io HTML5:** zip with `index.html` at root, **≤1,000 files, ≤500 MB extracted, ≤200 MB per file, ≤240-char paths**, relative paths only, UTF-8, case-sensitive; embed sizes/fullscreen/mobile-friendly options; **"SharedArrayBuffer support" checkbox** in Frame/Embed options is **experimental** (served from `html.itch.zone` with COOP/COEP/CORP; localStorage moves with the domain; historically Chromium-only). Single-threaded Godot 4.3+ builds avoid the need. https://itch.io/docs/creators/html5 ; https://itch.io/t/2025776/experimental-sharedarraybuffer-support ; https://itch.io/blog/456223/godot-cross-origin-isolation-and-sharedarraybuffers (2022)

### C3. WebCrypto Ed25519 (for verifying Polaris Key JWS in the browser)

- Firefox 129 (Aug 2024), Safari 17.0 (Sep 2023), Chrome 137 (May 2025, default-on) ⇒ all engines; "79% and counting" of users (Aug 2025); IPFS team expects "confident reliance" ~2027. Secure context only; available in Workers. Interop caveats documented earlier (Igalia): WebKit randomizes signatures (irrelevant for verify), and engines differ on small-order-point rejection (irrelevant for honest signatures). https://blog.ipfs.tech/2025-08-ed25519/ ; https://blogs.igalia.com/jfernandez/?p=1913 ; https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/verify
- From Godot: `JavaScriptBridge.eval()` / `get_interface("crypto")`, promise chaining with `.then(callback)` where callbacks created by `JavaScriptBridge.create_callback()` receive one Array argument; `PackedByteArray` ⇄ `Uint8Array`. Export templates can omit eval (`javascript_eval=no`): check the `web` feature tag / `JavaScriptBridge` availability. https://docs.godotengine.org/en/stable/tutorials/platform/web/javascript_bridge.html . Cleaner: do verification in **the page's own JS bootstrap (custom HTML shell) before the engine starts**, and hand the verified build info to Godot.

### E4. Cross-cutting (all platforms): Godot patch PCKs

Godot 4.4 patch PCKs and 4.6 delta encoding (Patching tab, base packs must be the exact packs loaded at runtime in the same order for delta patches; cumulative load-time cost per patch layer). Docs recommend signing patches with asymmetric keys and embedding the public key in the main PCK. `ProjectSettings.load_resource_pack(path, replace_files)` — packs cannot be unloaded at runtime. https://docs.godotengine.org/en/stable/tutorials/export/exporting_pcks.html (4.7: https://docs.godotengine.org/en/4.7/tutorials/export/exporting_pcks.html). Combine with PK signed release metadata for a **content-patch channel independent of the exe** (helps SmartScreen hash reputation, Steam/itch bandwidth, and Store certification—except where 10.2.2 applies).

## F. Suggested Polaris Key capability list (derived)

1. **Gateway:** always 200/206 streaming, no redirects for public installer URLs (winget), full `Range` (App Installer, zsync, R2 web), correct MIME (`application/appinstaller|msix|msixbundle|wasm|octet-stream`), stable per-version immutable URLs, SHA-256 in `/version`.
2. **Feeds per channel (stable/beta/pr-N):** Sparkle appcast (+Windows enclosures), `/version` JSON (add `sha256`, `size`, `url`, `channel`, `publisher`), `.appinstaller`, Velopack `releases.{channel}.json`, `.zsync`, winget REST source (optional), Flatpak/Scoop-friendly JSON.
3. **Orchestrator jobs (GitHub Actions/CI calling vendor CLIs):** `msstore`, `wingetcreate`, `snapcraft`, `steamcmd`, `butler`, `appimagetool`, `flatpak build-update-repo` — PK stores per-surface IDs (productId, flightId, snap name, steam appid/branch, itch game/channel) and status (e.g. `store-certifying`, up to 3 business days) so channel state = per-surface state.
4. **Web hosting mode:** R2 + Worker origin with COOP/COEP/CORP, br/gzip selection, immutable build paths, channel pointers, per-channel service-worker scope, signed `version.json`.
5. **Signing:** keep Ed25519 for manifests/appcasts/JWS; use Authenticode/Artifact Signing (Windows), MSIX cert, GPG (AppImage/OSTree) as _separate_ trust roots — none of them is Ed25519-compatible except Sparkle/WinSparkle's EdDSA.
6. **Godot SDK layering:** (a) pure GDScript: fetch `/version` (HTTPRequest), compare, SHA-256 (HashingContext), patch-PCK download + `load_resource_pack`, AppImage update via `OS.execute`; (b) native GDExtension: Ed25519 verify (gd-ed25519/Monocypher or libsodium), WinRT StoreContext, WinSparkle/Velopack bridge, Flatpak portal, GodotSteam; (c) web: WebCrypto Ed25519 via JS shell/`JavaScriptBridge`; (d) **updater auto-selection/disable** by runtime context (Store package identity, Steam, Flatpak, Snap, AppImage, web).
7. **Policy guardrails in metadata:** flag per surface `selfUpdateAllowed` (false for Store/Steam/Flathub/Snap/itch app), `codePacksAllowed` (false/risky for Store 10.2.2), `commerce` (`store-iap` | `steam` | `own`).
