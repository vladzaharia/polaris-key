# S-02: Range, If-Range and cold-miss behaviour of R2 bytes behind Cloudflare

Run 2026-09-30. The harness is in [`prototype/r2-range/`](../prototype/r2-range/README.md). The
repo's Worker (`packages/worker`) was not modified.

## 1. Question

How do R2 objects behave on each of three serving paths?

- **A**: an R2 custom domain bound to the bucket, with caching on.
- **B**: a Worker gateway that reads the R2 binding, with or without a cache.
- **C**: `r2.dev`.

The behaviours in question are a single `Range` (cold and warm), multi-range, `If-Range`
(matching and stale), the ETag format, `HEAD`, compression, objects above the cacheable limit, and
latency. Which path should serve ungated blobs and chunk bundles? What must SDKs send? README §3.5
assumes "a strong `ETag` equal to the SHA-256" and `If-Range` everywhere. CONTENT §10 fetches
missing chunk runs "by Range with If-Range on the chunk bundle's hash".

## 2. Short answer

1. **Path A cannot meet README §3.5, so ungated bytes must go through a Worker (path B).**
   - R2's ETag is the object's MD5 for a single-part upload [V] [E], and `md5(part md5s)-N` for a
     multipart upload [V] [E].
   - R2 has no way to set the ETag [V], and it does not add `Repr-Digest`.
   - On path A, the edge compares `If-Range` "exactly" with the _cached_ ETag, and a mismatch
     returns the complete file [V]. So an SDK that follows today's rule (`If-Range: "<sha256>"`)
     would get a **full 200 for every chunk run** on path A. For the real v1→v2 update that is
     10.4 MB instead of 0.99 MB [M].
   - A Transform Rule can rewrite the ETag the client sees, but not the one the cache compares
     against [I]. This confirms P2-01's rule that "every read goes through the Worker".
2. **R2 itself does not evaluate `If-Range`.** The Workers API says of conditional headers: "All
   conditional headers aside from `If-Range` are supported" [V]. A Worker that passes the request
   headers to `get(key, { range: headers, onlyIf: headers })` therefore splices silently. In the
   emulation it answered a stale `If-Range` with **206**, and answered multi-range, inverted,
   `bytes=-0` and past-the-end ranges with the _whole_ object labelled as a 206 [E].
   - The Worker must parse `Range` and evaluate `If-Range` itself, then call `get()` with a
     concrete `{offset, length}` or `{suffix}`. The probe Worker's `/b/` mode does this, and passes
     every case [E].
   - P2-01's note that "R2's `get(key, {range, onlyIf})` takes the request headers directly" is
     corrected in that brief.
3. **Serve ungated bytes through a Worker with Workers Caching** (the 2026 cache in front of the
   Worker). If a live check rules it out, fall back to the same Worker with `caches.default`.
   - With Workers Caching, Cloudflare strips `Range`, stores the Worker's full 200, slices ranges
     itself, and collapses misses through a tiered topology [V].
   - The Cache API alternative is per colo and not tiered. `cache.put` is incompatible with tiered
     caching, and it cannot store a 206 [V].
   - Workers Caching is **not emulated** by wrangler 4.104 (Range still reached the Worker [E]).
     Its live behaviour is hand-off row H3.
   - Gated bytes stay on a non-caching entrypoint with `Cache-Control: private, no-store`.
4. **Multi-range: never, in v1.**
   - The probe Worker answers any multi-range request with a full 200, by design [E].
   - The edge gives a multipart 206 only when "Origin Range Requests" applies. That setting is off
     for every extension by default [V]. Workers Caching documents only single-range slicing [V].
   - The fallback for one real bundle is 4,124,624 B instead of the 347,538 B needed, 11.9× [M].
   - Sixteen single-range requests, six in parallel, cost about the same wall time locally as the
     one full-bundle read [E].
   - No capability probe is needed. If a live run ever shows multipart 206 on the chosen path,
     advertise it from the server (a feed or transport field), never by client sniffing [I].
5. **Chunk bundles: keep 4–16 MiB, default 4 MiB.**
   - The number of requests is set by the chunk layout, not the bundle size: 29 runs for this
     update at a 4 MiB target [M].
   - Bundle size sets what a failure or a cold miss costs. A mismatched `If-Range`, an ignored
     `Range` or a multi-range fallback returns the whole bundle [E] [V].
   - Every cached path fills the edge with the complete object on a cold miss, because Origin Range
     Requests is off by default [V].
   - Every cache involved caps an object at 512 MB on this plan [V], so the upper bound is not a
     limit here.
6. **ETag and If-Range rule for SDKs.**
   - Send `If-Range` only with the strong validator `"<sha256hex>"` of the object the signed
     manifest names. Never send a weak tag, a date or a validator learned from another host.
   - Accept a 206 only when `Content-Range` matches the request, and the ETag (when present)
     equals that same `"<sha256hex>"`.
   - A 200 means that strategy failed: fall back as P4-11 already says.
   - Web clients pay one CORS preflight per bundle URL for `If-Range`. A single safelisted `Range`
     needs none [M]. The byte route must therefore answer `OPTIONS` and allow `Range, If-Range`.
7. **Compression-off rule: yes.**
   - Serve bundles and blobs as `application/octet-stream` with `Cache-Control: …, no-transform`
     and no `Content-Encoding`. `application/octet-stream` is not on Cloudflare's compressible list,
     and Cloudflare compresses only 200s [V].
   - Recompression is what weakens an ETag to `W/"…"` [V], which would break `If-Range`.
   - Browsers send `Accept-Encoding: identity` on their own when `Range` is set [M].
   - Godot's `HTTPRequest` sends `gzip, deflate` even with `Range` unless `accept_gzip = false`
     [M]. SDKs must send `identity` for byte fetches.

### 3.3 The probe Worker and its modes

`prototype/r2-range/worker/src/index.js` has three modes:

- **`/b/` (path B).** The README §3.5 headers:
  - `ETag: "<sha256hex>"` taken from the content-addressed key, and `Repr-Digest: sha-256=:<b64>:`;
  - `Accept-Ranges: bytes` and `Cache-Control: public, max-age=31536000, immutable`;
  - its own RFC 9110 `Range` parser, and `If-Range` evaluated with a strong, exact comparison;
  - `If-None-Match` answered from the key, with no R2 read;
  - one R2 `get(key, { range: {offset,length}|{suffix} })` per request;
  - multi-range answered with a full 200.
- **`/c/` (path B with `caches.default`).** The same, plus `match()` first. A miss on a full 200
  tees into `put()`; a miss on a 206 serves the range and fills the full object in `waitUntil`.
- **`/r/` (an emulation of path A's origin).** `get(key, { range: request.headers, onlyIf:
request.headers })` and R2's own `httpEtag`. This is what an R2 public bucket or a naive
  gateway answers before any cache. It is **not** Cloudflare's edge.

A second config (`wrangler.wcache.jsonc`) turns on Workers Caching (`"cache": { "enabled": true }`)
for path Bw.

### 4.6 Time to first byte, bytes fetched and throughput

These numbers are **loopback against miniflare** [E]. They show the harness works and that the
Worker adds only a few milliseconds. They say nothing about the edge, R2's region (ENAM) or a WAN;
those are hand-off rows H1 and H2. Path A at the edge and path C are not in this table: A-origin is
R2's own answer without the zone cache, and C is hand-off row H6.

The single-range request is `bytes=0-1048575` in both the cold case (the first request for a fresh
key) and the warm case (the same range again). Every path answered both with a **206 carrying
1,048,576 B**, at every size (on the 1 MiB object that range is the whole object). The fallbacks
fetch the whole object: on B, Bc and Bw a stale `If-Range` or any multi-range request gets a 200 of
the full size (1,048,576 / 4,194,304 / 8,388,608 / 16,777,216 / 67,108,864 B). A-origin answers a
stale `If-Range` with a 206 of 1,048,576 B, which splices two versions (§4.1), and a 2-range request
with a 206 of the whole object.

## 5. Discussion

### 5.1 Why path A fails the design, not just the ETag

- **ETag.** R2 fixes it as an MD5, or an MD5-of-parts-N [V] [E]. The cache stores the origin's
  ETag, and `If-Range` "must exactly match the cached ETag" [V].
  - A Transform Rule that rewrites `ETag` to `"<sha>"` for clients cannot change the stored value
    the cache compares against [I].
  - So clients would have to learn and send R2's MD5. That value is not in the signed manifest,
    differs by upload method, and is useless to a client that verifies SHA-256.
- **No `Repr-Digest`.** Only a Response Header Transform could add one. It would need a base64
  function over a URI segment; that was not checked, and it would be fragile anyway [I].
- **Not cached by default.** Keys have no file extension, so path A needs a Cache Rule before it
  caches anything [V]. On this account's Free zones, Tiered Cache is off, so every colo misses to
  R2 on its own (it can be turned on) [M].
- **Cold misses.** A ranged request that misses makes the edge fetch the complete file [V] (Origin
  Range Requests has no extension on by default). When the client's range starts deep in the
  object, TTFB then depends on how fast R2 streams to that colo [I]. H1 measures it.
- **What path A is still good for.** Nothing in the design. Ungated full-object downloads by
  outlets that do not send `If-Range` would work, but they would lose `Repr-Digest`. P2-01
  already forbids an R2 public domain, and this spike confirms that.

### 5.2 Why Workers Caching (Bw) over the Cache API (Bc)

| Property            | Bc (`caches.default`)                                                            | Bw (Workers Caching)                                                                   |
| ------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Scope               | Per colo; `put` is not compatible with tiered cache [V]                          | Lower tier near the client plus an upper tier; collapses misses per key and colo [V]   |
| Range from cache    | `match()` with `Range` returns 206 from a cached 200 [V] [E]                     | Cloudflare strips `Range`, stores the full 200, slices [V]                             |
| Cold ranged miss    | Serve the 206 from R2, then a second, full R2 read to fill (our `miss-fill`) [E] | One full fetch through the Worker; the range is served from it [V]                     |
| Worker CPU on a hit | Runs every time                                                                  | Not run on a HIT [V]                                                                   |
| Price               | Worker request plus R2 Class B on a miss                                         | Every request billed at the Workers request rate, including hits; no CPU on hits [V]   |
| Size cap            | 512 MB [V]                                                                       | 512 MB at launch [V]                                                                   |
| Local emulation     | Works in miniflare [E]                                                           | **Not emulated** by wrangler 4.104 [E]                                                 |
| Gated bytes         | Skip the cache in code                                                           | Disable caching for that entrypoint; do not use `no-store` on a caching entrypoint [V] |

Workers Caching is newer, and its `If-Range`-on-hit behaviour is documented only through the
generic cache Range page. That is why H3 exists. The Worker code is identical for both: when
`Range` is absent it returns a full 200. So P2b-04 can switch between them with configuration
alone.

### 5.3 Why "never multi-range" rather than "behind a probe"

- On path B the Worker could build `multipart/byteranges` itself, but it would need one R2 read per
  part.
- On a cached path it depends on a per-zone setting (Origin Range Requests), which Workers Caching
  does not document at all.
- The failure mode is a full 200 of the whole bundle, the most expensive outcome.
- In browsers, multi-range also costs a CORS preflight [M].
- Parallel single ranges over HTTP/2 give the same wall-clock result with no special case [E] [I].

A runtime probe would add a request and a code path to every SDK to save a few round trips. That
is not worth it at 4–16 MiB bundles with a 6-way pool.

## 6. Recommendation

1. **Ungated blobs and bundles.** Serve them from a Worker on the separate bytes domain, reading
   the R2 binding, with Workers Caching on **for one named byte-serving entrypoint only** (§6.1).
   The fallback is the same entrypoint with `caches.default`: full 200s only, and `match()` for
   ranges. Never attach an R2 custom
   domain or `r2.dev` to the bucket. The headers are those of README §3.5, plus:
   - **`Range`**: parsed by the Worker. One range only.
     - Multi-range, an unparseable header or a non-`bytes` unit → full 200.
     - Inverted → 200.
     - `bytes=-0` and a start at or past the size → 416 with `Content-Range: bytes */<size>`.
     - An end past the size is shortened.
     - Pass R2 a concrete `{offset, length}` or `{suffix}`, **never the request `Headers`**.
   - **`If-Range`**: evaluated by the Worker, with a strong, exact comparison against
     `"<sha256hex>"`. Anything else (weak, a date, R2's MD5) → full 200. **Never pass `If-Range`
     to R2**; R2 ignores it.
   - `If-None-Match` is answered from the key, with no R2 read.
   - Content and caching headers:
     - blobs and bundles fetched by Range: `Content-Type: application/octet-stream` and no
       `Content-Encoding`. A route that serves an allowlisted real type instead (P2-01: APK,
       `application/wasm`, zip) relies on `no-transform` alone, because some of those types,
       `application/wasm` among them, are on Cloudflare's compressible list [V];
     - `Cache-Control: public, max-age=31536000, immutable, no-transform`;
     - `X-Content-Type-Options: nosniff`.
   - CORS for `web`:
     - answer `OPTIONS` with `Access-Control-Allow-Headers: Range, If-Range, If-None-Match` and
       `Access-Control-Max-Age: 7200`;
     - expose `ETag, Content-Range, Content-Length, Accept-Ranges, Repr-Digest`.
2. **Gated bytes.** Serve them from the default (uncached) entrypoint, never through the cached
   one, with `Cache-Control: private, no-store, no-transform` (P2-01, P2b-04). `no-transform`
   matters here too: a gated allowlisted type such as `application/wasm` would otherwise be
   compressible, and a compressed 200 carries a weak ETag, which breaks `If-Range`.
3. **Multi-range: clients never send it** (v1). There is no capability probe. If a later live
   measurement shows multipart 206 on the chosen path, it becomes a server-advertised capability.
4. **Chunk bundles: 4–16 MiB confirmed; the default target is 4 MiB.** 16 MiB is the cap for
   packs large enough that bundle count matters. Keep bundles in file order (E8 §2.5 point 4),
   because the run count, not the bundle size, drives the request count.
5. **SDK ETag and If-Range rule (P4-11, the SDK HTTP layers).**
   - Send `Range: bytes=<o>-<o+len-1>`, `If-Range: "<sha256hex of the bundle, from the signed
index>"` and `Accept-Encoding: identity`.
   - Accept only a 206 whose `Content-Range` equals the request and whose `ETag`, if present,
     equals the same quoted hex.
   - A 200, or any other ETag, fails that strategy.
   - Never send a validator the client did not derive from the signed manifest.
   - Godot: `accept_gzip = false` or an explicit `identity`. Web: expect one preflight per bundle
     URL per `Max-Age`.
6. **Compression-off rule for bundles: yes**, as in point 1. The edge never compresses
   `application/octet-stream` and never compresses a 206. `no-transform` makes that explicit, and
   keeps the ETag strong on 200s. So every byte response, ungated or gated, octet-stream or an
   allowlisted type, carries `no-transform`.

### 6.1 The caching layer in `packages/worker`

`packages/worker` is one Worker: it serves the console host, the API and the bytes host. Workers
Caching changes what that means, and five facts from Cloudflare's docs shape the rule [V]:

- Once a `cache` block turns caching on, it applies to **every** `fetch` entrypoint that does not
  opt out, including loopback calls through `ctx.exports`. Custom RPC methods bypass it.
- A response with no `Cache-Control` is still cached: a 200 for 2 hours, a 404 for 3 minutes.
- The cache key is the path and query, the target entrypoint, `ctx.props` and (by default) the
  Worker version. **The hostname is not in it**, and neither is `Origin`. A Worker reached on
  several hostnames serves one cache to all of them.
- A `206` that the Worker returns itself is never stored. Cloudflare strips `Range`, asks for the
  full `200`, stores it and slices.
- `GET` and `HEAD` for one URL share one cache entry. So a cold `HEAD` is expected to fill the
  entry with a full `GET` from R2 [I]; H3 checks it.

So the rule, for P2-01 and P2b-04:

1. **Opt in one entrypoint, never the Worker.** Never set a top-level `[cache] enabled = true` in
   `packages/worker/wrangler.toml`. Declare `[exports.default.cache] enabled = false` explicitly,
   and turn caching on only for a named `WorkerEntrypoint` (proposed name `PublicBytes`) whose
   `fetch` serves ungated `blobs/` and `bundles/` reads and nothing else. The default entrypoint
   routes, gates and authenticates, and calls `ctx.exports.PublicBytes.fetch(request)` only once it
   has decided the request is ungated. It strips `Authorization` and `Cookie` before the call; an
   `Authorization` header would bypass the cache anyway. Per-entrypoint `exports` needs wrangler
   4.107 or later; the probe and the repo pin 4.104 (§3.2), so the bump is part of the work.
   The probe's `wrangler.wcache.jsonc` uses the top-level form because the probe is a
   single-purpose Worker. It is not the pattern to copy.
2. **CORS is added outside the cache.** The cached entrypoint never reads `Origin` and never sets
   an `Access-Control-*` header. The default entrypoint adds them to the response that comes back
   from `ctx.exports`, which is P0-05's existing rule (CORS after the handler, because the cache is
   keyed without the origin). A header set inside the cached entrypoint would be replayed to every
   origin. `Vary: Origin` inside the cached entrypoint would also be correct, but it splits the
   cache per origin, so it is the second choice.
3. **Nothing in the cached response depends on the host.** The console host's
   `Content-Disposition: attachment` and the bytes host's allowlisted types are different
   representations of one path, and the cache would serve whichever came first to both hosts. So
   only bytes-host routes reach `PublicBytes`; console-host downloads stay on the uncached default
   entrypoint. If a host-specific variant is ever needed inside the cache, pass it in `ctx.props`,
   which is part of the key.
4. **Every response from the cached entrypoint sets `Cache-Control` explicitly.** A 200 gets
   `public, max-age=31536000, immutable, no-transform`. A 404, a 5xx or any other error gets
   `no-store`, so a blob that is not yet promoted is not remembered as missing for 3 minutes. It
   returns a full `200` when `Range` is absent, which is always the case behind Workers Caching.
5. **Fallback: `caches.default` for full 200s only.** If Workers Caching is not available, or H3
   contradicts the docs, keep the same entrypoint split with no `cache` block. `PublicBytes` then
   `put`s full 200s (the Cache API refuses a 206, [V] and in both browsers' Cache API [M]) and
   answers ranges with `match()`. The Cache API key includes the hostname, so rule 3 holds there
   by construction.
6. **Gated bytes never enter either cache.** They stay on the default entrypoint with
   `private, no-store, no-transform`. Cloudflare's docs recommend disabling the cache for an
   entrypoint rather than returning `no-store` from a cached one.

P2b-04 records rules 1–3 and 6 in the threat model: what is allowed into the shared cache, and why
it is shared across hosts and origins.

### 6.2 Cross-check: P2-01 as merged

P2-01 merged while this spike ran. Its `blobResponse` (`packages/worker/src/core/blobs.ts`) was
read against §6 [V, repo code read, not executed against R2]:

| Rule (§6)                                                         | P2-01 as merged                                                               | Verdict      |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------ |
| Worker parses `Range`; one range; multi, bad unit, inverted → 200 | `parseRange`: single `bytes=` range only, anything else → `null` → full 200   | matches      |
| `bytes=-0`, start ≥ size → 416 with `bytes */<size>`              | `"unsatisfiable"` → 416, `Content-Range: bytes */<size>`, `no-store`          | matches      |
| `If-Range` strong exact match with `"<sha256>"`; never sent to R2 | exact string compare with the SHA ETag; R2 gets `{offset, length}` only       | matches      |
| `If-None-Match` from the key                                      | answered before the body read, after one `head()` that checks the stored hash | close enough |
| Ungated `public, max-age=31536000, immutable, no-transform`       | as stated                                                                     | matches      |
| Gated `private, no-store, no-transform`                           | `private, no-store` (no `no-transform`)                                       | **gap**      |
| Errors from a (future) cached entrypoint carry `no-store`         | 404 from `notFound()` carries no `Cache-Control`                              | gap, later   |
| Nothing host-dependent inside a cached response (§6.1 rule 3)     | `Content-Type`/`Content-Disposition` depend on `opts.host`                    | gap, later   |

The first gap matters today only for a gated allowlisted compressible type (`application/wasm`): a
compressed 200 gets a weak ETag and a later `If-Range` falls back to a full 200 [V] [I]. The other
two matter only when Workers Caching is turned on, which no work package has done yet; they are
P2b-04's to close when it adds the cached entrypoint. Every R2-facing read is `head()` then
`get()`, two Class B operations per uncached request; Workers Caching (§6 point 1) removes both on
a hit.

## 8. Hand-off: live measurements a human must run

needs a public R2 custom domain bound to the whole bucket. On the dev bucket that would publish
every object P2-01 writes there, gated ones included, and P2-01 age-locks its `blobs/` and
`bundles/` prefixes. A throwaway bucket keeps both problems out, and teardown is deleting it.
`wrangler deploy --env live` binds it (both probe configs); local runs keep the dev bucket name,

## 9. Limits

- No live edge measurement: every "path A / Bw at the edge" cell is documentation [V]. No vantage
  points, colos or `cf-cache-status` values from Cloudflare's edge.
- The miniflare R2 and Cache API emulation diverges from Cloudflare in at least two places seen
  here. `match()` returned 200 for `bytes=-0`, where Cloudflare documents 416. `get()` with range
  Headers returned the whole object for unsatisfiable or multi ranges. Cloudflare's behaviour for
  those is H7.
- Firefox is unmeasured (its headless launch hung). WebKit's no-Range `Accept-Encoding` is what
  Playwright reports, not a packet capture.
- The Bc and Bw 600 MiB rows were not run.
