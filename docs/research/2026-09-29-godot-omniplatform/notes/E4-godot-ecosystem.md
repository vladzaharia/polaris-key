# E4 - Godot ecosystem research for a first-class Polaris Key Godot SDK

Research date: 2026-09-29. Engine landscape at time of writing: Godot 4.7-stable (June 2026), 4.7.1 (2026-07-14) and 4.7.2 maintenance releases out; 4.8 in development (its docs are what `docs.godotengine.org/en/latest` currently serves - I checked 4.4/4.5/4.6/4.7 doc snapshots separately where version matters). Godot's own support table lists 4.7 and 4.6 as fully supported, 4.5 as partial (security/platform only), so 4.4 is already out of the patch window ([release policy](https://docs.godotengine.org/en/latest/about/release_policy.html)).

Method: web search + page fetches + one hands-on experiment (a pure-GDScript Ed25519 verifier benchmarked on Godot 4.7-stable, Appendix A). The web-search budget ran out near the end, so a few items are explicitly marked **UNVERIFIED**. Nothing in the repo was modified; this prototype was a scratch experiment and was not kept (the faster, corpus-tested port is in `../prototype/`).

Repo facts I checked (read-only) because they drive the recommendation: the frozen wire crypto is compact JWS with **EdDSA/Ed25519**, `typ`-separated, `kid` chosen from a caller-supplied trust set (`packages/shared-jws/src/index.ts`); SDKs re-implement the construction natively and are held to `conformance/corpus`; the client README says Python and Swift "carry independent ports of the same rules" proven identical by the corpus. A Godot SDK would be the fourth independent port.

## 1. Addon packaging and distribution

### 1.1 Asset Library vs the new Asset Store (status: Sept 2026)

- The Godot Asset Store was announced 2026-05-22 as "live and stable", to be fully integrated in Godot 4.7. Features: shared Godot accounts, reviews, publisher analytics, **multiple downloadable versions per asset**, changelog pages, custom tags. The old Asset Library is "deprecated ... set as a read-only repository in the near future"; assets were **not** auto-migrated - authors must resubmit ([announcement](https://godotengine.org/article/introducing-the-godot-asset-store/)).
- Nuance: the docs and the site still call the store "beta" with "pain points, bugs, and usability issues" ([docs](https://docs.godotengine.org/en/4.7/community/asset_store/what_is_asset_store.html), [store home](https://store.godotengine.org/)). The old Asset Library page was still live and showing September 2026 updates when I fetched it (no deprecation banner visible) - so in practice both exist today ([AssetLib](https://godotengine.org/asset-library/asset)).
- Editor integration: from 4.7 there is an "Asset Store" main-screen tab in the editor (non-template assets) and an Asset Store tab in the Project Manager (templates). Install goes through a "Configure Asset" dialog that lists files and lets you deselect them ([using in editor](https://docs.godotengine.org/en/4.7/community/asset_store/using_in_editor.html)). By inference from "fully integrated in Godot 4.7", editors older than 4.7 keep the legacy AssetLib tab, so 4.4-4.6 users probably cannot browse the store in-editor; they can still download the zip from the website and import it.
- Submission rules ([docs](https://docs.godotengine.org/en/latest/community/asset_store/submitting_to_asset_store.html)): asset must work in its stated Godot version; include `.gitignore`; avoid submodules (or make them non-essential); licence must match the repo; for plugins **ship a copy of licence + readme inside the plugin folder**; each version entry has changelog, **minimum (and optional maximum) Godot version**, misc info, **max 1 GB per version**; GitHub is the recommended host; review queue with feedback. The docs say nothing about GDExtension binaries, but binary-bearing addons are already listed (gd-ed25519, GodotApplePlugins - see 2.3).
- Roadmap ([roadmap](https://store.godotengine.org/roadmap)): drag-and-drop install, paid assets (currently free only), **CLI tool for uploading**, better review score, discovery, mobile view, and engine-side "deprecate current Asset Library", "global addons" (install engine-wide), GDScript/C# interoperability, and an **in-editor asset updater via the store API**. No public API/CLI is documented today (store home mentions none) -> publishing is a manual web upload for now. Plan for a manual release step, or watch for the CLI.
- Practical consequence: ship through **three channels at once** - GitHub Releases (canonical zip, what CI produces), Asset Store (primary discovery for 4.7+), and - while it lives - Asset Library (only reaches <=4.6 editors). Talo does GitHub + itch.io + Asset Store; GodotSteam is on GitHub->Codeberg + Asset Library + Asset Store ([Talo](https://github.com/TaloDev/godot), [GodotSteam](https://codeberg.org/godotsteam/godotsteam)).

### 1.2 addons/ conventions, plugin.cfg, EditorPlugin, autoload

From the plugin docs ([making plugins](https://docs.godotengine.org/en/latest/tutorials/plugins/editor/making_plugins.html)):

- Layout `res://addons/<name>/plugin.cfg` + a `@tool` script extending `EditorPlugin`. `plugin.cfg` keys: `name`, `description`, `author`, `version`, `script`. Every script the editor plugin uses must be `@tool` (a non-tool script "acts like an empty file" in the editor).
- Autoload from a plugin: `_enable_plugin()` -> `add_autoload_singleton("Name", "res://addons/x/file.tscn")`; `_disable_plugin()` -> `remove_autoload_singleton`. (Nakama, by contrast, still asks users to register `Nakama.gd` manually under Project Settings > Autoload - [Heroic docs](https://heroiclabs.com/docs/nakama/client-libraries/godot/).)
- Docks: 4.6 introduced `EditorDock` + `EditorPlugin.add_dock()`. `add_control_to_dock()` still exists in 4.4-4.7 (I diffed the 4.4/4.5/4.6/4.7 class docs), so an SDK that supports 4.4 must use `add_control_to_dock` or feature-detect `add_dock`.
- Sub-plugins: a parent plugin can enable/disable children with `EditorInterface.set_plugin_enabled()` - useful for optional per-platform pieces.
- **`.uid` files (4.4+)**: every `.gd`/shader gets a sidecar `.gd.uid`; the Godot team says commit them and never gitignore them, and for addons they travel with the source so refactors do not break user references ([UID article](https://godotengine.org/article/uid-changes-coming-to-godot-4-4/)). Release zips must include `.uid` files.
- Versioning: `plugin.cfg` `version` (semver string) is display-only; the real compatibility contract is the Asset Store's per-version min/max Godot fields. Recommended: `plugin.cfg version` == store version == git tag == `PKey.SDK_VERSION` constant.
- Config location: Talo writes `addons/talo/settings.cfg` ([docs](https://docs.trytalo.com/docs/godot/install)) - inside the addon folder, which an update clobbers (my inference). Better: a `Resource` (`res://polaris_key.tres`) or `ProjectSettings` keys under a plugin-specific prefix. A forum thread confirms the convention `addons/<plugin>/config/...` for plugin-created ProjectSettings ([thread](https://forum.godotengine.org/t/is-there-a-convention-for-projectsettings-created-by-a-plugin/54031)).

### 1.4 C# vs GDScript

- Cross-language rules ([docs](https://docs.godotengine.org/en/latest/tutorials/scripting/cross_language_scripting.html)): C# -> GDScript via `GodotObject.Call()` (fails silently on bad args); GDScript fields via `Get/Set`; GDScript signals must be connected with `Connect()` from C# (no static types); **no cross-language inheritance**. Docs recommend addon authors keep separate implementations or wrapper classes.
- Observed practice: Nakama = GDScript core + C# adapters; GD-Sync = both languages with parity; Duende's OAuth tutorial uses C# only because it needs NuGet ([article](https://duendesoftware.com/blog/20260804-authenticating-players-in-godot-4-with-oauth)).
- Web caveat: the Web export doc states C# is not exportable for Web in Godot 4 ([docs](https://docs.godotengine.org/en/latest/tutorials/export/exporting_for_web.html)) - irrelevant to Diceroll (GDScript) but it means a C#-only design would exclude the Web target entirely.
- Recommendation: GDScript is the only real implementation; optionally add a thin C# facade later (`PolarisKey.cs` that `Call()`s the autoload and re-exposes signals), never a parallel core.

## 2. GDExtension vs pure GDScript

### 2.1 Platform coverage of a GDExtension

- **Web**: needs "Extensions Support" in the export preset and cross-origin-isolation headers (COOP/COEP; the PWA service-worker option can fake them), and the extension must be compiled for `wasm32` ([export docs](https://docs.godotengine.org/en/latest/tutorials/export/exporting_for_web.html)). Official template packs do ship the `web_dlink_*` variants (4.5 pack: `web_dlink_release.zip` 10.5 MB vs `web_release.zip` 9.0 MB, ~+1.5 MB - [archive listing](https://archive.org/details/godot-4.5-export-template-packages)), but the _default_ templates "do not include GDExtension support" ([compiling for web](https://docs.godotengine.org/en/latest/engine_details/development/compiling/compiling_for_web.html)). Pitfalls: the extension must be built `threads=no` for the nothreads template or it hangs on the loading screen ([forum](https://forum.godotengine.org/t/how-to-build-a-gdextension-c-library-for-web/129067)); Emscripten version mismatches broke dlink loading in 4.4 with emsdk 4.x ([#105717](https://github.com/godotengine/godot/issues/105717)); and **Godot 4.8 will bump the required Emscripten to 6.0.1** and the PR calls this "compatibility breaking" for official builds ([#122412](https://github.com/godotengine/godot/pull/122412)) - one test showed 4.0.20-built extensions loading in 6.0.1 templates, but that is one sample. COOP/COEP also blocks embedding in third-party iframes (itch.io etc.) unless the PWA workaround is used.
- **iOS**: `godot-cpp` emits a `.dylib` that the exporter converts to a framework; there is a history of regressions (link error "cannot be mmap()ed" + runtime "framework not found" in 4.3-dev5, fixed by PR #95323 - [#90168](https://github.com/godotengine/godot/issues/90168)). Working shipping examples use `.xcframework` (SwiftGodot-based GodotApplePlugins ships an iOS xcframework + macOS dylibs - [repo](https://github.com/migueldeicaza/GodotApplePlugins)).
- **Android**: `.so` per ABI. The current godot-cpp-template matrix lists only `android.x86_64` and `android.arm64` (no armeabi-v7a/x86) ([example.gdextension](https://github.com/godotengine/godot-cpp-template/blob/main/project/bin/example.gdextension)). Google Play requires **16 KB page-size support** for new apps/updates targeting Android 15+ from 2025-11-01; native code must be built with 16 KB alignment (NDK r28+) ([Android doc](https://developer.android.com/16kb-page-size)); Godot 4.5 added 16 KB compatibility for the engine ([4.5 notes](https://godotengine.org/releases/4.5/)). A GDExtension .so built with an older NDK fails on such devices.
- **macOS**: official exports are Universal 2; hardened runtime + notarization apply; Godot's own doc says to enable **"Disable Library Validation" "if you are using GDExtension add-ons"** ([macOS export](https://docs.godotengine.org/en/latest/tutorials/export/exporting_for_macos.html)) - i.e., shipping a native lib makes every game relax a hardened-runtime protection. Note also App Sandbox forbids `OS.execute/create_process` outside the bundle.
- **Windows/Linux**: template lists windows x86_32/x86_64, linux x86_64/arm64/**rv64** - a 10+ file build matrix per Godot minor.

### 2.2 Compatibility and maintenance

- Extensions built for an older minor should load on newer minors, not vice-versa; 4.0 extensions do not load on 4.1+; `compatibility_minimum` (4.1+) / `compatibility_maximum` (4.3+) / `reloadable` in `.gdextension` ([gdextension_file](https://docs.godotengine.org/en/latest/engine_details/engine_api/gdextension/gdextension_file.html), [godot-cpp](https://github.com/godotengine/godot-cpp)). Engine PRs that change method signatures must add GDExtension compatibility methods ([release policy](https://docs.godotengine.org/en/latest/about/release_policy.html)). godot-cpp `main` (v10+) supports Godot 4.3+ with `api_version=` to target older engines. 4.6 moved the extension interface definition to JSON; 4.5 added main-loop callbacks ([4.6](https://godotengine.org/releases/4.6/), [4.5](https://godotengine.org/releases/4.5/)).
- Contrast: **iOS `.gdip` static-lib plugins** and other engine-header-linked plugins are _not_ ABI-stable: "Godot does not maintain C++ ABI stability across minor versions... a bridge compiled for 4.2 crashes when linked into 4.3" ([poingstudios issue](https://github.com/poingstudios/godot-swift-plugin/issues/4)); the godot-mobile-plugins org mirrors per-release iOS static libs and headers twice a week for exactly this reason ([godot-ios-builds](https://github.com/godot-mobile-plugins/godot-ios-builds)). The stable `gdextension_interface.h` C interface is the ABI-safe route.
- Binary size: small for C crypto (Monocypher is tiny), ~+1.5 MB for the Web dlink template, ~2.5 MB for GodotApplePlugins release builds ([store page](https://store.godotengine.org/asset/xogot/godot-apple-plugins/)). Size is not the problem; matrix + signing + template coupling is.

### 2.3 Existing Ed25519 GDExtensions

- **The only Godot 4 Ed25519 GDExtension I could find is [freehuntx/gd-ed25519](https://github.com/freehuntx/gd-ed25519)** ([store page](https://store.godotengine.org/asset/freehuntx/ed25519/)): vendored Monocypher, RFC 8032 Ed25519 (SHA-512), `Ed25519.verify(signature, message, public_key) -> bool`, plus X25519/XChaCha20-Poly1305/BLAKE2b; claims Linux, Windows, macOS, Android, iOS and Web (WASM); README build commands only list Linux/Windows/macOS/Web; v1.0.0 "unstable", MIT, min Godot 4.4, ~8 stars/2 forks, last updated 2026-07-16. Web randomness via `getentropy` -> Web Crypto. Not something to hang a licensing product's trust root on without vendoring/forking and owning the build.
- **"godot-sodium" and "GodotEd25519": no such projects turned up** in several searches (Asset Library/Store, GitHub, general web). Treat those names as non-existent unless someone can produce a URL.
- Godot's built-in `Crypto` does RSA sign/verify, HMAC (SHA-256/SHA-1 only) and random bytes - **no Ed25519, no ECDSA** ([Crypto](https://docs.godotengine.org/en/latest/classes/class_crypto.html)); `HashingContext` offers **MD5/SHA-1/SHA-256 only, no SHA-512** ([HashingContext](https://docs.godotengine.org/en/latest/classes/class_hashingcontext.html)). So the wire's Ed25519 needs an implementation shipped by us.
- Browser alternative for Web builds only: WebCrypto Ed25519 via `JavaScriptBridge.eval` (async Promise). Ed25519 shipped in Firefox 129, Safari 17, Chrome 137 (May 2025) ([IPFS blog](https://blog.ipfs.tech/2025-08-ed25519/)); requires a secure context.
- **Pure GDScript is viable: see Appendix A** - a ~400-line prototype (SHA-512 + TweetNaCl-derived Ed25519 verify) passes RFC 8032 vectors and Node-generated vectors and runs in ~25-45 ms per verify on Godot 4.7 desktop.

## 3. Native platform plugins in Godot 4.x

### 3.1 Android (plugin v2)

- v2 = AAR built against the Godot Android library; init class extends `GodotPlugin`; methods callable from GDScript need `@UsedByGodot` (name must match exactly); signals via `getPluginSignals()` + `emitSignal()`; packaged with an `EditorExportPlugin` (`plugin.cfg` + `@tool` script), **replacing the old `.gdap`**; the export plugin uses `_get_android_libraries` (local AARs), `_get_android_dependencies` (+ maven repos), and manifest hooks `_get_android_manifest_{element,application_element,activity_element}_contents`; GDScript gets it with `Engine.get_singleton("Name")`; requires Godot 4.2+ **with Gradle build enabled** ([Android plugins](https://docs.godotengine.org/en/latest/tutorials/platform/android/android_plugin.html)). A v2 plugin can also bundle a GDExtension (`getPluginGDExtensionLibrariesPaths()`, `android_aar_plugin = true` in `.gdextension`). Templates: [Godot-Android-Plugin-Template](https://github.com/m4gr3d/Godot-Android-Plugin-Template), [GDExtension-Android-Plugin-Template](https://github.com/m4gr3d/GDExtension-Android-Plugin-Template).
- **Play In-App Updates**: community plugins exist and are tiny: [dcryptoniun/Godot-Android-InAppUpdate](https://github.com/dcryptoniun/Godot-Android-InAppUpdate) (Godot 4.5+, AAR + `export_plugin.gd`, `checkUpdateAvailable / startFlexibleUpdate / startImmediateUpdate / completeFlexibleUpdate`, signals `update_info_received`, `update_status_changed`, ...; ~3 stars) and [icecube092/GodotInAppUpdate](https://github.com/icecube092/GodotInAppUpdate) (4.6). Low adoption; expect to own/fork.
- **Play Asset Delivery**: I found **no Godot plugin or proposal** (searches returned only Unity/Unreal integrations). PAD has install-time (1 GB), fast-follow (1 asset pack, 512 MB) and on-demand (512 MB) types ([Android docs](https://developer.android.com/guide/playcore/asset-delivery/integrate-java)); nothing in Godot's Gradle export wires asset-pack modules. Treat PAD as greenfield; a Polaris Key CDN download of packs into `user://` covers the same need without it.
- **Play Billing / Play Games**: godot-sdk-integrations maintains [godot-google-play-billing](https://github.com/godot-sdk-integrations) (Kotlin) and godot-play-game-services (GDScript+AAR) - proof the AAR+export-plugin route is the mainstream one.
- **In-app review**: [godot-mobile-plugins In-app Review](https://store.godotengine.org/asset/cengiz/inapp-review-plugin/) (Play + StoreKit, `generate_review_info()` -> `launch_review_flow()`).
- **Secure storage (Keystore)**: **no standalone Godot Keychain/Keystore plugin found.** [GD Credentials](https://github.com/whogben/gd_credentials) is pure GDScript AES-ECB with a developer-supplied password (not a keychain). The godot-oauth2 plugin uses Keystore/Keychain _internally_ for tokens but exposes no generic API ([store page](https://store.godotengine.org/asset/cengiz/oauth2-plugin/)). Since Polaris Key artifacts are signed documents (integrity, not confidentiality), native secure storage is a Phase-2 nicety, not a launch requirement (my inference from the client-core README: it caches signed docs and a monotonic clock floor).
- **Install-source / channel detection on Android** (`PackageManager` installer info) is not exposed by Godot and I did not research a plugin - **UNVERIFIED**; would be a ~20-line Kotlin method in our own AAR.

### 3.2 iOS

Three mechanisms, all still valid in 4.7:

1. `.gdip` + static `.a`/`.xcframework` (Objective-C/Swift compiled against engine headers; `[config]` name/binary/initialization/deinitialization, `[dependencies]` linked/embedded/system/capabilities/files, `[plist]`, linker flags; `Engine.has_singleton()`/`get_singleton()` in GDScript) - **version-coupled** (see 2.2) ([iOS plugins](https://docs.godotengine.org/en/latest/tutorials/platform/ios/ios_plugin.html)).
2. `EditorExportPlugin` Apple-embedded APIs: `add_apple_embedded_platform_framework / embedded_framework / linker_flags / plist_content / project_static_lib / bundle_file / cpp_code` exist from **4.5** (the `add_ios_*` names are deprecated aliases; 4.4 only has `add_ios_*`); `_end_generate_apple_embedded_project`. **`add_apple_embedded_platform_spm_package` (Swift Package Manager) and `.gdip` `spm_packages` exist only in master/4.8-dev docs, not 4.7** (I diffed the 4.4-4.7 class docs).
3. **GDExtension via the C interface, packaged as a static xcframework** - the ABI-stable route; GodotApplePlugins (SwiftGodot) ships this way with empty stubs for Windows/Linux so scripts compile everywhere; it bundles GameCenter, StoreKit 2, Sign in with Apple, file picker, ARKit, CoreMotion (min iOS 17/macOS 14; Godot 4.3-4.8; MIT) ([store](https://store.godotengine.org/asset/xogot/godot-apple-plugins/), [repo](https://github.com/migueldeicaza/GodotApplePlugins)). The stub pattern is worth copying.

- **TestFlight vs App Store**: the same binary is promoted from TestFlight to the App Store, so a build-time stamp cannot distinguish them; it must be detected at runtime. Options: `Bundle.main.appStoreReceiptURL?.lastPathComponent == "sandboxReceipt"` (true for TestFlight _and_ debug, false for App Store) or StoreKit 2 `AppTransaction.shared`'s `environment` (iOS 16+; TestFlight reports sandbox) ([Apple forum 704156](https://developer.apple.com/forums/thread/704156), [forum 791170](https://developer.apple.com/forums/thread/791170)). Both need native code; GodotApplePlugins' StoreKit2 wrapper is the natural base, but I did not confirm it exposes `AppTransaction`.
- **Keychain**: same gap as Android - no maintained generic plugin found.
- App Store rules that constrain an in-game updater: guideline 2.5.2 forbids downloading/executing code, but the Developer Program License Agreement allows _interpreted_ code if it does not change the app's primary purpose, does not create a store, and does not bypass signing/sandbox ([forum 52161](https://developer.apple.com/forums/thread/52161)). Google Play: apps may not self-update outside Play or download executable code (dex/JAR/.so); interpreted code in a VM/interpreter is exempt but must not enable policy violations ([Play policy](https://support.google.com/googleplay/android-developer/answer/9888379)). Implication: on iOS/Android, the SDK should default to **data-only packs** (and treat GDScript-bearing packs as a per-product opt-in with a legal review), and "app update available" must deep-link to the store.

### 3.3 macOS / Windows / Linux

- macOS: `EditorExportPlugin.add_macos_plugin_file()` puts files into the bundle `PlugIns` dir. **Sparkle 2** (EdDSA-signed appcasts, delta updates, must be embedded+signed, needs hardened runtime + library validation considerations; [docs](https://sparkle-project.org/documentation/)) has **no Godot integration that I could find** - it would be a GDExtension wrapper plus the Disable-Library-Validation entitlement. **Velopack** (Windows/macOS/Linux, `releases.{channel}.json`, delta downloads, `Update.exe` applies) documents .NET as the primary SDK ([docs](https://docs.velopack.io/integrating/overview)); no Godot integration found (Godot C# could call it, but that excludes GDScript projects). WinSparkle: no Godot integration found.
- Windows Store: `StoreContext.GetAppAndOptionalStorePackageUpdatesAsync` / `RequestDownloadAndInstallStorePackageUpdatesAsync` need MSIX package identity ([docs](https://learn.microsoft.com/en-us/windows/uwp/packaging/self-install-package-updates)); Godot's Windows export docs mention code signing (env vars `GODOT_WINDOWS_CODESIGN_*`) but no MSIX export ([docs](https://docs.godotengine.org/en/latest/tutorials/export/exporting_for_windows.html)), so Store-packaged Godot builds are a hand-rolled pipeline.
- Realistic desktop stance: **channel-aware policy** - Steam/itch/MAS/Store builds are store-managed (SDK only shows "update available" and never self-updates); direct-download builds use an SDK-driven download+verify+hand-off flow (see 6).

### 3.4 Deep links, OAuth, QR

- **Godot core does not deliver received URLs on mobile**; the community route is the [Deeplink plugin](https://store.godotengine.org/asset/cengiz/deeplink-plugin/) (Android App Links via intent; iOS Universal Links; **custom schemes work on Android but have restricted support on iOS**; `Deeplink` nodes with scheme/host/path, `deeplink_received` signal; `initialize()` early). I did not find a documented core API for macOS/Windows custom-URL-scheme delivery - **UNVERIFIED**; for desktop OAuth, avoid custom schemes anyway.
- **OAuth/OIDC**: RFC 8252 recommends loopback (127.0.0.1) redirect for desktop and claimed-https/private-scheme redirects + in-app browser tabs for mobile ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)); device flow (RFC 8628) for TV/limited-input. Godot ships `TCPServer` for a GDScript loopback listener and `OS.shell_open` for the browser (Duende's C# article does the same with `HttpListener`/`OS.ShellOpen` and a device-flow + QR variant). Existing plugins: [godot-oauth2](https://store.godotengine.org/asset/cengiz/oauth2-plugin/) (Android Custom Tabs + iOS `ASWebAuthenticationSession`, PKCE, presets, requires the Deeplink plugin on Android; store page says Godot 4.7+) and [Godot OAuth2 Server](https://godotengine.org/asset-library/asset/edit/17296) (desktop loopback - that specific submission was rejected; treat as unavailable).
- **QR**: [Kenyoni QR Code](https://store.godotengine.org/asset/kenyoni/qr-code/) (GDScript addon, Godot 4.4+, MIT, v2.0.0, updated 2026-07-21; `QRCodeRect` node + `QRCode` class) is enough for device-flow "scan to activate"; godot-mobile-plugins has native QR generate/scan for Android/iOS ([QR](https://store.godotengine.org/asset/cengiz/qr-plugin/)).

## 4. EditorExportPlugin, export presets, CI exports

- `EditorExportPlugin` hooks ([class ref](https://docs.godotengine.org/en/latest/classes/class_editorexportplugin.html)): `_export_begin(features, is_debug, path, flags)`, `_export_file(path, type, features)` (call `skip()` to exclude, or `add_file(path, bytes, remap=true)` to remap), `_export_end()`, resource/scene customization (`_begin_customize_resources/_customize_resource/_get_customization_configuration_hash`), `_get_export_features(platform, debug)` (inject feature tags), `_get_export_options(platform)` (adds per-preset fields to the export dialog - what Play Games uses for `game_id`), `_get_export_option_visibility/_warning`, `_supports_platform`, `add_file`, `add_shared_object`, `add_macos_plugin_file`, Android manifest/Gradle hooks (section 3.1), Apple hooks (3.2). Note: `add_file` data is **not imported**, so use it for JSON/text/binary read via `FileAccess`, not for `Resource`s.
- Per-preset stamping recipe: register the export plugin from the EditorPlugin (`add_export_plugin`); in `_export_begin` read `get_export_preset()`, `get_option("polaris_key/channel")`, `get_export_preset().get_or_env(name, "ENV_VAR")` (option-or-environment - exists since 4.4; Godot's own convention is `GODOT_<PLATFORM>_<OPTION>` env vars, e.g. `GODOT_WINDOWS_CODESIGN_IDENTITY`), `get_version()`, `get_custom_features()`, `get_patches()`; then `add_file("res://.polaris_key/build.json", bytes, false)` with `{product, channel, platform, version, build, features, git_sha}`; and return feature tags such as `pkey_channel_steam` from `_get_export_features`. Runtime: `FileAccess.open("res://.polaris_key/build.json")` and `OS.has_feature("pkey_channel_steam")`.
- Feature tags: built-ins (platform, arch, debug/release, editor/template, threads, texture formats) + **custom features** in the export preset's Custom field; "only used when running the exported project... not from the editor"; use `ProjectSettings.get_setting_with_override()` for `.feature`-suffixed settings ([feature tags](https://docs.godotengine.org/en/latest/tutorials/export/feature_tags.html)). Because custom tags do not exist in the editor, the SDK needs an explicit `PKey.build_info` fallback (`channel = "dev"`) when the stamp file is absent.
- CLI/CI ([CLI docs](https://docs.godotengine.org/en/latest/tutorials/editor/command_line_tutorial.html)): `--export-release|--export-debug <preset> <path>`; `--export-pack <preset> <path.pck|.zip>` (extension picks format); **`--export-patch <preset> <path>` with `--patches <comma-separated>`** (patch PCKs are 4.4+; docs describe Patching tab > Base Packs > Export as Patch); relative paths resolve against the `project.godot` dir; `--install-android-build-template`; `--headless`; `--import` first. Credentials live in `.godot/export_credentials.cfg` (do not commit) while `export_presets.cfg` is safe to commit ([exporting projects](https://docs.godotengine.org/en/latest/tutorials/export/exporting_projects.html)).
- **Delta patches** (4.6+, GH-112011; [dev5 notes](https://godotengine.org/article/dev-snapshot-godot-4-6-dev-5/), [4.6](https://godotengine.org/releases/4.6/)): opt-in in the Patching tab; compression level default 19, minimum size reduction %; costs a few ms per patched file and **cumulative load time per stacked patch**; for smallest patches disable resource compression (import settings / "Compress Binary Resources" / GDScript export mode) and clear `.godot/imported`; and **the Base Packs list must be byte-identical to what the game loads at runtime, in order** - re-exports are non-deterministic and delta patches fail otherwise ([exporting PCKs](https://docs.godotengine.org/en/latest/tutorials/export/exporting_pcks.html)). Implication for Polaris Key: the release pipeline must archive the exact shipped pack bytes and record their hashes as the delta base; the manifest should carry `base_sha256` and a fall-back full-pack URL.
- `PCKPacker`: `pck_start(path, alignment=32, key, encrypt_directory)`, `add_file`, `add_file_removal` (4.4+, "mainly for patches"), `add_file_from_buffer` (**4.7+**), `flush` ([class ref](https://docs.godotengine.org/en/latest/classes/class_pckpacker.html)). Good for data-only packs of _non-imported_ content (JSON, text `.tres`, raw audio/images loaded via `Image.load_from_buffer`); imported assets (textures, models) need the editor importer, i.e., a real `--export-pack` with a dedicated preset/filters. The docs also warn against using raw runtime loading for project resources ([runtime loading](https://docs.godotengine.org/en/latest/tutorials/io/runtime_file_loading_and_saving.html)).
- Version-availability notes from my doc diffs: `EditorExportPreset.get_patches/get_or_env/get_custom_features` exist in 4.4-4.7; `add_apple_embedded_platform_*` from 4.5; `PCKPacker.add_file_from_buffer` 4.7; `add_apple_embedded_platform_spm_package`, HTTPRequest resume (`append_to_download_file`, `keep_partial_download`) and `OS.create_instance` are master-only (4.8-dev).

## 5. Runtime content loading

- `ProjectSettings.load_resource_pack(pack, replace_files=true, offset=0) -> bool`: loads `.pck`/`.zip` into `res://`; by default a pack's files **replace** same-path files (pass `false` to opt out; load order matters); `offset` only for `.pck`; `DirAccess` does not see changes after loading ([ProjectSettings](https://docs.godotengine.org/en/latest/classes/class_projectsettings.html)). **There is no unload API** through 4.7 (I searched every 4.3-4.7 ProjectSettings snapshot for `unload_resource_pack`; the forum shows users asking) -> design packs as append-only; changing content = restart or a fresh pack mounted later with higher priority.
- Load early: preloaded scenes will not see later packs; docs say load from an autoload's `_init()`, not `_enter_tree()`/`_ready()` ([exporting PCKs](https://docs.godotengine.org/en/latest/tutorials/export/exporting_pcks.html)). Security warning in the same page: packs can carry code; use asymmetric signatures (public key in the main PCK, sign patch/expansion PCKs) - exactly Polaris Key's model. There is no built-in DRM/copy protection.
- Class registry pitfall: scripts in a runtime-loaded pack that use statically typed custom `class_name` types fail ("Could not find type ... in the current scope") because the loader project does not know those globals (reported on 4.2.1; workaround = type as built-in parent; may have changed) ([forum](https://forum.godotengine.org/t/static-typing-prevents-gdscript-parsing-in-runtime-loaded-resource-packs/58732)). This is why [godot-patch-loader](https://github.com/Ryan-000/godot-patch-loader) (GDExtension, 4.4+) loads `patch_<n>.pck` at `MODULE_INITIALIZATION_LEVEL_CORE`, so patches can override GDScript, .NET assemblies, scenes and resources; it cannot patch native libs and applies only once at startup.
- **UID cache / `.godot` metadata overwritten by packs: UNVERIFIED** - I found no issue or doc confirming or refuting that a patch/DLC pack's `.godot/uid_cache.bin` or `global_script_class_cache.cfg` replaces the base game's when `replace_files=true`. Reasoned from engine behavior it is plausible; write a spike (Section 9).
- Android: [godot#105009](https://github.com/godotengine/godot/issues/105009) - `load_resource_pack` on Android startup **freezes the UI during the load**, regression after 4.4-beta1, still open, no fix version; suggested mitigation is deferring the call until after UI init (i.e., do it after showing the boot screen, accept a hitch, or load smaller packs). Separate 4.6 change: **official templates ignore `--main-pack`, `--path`, `--scene`, `-s`** (`disable_path_overrides` default; [PR #111909](https://github.com/godotengine/godot/pull/111909), merged 2025-11-12, Web exempt); Android got a restricted re-enable for packs bundled in the APK in 4.7/4.6.3 ([PR #119495](https://github.com/godotengine/godot/pull/119495)). Reports: [4.6 breaks `--main-pack`](https://forum.godotengine.org/t/export-to-current-aos-project-pck-error-in-4-6-in-4-5-1-it-works-well/132921). Details in 6.
- Web: `user://` is IndexedDB-backed; persistence requires cookies/IndexedDB allowed, third-party cookies in iframes, and fails in incognito; `OS.is_userfs_persistent()` can false-positive ([Web export](https://docs.godotengine.org/en/latest/tutorials/export/exporting_for_web.html)). Documented pattern for extra packs: `HTTPRequest` -> write to `user://x.pck` -> `load_resource_pack("user://x.pck")`; forum threads about multiple PCKs on Web include unresolved failures using `res://` paths ([thread](https://forum.godotengine.org/t/multiple-pcks-within-web-export/59718)) - **verify on 4.7 with a spike**; also `.pck` and `.wasm` should be gzip/brotli-served.
- Loader-UI mechanics: `ResourceLoader.load_threaded_request(path, type_hint, use_sub_threads, cache_mode)` + `load_threaded_get_status(path, progress)` polled per frame ([background loading](https://docs.godotengine.org/en/latest/tutorials/io/background_loading.html), [ResourceLoader](https://docs.godotengine.org/en/latest/classes/class_resourceloader.html)). **On single-threaded Web exports it effectively blocks** ([forum](https://forum.godotengine.org/t/is-nonblocking-background-loading-on-web-posible/140001)); the SDK's BootScreen therefore needs a Web branch (show the progress UI _before_ the blocking `load()`, or slice work across frames).
- Downloads: `HTTPRequest` (`download_file`, `download_chunk_size`, `body_size_limit`, `use_threads`); **resumable download properties are 4.8-dev only**; on 4.4-4.7 implement Range/resume manually (own `HTTPClient` loop or per-chunk HTTPRequest to part files) - or, better, make packs small and content-addressed so retry = re-fetch the pack.
- Helpful third-party loaders for UX inspiration: [Maaack's Scene Loader](https://store.godotengine.org/asset/maaack/maaacks-scene-loader/) (loading screen, progress bar, error handling; 4.3+ compatible).

## 6. Self-update of the main pack/binary

- `OS.create_process(path, args, open_console)` spawns a detached process (Android/Linux/macOS/Windows; macOS sandbox limits it to embedded helpers; `.app` bundles ignore args), `OS.execute` runs-and-waits, `OS.set_restart_on_exit(restart, args)` restarts on `SceneTree.quit()`/close **on desktop only, not from the editor, not mobile/Web** ([OS](https://docs.godotengine.org/en/latest/classes/class_os.html)). `OS.create_instance` is 4.8-dev only.
- **The classic relaunch `game --main-pack user://new.pck` is no longer available on official desktop templates from 4.6** (PR #111909; forum reports; the CLI doc still lists `--main-pack` but tags it "extended": only editor builds and templates compiled with `disable_path_overrides=false`). Docs' ZIP-launcher script example is stale for the same reason. Alternatives that survive: (a) place a new `<exe-basename>.pck` next to the executable (the engine auto-discovers it; needs a writable install dir - fails under Program Files, sandboxed installs, MAS); (b) bootstrap autoload `_init()` calling `load_resource_pack(replace_files=true)` for signed override packs; (c) ship a custom template with `disable_path_overrides=no` (defeats the point of official templates); (d) a **separate launcher app** (zip::launcher pattern) that owns install + verification; (e) native updater (Sparkle/Velopack) for the whole app; (f) on Android the APK-bundled `data.pck` route only.
- Existing game-level updaters: [zip::launcher](https://github.com/Joy-less/zip-launcher) (Godot-made launcher; JSON config with per-platform URLs; whole-zip downloads, no delta), [godot-patch-loader](https://github.com/Ryan-000/godot-patch-loader) (4.4+ GDExtension, `patches/patch_N.pck`), and **CAVS** (announced 2026-07-09: runtime PCK delta updates, signature verification, analysis CLI, benchmarking vs butler/bsdiff/xdelta3 - a direct peer to what Polaris Key would offer; [forum](https://forum.godotengine.org/t/cavs-open-source-toolkit-for-smaller-godot-updates-pck-analysis-and-runtime-content-patching/141435)). "GGUpdater": not found. The "Godot Launcher"/"Version Updater"/"Plugin Updater" projects ([Maaack](https://github.com/Maaack/Godot-Plugin-Updater), etc.) update the **editor or addons**, not shipped games.
- Outside stores: itch.io's butler uses rsync+bsdiff-style patches and the itch app auto-updates ([itch docs](https://itch.io/docs/itch/integrating/updates.html)); Steam uses depots/branches (GodotSteam exposes DLC info - [classes/apps](https://godotsteam.com/classes/apps/)). Commercial Godot games mostly ride Steam/itch/store update rails and only ship in-game content packs or a custom launcher when off-store; I found no public write-up of a large commercial Godot game with its own binary self-updater (absence of evidence).
- Web: no binary to update; use PWA update signals - `JavaScriptBridge.pwa_needs_update()`, `pwa_update()`, `pwa_update_available` signal ([JavaScriptBridge](https://docs.godotengine.org/en/latest/classes/class_javascriptbridge.html)) - plus cache-busting on pack URLs.

- gd-ed25519's CI pattern is a good model for native pieces: `godot --headless -s res://tests/test.gd` covering RFC vectors ([README](https://github.com/freehuntx/gd-ed25519)).

### DX synthesis for `polaris_key`

```gdscript
# project.godot: autoload "PKey" registered by the plugin (name is per-project configurable)
func _ready() -> void:
    PKey.download_progress.connect(_on_progress)          # (item, received, total)
    var boot: PKeyBootResult = await PKey.boot()          # one coroutine: trust -> license -> config -> release check -> required packs
    match boot.state:
        PKey.Boot.READY: get_tree().change_scene_to_file(boot.main_scene)
        PKey.Boot.UPDATE_REQUIRED: %Prompt.show_update(boot.release)   # store link or in-app apply
        PKey.Boot.OFFLINE_GRACE: ...
        PKey.Boot.BLOCKED: %Prompt.show_license(boot.license)
```

- One `Resource` config (`PKeyConfig`: product slug, **pinned trust keys by kid**, API base, default channel, required/optional pack ids, offline grace policy) created by the plugin's setup dock at `res://polaris_key.tres` (outside `addons/`).
- Result objects, not exceptions (Nakama `is_exception`), carrying the server's machine-readable error code (mirrors `PolarisError`).
- Signals: `boot_state_changed`, `download_progress`, `update_available`, `license_changed`, `config_changed`, `pack_mounted`.
- `PKeyBootScreen` scene (drop-in, `Control`-rooted): `@export var config: PKeyConfig`, `@export var theme: Theme`, `@export var main_scene: PackedScene/String`, exported `PackedScene` slots for progress widget / prompt dialog / branding, virtual hooks (`_on_update_available(release) -> bool`), threaded-load path + Web nothreads path, `finished(result)` signal; inherited-scene customization instead of code forks.
- Channel model: build-time stamp (`pkey_channel_*` feature tags) for store/source; runtime probe for the two places where one binary spans channels (TestFlight vs App Store; Play tracks). Policy table: `store_managed` (never self-update; show store link), `self_managed` (download+verify+apply), `content_only` (packs only).

## 9. Recommendation

### 9.1 Architecture: **hybrid, GDScript-first (core 100% GDScript, native only as optional per-platform shims)**

1. **Core in pure GDScript** - HTTP, JWS parsing, **Ed25519 verify (pure GDScript, corpus-tested)**, SHA-512, semver/channel, clock floor, config resolution, cache in `user://`, pack downloader/mounter, BootScreen. Rationale: (a) the only thing that would otherwise force a GDExtension is Ed25519 verify, and the prototype (Appendix A) shows GDScript does it in tens of milliseconds; (b) a GDExtension in the trust path multiplies the platform matrix (Web dlink + Emscripten coupling + COOP/COEP, iOS xcframework, Android 16 KB + ABIs, macOS Disable-Library-Validation, 10+ binaries per Godot minor) and _every one of those is a place a licensing check can silently fail to load_; (c) a pure-script core runs unmodified on all six export targets Diceroll needs, including Web on stock templates.
2. **Native shims are additive and optional**, each behind a GDScript interface with a stub implementation on unsupported platforms (copy GodotApplePlugins' "empty stubs" idea): Android AAR (install source, in-app updates), iOS GDExtension-via-C-interface xcframework (TestFlight/`AppTransaction` environment, later Keychain), later desktop updater adapters. Absent shim => SDK degrades to `unknown` channel + store link, never fails boot.
3. **Do not build on `.gdip`/engine-header-linked iOS code** (ABI coupled to each Godot release); use the GDExtension C interface for anything iOS-native.
4. **Optionally** vendor/fork a Monocypher GDExtension as a _performance accelerator_ behind the same `Ed25519` interface if on-device benchmarks demand it (unlikely) - never as the only path.
5. **Web fast path** (optional): WebCrypto Ed25519 via `JavaScriptBridge` when available; fall back to pure GDScript.

Risk to manage on the pure-GDScript verify: Ed25519 verification is not uniquely specified across libraries (canonical encodings, small-order keys, cofactored vs cofactorless). In my probe Node/OpenSSL accepted small-order and non-canonical-A cases and my port agreed on all three probes, but **workerd (BoringSSL) may differ**; the conformance corpus - not this note - decides. Add negative vectors for these to `conformance/corpus` if absent. (Any such corpus change is wire-adjacent and falls under the repo's plan-mode rule.)

### 9.2 Packaging

- Repo layout (source of truth in this monorepo, e.g. `sdks/godot/`): `addons/polaris_key/{plugin.cfg, plugin.gd, polaris_key.gd (autoload), core/, ui/boot_screen.tscn, ui/theme/, export/export_plugin.gd, platform/{android,ios}/ , LICENSE, README.md}` **with all `.uid` files committed**, plus `demo/` project and `test/` (GUT or gdUnit4) - the store's rule "licence+readme inside the plugin folder" is satisfied by the addon dir.
- Plugin behavior: `_enable_plugin` registers the autoload; `_enter_tree` registers the `EditorExportPlugin` and a setup dock (use `add_control_to_dock` for 4.4 compat, `add_dock` when available); the setup dock writes `res://polaris_key.tres`, validates the pinned key, and offers `pkey`-CLI integration (`pkey init` already exists in this repo).
- Release: CI builds `polaris-key-godot-vX.Y.Z.zip` (GitHub Release = canonical), then a manual Asset Store upload (no API/CLI yet) with **min Godot 4.4**, and (while alive) the legacy Asset Library entry for <=4.6 editors. Keep `plugin.cfg` version, tag, store version and `PKey.SDK_VERSION` identical.
- Docs/examples: a "Diceroll-style" minimal boot flow, the export-preset walkthrough, and a CI snippet for stamping.

### 9.3 Minimum Godot version

- **Source-compatible floor: 4.4** (matches the brief; 4.4 has patch PCKs/`--export-patch`, `.uid`, `PCKPacker.add_file_removal`, typed dictionaries). Do not use 4.5+ syntax (`@abstract`, variadic `...args`) in shipped scripts, and gate newer APIs with `has_method`/`ClassDB.class_has_method` checks.
- **Supported/CI matrix: 4.4, 4.5, 4.6, 4.7 (+ 4.8 beta when it appears)** with GUT (branch per version) or gdUnit4; **blessed versions: 4.6+** (only 4.6/4.7 get full engine fixes; delta patches need 4.6+).
- Feature gates: delta patches >= 4.6; `add_dock` >= 4.6; Apple embedded export APIs >= 4.5 (fallback `add_ios_*`); `PCKPacker.add_file_from_buffer` >= 4.7; Asset Store in-editor >= 4.7; `--main-pack` on desktop: never rely on it (>= 4.6 templates).
- Native shims may set a higher floor per shim (e.g., an iOS shim built as GDExtension could declare `compatibility_minimum = "4.4"`).

## Appendix A - Pure-GDScript Ed25519 verify prototype (hands-on result)

Purpose: test whether an SDK can avoid a GDExtension for the one crypto primitive Godot lacks. Code: a scratch project (not kept; see ../prototype/ for the kept, faster port) (`fe.gd` generated by `gen_fe.py`, `consts.gd` by `gen_consts.py`, `sha512.gd`, `ed25519_pure.gd`, `bench.gd`, `edge.gd`; vectors from Node `crypto` + RFC 8032). (Output log not kept.)

Design: 16 x 16-bit limbs in `PackedInt64Array` (TweetNaCl layout), unrolled generated `Fe.mul`; SHA-512 written in GDScript because `HashingContext` has none; verification = decode `-A`, `h = SHA512(R||A||M) mod L`, Straus double-scalar mult `[S]B + [h](-A)` with the unified addition formula, canonical `S < L` check, compare encoded `R'` to `R`.

Results on Godot 4.7.stable (official Linux editor binary, headless), 4 vCPU 2.1 GHz Xeon VM:

- Correctness: SHA-512 known-answer OK ("abc", empty); RFC 8032 TEST 1 and TEST 2 verify true; 5 Node-generated valid signatures (empty, 3 B, 300 B, 1000 B, 3 KB JWS-like) true; tampered message / R / S false; `S+L` malleability false; all 11 vectors match.
- Latency: **~25-45 ms per verify** for small messages (median 27 ms over 7 runs; ~4,950-5,050 field multiplications; one field mul ~4.7-5.5 us); **46-58 ms for a 64 KiB message** (the JWS cap; SHA-512 in GDScript costs ~1.2 ms per 4 KiB, ~19-26 ms per 64 KiB).
- Edge parity probe against Node/OpenSSL: small-order A=identity accepted by both; non-canonical A (y=p+1) accepted by both; non-canonical R rejected by both.
- Not measured: ARM mobile, Web/wasm, memory. Prototype is variable-time (fine for public-data verification), not hardened, not yet fed the real corpus.
- Conclusion: cost is negligible next to a network round trip; no GDExtension needed for the trust path. Add frame-slicing only if device benchmarks say so.
