# DX consolidation: the integrated target (2026-10-07)

**Inputs.** The owner brief (`owner-brief.md`) and the fifteen audits in `audits/`. The
repository read is `pk-wt/dx-plan` (v0.8.31 plus batch 5). Batch 6 (LX-08, HA-12, UK-13, UK-14
and the owner's minor fixes on `fix/ux-polish-1007`) has since merged into `integ/batch-6` as
reviewed. Three critiques (coverage, feasibility, simplicity) were then applied; README §11 logs
what changed.

**Status.** This document is the decision record for the consolidation. Where an audit
disagrees with it, this document wins; the audits remain the evidence (file and line references
live there). It replaces the audits' work-package ids with one numbering (§3.2). Nothing here
changes `PROTOCOL_VERSION`. Three wire trains and two contract-text slots remain beside HA-12
(done), all additive inside v4 (§1.5).

**Short version.**

- A **product** is Core plus **five features** (Licensing, Managed config, Ship builds, Sign-in,
  Cloud Sync) over the seven unchanged service slugs. Each feature's row holds its own switches
  (Package feeds, In-app updates, Customer portal, Polaris Key storefront, Minted tokens) and
  facts (Commerce: a storefront is ready).
- A licence is **in an account, waiting or floating**. Every licence has a **tier**, its
  template; an **add-on** is a sub-licence it holds; its **limits** resolve licence > tier >
  platform default through one resolver, and a **duration** says how long it runs.
- **Entitlements** move from Config to Licensing, with no wire change. **Config** keeps a
  five-layer chain, including the licence layer (U-03's run is cancelled, pending the owner).
- One **access policy** decides who gets a licence automatically. One **issuance function**
  serves sign-in, Discover, store purchases, codes and checkout.
- Every person is an **account**, operators included. The console runs on **RBAC** with the
  owner's four built-in roles. One **personal token** (`pkeyp_`) per scope covers packages or the
  CLI.
- A **distribution channel** is where builds reach customers. A **storefront** is the selling
  facet of the same channel. Both use one page, one catalogue and one read model, scoped by
  what the product actually builds.
- One **Integration** read model and page, fed by SDK sightings (plus the two facts no SDK
  request carries), replaces five planned setup surfaces. One snippet generator and one `polaris-key.json` file feed the
  console, the CLI, the docs and the READMEs.
- The **code-quality** work (layering, one route table with `can()`, one data layer, one wizard
  kit, one generator registry, one data-migration runner) runs first, because every feature track
  builds on it. Every schema contract takes two releases.

## 1. Concept model

### 1.1 The shape

```text
Platform
├─ Accounts ── sign-in methods (links) · profile · Library · consents · personal tokens
│     └─ console membership ── role bindings (platform · product · all products) ← SSO rules
├─ Connections (sign-in providers and SSO with verified domains · email · store team keys)
└─ Products
     ├─ Core: presentation · signing keys · devices · users · activity · settings · Integration
     ├─ Licensing ── tiers · add-ons · entitlement catalog · access policy · licences
     │                 licence = holder + tier + limits + duration(+subscription) + add-ons + keys + devices
     ├─ Managed config ── catalog (settings · secrets · minted tokens) · profiles (Default + per tier)
     ├─ Ship builds ── releases (apps · packs · packages) · release tracks · update feeds
     │                 distribution channels (+ storefront facet) · package feeds · rollouts
     ├─ Sign-in ── sign-in surfaces · card shortcuts · product connections · consent claims · key entry
     └─ Cloud Sync ── synced settings (on config.*) · records with files (saves template)
Commerce (a fact, not a switch): storefronts · offers → SKUs · purchases · subscriptions
```

### 1.3 The three chains

**Config (server merge, config and secrets only)**

1. Catalog defaults.
2. Default profile.
3. Tier profile.
4. Licence config overrides.
5. Account overrides.

Client resolution is unchanged (WIRE-CONTRACT-V4 §2.2.1): a lock wins, then the person's own
choice (the `local` slot, synced with Cloud Sync), then the environment, then the highest remote
default, then the fallback. Mapped onto the brief's "user > license > config profile > defaults":

- _user_ is layer 5 plus the person's own choice;
- _license_ is layer 4;
- _config profile_ is layers 3 and 2;
- _defaults_ is layer 1.

The device layer is gone: it had no writer. Licence profile stacks fold into layer 4.

**Licence limits (licence > tier > platform default, every field; every licence has a tier)**

- **Expiry:** a date, computed from the tier's term at create or re-tier.
- **Device limit:** the base value, plus seat-pack add-ons.
- **Offline days:** tiers now carry them.
- **Fingerprint mode:** tier only.
- **Version window:** override, not intersection, and taken from the anchor licence only (never
  widened across licences); then clamped by `keepVersion`.
- **Channels:** the base set overrides (licence, then tier, then `["stable"]`). Add-ons then add
  channels by union. `stable` is always granted. Choosing `dev` in an editor also stores `beta`;
  nothing widens a grant at resolve time (WIRE-CONTRACT-V4 §5.1 rule 4).

**Entitlements (one licence, the anchor)**

1. Tier entitlements.
2. Licence entitlement overrides.
3. Licence-held add-on grants (every grant references an add-on), combined by kind: features
   any or union, quantities max-of-slices plus the sum of grants, consumables only in the ledger.
   A paid grant is never cancelled by a tier or licence value.
4. Platform keys from Limits.

There is no device layer, no account-held or store-held grant, and no union across a person's
licences: the person picks the licence (one `rankLicenses()`).

## 2. Glossary

UI words are on the left. Identifiers in code, manifests and on the wire stay as listed, so no
rename touches the wire. OB-01 lands these in `start/concepts.md` (rule 4). One word per concept
and one concept per word (C-58): licence metadata is **Limits** and how long a licence runs is
its **Duration** ("terms" is kept for legal terms only); update lanes are **Release tracks**, so
