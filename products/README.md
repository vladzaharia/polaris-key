# products

In-repo fixture copies of product data (`catalog.json` and `product.json`) and the script that turns one into local seed SQL.

## Where it sits

- A product describes itself in a `.pkey/` directory in its own repo. `products/<slug>/` is the same data in fixture form.
- `packages/shared-manifest` tests read `products/djdl/` as the real valid fixture (`schema-parity.test.ts`, `assetRefs.test.ts`, `reservedNames.test.ts`).
- `gen-seed.ts` reads `product.json` and `catalog.json` through `@polaris-key/catalog` and `@polaris-key/manifest` and prints SQL for a local database. It does not mint sealed product keys or store secret values, so it is not an onboarding path.
- Nothing in the Worker or the SDKs reads this directory at runtime. Real products register through the console or the GitHub link flow.

## Layout

```
products/
  djdl/
    product.json    metadata, modules, tiers, devices.registration, signing key id and public key
    catalog.json    the config catalog entries
  gen-seed.ts       emits seed SQL for one product directory
  package.json      @polaris-key/products; scripts gen-seed, typecheck, test
```

`products/*/seed.sql` is the generated output and is git-ignored.

## Rules here

- Products are data. Never add a product-specific key to code: adding or changing a product must never need a Worker redeploy. See [AGENTS.md](../AGENTS.md).
- A validation rule needs a mutation-table entry. The fixtures here must pass both the validator and the JSON Schemas, which `packages/shared-manifest/test/schema-parity.test.ts` checks. See [AGENTS.md](../AGENTS.md).
- Raw hardware values are hashed on-device and never transmitted. See [AGENTS.md](../AGENTS.md).
