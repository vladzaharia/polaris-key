`PLATFORM_KEK` is the one piece of configuration on this platform whose misconfiguration is
**silent**: every sealed value — a product's signing key, its secrets — fails to open,
`loadProduct` returns `null`, and every route for that product serves a plain `404` with no log
line, indistinguishable from a product that was never registered. The admin console itself does
not depend on the KEK, so a bad keyring can leave `/manage` looking completely healthy while
every product's public routes are dark. Read the rotation procedure below before you touch it,
and if products are 404ing at once with nothing else broken, start at _Troubleshooting_ at the
bottom of this page.

In the console, **Platform → Settings → Keyring** (`#/platform/settings`) shows the keyring
read-only: which KEK secrets are set, the active kid, every kid in the ring with how many values it
seals, and how many values are still on an older key or under a key that has left the ring (those
cannot be opened). A `PLATFORM_KEK` kept beside `PLATFORM_KEK_KEYS` is marked as the legacy key,
open only, with what is still under it and when it is safe to delete: that is the rotation for an
environment whose current KEK nobody holds (_Rotating when the old KEK is unknown_, below). It
also says when the ring does not parse. **Platform → Deployment**
(`#/platform/deployment`) shows the build this instance
runs, the D1 migrations it has applied against the build's newest, the required indexes, which
bindings are present, and the **Platform activity** log, where every re-seal sweep is recorded with
who ran it and how many values it re-sealed. Check it first when every product goes dark after a
deploy. The re-seal sweep itself is the `POST /manage/api/products/kek` call in the runbook below.

What follows is the operations runbook for an already-deployed instance, rendered here in full
from `docs/RUNBOOK.md` so it can never drift from what this page says. For first-time production
bootstrap, see [Deploying to production](/docs/admin/deploy/) instead.
