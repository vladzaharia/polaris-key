Your app starts a sign-in, the person finishes it in a browser, and the app ends up with a device token and a license.

<Requires features={["sign-in"]} role="Product admin" />

Before you start:

- A product with Identity on. See [Your first product](/docs/start/first-product/).
- Your SDK installed. See [Install the SDKs and the CLI](/docs/build/install/).

## Steps

1. **Console** Open **Core → Services** and switch **Identity** on. Without License, this also makes keyless registration require sign-in.
2. **CLI** Optional: link your own provider with the `oidc:` block of `.pkey/product`, then select **Resync from repo** on **App sign-in**. Without it the product uses the platform provider.
3. **CLI** Optional: map groups to tiers with `groupRoleMap`, or set an `autoIssue` policy with mode `oidcDefault` so people in no group land on a default tier.
4. **Console** Optional: open **App sign-in** and set what customers can do: adding a license by key, showing the product in libraries and key reissue. Email codes and passkeys are always on.
5. **App** Start the sign-in with the SDK's `signIn.start`, per the table. The `device-code` channel shows the user code and a QR code, then polls. The `redirect` channel gives you a URL to open and takes the callback URL back; with no `redirectUri` it is the [native redirect](/docs/features/sign-in/native-redirect/), which opens the browser itself.
6. **App** Read the outcome: `signedIn`, `choose` (the app shows the license choice), `cancelled` or `expired`. The SDK has stored the device token; refresh the license status.
7. **Server** Optional: read the signed-in account on your backend, as [Your backend](#your-backend) shows. The license document carries `profile.user` with the account's pairwise subject (`ps_…`) while an account is signed in on that device.

| SDK    | Sign-in                                                                                             | Where the code is                              |
| ------ | --------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| Node   | `identity.signIn.start()`: `device-code` or `redirect`                                              | [Node](/docs/build/sdks/node/your-own-ui/)     |
| Python | `identity.sign_in.start()`: `device-code` or `redirect`                                             | [Python](/docs/build/sdks/python/your-own-ui/) |
| React  | `usePolarisAuth().signIn.start()`: both channels                                                    | [React](/docs/build/sdks/react/your-own-ui/)   |
| Swift  | `identity.signIn.start(_:)`: `.deviceCode` or `.redirect`, with a form in the kit                   | [Swift](/docs/build/sdks/swift/your-own-ui/)   |
| Kotlin | `identity.signIn.start()`: `DeviceCode` or `Redirect`, with the device-code form in the Compose kit | [Kotlin](/docs/build/sdks/kotlin/your-own-ui/) |
| Godot  | `identity.sign_in.start()`: `device-code` or `redirect`, with a dialog in the kit                   | [Godot](/docs/build/sdks/godot/your-own-ui/)   |

A session has `wait` (device code), `complete(callbackUrl)` (redirect), `reopen` and `cancel`. Swift spells them `wait()`, `complete(callbackUrl:)`, `reopen()` and `cancel()`; Godot, `wait()`, `complete(callback_url)`, `reopen()` and `cancel()`. Use the [device flow](/docs/features/sign-in/device-flow/) where the host can't receive a redirect, and the [web redirect](/docs/features/sign-in/web-redirect/) where it can. A desktop or mobile app that opens the system browser uses the [native redirect](/docs/features/sign-in/native-redirect/): the same `redirect` channel with no `redirectUri`.

## After sign-in

With `licenseChoice: "app"`, a sign-in that needs a license choice settles `choose` with a short-lived `grant`. Run the choice with `identity.choice` (`licenses`, `devices`, `complete`, `cancel`), or `useLicenseChoice` in React. The calls on the signed-in account:

| Node                           | Python            | Does                                                         |
| ------------------------------ | ----------------- | ------------------------------------------------------------ |
| `identity.subject()`           | `subject()`       | The account's pairwise subject (`ps_…`), or `null`           |
| `identity.signOut()`           | `sign_out()`      | Signs out. `released` says whether the device lost its token |
| `identity.attach({ confirm })` | `attach(confirm)` | Previews, then adds the device's license to the account      |
| `identity.openAccount()`       | `open_account()`  | Opens the account page in Polaris Locker                     |

Swift, Kotlin and Godot have the same calls. The choice settles `.chooseLicense(PendingSignIn)` in Swift, `SignInOutcome.Choose` in Kotlin and `license_choice` in Godot, each with the `grant`:

| Swift                                     | Kotlin                                    | Godot                                     |
| ----------------------------------------- | ----------------------------------------- | ----------------------------------------- |
| `identity.choice.complete(grant:choice:)` | `identity.choice.complete(grant, choice)` | `identity.choice.complete(grant, choice)` |
| `identity.subject()`                      | `identity.subject()`                      | `identity.subject()`                      |
| `identity.signOut()`                      | `identity.signOut()`                      | `identity.sign_out()`                     |
| `identity.attach(confirm:)`               | `identity.attach(confirm)`                | `identity.attach(confirm)`                |
| `identity.openAccount()`                  | `identity.openAccount()`                  | `identity.open_account()`                 |

Swift throws a `ChoiceError` for a choice refusal; Kotlin and Godot answer a result (`ChoiceResult.Refused`, a `PKeyChoiceResult` of kind `refused`) that carries the `code`, `manageUrl` or `signInUrl`.

An app that talks to its own backend can send a signed-in device's token there. `identity.accessToken()` (Node) or `usePolarisAuth().accessToken()` (React) trades the device token for an access token that lasts 600 seconds, to send as `Authorization: Bearer`; Python, Swift, Kotlin and Godot: planned. The token proves the device holds a sign-in. It is not a license check: it carries no tier and no entitlement, so check the license where it matters. The SDK keeps it in memory, reuses it until a minute before it expires and drops it at sign-out; `{ refresh: true }` asks again. It needs the product's sign-in issuer on: without it the call throws `service-unavailable`, and `invalid_grant` means the device holds no sign-in.

A key activation can answer two typed outcomes. Neither wipes the device's token or cache.

- `key-entry-limit`: the key has no entries left. It carries `manageUrl` and `keyEntries` (`used`, `limit`). Offer the link, or sign-in.
- `license-owned`: the license is in an account and never moves by its key. It carries `signInUrl`. Offer sign-in.

In Swift they are `.keyEntryLimit` and `.licenseOwned`, in Kotlin `KeyEntryLimit` and `LicenseOwned`, in Godot `KIND_KEY_ENTRY_LIMIT` and `KIND_LICENSE_OWNED` (`manage_url`, `key_entries`, `sign_in_url`).

The kit's form is [SignIn](/docs/build/ui/components/sign-in/). Which SDK has each part is listed in [Parity](/docs/reference/parity/).

## Check it works

Run `pkey dev`, which includes a fake provider that signs in one person and an **Approve** button ([Run Polaris Key locally](/docs/build/local/)). Start the sign-in from your app, approve it and see the license status leave `needs-activation`.

On your product, a signed-in device shows under **Core → Devices**, and the person's license under **License → Licenses**.

On **Integration**, Sign-in shows **Verified** for the platform you ran. If it says Not seen yet, see [Not seen yet](/docs/build/troubleshooting/#not-seen-yet).
